## 逐题答案

### 1-3. 图片懒加载

#### 思维导图关键点

```txt
图片懒加载
├─ 首选 IntersectionObserver
├─ 进入可视区再替换真实 src
├─ 优点：不用频繁手写 scroll 计算
├─ 兼容性不足时降级
└─ 老浏览器：scroll + throttle + getBoundingClientRect
```

#### 60-90 秒口语稿

图片懒加载我一般优先用 `IntersectionObserver`。它本质上是让浏览器帮我们监听元素和视口的交叉状态，图片进入可视区时再把占位图替换成真实 `src`，比手写 `scroll` 监听更省心，也更不容易频繁触发布局计算。兼容性上如果浏览器不支持，我会降级成 `scroll + throttle + getBoundingClientRect` 的方案，同时注意首屏要主动执行一次，图片加载完成后及时解绑监听。真实业务里像商品列表、信息流、广告卡片这种页面，如果图片很多，不做懒加载会明显拖慢首屏和滚动性能。

#### 高频追问

1. 为什么 `IntersectionObserver` 更适合做懒加载  
因为它把“可见性检测”交给浏览器统一调度，避免你自己在高频滚动里反复做坐标计算。

2. 老浏览器降级方案最容易漏什么  
最容易漏的是首屏主动触发一次、图片加载完成后解绑监听，以及节流频率不能太激进。

3. 懒加载和列表白屏怎么权衡  
首屏附近的资源可以适当做预加载或加大根边距，不要一味追求最晚加载。

### 4-6. 单行、多行溢出与兼容性

#### 思维导图关键点

```txt
文本溢出
├─ 单行：white-space + overflow + text-overflow
├─ 多行：-webkit-line-clamp
├─ 多行本质依赖私有实现
├─ 兼容差时可降级
└─ 降级方案：渐隐、固定高度、JS 计算
```

#### 60-90 秒口语稿

单行省略最经典的写法是 `overflow: hidden`、`white-space: nowrap`、`text-overflow: ellipsis`。多行省略在业务里最常用的是 `display: -webkit-box`、`-webkit-box-orient: vertical`、`-webkit-line-clamp`，但它本质上还是偏私有实现，所以兼容性不能想得太理想。如果目标浏览器不支持，我会根据场景选择降级方案，比如固定高度加渐隐遮罩，或者用 JS 按容器宽高做截断。真实业务里像卡片标题、广告文案、推荐流摘要，多行省略是高频需求，但一定要先确认设计是否真的要求“完全一致”，不然很容易在兼容上过度投入。

#### 高频追问

1. 为什么多行省略不像单行那样稳定  
因为它长期依赖 WebKit 风格的实现，标准化程度和兼容性都不如单行省略稳定。

2. 什么时候不建议用 JS 截断  
列表特别长、内容频繁变化、容器尺寸不断变化时，JS 截断的维护和性能成本会比较高。

3. 为什么有时候省略号不生效  
通常是宽度约束不成立，或者 `overflow`、布局模式、换行规则没有配套。

### 7-8. 跨域与 CORS

#### 思维导图关键点

```txt
跨域
├─ 浏览器同源策略限制
├─ 维度：协议 / 域名 / 端口
├─ 跨域不是请求发不出去
├─ 是响应被浏览器拦截
└─ 解决：CORS / BFF / 网关 / JSONP(历史) / postMessage
```

#### 60-90 秒口语稿

跨域本质上是浏览器同源策略带来的限制，同源要同时满足协议、域名和端口都一致。很多人会误以为“跨域就是请求发不出去”，其实通常请求已经发到服务端了，真正被浏览器拦的是响应读取权限。工程上最常见的解决方式是服务端正确配置 CORS；除了本地代理，还可以通过 BFF、中间层网关、同域转发去收敛跨域问题。如果是窗口通信场景，也可以用 `postMessage`。真实业务里前端最常见的坑不是不知道什么叫跨域，而是把开发代理误当成生产方案，结果一上线就暴露出跨域和鉴权问题。

#### 高频追问

1. 为什么要设置跨域  
因为浏览器默认不允许当前源随意读取其他源的响应内容，这是安全边界的一部分。

2. 除了代理还能怎么办  
服务端配置 CORS、前后端同域部署、BFF 汇总接口、网关转发，特殊历史场景下还有 JSONP。

3. 预检请求是怎么来的  
当前端发的是“非简单请求”时，浏览器会先发 `OPTIONS` 预检，看服务端是否允许。

### 9. 闭包

#### 思维导图关键点

```txt
闭包
├─ 函数记住定义时的词法作用域
├─ 外层函数结束后仍可访问变量
├─ 核心价值：保留状态、封装私有数据
└─ 风险：长生命周期引用导致回收不掉
```

#### 60-90 秒口语稿

闭包我会理解成“函数把它定义时的词法作用域记住了”。所以即使外层函数已经执行结束，内部函数后续仍然能访问外层那层环境里的变量。它最核心的价值是保留状态和做私有封装，比如计数器、防抖、节流、缓存函数都会用到闭包。闭包本身不是坏事，真正的风险是你让闭包长期持有已经没用的大对象、DOM 或上下文，导致垃圾回收回不掉。真实业务里像事件监听、定时器和缓存对象，如果清理不及时，就很容易把闭包和内存问题绑在一起。

#### 高频追问

1. 闭包和作用域链是什么关系  
作用域链回答“变量往哪找”，闭包回答“为什么函数离开定义位置后还能沿那条链继续找”。

2. 为什么循环里配合 `var` 容易出问题  
因为多个闭包共享的是同一个函数作用域绑定，不像 `let` 会为每轮创建新的块级绑定。

3. 闭包是不是一定有性能问题  
不是，问题不在闭包本身，而在你是否留下了不必要的长生命周期引用。

### 10-12. 防抖、节流、请求乱序

#### 思维导图关键点

```txt
高频输入与事件
├─ 防抖：停下来再执行
├─ 节流：按固定频率执行
├─ 搜索输入更常用防抖
├─ 鼠标移动更常用节流
└─ 请求乱序还要加取消或序号校验
```

#### 60-90 秒口语稿

防抖和节流我会按场景区分。像 `input` 搜索更适合防抖，因为用户停下来再发请求更合理；像鼠标移动、滚动、窗口缩放这类高频事件更适合节流，避免函数触发太密。搜索场景里还有一个常见坑是请求乱序，也就是第一次请求比第二次慢，最后旧结果把新结果覆盖了。这个问题不能只靠防抖，还要加请求序号、时间戳或者 `AbortController`，保证只接受最后一次有效响应。真实业务里搜索联想、远程下拉、筛选面板都很容易踩这个坑，线上看起来像“结果闪回”或者“输入和结果对不上”。

#### 高频追问

1. 搜索乱序为什么不能只靠防抖  
因为即使减少了请求次数，也不能保证服务端响应顺序和发起顺序一致。

2. 节流一定比防抖好吗  
不是，关键看你要的是“最终一次”还是“持续反馈”。

3. `AbortController` 和序号校验怎么选  
能取消请求时优先取消；如果链路里不好取消，至少要做响应有效性校验。

### 13-14. 事件流与事件委托

#### 思维导图关键点

```txt
事件系统
├─ 捕获阶段
├─ 目标阶段
├─ 冒泡阶段
├─ 事件委托利用冒泡
└─ 适合动态列表和大量子节点
```

#### 60-90 秒口语稿

浏览器事件流可以分成捕获、目标和冒泡三个阶段。大多数业务里我们更常遇到的是冒泡，因为很多点击事件默认都沿着 DOM 树往上冒泡。事件委托就是利用这件事，把本来该绑在很多子元素上的监听器，统一绑到父节点上，再根据事件源判断具体点到了谁。它的优点是减少监听器数量，也更适合动态节点场景。真实业务里像表格、列表、菜单、广告素材墙这类节点很多而且会频繁增删的页面，事件委托通常比一个个绑监听器更稳。

#### 高频追问

1. 事件委托为什么适合动态列表  
因为新节点插入后不需要重新给每个子项单独绑事件。

2. 什么情况下事件委托不合适  
不冒泡的事件、或者你非常依赖子节点自身独立监听上下文时，就要谨慎。

3. `stopPropagation` 会影响什么  
它会阻止事件继续向上传播，也可能让外层依赖委托的逻辑失效。

### 15. git merge 和 git rebase 的区别

#### 思维导图关键点

```txt
merge vs rebase
├─ merge：保留分叉历史
├─ rebase：把提交接到新基线上
├─ merge 更稳，历史更真实
├─ rebase 更线性，日志更干净
└─ 不要 rebase 已经共享的公共分支
```

#### 60-90 秒口语稿

`merge` 和 `rebase` 的核心区别，不是“哪个更高级”，而是历史组织方式不同。`merge` 会保留分叉结构，生成一个合并提交，优点是历史真实、协作更稳；`rebase` 会把当前分支的提交重新接到新的基线上，优点是提交历史更线性、日志更干净。团队协作里我的经验是：公共分支优先用 `merge`，个人开发分支在提交前可以适度 `rebase` 整理历史，但不要去 `rebase` 已经共享给别人的分支。真实业务里最容易出问题的不是命令不会用，而是把 `rebase` 用在协作分支上，最后把同事的历史改乱了。

#### 高频追问

1. 为什么不建议 rebase 公共分支  
因为它会改写提交历史，别人基于旧历史继续开发时很容易冲突和混乱。

2. 什么场景更适合 merge  
团队协作分支、需要保留真实合并点、排查回滚链路时更适合。

3. 什么场景更适合 rebase  
个人分支整理提交、想让 PR 历史更线性时更适合。

### 16. Vue 多还是 React 多

#### 思维导图关键点

```txt
技术栈偏好题
├─ 不争谁绝对更多
├─ 先说自己项目背景
├─ 再说自己的主熟悉栈
├─ 最后补迁移能力
└─ 重点是学习能力和适配能力
```

#### 60-90 秒口语稿

这类题我不会回答成“Vue 一定更多”或者“React 一定更多”，因为不同团队、不同业务背景差异很大。更稳的答法是先结合自己的项目经历说明当前主要使用哪套技术栈，再补一句自己对另一套也有理解，迁移成本可控。比如我会说，我过去项目里 React 用得更多，所以我对 Hooks、状态管理和工程配套更熟，但 Vue 的响应式、模板体系和常见开发方式我也理解，切换不会有本质障碍。真实面试里这题考的往往不是你站队，而是你会不会把技术栈偏好题答成“我只会这一套”。

#### 高频追问

1. 面试官为什么爱问这个  
因为他想看你是不是只会单一栈，以及你怎么表达技术迁移能力。

2. 如果团队正好用另一套怎么办  
重点强调底层能力、组件化思维和状态管理思维可以迁移。

3. 这题最忌讳怎么答  
最忌讳答成情绪化站队，或者直接贬低另一套技术栈。

### 17. Hooks 在 React 什么地方都能使用吗

#### 思维导图关键点

```txt
Hooks 规则
├─ 只能在函数组件或自定义 Hook 顶层调用
├─ 不能写在条件、循环、嵌套函数里
├─ 核心原因：React 依赖调用顺序定位状态
└─ 这是值得单独深挖的系统题
```

#### 60-90 秒口语稿

Hooks 不是在 React 里什么地方都能用，它只能在函数组件或者自定义 Hook 的顶层调用，不能放在条件判断、循环或者普通函数里。底层原因不是官方强行规定，而是 React 内部要依赖每次渲染时一致的调用顺序，才能把当前这个 Hook 和上一次渲染对应起来。如果顺序变了，状态就会串。真实业务里最常见的坑就是有人把 `useEffect` 或 `useState` 放进条件分支，代码能写出来，但状态很容易错位。

#### 高频追问

1. 为什么顺序这么重要  
因为 React 内部是按调用顺序去读取和复用当前组件上的 Hook 状态槽位。

2. 自定义 Hook 为什么可以用 Hooks  
因为它最终也必须在函数组件渲染过程中，以稳定顺序被调用。

3. 为什么这题值得单独抽专题  
因为继续往下追会自然连到 Fiber、Hook 链表、闭包、依赖比较和副作用时机。

4. 现在还有什么现代补充口径  
React 19 官方文档已经把 `use` 标成特殊例外，它可以条件调用和循环调用，但其他大多数 Hook 仍然必须遵守顶层调用规则。

### 18. Vue2 和 Vue3 响应式区别

#### 思维导图关键点

```txt
Vue 响应式
├─ Vue2：Object.defineProperty
├─ Vue3：Proxy
├─ Vue2 对新增属性、删除属性、数组索引有局限
├─ Vue3 拦截范围更完整
└─ 这是值得单独深挖的系统题
```

#### 60-90 秒口语稿

Vue2 和 Vue3 响应式最大的区别，是底层拦截方式不同。Vue2 主要基于 `Object.defineProperty`，它能劫持已有属性的 `get/set`，但对新增属性、删除属性、数组索引修改这类场景天然不够直接，所以需要一些额外 API 和约束。Vue3 改成了 `Proxy`，可以直接拦截对象层面的更多操作，能力更完整，也更适合现代响应式系统设计。所以如果面试官问区别，我不会只背“一个是 defineProperty，一个是 Proxy”，还会补一句它们在拦截能力边界、数组处理和对象新增删除上的真实差异。真实业务里这会直接影响你排查“为什么这里没更新”和“为什么这里必须用特定 API”这类问题。

#### 高频追问

1. Vue2 为什么对新增属性不友好  
因为它只能在初始化时把已有属性转换成响应式，后加的属性默认不在那套拦截链里。

2. Vue3 一定比 Vue2 快吗  
不能简单这么答。更准确是 Vue3 的响应式模型更现代、边界更完整，但真实性能还要看场景和整体实现。

3. 为什么这题值得抽专题  
因为继续往下追会自然连到依赖收集、effect、数组处理、`ref/reactive` 和编译期优化。

4. 现在最值得补的现代口径是什么  
Vue2.7 虽然回移了 Composition API，但官方文档明确说底层仍然是 Vue2 的 getter/setter 响应式，所以 Vue2 的 change detection caveats 仍然存在。

### 19. 虚拟 DOM diff 中为什么 key 不能用 index

#### 思维导图关键点

```txt
key
├─ 用来标识节点身份
├─ index 只代表当前位置
├─ 插入删除重排时身份会错位
├─ 可能导致复用错误
└─ 表单、动画、局部状态最容易出问题
```

#### 60-90 秒口语稿

`key` 的作用不是单纯消除警告，而是帮助虚拟 DOM 在 diff 时稳定识别“谁是谁”。`index` 只能表示当前位置，列表一旦发生插入、删除或重排，节点原本的身份就和位置脱钩了，这时候继续用 `index`，框架就可能把旧节点错误复用到新位置上。最典型的问题就是表单输入错位、局部状态串位、动画异常。真实业务里如果列表是静态不变的，`index` 不一定立刻出事，但只要存在排序、筛选、插入删除，我都会优先用稳定唯一 ID。

#### 高频追问

1. 什么场景下用 `index` 风险最大  
有插入、删除、拖拽排序、筛选切换时风险最大。

2. 为什么表单列表最容易暴露问题  
因为每一项往往都带本地状态，一旦节点复用错了，状态就会串位。

3. 静态列表能不能用 `index`  
如果列表完全静态、不会重排，风险会小很多，但工程上我仍然更推荐稳定 ID。

### 20. 事件循环代码输出题

#### 思维导图关键点

```txt
事件循环判断套路
├─ 先找同步代码
├─ 再看当前宏任务里注册了什么
├─ Promise.then / await 后续进微任务
├─ setTimeout 进后续宏任务
└─ 当前宏任务结束后先清空微任务
```

#### 60-90 秒口语稿

遇到事件循环代码输出题，我一般不会靠感觉猜，而是按固定顺序判断。第一步先把同步代码顺序跑完；第二步看当前这轮宏任务里注册了哪些微任务和后续宏任务；第三步记住一个最关键的边界，就是当前宏任务结束后会先清空微任务，再进入下一轮宏任务。所以像 `Promise.then`、`queueMicrotask`、`await` 后续逻辑，通常都会早于下一轮 `setTimeout`。真实业务里如果你把这个顺序搞反，最容易出问题的就是日志顺序、状态更新时机和 DOM 读取时机。

#### 高频追问

1. 为什么 `Promise.then` 常常比 `setTimeout` 早  
因为它走的是微任务，而微任务会在当前宏任务结束后优先清空。

2. `setTimeout(fn, 0)` 为什么不是立刻执行  
因为它只是尽快进入后续宏任务队列，不会打断当前调用栈。

3. 这题怎么和真实项目联系起来  
像 loading 消失时机、状态批处理、日志顺序、异步回调读 DOM 都会受它影响。

### 21. 手撕：比较版本号排序

#### 思维导图关键点

```txt
版本号排序
├─ 按 '.' 切段
├─ 每段转成数字比较
├─ 不足位补 0
├─ 从左到右比较
└─ 返回排序结果
```

#### 60-90 秒口语稿

这题我会先把版本号按 `.` 切成数组，然后从左到右逐段比较。每一段都转成数字，不够的位补 `0`，比如比较 `1.2` 和 `1.2.0.1` 时，前两段相同，第三段就把前者看成 `0`，继续比较。这样处理能覆盖位数不同的情况，复杂度也比较稳定。如果是排序，就把这个比较逻辑塞进排序函数里。真实业务里像客户端版本灰度、配置兼容、包版本判断都会遇到这类比较逻辑。

#### 核心代码

```js
function compareVersion(a, b) {
  const arr1 = a.split(".");
  const arr2 = b.split(".");
  const len = Math.max(arr1.length, arr2.length);

  for (let i = 0; i < len; i++) {
    const n1 = Number(arr1[i] || 0);
    const n2 = Number(arr2[i] || 0);

    if (n1 > n2) return 1;
    if (n1 < n2) return -1;
  }

  return 0;
}

function sortVersions(list) {
  return list.slice().sort(compareVersion);
}
```

#### 高频追问

1. 为什么每段要转数字  
因为字符串比较会把 `"10"` 错判成比 `"2"` 小。

2. 为什么不足位补 0  
因为 `1.2` 和 `1.2.0` 在很多版本语义里应视为同级。

3. 复杂度是多少  
单次比较大致是 `O(k)`，`k` 是版本段数；排序总体大致是 `O(n log n * k)`。
