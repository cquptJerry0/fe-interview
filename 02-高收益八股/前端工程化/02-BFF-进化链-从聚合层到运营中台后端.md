# BFF 进化链：从聚合层到运营中台后端

## 问题

面试官可能会连续问：

1. 什么是 BFF，为什么会出现 BFF？
2. BFF 和前端直接调用微服务相比，解决了什么问题？
3. 标准 BFF 通常只是聚合层，为什么你们中台的 BFF 还有 MySQL、Redis、批量任务和 Lambda？
4. BFF 变厚是不是架构越界？它的边界在哪里？

这组问题不能从 Redis、MySQL、MQ、FaaS 等技术名开始背。真正需要回答的是一条架构演进链：旧架构为什么成立，后来什么条件发生变化，出现了什么新矛盾，BFF 如何解决，以及运营中台为什么又推动 BFF 继续演进。

## 一、思维导图关键点

```text
为什么出现 BFF
│
├─ 单体 Web
│  ├─ 页面、业务逻辑、数据库在同一服务
│  ├─ 通常只有 PC 浏览器一种客户端
│  ├─ 页面和后端不存在明显的适配鸿沟
│  └─ 变化：SPA、移动端出现，前端需要独立迭代
│
├─ 前后端分离 + 单体 REST API
│  ├─ 前端开始直接调用后端接口
│  ├─ 后端仍然是单体，数据比较集中
│  ├─ 一个页面多调用几个接口暂时可以接受
│  └─ 变化：后端微服务化，同时出现 Web、App、小程序等多端
│
├─ 微服务 + 前端直连
│  ├─ 一个页面动作跨多个领域服务
│  ├─ 请求数量和调用顺序进入前端
│  ├─ 内部 RPC 协议无法直接暴露给浏览器
│  ├─ 鉴权、字段转换、异常兜底散落在前端
│  ├─ 多端需要不同的数据粒度
│  └─ 下游变化直接冲击客户端
│
├─ 标准薄 BFF
│  ├─ 聚合数据
│  ├─ 裁剪和转换字段
│  ├─ 转换协议
│  ├─ 收口鉴权
│  └─ 屏蔽下游变化
│
└─ 运营中台推动 BFF 继续变厚
   ├─ 数据闭环：列表、详情、配置聚合
   ├─ 状态闭环：草稿、权限、任务记录、版本
   ├─ 流程闭环：批量操作、测试、审核、发布、通知
   └─ 运行闭环：分片重试、异步任务、Lambda、独立部署
```

### 整体性质模型

无论薄 BFF 还是厚 BFF，本质上都在做同一件事：

```text
后端按领域和资源提供能力
              ↓
BFF 把这些能力组织成某一类前端需要的体验闭环
              ↓
前端按页面和用户任务完成操作
```

BFF 的厚度，取决于它承担的体验闭环有多深：

```text
BFF
= 体验适配
+ 体验专属状态
+ 体验流程编排
+ 运行治理
```

只有体验适配时，它是标准薄 BFF。

当运营中台开始产生草稿、配置、任务状态、权限和流程时，它就会承担应用后端职责。

当接口在冷热、资源、超时和发布节奏上出现明显差异时，它还会继续长出批处理器、异步 Worker、Lambda 或 FaaS 等运行治理能力。

### 边界模型

BFF 可以变厚，但不能无限吸收业务：

```text
只服务当前运营体验的适配、状态和流程
→ 可以留在 BFF / 运营应用后端

属于素材主数据、跨端复用规则、领域一致性约束
→ 必须留在下游领域服务

开始被多个应用共同使用的能力
→ 应该拆成共享服务或独立中台能力
```

判断重点不是“有没有数据库”，而是“谁拥有这份状态，谁负责这条业务规则”。

## 二、主回答

我理解 BFF 不能只从“聚合层”这个结论开始背，最好先看它是在什么架构变化下出现的。

最早的单体 Web 里，页面渲染、业务逻辑和数据库访问都在一个服务中，而且通常只有 PC 浏览器这一种客户端，所以页面和后端之间没有明显的适配问题。

后来前后端分离，前端开始直接调用 REST API。这个阶段虽然一个页面可能需要调用多个接口，但后端通常还是单体服务，数据比较集中，请求数量也有限，所以前端做一点数据拼装暂时还能接受。

真正的转折点是微服务化和多端同时出现。后端开始按照用户、权限、素材、审核、配置等领域拆成多个服务，但前端页面仍然按照用户任务组织。比如一个素材列表或者面板发布页面，可能同时依赖素材信息、标签、权限、配置、审核状态和下发信息。

如果前端直接调用这些微服务，请求编排、协议转换、鉴权、字段适配和异常兜底就会漂到前端；Web、App 等不同客户端还会重复实现类似逻辑；下游服务一旦调整接口，也会直接影响客户端。

所以从业界标准定义来说，BFF 是为某一类前端体验定制的后端层。它位于客户端和下游领域服务之间，负责数据聚合、字段裁剪、协议转换、统一鉴权，并屏蔽下游变化。

它解决的核心矛盾是：后端按照领域和资源组织能力，而前端按照页面和用户体验消费能力。标准 BFF 就是在两者之间做体验适配，因此通常比较薄。

但 `tool_platform` 里的素材运营中台又往前走了一步。运营中台不是一个只读展示页面，而是运营人员实际生产素材、编辑配置、批量处理、测试、审核和发布的工作台。这个前端体验本身就会产生状态和流程。

因此，中台 BFF 会逐渐变厚。

第一，页面查询需要聚合多个数据源，还会频繁读取平台配置、字典和会话信息，所以会引入缓存，降低延迟并保护下游。

第二，批量上传草稿、平台配置版本、测试任务和权限记录等数据只属于当前运营应用，需要自己的 MySQL 持久化。这里保存的是运营应用状态，不是重新保存一份素材主数据。

第三，批量创建、资源替换、自动化测试和发布流程无法都当成简单同步 CRUD。系统需要分片、并发控制、重试、任务状态、外部系统回调和通知，因此 BFF 开始承担流程编排职责。具体实现可以是 `batchProcess`、任务系统、回调、异步 Worker 或 MQ，并不是所有异步场景都必须使用同一种中间件。

第四，当接口越来越多，不同接口在冷热、执行时间、资源和发布节奏上出现明显差异时，系统会进一步按 Lambda 或 FaaS 入口拆分，隔离发布和运行风险。

所以我对这个项目的整体理解是：它最初是一个负责数据聚合和协议适配的薄 BFF，后来因为承担了运营体验的应用状态和业务流程，逐渐演进成了一个以 BFF 为入口的运营应用后端。

但它仍然有明确边界。素材实体、素材上线状态以及跨端复用的领域规则，仍然应该由素材领域服务负责；只有服务于当前运营体验的聚合、草稿、配置、任务和流程编排，才适合放在这一层。如果一项能力开始被多个应用复用，就应该继续从 BFF 中拆出去。

例如在素材自动化测试中，BFF 不只是返回页面数据，还要维护测试任务状态、校验操作权限、触发 CQ 测试、同步素材测试状态、发送飞书通知并记录日志。这已经是一条完整的运营流程，也最能说明为什么中台 BFF 会从聚合层逐渐演进成应用后端。

## 三、三个 tool_platform 真实案例

### 案例一：素材列表——标准薄 BFF 的数据闭环

#### 业务目标

运营人员希望在一张素材列表里完成搜索、筛选、查看附加信息和批量操作。

页面看到的是统一的“素材列表”，但后端数据来自不同系统：

```text
前端输入搜索条件
        ↓
getMaterialList BFF 接口
        ├─ Normal / Tag → Feed 服务
        ├─ Doris        → OneService
        └─ Hive         → TQS
        ↓
MaterialService.packList
        ├─ 用户信息
        ├─ 分类和标签
        ├─ 使用量
        ├─ 分级下发信息
        ├─ 合同和版权
        ├─ diff 信息
        └─ 付费策略
        ↓
返回前端需要的统一列表模型
```

对应代码和业务文档：

```text
apps/material/src/routes/list/index.tsx
apps/material/api/lambda/material/getMaterialList.ts
apps/material/biz-context/biz/material_list.md
```

#### 为什么需要 BFF

如果没有 BFF，前端需要知道当前搜索应该走 Feed、Doris 还是 Hive，还要自己补充用户、标签、版权和下发信息。数据源选择、服务调用顺序和字段组装都会进入前端。

BFF 在这里承担的是标准职责：根据搜索模式路由数据源，调用多个下游服务，再把领域数据转换成页面需要的列表模型。

#### 边界在哪里

BFF 负责列表视图的组装，但素材实体和素材状态的权威来源仍然是素材服务。删除 BFF 的聚合结果不能影响素材主数据。

这个案例对应整体模型中的第一层：

```text
数据闭环 → 标准薄 BFF
```

### 案例二：批量素材上传——为什么 BFF 开始拥有应用状态

#### 业务目标

运营人员上传一批素材文件后，不能立即把所有内容写入正式素材库。运营需要先预览、修改标题和标签、检查解析结果，再选择哪些草稿正式上线。

因此，批量上传采用业务上的两阶段流程：

```text
阶段一：创建草稿

上传 ZIP / 文件
→ 前端解析 icon、resource、config
→ 运营预览和编辑
→ 创建 material_draft
→ status = draft

阶段二：批量上线

运营勾选草稿
→ 调用 batch_upsert_material
→ MaterialService.batchCreate 创建正式素材
→ 更新 draft.status = submitted / failed
→ 写入 item_id 或 error_message
→ 返回结果并按需发送飞书通知
```

对应代码和业务文档：

```text
apps/material/src/routes/upload/index.tsx
apps/material/src/routes/upload/components/BatchAddMaterialModal/index.tsx
apps/material/api/model/material/material_draft.ts
apps/material/biz-context/biz/batch_operations.md
```

#### 为什么 BFF 需要 MySQL

`material_draft` 不是素材领域服务中的正式素材。它记录的是运营上传过程中的临时状态，包括草稿内容、提交状态、失败原因和正式素材 ID。

这些数据只服务当前运营体验，但又需要跨请求保存、查询和修改，因此不能只放在前端内存或 Redis 中，需要由运营应用自己的 MySQL 持久化。

这说明判断 BFF 能不能有数据库，不能看“BFF 是否应该保持薄”，而要看“这份状态属于谁”。

#### 为什么批量能力会继续变复杂

项目中的第二代批量能力使用 `batchProcess` 提供分片、并发控制、重试、部分失败处理和进度回调。原因不是为了堆技术，而是批量场景天然需要控制下游压力，并允许部分失败后继续处理。

#### 边界在哪里

BFF 拥有草稿状态，素材服务拥有正式素材。BFF 可以记录“这次上传是否提交成功”，但不能成为素材内容、素材状态和素材领域规则的第二个真源。

这个案例对应整体模型中的第二层：

```text
数据闭环 + 状态闭环
→ BFF 开始承担运营应用后端职责
```

### 案例三：AutoTest——为什么 BFF 会承担流程编排

#### 业务目标

素材进入正式发布前，需要经过自测、待测、QA 测试、通过或不通过等完整流程。部分素材还要接入 CQ 自动化测试，并在状态变化时通知相关人员。

AutoTest 的核心状态流转是：

```text
创建任务
   ↓
SelfTest
   ├─ 跳过测试 → Skip
   └─ 自测完成 → WaitingQA
                    ├─ 回退 → SelfTest
                    └─ 开始测试 → QATesting
                                      ├─ 通过   → Pass
                                      ├─ 不通过 → NotPass
                                      └─ 回退   → WaitingQA
```

但真正执行一次状态变更时，系统还需要完成：

```text
查询任务、平台配置和权限
→ 校验操作人是否有权限
→ 获取素材详情
→ 根据状态决定提交或取消 CQ 任务
→ 调用 Feed 更新素材 test_status
→ 更新测试任务记录
→ 发送飞书卡片通知
→ 记录操作日志和埋点
```

对应代码和业务文档：

```text
apps/material/api/lambda/autoTest/createTask.ts
apps/material/api/lambda/autoTest/getTask.ts
apps/material/api/lambda/autoTest/updateTask.ts
apps/material/api/service/autoTask.ts
apps/material/api/model/material/t_auto_test_task.ts
apps/material/biz-context/biz/auto_test.md
```

#### 为什么这已经不只是聚合层

AutoTest 自己拥有任务表、权限表和状态机，还要编排 CQ、Feed、飞书通知、日志和 ID 生成服务。前端只是在页面上点击“开始测试”或“测试通过”，真正的业务流程由 BFF 内部推进。

这时 BFF 已经从“把多个接口拼成一个返回值”，演进成“把多个领域能力组织成一个运营用例”。这就是运营应用后端的典型职责。

#### Lambda 在这里解决什么问题

创建任务、查询任务、更新任务和权限管理分别放在不同的 `api/lambda/autoTest` 入口中，公共业务逻辑沉淀到 `AutoTaskService` 和 `AutoTestPermissionService`。

Lambda 解决的是接口入口、发布和运行隔离问题；Service 负责复用流程逻辑。它属于运行治理层，不是 BFF 标准定义的一部分。

#### 边界在哪里

测试任务生命周期属于运营应用，因此由 AutoTest 维护；素材自身的 `test_status` 仍然通过 Feed 服务更新。运营流程状态和素材领域状态有关联，但不能合并成同一个数据真源。

这个案例对应整体模型中的第三层和第四层：

```text
数据闭环
+ 状态闭环
+ 流程闭环
+ 运行治理
→ 以 BFF 为入口的运营应用后端
```

三个案例最终可以收束成一条进化链：

```text
素材列表
→ 组织多个数据源
→ 标准薄 BFF

批量素材上传
→ 产生草稿和批量处理状态
→ BFF 开始拥有应用状态

AutoTest
→ 维护状态机并编排多个外部系统
→ BFF 演进成运营应用后端
```

真正需要记住的不是项目用了多少中间件，而是：

```text
BFF 从体验适配开始；
当运营体验产生自己的状态和流程时，它会逐渐变厚；
当能力成为领域真源或需要跨应用复用时，它必须继续下沉或分裂。
```
