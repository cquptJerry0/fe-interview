### 2 和 6. `aaa - bbb` 垂直高度计算与 BFC

#### 原始题干

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Document</title>
    <style>
      p {
        font-size: 16px;
        line-height: 1;
        margin-top: 10px;
        margin-bottom: 15px;
      }
    </style>
  </head>
  <body>
    <p>aaa</p>
    <p></p>
    <p></p>
    <p></p>
    <p>bbb</p>
  </body>
</html>
```

#### 思维导图关键点

```txt
CSS 间距题
├─ 先确认测量口径
├─ 文本内容区之间是 15px
├─ 连文本高度一起算是 47px
├─ 原因不是空 p 撑高
├─ 是 margin collapse
└─ 追问自然会进 BFC
```

#### 60-90 秒口语稿

这题最稳的答法不是上来报数字，而是先确认口径。如果问 `aaa` 和 `bbb` 两行文本内容区之间的垂直间距，我会答 `15px`；如果把两行文本自身高度也算进去，就是 `47px`。真正原因不是中间 3 个空 `p` 把高度堆起来了，而是这些块级盒子在同一个块级格式化上下文里发生了垂直 `margin collapse`，同时空块元素自己的上下 `margin` 也继续参与整条折叠链，所以最后只保留最大正值 `15px`。这也是为什么面试官会顺着追问 `BFC`。真实业务里像富文本、文章详情、CMS 输出的段落标签，经常会出现“设计看起来间距很大，页面实际只剩一小截”的问题，本质上很多就是 `margin collapse`。

#### 高频追问

1. 为什么空 `p` 不会被 `line-height` 自动撑高  
因为空块级元素没有文本行盒，真正决定中间距离的是垂直 `margin`，不是空标签的内容高度。

2. 为什么这题会追到 `BFC`  
因为这题本质不是算数题，而是在考同一个块级格式化上下文里相邻块级盒子的垂直 `margin` 为什么不会老老实实相加。

3. 怎么验证自己的判断没错  
给中间空块加 `border`、`padding`、内容或者显式高度，打断折叠链，看结果是否变化。

### 3. 对象方法和 `this` 指向

#### 原始题干

```js
const obj = {
  fn1() {
    const fn = () => {
      console.log(this);
    };
    fn();
    fn.apply(window);
  },

  fn2() {
    function fn() {
      console.log(this);
    }
    fn();
    fn.apply(window);
  },
};

obj.fn1();
obj.fn2();
```

#### 思维导图关键点

```txt
this 输出题
├─ 先区分箭头函数和普通函数
├─ 箭头函数没有自己的 this
├─ 普通函数 this 看调用方式
├─ fn1 输出 obj、obj
└─ fn2 输出 window、window
```

#### 60-90 秒口语稿

这题在浏览器普通脚本、非严格模式下，输出是 `obj、obj、window、window`。关键是先分清箭头函数和普通函数。`fn1` 里的箭头函数没有自己的 `this`，它不会在调用时重新绑定，而是沿外层词法环境去拿，所以 `obj.fn1()` 执行时，外层 `this` 是 `obj`，后面无论 `fn()` 还是 `fn.apply(window)`，拿到的都还是 `obj`。`fn2` 里的普通函数有自己的动态 `this`，看调用方式，所以普通调用和 `apply(window)` 都是 `window`。真实业务里这直接关系到对象方法里的回调是不是会把 `this` 丢掉，尤其是事件系统、定时器和类库回调场景。

#### 高频追问

1. 为什么 `apply` 改不了箭头函数的 `this`  
因为箭头函数没有自己的动态 `this` 槽位，它只会沿外层词法环境取值。

2. 如果写成 `const detached = obj.fn1; detached()` 会怎样  
这时变的是外层 `fn1` 这次调用的 `this`，非严格模式下通常会变成 `window`，箭头函数也就会跟着拿到 `window`。

3. 这题和闭包、词法作用域是什么关系  
它本质上也是“规则先静态确定，值在运行时按外层环境去取”的表现，继续追就会连到执行上下文和闭包。

### 4 和 7. `Promise + setTimeout` 与事件循环

#### 原始题干

```js
new Promise((res, rej) => {
  console.log(1);
  setTimeout(() => {
    console.log(2);
    res("success");
    console.log(3);
  }, 0);
}).then((res) => console.log(res));

console.log(4);
```

#### 思维导图关键点

```txt
事件循环
├─ 先找同步代码
├─ Promise 执行器同步执行
├─ then 进入微任务
├─ setTimeout 进入后续宏任务
└─ 当前宏任务结束后先清空微任务
```

#### 60-90 秒口语稿

这道输出题我会先按事件循环来拆。`new Promise` 里的执行器本身是同步代码，所以先输出 `1`；`setTimeout` 只是注册一个后续宏任务；脚本继续往下执行，输出 `4`。然后进入下一轮，执行定时器回调，先输出 `2`，调用 `res('success')` 时不会立刻执行 `then`，而是把它放进微任务队列，所以接着同步输出 `3`。等当前这个定时器回调结束，才会清空微任务，最后输出 `success`。真实业务里如果把这个边界搞反，最常见的问题就是日志顺序、状态更新时机和 DOM 读取时机全错位。

#### 高频追问

1. 为什么 `res()` 后不是立刻打印 `success`  
因为它触发的是微任务排队，不会打断当前宏任务里的同步代码。

2. 为什么大家说微任务优先  
更准确的说法是：当前宏任务结束后，会先清空微任务，再进入下一轮宏任务。

3. `setTimeout(fn, 0)` 为什么不是立刻执行  
因为它只是尽快进入后续宏任务队列，不会插进当前调用栈。

### 5. 作用域链

#### 原始题干

```js
const a = 10;

function fn() {
  const a = 20;
  test();
}

function test() {
  console.log(a);
}

fn();
```

#### 思维导图关键点

```txt
作用域链
├─ 变量查找看定义位置
├─ 不看调用位置
├─ test 定义在全局
├─ 所以输出 10
└─ 这题是闭包和词法作用域的地基
```

#### 60-90 秒口语稿

这题输出是 `10`，因为 JavaScript 变量查找看的是词法作用域，也就是函数定义在哪里，而不是函数在哪里被调用。`test` 是在全局作用域里定义的，所以它查找 `a` 时，不会因为自己是在 `fn` 里面被调用，就去拿 `fn` 作用域里的 `a = 20`，它会沿着定义时那条外层作用域链往全局找，最后拿到 `10`。真实业务里很多回调函数被传来传去时，大家容易误以为“在哪里调用就用哪层变量”，但其实这正是最容易混掉作用域链和调用栈的地方。

#### 高频追问

1. 如果把 `test` 写到 `fn` 里面，结果会怎样  
会输出 `20`，因为这时它的定义位置变了，外层作用域也跟着变了。

2. 为什么调用关系改不了变量查找路径  
因为调用栈决定谁先执行，词法作用域决定变量往哪找，它们不是一回事。

3. 这题和闭包有什么关系  
闭包能成立的底层前提，就是函数会记住自己定义时的外层作用域关系。

### 8. 浏览器输入 URL 发生了什么

#### 思维导图关键点

```txt
输入 URL
├─ Browser Process 发起 navigation
├─ beforeunload / Cache / Service Worker / 网络栈
├─ response headers 决定 commit / renderer process
├─ Blink 解析 HTML / CSS / JS
├─ RenderingNG: style -> layout -> paint -> raster
├─ Viz aggregate + draw
└─ 最终出像素
```

#### 60-90 秒口语稿

这题我不会只答 DNS、TCP、HTTP、渲染，而是会把它讲成一条完整链。用户在地址栏输入 URL 后，先由 browser process 发起 navigation，旧页面可能先走 `beforeunload`。接着这个请求可能命中缓存、Service Worker，也可能真正进入 DNS、建连、TLS 和 HTTP。拿到响应头后，browser process 会判断是不是重定向、错误页、下载，以及新文档该交给哪个 renderer process。等 renderer 创建文档并回 ACK，才算 commit。commit 之后 Blink 开始解析 HTML、CSS、JS，再进入现代 Chromium 的 RenderingNG 流水线，先做 style、layout、paint，再继续做 layerize、raster、activate。最后由 Viz 统一聚合多个 compositor frame，并通过 GPU draw 到屏幕上。真实业务里如果你看到 DOMContentLoaded 已经很早了但首屏还是慢，问题往往不在网络，而是卡在后面的样式计算、主线程长任务、raster 或最终 draw。

#### 高频追问

1. `commit` 是什么  
它是导航里的关键边界。browser process 选定 renderer process 后，把响应交给它，等 renderer 创建文档并回 ACK，才算 commit。

2. 为什么跨站导航可能切进程  
因为 Site Isolation 会把跨站文档放进不同 renderer process，这和安全边界强相关。

3. Viz 为什么值得讲  
因为现代 Chromium 不是 renderer 直接把内容画到屏幕，而是 renderer 产出 compositor frame，Viz 负责统一 aggregate 和最终 draw。

这题值得单独深挖，因为它天然串起导航、多进程、Blink、RenderingNG 和 Viz。

### 9. 回流和重绘

#### 思维导图关键点

```txt
渲染更新
├─ 回流：布局变了，要重新算几何信息
├─ 重绘：布局不变，只改视觉表现
├─ 回流通常比重绘更重
├─ 不要频繁读写交错
└─ 动画优先考虑合成层友好属性
```

#### 60-90 秒口语稿

回流和重绘的区别，核心在于有没有影响布局。回流也叫重排，意思是元素的几何信息变了，浏览器要重新计算位置和尺寸，比如改宽高、增删节点、读写布局相关属性时都可能触发。重绘则是布局没变，只是视觉表现变了，比如颜色、背景、阴影这类更新。一般来说回流比重绘更重，因为它后面往往还会连着重绘一起发生。工程上最常见的优化点是避免频繁读写布局交错，减少大面积 DOM 改动，动画尽量用对合成层更友好的属性。真实业务里像瀑布流、复杂表格、拖拽面板，一旦读写布局操作太碎，就很容易引发卡顿。

#### 高频追问

1. 为什么读取某些布局属性也可能触发回流  
因为浏览器为了给你返回准确的最新布局值，可能先强制把前面的样式和布局结算掉。

2. 为什么说回流通常比重绘更重  
因为回流要先重新算布局，而布局一变，后面通常还会继续重绘。

3. 动画为什么常建议用 `transform` 和 `opacity`  
因为这类属性更容易走合成路径，减少回主线程重新布局和绘制的概率。

### 10. 闭包

#### 思维导图关键点

```txt
闭包
├─ 函数记住定义时的词法作用域
├─ 外层函数结束后仍可访问变量
├─ 核心价值：保留状态
└─ 风险：长生命周期引用
```

#### 60-90 秒口语稿

闭包我会理解成“函数把定义时的词法作用域记住了”。所以即使外层函数执行结束，内部函数后续仍然能访问那层环境里的变量。它最核心的价值是保留状态和做私有封装，比如计数器、防抖、节流、缓存函数都会用到闭包。闭包本身不是性能问题，真正的风险是把已经没用的大对象、DOM 或上下文通过闭包长时间引用住，导致回收不掉。真实业务里像事件监听、定时器和缓存逻辑，如果清理做得不好，闭包就很容易和内存问题绑在一起。

#### 高频追问

1. 闭包和作用域链有什么关系  
作用域链回答变量往哪找，闭包回答为什么函数离开定义位置后还能继续沿那条链找。

2. 为什么循环里配合 `var` 容易出问题  
因为多个闭包共享的是同一个函数作用域绑定，而不是每轮独立绑定。

3. 闭包是不是等于匿名函数  
不是，命名函数一样可以形成闭包。

### 11. 项目里遇到的难题怎么讲

#### 思维导图关键点

```txt
项目难题
├─ 先讲背景和目标
├─ 再讲约束和难点
├─ 再讲方案和取舍
├─ 最后讲结果和复盘
└─ 重点不是炫技，是说明判断力
```

#### 60-90 秒口语稿

这类题我不会上来就堆技术名词，而是按“背景、问题、方案、取舍、结果”去讲。先说明当时的业务目标和约束，比如性能压力、稳定性要求、协作复杂度或者上线时间；然后讲清真正的难点是什么；再说我为什么选择当前方案而不是别的方案；最后补结果，比如指标改善、故障收敛、研发效率提升，以及事后复盘。如果你项目里没有特别宏大的故事，也没关系，重点是讲出你怎么判断、怎么取舍、怎么落地。真实面试里这题考的通常不是你做过多大的系统，而是你有没有工程判断力。

#### 高频追问

1. 结果一定要量化吗  
最好能量化，哪怕只是首屏时间、错误率、成本、提效比例中的一个。

2. 如果项目没有特别大的难题怎么办  
可以讲一个局部问题，但要把分析、权衡和落地过程讲透。

3. 最忌讳怎么答  
最忌讳答成流水账，或者只说“我负责了很多”，却没有清楚的问题和结果。

### 12. 为什么项目要使用 `SSR`

#### 思维导图关键点

```txt
SSR
├─ 更早返回可解析 HTML
├─ 有利于首屏和 SEO
├─ 适合首屏敏感、搜索敏感场景
├─ 代价是服务端复杂度更高
└─ 后面还有 hydration 成本
```

#### 60-90 秒口语稿

项目使用 `SSR`，我一般会从首屏、SEO 和内容可达性三件事来讲。服务端先把首屏 HTML 输出出来，浏览器更早拿到可解析内容，所以通常比纯客户端渲染更容易优化首屏感知；如果页面有搜索收录诉求，`SSR` 也更友好。但 `SSR` 不是白拿收益，它会提高服务端渲染复杂度，还会带来同构代码、缓存策略、数据预取和 hydration 的成本。所以我不会把它答成“SSR 一定更好”，而是会说它适合首屏敏感、内容型、搜索敏感的页面。真实业务里像营销落地页、搜索结果页、内容详情页，这类页面更容易从 `SSR` 里获得收益。

#### 高频追问

1. `SSR` 一定比 CSR 快吗  
不一定。它通常能更早给出 HTML，但整体体验还受接口、资源、hydration 和客户端执行影响。

2. 为什么 `SSR` 对 SEO 更友好  
因为搜索引擎更容易直接拿到完整内容，而不是只拿到一个空壳容器。

3. 什么时候不建议上 `SSR`  
后台系统、强交互但不依赖收录的页面，收益可能没有成本大。

### 13. 平时怎么使用 `AI`

#### 思维导图关键点

```txt
AI 使用
├─ 用来提效，不替代判断
├─ 适合查思路、出草稿、补测试
├─ 结果必须自己校验
├─ 敏感逻辑不能盲信
└─ 重点是把它接进工程流
```

#### 60-90 秒口语稿

我平时会把 `AI` 当成提效工具，而不是“替我做判断的人”。比较常见的用法是让它帮我快速梳理思路、生成初版代码、补测试样例、解释陌生报错或者整理方案对比。但它给出的内容我一定会自己校验，尤其是边界逻辑、性能敏感点和业务关键路径，不能直接照搬。更高价值的用法，其实不是问它“怎么写一段代码”，而是把它接进自己的工程流程里，比如做代码评审前的草拟分析、接口 mock、文档整理或者问题排查的第一轮假设收集。真实业务里，能不能把 `AI` 用好，关键不在提示词有多花，而在你有没有自己的判断基线。

#### 高频追问

1. 你最常用它解决什么问题  
通常是资料归纳、代码草稿、测试样例、报错解释和方案对比。

2. 为什么不能直接信它  
因为它很容易在细节、版本差异和边界条件上自信但不准确。

3. 怎么避免 AI 产出“看起来对、实际上错”  
把它当起点，不当终点，自己做验证和兜底。

### 14. 怎么理解 `rules`

#### 思维导图关键点

```txt
rules
├─ 不是形式主义
├─ 本质是团队共识
├─ 目标是降低沟通和返工
├─ 好规则要可执行、可解释
└─ 规则也要随场景迭代
```

#### 60-90 秒口语稿

我理解的 `rules` 不是形式主义，也不是为了多一层限制，而是团队在协作里沉淀出来的可复用共识。它的核心价值是降低沟通成本、减少返工、让代码风格、目录结构、提交流程和风险控制更稳定。但我也不会把规则理解成“越多越好”，好的规则应该是可执行、可解释、能服务真实效率的。如果一条规则已经和实际场景脱节，就应该被调整，而不是机械执行。真实业务里最有效的规则通常不是写得最长的那种，而是能直接嵌进代码评审、CI、模板和脚手架里的那种。

#### 高频追问

1. 为什么团队需要规则  
因为多人协作下，如果完全靠口头约定，质量和效率都会很不稳定。

2. 规则和灵活性会不会冲突  
会，所以规则要抓高频、关键、容易出错的点，而不是什么都管。

3. 什么样的规则最有效  
能被工具化、自动化、流程化的规则最有效。

### 15. 类似百度搜索页的页面怎么做

#### 思维导图关键点

```txt
搜索页实现
├─ 先拆输入、结果区、分页器
├─ 再做状态：keyword、loading、list、page
├─ 请求要考虑防抖和乱序
├─ 分页切换要保留查询条件
└─ 口述时先讲结构再讲边界
```

#### 60-90 秒口语稿

如果现场让我写一个类似百度搜索页的页面，我会先拆结构，再补状态和边界。结构上至少分成搜索输入框、结果列表、分页器三块；状态上要有 `keyword`、`loading`、`list`、`page` 和可能的 `error`。交互上用户输入关键字后触发查询，请求完成后渲染结果，分页切换时要带着当前关键字继续查下一页。因为这是搜索场景，所以我还会主动提一句，请求层要考虑防抖和乱序，避免用户快速输入时旧请求覆盖新结果。真实业务里这类题不只是考你能不能写 UI，更考你会不会在口述时主动把状态管理、请求边界和交互细节一起讲出来。

#### 高频追问

1. 为什么分页切换要保留查询条件  
因为分页本质上是同一查询条件下的数据翻页，不应该把上下文丢掉。

2. 这题最容易漏什么  
最容易漏 loading、空态、错误态和请求乱序。

3. 如果时间很短怎么答更稳  
先保证结构和主流程跑通，再口头补边界处理。

### 16 和 17. `pnpm` 与幻影依赖

#### 思维导图关键点

```txt
pnpm
├─ 通过硬链接和内容寻址节省磁盘
├─ node_modules 结构更严格
├─ 目的是减少重复安装和依赖污染
├─ 幻影依赖：项目用了没声明的包
└─ pnpm 更容易把这类问题暴露出来
```

#### 60-90 秒口语稿

我选择 `pnpm`，核心原因通常有两个：第一是它通过内容寻址存储和硬链接复用包内容，磁盘占用和安装效率更好；第二是它的 `node_modules` 结构更严格，更容易暴露不规范的依赖使用。所谓幻影依赖，本质上就是项目代码用了一个自己并没有显式声明的包，只是因为传统扁平化安装把它“顺手放到了能被找到的位置”，所以代码暂时能跑。一旦安装结构变化或者换了包管理器，这种隐性依赖就会暴露。真实业务里 `pnpm` 的价值不只是快，而是它能更早把依赖边界问题暴露出来，避免项目规模变大以后出现“本地能跑、换环境就挂”的情况。

#### 高频追问

1. 什么叫幻影依赖  
就是项目用了没在自己 `package.json` 里声明的包，但由于安装结构原因侥幸可用。

2. 为什么传统安装方式更容易藏住这个问题  
因为扁平化后很多依赖被提到上层目录，模块解析时可能误打误撞找到它们。

3. `pnpm` 的价值只是更快吗  
不是，更大的价值之一是依赖边界更严格，问题暴露得更早。

#### 专题建议

建议后续单独抽专题：`Node 模块解析、扁平化安装与 pnpm 幻影依赖`

### 18. 反转链表

#### 思维导图关键点

```txt
反转链表
├─ 三指针
├─ prev / cur / next
├─ 每次反转当前指针
├─ 再整体向前推进
└─ 最后返回 prev
```

#### 60-90 秒口语稿

反转链表我一般会用三指针解。核心就是准备 `prev`、`cur`、`next` 三个变量：先保存当前节点的下一个节点，然后把当前节点的 `next` 指向前一个节点，再整体往前推进，也就是 `prev = cur`、`cur = next`。循环结束后，`prev` 就是新的头节点。这个解法的关键不是背代码，而是口头上要讲清指针怎么变。真实面试里这题考的通常不是算法有多难，而是你能不能把指针修改过程讲得稳定、不打结。

#### 核心代码

```js
function reverseList(head) {
  let prev = null;
  let cur = head;

  while (cur) {
    const next = cur.next;
    cur.next = prev;
    prev = cur;
    cur = next;
  }

  return prev;
}
```

#### 高频追问

1. 为什么要先存 `next`  
因为一旦把当前节点反向指过去，原来的后继就丢了。

2. 空链表和单节点链表怎么处理  
这套写法天然兼容，循环会直接结束或只走一次。

3. 时间和空间复杂度是多少  
时间 `O(n)`，额外空间 `O(1)`。

### 19. 反问：学习建议

#### 思维导图关键点

```txt
反问
├─ 不问福利
├─ 优先问能力成长
├─ 问团队对优秀前端的期待
├─ 问当前岗位常见挑战
└─ 问学习路径和改进建议
```

#### 60-90 秒口语稿

如果到了反问环节，我会尽量把问题落到能力成长和岗位预期上，而不是泛泛地问福利。比如我会问：这个岗位上做得比较好的前端，通常和一般同学最大的差别是什么；或者如果我想更贴近你们团队的要求，接下来最值得补的能力是什么。这样的反问一方面更容易拿到真实反馈，另一方面也会让面试官觉得你关注的是长期成长而不是只想结束面试。真实面试里，反问不一定要多，但最好能体现你对岗位、能力边界和成长路径有判断。

#### 高频追问

1. 为什么不建议问太空泛的问题  
因为很容易让反问环节变成礼貌性收尾，没有信息量。

2. 什么样的问题更加分  
和岗位预期、团队判断标准、成长路径相关的问题更容易加分。

3. 反问一定要技术吗  
不一定，但最好和岗位能力建设有关，而不是完全脱离岗位本身。
