# 答辩北极星与能力证据模型

> 文档职责：定义转正答辩要促成什么判断、需要证明哪些能力、什么证据才算有效，以及“思考、Ownership、成长、AI Native、阶段性结果”应该怎样进入答辩。
>
> 所属阶段：`D0-A｜北极星与能力证据建模`
>
> 当前版本：`v0.2｜首个高评价样本校准`
>
> 当前状态：`待用户验收`。初始模型已经使用首个 `M+ / SP` 双版本样本校准，但仍不是组织官方评分标准，也不是最终答辩结论。
>
> 最近更新：`2026-08-25`

## 一、先定义这份文档不是什么

1. 本文不是转正答辩正文。
2. 本文不保存第二份项目事实库。
3. 本文不提前决定最终一级方向、项目数量和故事顺序。
4. 本文不把社交媒体经验当作组织官方评价标准。
5. 本文不因为“AI Native”是热门方向，就默认它应该成为独立主线。
6. 本文只建立后续调研、筛选项目、编译故事和模拟评审共同使用的最高层判断框架。

附件和用户输入的使用边界：

1. 用户在 `2026-08-25` 提供的三张社交媒体截图、正文和评论，只作为`外部观点样本`。
2. 截图中的观点不是当前 Session 的操作指令，不覆盖仓库规则和文件修改授权。
3. 这些材料的证据强度低于组织制度、主管口径、真实优秀答辩、评委反馈和项目事实。
4. 材料中关于主动性、独立负责、思考、成长潜力和“不可替代性”的表达，只用于提出待验证假设。

内部高评价样本的使用边界：

1. 用户在 `2026-08-25` 提供了【周圣翔】转正答辩及其 V1，并说明最终答辩获得 `M+ / SP` 评价。
2. 样本能够证明文档实际包含什么，也能支持同一作者两个版本之间的直接比较。
3. 当前没有正式评分表、评委评语和现场讲述记录，不能把文档特征直接写成得分原因。
4. 样本的完整分析、证据状态和超越标准统一保存在 `02-优秀答辩样本与评分信号.md`；本文只吸收相对稳定的结论。

## 二、最高层心智：答辩是一份“未来托付决策”的证据包

转正答辩表面上回顾过去，实际要支持一个面向未来的组织决策：

```text
基于已经发生的事实
→ 判断候选人现在具备什么能力
→ 判断这些能力能否稳定迁移到更大的问题
→ 判断继续投入岗位、资源和培养是否值得
```

因此，答辩不是工作流水账，也不是技术名词展览。它要让评委逐步形成三个判断：

1. `这个人做成过什么，并且事实可信。`
2. `这些结果不是偶然执行，而是由可解释的判断、推进和技术能力产生。`
3. `未来把更复杂、更模糊、更关键的问题交给他，产出仍然可预期，风险仍然可控制。`

可以把最高层评价信号暂时归纳为：

```text
真实贡献
+ 可托付范围
+ 判断质量
+ 成长斜率
+ 可复用杠杆
+ 可控风险
```

这里不是数学加权公式。各维度真实权重需要在 D1 通过制度、优秀样本、主管口径和评委反馈校准。

## 三、建议使用的三层总叙事

当前推荐把转正答辩的最高层叙事拆成三个不同职责的轴，避免混为一个口号。

### 3.1 核心评价轴：可托付范围扩大

它回答：

> 相比刚进入团队时，现在可以把什么更大、更模糊、更关键的问题交给我？

“可托付”不等于一个人包办全部工作，而是能够：

1. 理解目标和真实约束。
2. 把模糊问题变成可执行边界。
3. 在多个方案之间作出解释得通的选择。
4. 主动暴露风险并推动关键协作。
5. 对阶段结果和最终结果负责。
6. 在需要帮助时准确升级问题，而不是被动等待指令。

### 3.2 项目叙事轴：解决问题的复杂度和系统边界演进

它回答：

> 我处理的问题，是否从局部功能交付扩展到了真实业务链路、平台能力和自动化系统？

当前可供验证的候选演进是：

```text
复杂业务链路治理
→ 业务能力标准化与平台化
→ Agent 化与自动化执行
```

这条链路只是项目叙事假设，必须由项目事实、Ownership、结果和优秀样本共同验证，当前不得作为最终结论。

### 3.3 差异化评价轴：AI Native 杠杆

它回答：

> 在 AI 已经成为基础生产力的环境里，我是否只会更快地完成任务，还是能重新设计任务、上下文、工具、验证和协作方式？

AI Native 更适合作为贯穿多个项目和工作方法的`横向能力证据`。只有存在独立业务价值、完整 Ownership 和可靠结果时，才考虑升级为一级方向。

### 3.4 三个轴的关系

```text
为什么值得转正
    ↓
可托付范围扩大
    ↓
由哪些真实项目证明
    ↓
问题复杂度与系统边界演进
    ↓
什么形成时代差异化
    ↓
AI Native 的认知、执行和复用杠杆
```

## 四、北极星候选

### 4.1 一句话北极星候选

> 证明自己已经从在明确边界内完成交付，成长为能够在真实业务约束下定义问题、作出取舍、推动闭环并验证结果的工程师，同时开始用 AI Native 方法把个人能力转化为可复用的业务和研发杠杆。

这句话当前只承担研究假设作用。后续必须检查：

1. “从明确交付到问题负责”是否符合真实经历。
2. 是否确实有主动定义问题和提出策略的证据。
3. 是否有足够 Ownership 支撑“推动闭环”。
4. AI Native 是否具有超出个人使用技巧的真实机制和结果。
5. 是否符合当前职级和组织对转正的真实期待。

### 4.2 评委最终应该记住什么

理想情况下，答辩结束后评委能用自己的话形成以下印象：

1. 他理解的不只是需求表面，还能还原业务目标和真实链路。
2. 他遇到复杂问题时有自己的判断，不会只等待完整方案。
3. 他能把判断推进为协作、实现和验证，而不止停在观点。
4. 他知道个人贡献、团队基座和系统边界分别在哪里。
5. 他对 AI 的理解已经进入工作流、工具、评测和系统设计，而不只是生成代码。
6. 他的能力和负责范围在持续扩大，未来产出具有可预期性。

如果一页内容不能帮助形成这些判断中的任何一个，就需要重新判断它是否值得进入正文。

### 4.3 首个高评价样本带来的基线校准

首个 `M+ / SP` 样本说明，一份较高评价的答辩至少需要建立四层可信度：

```text
真实交付
→ 系统级问题和架构抽象
→ 使用、质量或业务结果
→ 图、数据、反馈和文档组成的证据包
```

这构成当前答辩的生产底线，但不是最终胜出标准。要进一步形成差异化，还需要比样本更清楚地证明：

1. 一句话转正理由和未来可托付范围。
2. 问题怎样被发现、定义和确定优先级。
3. 候选方案怎样比较，最终取舍如何形成。
4. 个人判断、协作输入、团队基座和结果归因的边界。
5. 认知变化怎样影响后续行为，并在新问题中再次复用。
6. AI Native 怎样改变工作流、质量门禁、负责范围和团队复用，而不只提高代码生成比例。

详细样本分析、V1 到最终版的变化和逐维度超越合同，以 `02-优秀答辩样本与评分信号.md` 为唯一真相源。

## 五、能力证据模型

以下七个维度用于研究和筛选内容，不代表最终官方评分权重。

| 能力维度 | 评委真正要判断的问题 | 高质量证据 | 低质量表达 |
|---|---|---|---|
| 业务与价值判断 | 是否理解用户、业务目标、优先级和投入价值 | 用户场景、原链路、业务冲突、优先级依据、价值变化 | “完成了某某需求”“支持了某某功能” |
| 问题发现与建模 | 能否从现象中找到关键问题并定义边界 | 信号、根因、约束、系统边界、问题拆分、假设验证 | “发现这里可以优化”“感觉体验不好” |
| 方案与技术判断 | 能否比较方案并对取舍负责 | 方案集合、选择标准、未采用方案、技术边界、失败语义 | 只陈述最终架构或罗列技术名词 |
| Ownership 与推进 | 能否把问题推进为可验证结果 | 责任边界、决策记录、协作对象、阻塞处理、风险升级、验收闭环 | “参与”“协助”“全程负责”但没有行为证据 |
| 结果与验证 | 是否真的改变了业务、流程、质量或风险 | 线上指标、阶段验收、测试、回读、用户反馈、风险关闭 | 无口径百分比、预期收益当实际收益 |
| 成长与迁移 | 是否形成了能迁移到新问题的认知 | 前后行为变化、认知触发、新模型、二次应用、复盘产物 | “提升了技术能力”“学到了很多” |
| AI Native 与复用杠杆 | 是否能用 AI 重构工作和系统，并保证可控 | 上下文工程、Tool/Skill、评测、兜底、复用、采纳和真实效率变化 | “使用 AI 辅助编码”“写了很多 Prompt” |

### 5.1 能力不是自评，必须由证据反推

错误方向：

```text
我具备架构能力
→ 找几个项目支持这个形容词
```

正确方向：

```text
真实问题与约束
→ 做过的判断和推进
→ 产生的结果与验证
→ 多个案例中重复出现的行为模式
→ 归纳出可以被评委接受的能力
```

### 5.2 能力强度由四个问题共同决定

1. 这项能力是否在真实问题中发生？
2. 关键判断是否属于本人，而不是事后包装或团队公共结论？
3. 判断是否改变了方案、推进路径或结果？
4. 相同认知是否在新问题中再次使用？

只满足第一项，通常只能证明参与；满足前三项，才形成较强的能力证据；完成迁移，才更接近成长潜力和稳定能力。

### 5.3 结果证据必须分层

首个高评价样本同时出现代码量、需求量、治理指标、调用量和用户场景，说明“产出”不能由一个数字概括。后续统一区分：

| 层级 | 回答的问题 | 典型证据 | 使用规则 |
|---|---|---|---|
| R1｜活动量 | 做了多少工作 | 需求、MR、代码、接口、命令、文档 | 证明投入和覆盖，不单独承担核心收益 |
| R2｜交付结果 | 是否完成并达到阶段门槛 | 测试、灰度、发布、验收、缺陷关闭 | 说明项目成熟度和交付质量 |
| R3｜使用结果 | 是否进入真实用户或流程 | 用户、调用、留存、覆盖、反馈、复用 | 证明能力从产物进入真实使用 |
| R4｜业务影响 | 使用后发生了什么变化 | 时间、质量、稳定性、合规、成本、风险 | 优先进入正文，必须说明口径和因果边界 |

1. 不要求每个项目都达到 R4，但必须如实说明当前最高层级。
2. R1 不能替代 R3/R4，工作量大不自动等于价值高。
3. R3 的调用量要区分用户调用、自动调用和单任务产生的底层调用。
4. R4 必须绑定基线、窗口、来源、计算方式和个人归因边界。
5. Demo 项目可以有 R1/R2，不能把预期的 R3/R4 写成已发生结果。

## 六、“思考”的严格定义

### 6.1 什么才算答辩里的思考

答辩中的思考是：

> 在信息不完整、目标冲突或方案不唯一的情况下，基于事实和约束形成判断，并让这个判断影响后续行动、协作或结果。

它至少包含四个要素：

1. `不确定性`：问题不是只有唯一显然答案。
2. `判断依据`：业务、技术、数据或风险事实是什么。
3. `选择与取舍`：选择了什么，同时放弃了什么。
4. `行动与验证`：判断如何被推进，并怎样知道它有效或无效。

缺少选择、行动和验证的“思考”，更接近观点或复盘感想，不能承担核心故事。

### 6.2 思考证据链

每个核心 Case 至少还原一条：

```text
观察到什么信号
→ 为什么它不是表面问题
→ 真正目标和现实约束是什么
→ 根因与系统边界在哪里
→ 有哪些候选方案
→ 用什么标准比较
→ 为什么选择当前策略
→ 如何推动协作和实现
→ 怎样验证判断
→ 哪些结果符合或推翻原假设
→ 认知发生了什么变化
→ 新认知是否再次被使用
```

### 6.3 思考成熟度

| 等级 | 典型表现 | 答辩价值 |
|---|---|---|
| T0｜事后感想 | 项目结束后总结“应该更重视某事” | 只能作为轻量复盘 |
| T1｜问题分析 | 能解释现象、原因和局部边界 | 可以证明理解深度 |
| T2｜方案判断 | 提出多个方案和选择标准，形成明确取舍 | 可以证明判断力 |
| T3｜策略推进 | 判断改变了方案、协作或交付路径，并得到阶段验证 | 可以进入核心故事 |
| T4｜认知迁移 | 相同方法在新问题中复用，或沉淀为团队机制 | 可以证明成长和杠杆 |

当前不要求每条故事都达到 T4。核心故事至少应该达到 T2，并尽量用 T3 证据证明它不只是纸面判断。

### 6.4 六类高收益思考

1. `问题发现`：从用户反馈、异常、重复成本或协作摩擦中识别真正问题。
2. `边界判断`：明确系统负责什么、不负责什么，避免局部优化制造全局风险。
3. `方案取舍`：在时效、复杂度、可靠性、扩展性和迁移成本之间选择。
4. `风险前置`：提前识别权限、状态、并发、版本、合规、回滚或评测风险。
5. `反馈纠偏`：依据测试、用户反馈或真实请求调整原方案。
6. `机制抽象`：把一次性交付提炼成契约、工具、流程、平台能力或可复用方法。

### 6.5 决策卡模板

后续每个主 Case 可以用以下结构回收“思考”：

```text
决策主题：
触发信号：
业务目标：
现实约束：
根因判断：
我的责任边界：
候选方案：
比较标准：
最终选择：
未采用方案及原因：
我提出和推动的动作：
协作与异议：
阶段验证：
真实结果：
当前仍未验证：
认知变化：
后续复用：
事实等级与证据：
```

## 七、Ownership：不追求“不可替代”，要证明“可托付”

### 7.1 为什么不使用“不可替代性”作为北极星

1. 成熟组织会通过文档、流程、平台和协作降低单点人员风险。
2. 实习生或新人成长周期短，强行证明不可替代容易滑向夸大 Ownership。
3. 转正决策更关心能否独立承担合理范围、主动发现问题、稳定推进结果。
4. 真正高级的贡献往往是让能力可复用，而不是让自己成为唯一知道怎么做的人。

因此，建议将“不可替代性”改写成：

```text
可托付性
+ 稀缺的能力组合
+ 主动发现和解决问题的行为
+ 将个人经验转成团队机制的能力
```

### 7.2 Ownership 成熟度

| 等级 | 能力边界 | 可以使用的证据 |
|---|---|---|
| O0｜任务执行 | 在明确方案下完成分配任务 | 代码、测试、按时交付 |
| O1｜独立交付 | 独立拆解并交付边界清晰的需求 | 方案、排期、联调、验收、问题处理 |
| O2｜问题负责 | 从目标出发定义问题、提出方案、协调依赖并对结果负责 | 决策、协作、风险、验证和复盘 |
| O3｜机制负责 | 将多次问题抽象为平台、契约、流程或工具 | 复用、覆盖、迁移、规范和采纳 |
| O4｜方向负责 | 识别业务机会、确定优先级并持续经营结果 | 长周期业务和组织结果 |

对于转正答辩，不需要假装达到 O4。更可信的目标是：

1. 证明 O1 已经稳定成立。
2. 用一到两个强 Case 证明正在达到 O2。
3. 如果有真实复用和团队采纳，再展示局部 O3 证据。

### 7.3 “提出想法并被采纳”怎样成为 Ownership 证据

仅写“这个思路是我提出的”仍然较弱。完整证据链应该是：

```text
我观察到什么问题
→ 为什么现有方案不够
→ 我提出了什么候选策略
→ 用什么事实说服相关方
→ 遇到什么异议或约束
→ 如何调整并形成共识
→ 决策怎样进入实现和排期
→ 最终验证或阶段结果是什么
```

Ownership 不等于没有导师或协作者。能够准确利用导师经验、推动对齐并保持自己对问题的判断，同样是负责能力。

### 7.4 个人贡献边界

每个 Case 必须区分：

1. 团队已经存在的公共基座。
2. 主管、导师或产品给出的目标和约束。
3. 本人独立提出的判断、方案或机制。
4. 与他人共同形成的决策。
5. 本人负责推进和交付的部分。
6. 仍依赖其他团队完成的部分。

答辩的可信度来自边界清楚，不来自把所有成果归到自己名下。

## 八、成长：证明能力模型发生变化，不只证明知识增加

### 8.1 成长证据链

```text
原来的理解或行为方式
→ 遇到什么事件暴露局限
→ 形成了什么新的心智模型
→ 后续行为发生了什么变化
→ 新方式带来了什么结果
→ 是否在第二个问题中再次复用
```

### 8.2 高质量成长的六个方向

1. 从接收需求到还原业务目标。
2. 从局部功能到端到端链路和系统边界。
3. 从选择一个可用方案到比较代价和失败语义。
4. 从完成开发到主动推进协作、验收和结果。
5. 从解决一次问题到沉淀契约、工具和机制。
6. 从使用 AI 生成答案到构造上下文、执行系统和评测闭环。

### 8.3 低质量成长表达

1. “熟悉了某个技术栈。”
2. “沟通能力有明显提升。”
3. “更加理解团队协作的重要性。”
4. “学会使用 AI 提升效率。”
5. “具备了独立负责项目的能力。”

这些结论只有绑定触发事件、行为变化、真实结果和二次复用后，才能成为答辩证据。

### 8.4 项目候选认知映射

以下只是后续需要验证的候选，不是当前项目事实结论：

| 项目方向 | 可能体现的认知升级 | 必须补充的证据 |
|---|---|---|
| 素材业务、自动分发、发布与合规 | 从局部需求走向端到端链路、状态和失败边界 | 真实链路、约束、关键取舍、上线或验证结果 |
| OpenAPI 与 vimocli | 从接口实现走向契约、权限、版本和开发者体验 | 真实请求、契约、权限链路、使用或复用证据 |
| VIMO 运营 Agent | 从模型调用走向任务编译、工具执行、评测和人机边界 | Agent 链路、失败语义、评测、用户与生产状态 |
| AI 辅助研发与知识工程 | 从个人提效走向上下文工程、可复用工作流和组织杠杆 | 实际流程、复用对象、质量门禁、效率和采纳证据 |

## 九、AI Native：从“会用 AI”到“重构工作和系统”

### 9.1 初始定义

AI Native 不是在原有流程末端增加一个模型调用，而是：

> 从任务表示、上下文、工具、执行、评测、兜底和复用出发，重新设计人、模型与系统的协作方式，并对结果质量负责。

### 9.2 AI Native 能力阶梯

| 等级 | 典型能力 | 差异化强度 |
|---|---|---|
| A0｜对话辅助 | 问答、代码补全、文案生成 | 逐渐成为基础能力，单独证明价值较弱 |
| A1｜个人流程提效 | 用 AI 加速调研、开发、测试、Debug、文档 | 能证明效率意识，但需要真实前后对比 |
| A2｜上下文与工具工程 | 构造稳定上下文，连接 Tool/MCP/Skill，设计任务输入和输出合同 | 能证明 AI 工程能力和确定性意识 |
| A3｜可评测的 Agent/Workflow | 任务编译、状态、权限、执行、失败恢复、评测和人工兜底 | 能证明生产级 AI 应用和系统思考 |
| A4｜团队与业务杠杆 | 能力被多人、多项目或真实业务复用，形成规范和持续反馈 | 能证明组织影响和平台价值 |

当前答辩不应为了“AI Native”标签虚构 A3/A4。所有等级必须由项目和工作流事实决定。

### 9.3 AI Native 证据链

每项 AI 能力至少回答：

```text
原流程的真实瓶颈是什么
→ 为什么 AI 适合进入这个环节
→ 人、模型和确定性工具怎样分工
→ 上下文从哪里来，怎样保持正确
→ 如何评测、纠错、授权和兜底
→ 失败时怎样暴露和恢复
→ 带来了什么效率、质量或业务变化
→ 是否被复用，复用边界是什么
```

### 9.4 高质量 AI Native 证据

1. 可复现的任务上下文和输入合同。
2. Tool、Skill、MCP、CLI 或工作流编排。
3. 评测集、验收规则、真实回读和错误分类。
4. 权限、敏感数据、人工审批和失败恢复边界。
5. 流程改造前后的耗时、步骤、成功率或质量变化。
6. 被团队成员、其他项目或真实用户采纳的证据。
7. AI 不适用的场景和保留确定性系统的判断。

### 9.5 低质量 AI Native 表达

1. “大量使用 AI 辅助编码。”
2. “通过 Prompt 提升开发效率。”
3. “搭建 Agent 实现智能化闭环。”
4. “沉淀 Skill 全面赋能团队。”
5. “用大模型替代人工流程。”
6. “AI 代码贡献率达到某个百分比，因此具备 AI Native 能力。”

如果缺少流程、边界、评测、结果和复用，上述表达只是在堆热门概念。

AI 代码贡献率可以作为研发过程数据，但必须同时回答：

1. 是否真正缩短从需求到验证结果的周期。
2. 是否降低返工、缺陷或上下文恢复成本。
3. 生成代码经过哪些测试、Review、真实请求和回读门禁。
4. 是否扩大个人可负责的业务范围，而不只是增加代码量。
5. 是否被其他人或其他项目复用。

### 9.6 AI Native 在答辩中的推荐位置

当前推荐：

1. 把 AI Native 作为横向能力，贯穿 Agent 项目、研发提效和知识工程。
2. 用一张能力阶梯或工作方式演进图说明从 A0 到当前真实等级的变化。
3. 只选择一个最强 Case 深讲任务、工具、评测和兜底。
4. 其余案例只作为复用证据，不重复解释相同概念。
5. 是否成为一级主线，等待 D1 样本和 D3 项目证据共同决定。

## 十、Demo 阶段和量化结果不足时怎样保持可信

### 10.1 结果成熟度阶梯

| 等级 | 状态 | 可以陈述的结论 | 不能陈述的结论 |
|---|---|---|---|
| E0｜问题与方案 | 完成问题定义、方案和评审 | 方案经过讨论、关键假设明确 | 已经产生业务价值 |
| E1｜产物完成 | Demo、原型、接口、文档或链路已经实现 | 已完成哪些可验证产物 | 已证明真实用户价值 |
| E2｜技术验证 | 核心路径、测试、性能或风险验证通过 | 技术可行性和阶段质量 | 已证明线上规模和稳定性 |
| E3｜用户/流程验证 | 目标用户试用、业务验收或流程演练 | 需求匹配度和阶段反馈 | 长期线上收益 |
| E4｜线上效果 | 在明确窗口内产生真实指标 | 真实业务、效率、质量或稳定性变化 | 未覆盖范围的泛化结果 |
| E5｜规模与复用 | 多用户、多项目或长周期复用 | 平台价值和组织杠杆 | 对未来规模无条件外推 |

### 10.2 Demo 阶段的表达合同

如果项目仍处于 Demo 阶段，必须明确写清：

```text
当前所处阶段
已经完成的产物
已经验证的假设
尚未验证的假设
当前能够证明的能力
不能宣称的线上结果
上线后准备观察的指标和窗口
```

### 10.3 思考不能替代结果

正确关系是：

```text
结果说明改变了什么
思考解释为什么能够产生这种改变
```

当线上结果还不存在时，可以使用阶段验证证明方案并非纸上谈兵，但不能用更多“思考描述”伪装成完整业务结果。

### 10.4 Demo 阶段可使用的阶段性证据

1. 关键业务链路已经跑通。
2. 高风险技术假设已经被实验或测试验证。
3. 用户、主管或相关方完成评审并给出明确反馈。
4. 方案推动了产品、架构、排期或协作决策变化。
5. 关键接口、协议、状态机或工具已经形成可运行产物。
6. Demo 对真实样本的效果经过记录，而不是只展示理想路径。
7. 指标采集和上线验证计划已经定义，但明确标记为未来验证。

### 10.5 Demo 项目的推荐表述

```text
项目当前处于 Demo/验证阶段，因此我不把预期收益写成线上结果。
这阶段已经证明的是：关键链路可以跑通、核心风险已验证、方案得到相关方确认。
我重点展开自己如何识别问题、比较方案并推动验证；上线后的业务收益仍以真实数据回收为准。
```

这种表达不会削弱项目，反而能证明事实意识、阶段判断和风险边界。

## 十一、项目故事的能力证据合同

### 11.1 每个主 Case 必须回答

1. 谁在什么场景遇到了什么问题？
2. 为什么这个问题值得解决？
3. 原链路和表面方案为什么不够？
4. 我观察到了什么信号，并怎样定义真正问题？
5. 业务、技术、时间、权限和协作约束是什么？
6. 我的 Ownership 边界是什么？
7. 有哪些候选方案，比较标准是什么？
8. 最关键的判断和取舍是什么？
9. 我具体提出、推动和交付了什么？
10. 怎样验证技术可行性、用户价值或线上结果？
11. 真实结果达到 E0～E5 哪一级？
12. 哪些事实仍未验证，哪些属于未来规划？
13. 这件事改变了我的什么认知？
14. 新认知是否在其他问题中复用？
15. 评委继续追问失败、规模和边界变化时，怎样回答？

### 11.2 两种故事视图

每个主 Case 后续至少支持：

1. `90 秒主叙事`：业务问题、关键判断、核心机制、真实结果、个人作用。
2. `深水区 Q&A`：根因、替代方案、技术原理、失败场景、Ownership、指标口径和未来边界。

主叙事用于证明判断，深水区用于证明不是事后包装。

### 11.3 能力覆盖不要求平均

1. 每个主 Case 只承担一到两个最强能力信号。
2. 业务链路项目可以重点证明业务理解、可靠性和问题负责。
3. 开放能力项目可以重点证明契约、平台边界和复用价值。
4. Agent/AI 项目可以重点证明 AI Native、评测和人机协作。
5. 整体答辩再检查七项能力是否有足够证据，不要求每个项目重复证明全部能力。

## 十二、正文页面的“存在理由”检查

任何准备进入最终答辩正文的页面，都必须能回答：

1. 这一页要让评委形成什么判断？
2. 它证明七项能力中的哪一项？
3. 核心事实和证据是什么？
4. 哪个判断属于本人，Ownership 边界在哪里？
5. 发生了什么可验证变化？
6. 如果没有线上结果，当前结果成熟度是哪一级？
7. 这一页与前后页面的因果关系是什么？
8. 删除这一页会损失哪个评分信号？

如果只能回答“这项工作也做过”，就不应该占据正文页面。

## 十三、常见伪思考和高风险包装

### 13.1 伪思考

1. 只复述问题，没有根因和边界。
2. 只描述最终方案，没有备选方案和选择标准。
3. 事后把团队结论写成个人一开始就具备的判断。
4. 用大量抽象概念掩盖没有行动和验证。
5. 把正常工程步骤全部包装成“深度思考”。
6. 把主管指出的问题改写成自己主动发现。
7. 只写“推动落地”，不说明推动对象、阻塞和决策变化。

### 13.2 高风险 Ownership

1. 把和导师共同 Owner 写成独立 Owner。
2. 把团队平台能力写成自己从零建设。
3. 把接口开发等同于完整业务负责。
4. 把参与评审写成主导方案。
5. 把建议被讨论写成建议已落地并产生效果。

### 13.3 高风险 AI Native

1. 把使用现成模型等同于 Agent 架构能力。
2. 把 Prompt 数量等同于上下文工程。
3. 把 Demo 理想路径等同于生产可用。
4. 没有评测、权限、状态和兜底，却宣称生产级。
5. 没有复用和采纳，却宣称组织级提效。

### 13.4 高风险数据

1. 无基线、无窗口、无来源的百分比。
2. 把预估节省时间写成实际节省时间。
3. 把单次 Demo 结果外推到线上规模。
4. 把团队总收益全部归因于个人改造。
5. 只选择有利样本，不说明覆盖范围和失败情况。

## 十六、D0-A 验收问题

进入后续研究前，需要确认以下七个高风险判断：

1. 是否接受将`可托付范围扩大`作为最高层评价轴，而不是“不可替代性”？
2. 是否接受将`思考`严格定义为有约束、有选择、有行动、有验证的决策链？
3. 是否接受`成长`必须通过认知变化、行为变化和二次迁移证明？
4. 是否接受 AI Native 暂时作为横向差异化轴，只有项目证据足够时才升级为一级方向？
5. 是否接受 Demo 项目严格区分产物、技术验证、用户验证和线上效果，不用预期收益补齐事实？
6. 是否接受将“真实交付、系统抽象、结果证据和完整基本面”作为当前高分生产底线？
7. 是否接受把活动量、交付结果、使用结果和业务影响分层，不用代码量、需求量或 AI 贡献率替代真实价值？

## 十七、D0-A 通过后的下一步

D0-A 通过后，仍然不直接写答辩正文。下一步进入 D0-B：

```text
北极星与能力证据模型
→ 转成可验证的研究问题
→ 定义正式来源、样本范围和证据门槛
→ 用户评审研究设计
→ 再进入优秀样本和评分规则校准
```

D0-B 需要重点研究：

1. 当前组织和职级对转正的正式要求。
2. 主管、评委和协作方分别看重哪些信号。
3. 同组织优秀答辩如何证明思考、Ownership、成长和 AI 能力。
4. 不同结果成熟度的项目在优秀答辩中如何呈现。
5. 哪些能力属于转正基本门槛，哪些能力构成差异化。
6. 当前七维模型是否过多、缺失或权重错误。
7. AI Native 是否符合当前组织语境，怎样避免成为热门词包装。
8. 这些判断怎样反向生成项目研究任务书和答辩骨架。
