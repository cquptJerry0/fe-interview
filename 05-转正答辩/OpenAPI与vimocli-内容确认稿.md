## 1. 背景

### 1.1 OpenAPI 与 vimocli 的用途

VIMO 素材模块提供素材管理与素材供给能力。OpenAPI 将素材查询、修改、面板分类配置和发布等能力提供给程序调用；vimocli 将这些接口组织为命令，供运营、研发、自动化脚本和 Agent 使用。

页面操作之外的批量任务，需要稳定的接口、明确的授权范围和可处理的返回结果。调用方还需要处理登录、国内外站点、业务线、参数和异常。OpenAPI 与 vimocli 集中承接这些共性问题，业务脚本和 Agent 可以直接围绕素材任务进行编排。

两者的职责分别是：

1. OpenAPI 负责业务契约与服务端校验，明确能操作什么、需要什么参数、允许操作哪些资源。
2. vimocli 负责命令语义和请求执行，统一处理身份、站点、业务线、PPE、输出及错误提示。
3. Skill 负责向 Agent 描述任务入口、命令用法、风险和验证方式，实际操作仍调用 vimocli。

### 1.2 我的负责范围

我负责 OpenAPI 与 vimocli 方向的建设，重点投入包括素材业务能力接入、公共鉴权中间件、浏览器 JWT 工具、CLI 命令与运行时设计，以及使用文档、版本推广和用户问题处理。

本节重点展开四项工作：

1. 将素材管理和素材供给相关操作接入 OpenAPI 与 vimocli。
2. 建设公共鉴权能力，并为素材 OpenAPI 增加独立的资源权限。
3. 封装浏览器 JWT 获取与刷新逻辑，支持接口自测和 Agent 复用登录态。
4. 完善 CLI 的业务命令、多站点请求、结构化输出、Skill 组织和更新机制。

责任口径：保留方向 Owner 的表述。BAM、ByteCloud、既有权限平台等作为依赖；团队早期 CLI/codegen 基础和协作者接入的业务能力，不归为个人独立实现。

## 3. 架构体系与工程设计

### 3.1 整体架构与职责

开放能力包含接口发布链和运行时调用链，两者分别说明。

接口发布链：

```text
素材领域能力 -> OpenAPI 契约 -> IDL/BAM -> 组件网关配置
                                    |
                                    v
                            vimocli API 生成与命令承接
```

运行时调用链：

```text
用户 / 脚本 / Agent
    -> vimocli 业务命令
    -> 身份与站点上下文
    -> 网关 OpenAPI / 已接入的个人 JWT 直连接口
    -> 对应服务端鉴权
    -> 素材领域服务与下游能力
```

上面是理解链路的文字草图，尚未确定正式图的布局。素材 OpenAPI 走其网关与资源权限链路，不把其他模块的直连能力概括为素材已经支持的路径。

主要职责：

1. 领域服务维护素材业务规则，OpenAPI 封装适合程序调用的入参和结果。
2. IDL/BAM 与组件网关承接类型契约、接口发布和路由。
3. 服务端鉴权识别可信身份，执行接口权限和必要的资源权限。
4. vimocli 提供业务命令及统一请求上下文，处理输出和可恢复错误。
5. Skill 说明如何选命令、组织参数、确认写操作和验证结果。

设计考虑：调用方声明业务目标，平台内部维护协议细节。例如面板发布由调用方提供素材 ID 或分类 ID，服务端负责解析相关 diff；CLI 不要求运营理解内部 diffId、md5 等实现。

### 3.2 鉴权中间件：统一身份，分别处理授权

公共中间件先验证 JWT 签名，再按 issuer 区分用户身份与网关身份。身份注入发生在后续业务授权之前，避免各子应用自行解析和建立用户身份。

| 请求路径 | 身份处理 | 后续授权 |
|---|---|---|
| 已接入的普通接口，携带用户 JWT | 公共中间件验签并注入用户身份 | 继续执行原 Kani 权限 |
| 网关 OpenAPI | 服务端验证网关身份 JWT | 执行数据库接口权限；素材写操作继续校验资源权限 |
| 普通浏览器接口，无 JWT | 沿用 CAS/会话 | 继续执行原业务权限 |

客户端与服务端视角需要分开：

1. 调用方可以携带个人凭证或服务账号凭证进入网关。
2. 服务端识别的是经过验签与 issuer 分类的身份，不能只看到 `x-jwt-token` 就判定授权方式。
3. 用户 JWT 直连复用的是用户的网页业务权限，不自动获得素材 OpenAPI 资源授权。
4. JWT 无效时明确失败，不回退到浏览器会话，避免请求中途改变调用主体。
5. 素材历史 HMAC 通道仍属于独立兼容路径，不混入上述 JWT 分类。

工程取舍：

1. 验签、身份归一和注入集中到公共包，子应用配置自身需要的 issuer、路径和授权信息。
2. 普通接口保留 Kani，减少逐接口重复建设身份接入逻辑。
3. 正式 OpenAPI 路径配置用于识别接口契约，不用于猜测 JWT 类型。
4. 国内外分别配置可信站点和密钥来源；同名 issuer 不代表不同站点凭证可以互换。

### 3.3 浏览器 JWT 工具：复用已有登录态

OpenAPI 测试页和 Agent 都需要从浏览器已有登录态获得可供程序调用的 JWT。两处独立实现会重复维护站点判断、过期处理和登录恢复。

我将共性逻辑抽取到 `@vimo/utils/browser`，集中处理：

1. 根据业务线及页面环境选择国内或海外 ByteCloud 站点。
2. 由浏览器携带现有 Cookie 请求 ByteCloud 签发接口，从响应头读取 JWT。
3. 按站点进行内存缓存，在到期前预留刷新时间。
4. JWT 请求收到 401 时刷新，并限制为一次重试。
5. 登录态失效时提供重新登录入口，限制回跳地址范围。

复用场景：

1. OpenAPI 测试页：已有登录态下发起真实接口请求，无需手工复制凭证。
2. 素材 Agent：为后续 CLI 执行提供用户凭证，减少重复登录。
3. main 服务 AiChatV2：复用公共获取逻辑，再处理自身的登录跳转与请求传递。

该抽取在 2026-07-22 的 MR !2809 中可核对。main 的后续引用也已确认，适合说明公共能力的实际复用。

安全边界：这里复用登录态，不自行签发 JWT。浏览器读取 `exp` 只用于缓存，不能代替服务端验签；“免登录”限定为已有有效登录态下免重复登录。

### 3.4 素材细粒度权限为什么独立维护

新增发布接口后，接口调用权不足以描述操作范围。同一个发布接口可以覆盖多个面板；素材修改接口也可以接收不同类型的素材。

我在素材 OpenAPI 中增加资源权限，保留既有网页权限的使用方式：

| 权限层次 | 控制范围 |
|---|---|
| 接口权限 | 指定业务线下，能否访问某个 path 和 HTTP operation |
| 面板权限 | 能否对指定 `sceneKey` 执行新增、修改或发布 |
| 素材权限 | 能否对指定 `itemType` 执行新增、修改或发布 |

独立维护的考虑：

1. 自动化任务需要明确的授权范围，不能仅凭一个接口权限操作其覆盖的全部资源。
2. 新增、修改和发布分别授权。能够编辑配置，不自动代表能够将配置正式发布。
3. 个人用户和服务账号可以使用同一套 OpenAPI 权限模型，分别申请所需接口及资源权限。
4. 保留原网页权限，避免为开放能力接入直接改变既有用户的操作范围。
5. 将其他模块的个人 JWT 直连方式直接用于素材，会失去当前 OpenAPI 资源权限的约束。直连与网关的选择需要结合授权目标。

资源权限放在业务侧执行：

1. 素材发布先回查素材实体，确认存在、业务线一致，并取得真实 `item_type`。
2. 再校验请求涉及的各素材类型发布权限，不仅依赖调用方声明的类型。
3. 面板操作按照实际目标 `sceneKey` 检查权限。
4. 校验失败返回 403，并给出缺失的资源、操作及申请入口。

粒度选择：目前按面板、素材类型和操作授权，能够覆盖这轮资源管控目标；未实现逐 RID 授权。是否进一步细化，需要结合实际隔离需求和权限维护成本。

接受的代价：网页权限与 OpenAPI 权限需要分别解释和维护。通过统一申请页、批量申请和定向错误链接降低用户排查成本。

### 3.5 权限申请与风险分级

新增约束同时需要配套申请入口，避免用户只能将 403 转交研发处理。

现有能力包括接口、面板、素材类型权限申请，以及个人与服务账号授权对象。申请通过飞书审批关联目标权限，回调后写入用户权限列表，并发送结果通知。

风险策略：

1. P2 个人账号权限支持自动开通。
2. P2 服务账号仍需要审批，P1/P0 权限也需要审批。
3. 批量申请按最高风险等级处理。
4. 审批回调按实例关联申请上下文，避免重复处理导致重复写入。

该部分可以解释便利性与风险之间的取舍：低风险个人调用减少等待；服务账号及高风险操作保留明确审批，不将所有能力都设为自动放行。

### 3.6 vimocli 架构与工程设计

#### 业务命令与生成代码分工

从 BAM/IDL 生成类型化 API 与 hidden 命令，手写语义命令面向素材任务。生成代码跟随契约变化，语义命令负责参数组织和用户体验，避免重新生成时覆盖人工维护的业务逻辑。

例如，用户面对的是素材查询、分类调整、按素材 ID 发布等动作。底层接口名、字段转换和服务调用细节留在 API 与适配层。

#### 站点、路由和身份集中声明

`OperationSpec` 按操作声明站点、服务、路径、鉴权模式及请求/响应转换。公共执行器补齐身份、PPE 和请求头，命令层不自行拼装国内外域名。

路由与授权模式采用明确配对：

1. `gateway` 对应 `gateway_db`。
2. `direct` 对应 `direct_kani`。
3. 未声明支持的站点直接报错，不自动转向其他站点。
4. 普通接口直连使用个人身份，不因本地存在活动服务账号而切换授权主体。

这样可以隔离站点差异，也能区分两类 403：OpenAPI 权限问题与普通业务 Kani 权限问题使用各自的排查入口。

#### 人、脚本和 Agent 的输出需求

1. 人工使用提供可读结果、错误提示和权限申请入口。
2. 脚本使用原始 JSON 与退出码判断执行结果。
3. Agent 使用结构化结果、错误信息和后续操作提示。
4. 素材等 64 位 ID 按字符串处理，避免数值转换造成精度损失。
5. 调试信息保留请求定位所需字段，对 JWT 和服务账号凭证脱敏。

写操作的说明需要包含验证方式，接口返回与业务结果分开判断。相关命令有写后回读时说明具体行为，不将其概括为所有命令均有统一事务或自动回滚能力。

#### Skill 组织与版本更新

将多个顶层 Skill 收敛为统一入口和分域说明。入口负责任务分流，素材、面板、实验、运维等内容按需读取，认证与公共选项集中维护。

Skill 保存用法与约束，CLI 承接实际鉴权、路由和执行。能力变化需要同时检查命令、npm 包和 Skill 描述是否一致。

CLI 自动更新、Skill 合并已有版本宣告证据。自动发布流水线目前只确认到开发与演练材料，暂不写成正式上线成果，也不写成版本一致性问题已经全部解决。

#### 本节行文方向

参考 onenet-cli 样本介绍职责分层、公共能力、命令契约和实际场景的组织方法。技术机制依据 vimocli 的实际代码选择，不照搬样本的分层名称和实现。
