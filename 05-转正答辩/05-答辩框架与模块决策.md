> 当前阶段工作台。这里记录结构候选、取舍和最终决定。项目事实查 `03`、`04`和`10-项目研究底稿`。在决策完成前，不在本文件生成整篇正文。

最近更新：`2026-09-03`

## 一、已经确认的结构原则

以下结论不再重复讨论：

1. 开头需要介绍 VIMO 的业务、用户、核心对象和个人负责范围。
2. 业务介绍和个人工作放在同一张图或同一组内容中，避免两段孤立背景。
3. 素材业务是主体，商业化快速展示。
4. 工作产出先建立覆盖面，重点项目再按证据密度展开。
5. 当前四个强候选为 TTP、自动链路、OpenAPI/vimocli、全球素材搬运重构。
6. `publish_task`属于自动分发和正式发布链路。
7. 全球素材搬运按存量链路重构展开。
8. OpenAPI/vimocli 投入较大，允许承载多个关键决策。
9. AI Native 的位置仍待决定，不预设独立大章节。
10. 故事主线要从材料中长出来，当前不先写抽象的能力总主题。

## 三、三套整体架构候选

### 方案 A｜业务全景 + 四个项目平铺

```text
1. 自我介绍与 VIMO 全景
2. TTP 预发与合规发布
3. 自动分发与正式发布
4. OpenAPI 与 vimocli
5. 全球素材搬运重构
6. 其他产出与 AI Native
7. 成长、不足和规划
```

优点：

1. 四个项目边界清楚。
2. 每项都有独立故事空间。
3. 证据和 Q&A 容易管理。

风险：

1. 项目感较重，容易像四份独立汇报。
2. 相邻项目的 Draft、发布、任务恢复会重复。
3. 时间不足时，每项都可能讲浅。

适用条件：正式讲述时间较长，四个项目都需要被完整评估。

### 方案 B｜一个素材业务大章，内部嵌入重点项目

```text
1. 自我介绍
2. VIMO 素材业务与我的工作
   2.1 业务全景、责任区和全部产出
   2.2 合规发布：TTP
   2.3 自动执行：自动分发与 publish_task
   2.4 开放调用：OpenAPI 与 vimocli
   2.5 跨业务复用：全球素材搬运重构
3. 商业化和其他交付
4. AI 工作方式
5. 成长、不足和规划
```

优点：

1. 接近优秀样本的做法，业务和工作自然放在一大块中。
2. 四个项目在同一张业务图上有位置，过渡成本低。
3. 可以按模块自由调整篇幅，不必形式上等长。

风险：

1. 素材大章可能过长。
2. 如果每个小节仍套完整模板，整体会显得臃肿。
3. AI Native 和 OpenAPI/vimocli 的关系需要处理清楚。

适用条件：需要先建立业务理解，再在同一方向里详略展开。当前材料与该方案匹配度最高。

### 方案 C｜按能力问题组织，项目作为证据

```text
1. VIMO 业务全景与个人责任区
2. 复杂链路的正确性与可恢复执行
   - TTP
   - 自动链路
   - 全球搬运
3. 后台能力的标准化与开放复用
   - OpenAPI
   - vimocli
   - Skill／Agent
4. 其他业务交付
5. 成长、不足和规划
```

优点：

1. 个人能力判断集中。
2. 项目之间能形成联系。
3. 有利于减少重复链路介绍。

风险：

1. 过早抽象会削弱真实业务主语。
2. TTP、自动链路和搬运的成熟度不同，硬放一章可能混淆。
3. 容易写出模型化的能力主线。

适用条件：讲述时长很短，并且能用少量内容准确保留每个项目的业务上下文。

## 四、当前领先方案

当前建议优先讨论 `方案 B`，再吸收 `方案 C` 的局部组织方式。

建议形态：

```text
总：VIMO 业务、个人责任区、全部产出
分：在素材业务大章内展开若干重点项目
收：其他产出、AI 工作方式、成长与下一步
```

选择理由：

1. 用户希望第一部分先让评委知道自己负责哪些业务。
2. R0 已经能把四个候选放进同一张业务图。
3. 四项候选贡献的判断不同，暂时无需强行压成两条能力线。
4. 商业化和小项可以在大章前部建立覆盖感，后面不再逐项解释。
5. 该结构最容易参考 S1 的优点，同时保留 VIMO 的真实业务逻辑。

这里仍是建议，尚未定案。需要结合讲述时长和页面预算决定四个候选的最终深度。

## 五、第一部分的三种组合

### 组合 1｜业务图 + 责任区 + 产出表

```text
VIMO 一句话说明
→ 用户和核心对象
→ 素材端到端业务图，标出我的责任区
→ 全部工作产出表
→ 重点项目热区
```

信息最完整，可能需要两至三页。

### 组合 2｜一张总图承载业务和工作

```text
左侧：素材接入、分类、面板、Draft、发布、端上
上方：OpenAPI／vimocli／Agent 入口
下方：全球搬运分支
图中高亮：TTP、自动链路、开放能力、搬运
图旁：商业化和其他产出数字卡
```

接近用户认可的样本做法。视觉设计难度较高，适合内容定案后制作。

### 组合 3｜业务全景 + 项目地图

第一页讲用户、对象和主链；第二页只讲个人项目、结果和后续重点。

优点是阅读清楚，缺点是业务和工作需要跨页对照。

当前倾向：`组合 2`作为目标，`组合 1`作为内容草图。若一张图过密，退回组合 1。

## 六、主 Case 数量与深度候选

### 配置 A｜四个都展开

| Case | 建议深度 | 主要承担的判断 |
|---|---|---|
| TTP | 中 | 合规、状态、事务、真实环境收口 |
| 自动链路 | 中到深 | 端到端执行、粒度、性能和恢复 |
| OpenAPI/vimocli | 深 | 权限、身份、contract、CLI 设计和复用 |
| 全球搬运 | 中 | 存量重构、跨系统长任务和阶段验证 |

适合材料篇幅充足。四项不等长。

### 配置 B｜三个主 Case + 一个阶段项目

```text
主 Case：TTP、自动链路、OpenAPI/vimocli
阶段项目：全球搬运重构
```

全球搬运保留问题、两个关键判断、共同 Owner 和阶段验证。适合时间中等。

### 配置 C｜两个深 Case + 两个中型 Case

```text
深 Case：自动链路、OpenAPI/vimocli
中型 Case：TTP、全球搬运
```

适合讲述时间较短。TTP 重点保留合规和 Diff，搬运重点保留重构边界和阶段状态。

当前不建议只讲两个项目。这样会削弱业务覆盖，也浪费 TTP 和全球搬运已有的强判断。

## 七、AI Native 的三个位置

### 位置 A｜独立一页

主例使用 Coco：模型提出 Patch，代码限定范围，人工 Apply。vimocli 和 Agent 作为补充。

适合：需要明确证明 AI Native，且页面预算允许。

### 位置 B｜融入 OpenAPI/vimocli

在 CLI、Skill 和 Agent 的承接关系里说明：Skill 保存业务方法，CLI 固定 contract，Agent 负责意图理解。

适合：避免新增章节；但 Coco 会缺少展示位置。

### 位置 C｜混合结构

1. OpenAPI/vimocli Case 中讲 Skill 与 Agent 的确定性执行边界。
2. 成长或工作方式部分用半页讲 Coco。

当前倾向：`位置 C`。它既能保留 Coco 的独立判断，又不会把成熟度不同的 AI 场景拼成大项目。
