# R2｜自动分发与正式发布

> 来源任务：[转正答辩 R2｜自动分发与 publish_task](codex://threads/01a05697-218e-77f1-ac4c-4b8357c43758)
>
> 最近核验：`2026-09-03`

## 1. 当前事实摘要

1. 自动链路接收素材或分类事件，计算目标分类和面板变化，更新 Draft，随后创建 `publish_task`并发布正式版本。
2. `distribute_record`在本轮前已经存在。7～8 月的重点是统一动态分类、分类同步、Draft 更新和正式发布的执行与恢复边界。
3. 用户是项目 Owner，直接负责 `publish_task`设计与落地、四类任务统计、批量 Plan、主库读取、无变化跳过，并参与消费性能分支的分析和收口。
4. `publish_task`属于自动执行链路，不能拆成孤立项目。
5. SG PPE 一批 50 条任务展开为 976 action、143 分类、16 面板，执行结果为 50 成功、0 失败。
6. 同批任务记录从 1188 秒降到约 12～24 秒；11.856 秒、24 秒和 8.95 秒的计时范围还未统一。

## 2. 业务、用户和真实链路

### 用户与触发

1. 素材运营修改素材状态、选择分类或面板配置。
2. 事件消费者接收素材和面板发布事件。
3. 系统计算素材应该进入或退出哪些分类，更新目标 Draft。
4. `publish_task`负责将真实 Draft 变化发布为正式版本。

### 原链路

```text
事件
→ FaaS 内部解析和部分业务计算
→ distribute_record
→ 逐任务、逐 action 读取规则和面板
→ 多次 Draft 事务
→ 扫描候选面板
→ 直接正式发布
```

主要问题：

1. Draft 更新失败和正式发布失败混在一起。
2. 同一分类和面板被重复加载、解析和写入。
3. 请求返回 502 时，后台可能仍在继续执行，前台结果与真实任务状态不一致。
4. 多实例抢占、Processing 超时、积压和失败缺少统一运行边界。

### 当前主链

```text
素材／分类事件
→ FaaS 只解析事件并调用服务端
→ Planner 计算普通分发或分类同步 Plan
→ distribute_record
→ CAS 抢占任务
→ 整批加载素材、规则、面板、分类和相似分类
→ 任务级展开 action
→ 分类级保序归并
→ 面板级事务和受控并发
   ├─ Draft
   ├─ 索引和操作记录
   ├─ distribute_record.result
   └─ publish_task
→ publishTask Timer
→ Pending／超时 Processing 扫描
→ CAS + 租约 + claimAt
→ 同面板任务聚合
→ PublishService
→ Published／Pending 重试／Failed
```

### 兼容边界

1. 新 `distribute_record`由新 task/consume 消费。
2. 历史 `upload_info_list`仍有旧入口。
3. 新正式发布使用 `publish_task` Timer。
4. 旧 `distributePublishNotify`代码仍保留，实际线上启停待确认。

## 4. 已确认的技术判断

### 4.1 按失败语义拆出 `publish_task`

问题：Draft 更新和正式发布的失败对象、重试成本和恢复方式不同。正式发布失败时重复修改 Draft 可能造成错误和额外成本。

选择：使用面板维度的 Pending 发布任务。

```text
publish_task
├─ Pending / Processing / Published / Failed
├─ 同面板 Pending 范围合并
├─ CAS 抢占
├─ 10 分钟租约
├─ claimAt 防旧消费者覆盖
├─ 空 Diff 视为成功 no-op
└─ 失败最多 3 次
```

普通分发和分类同步的事务边界不同：

| 链路 | 当前边界 | 恢复依据 |
|---|---|---|
| 普通分发 | Draft、索引、操作记录和 `publish_task`在同一面板事务 | 发布意图与 Draft 同时提交 |
| 分类同步 | 事务内保存 Draft、操作记录和 `distribute_record.result`；事务后建 `publish_task` | result 可以证明 Plan 已应用，重试时只补建单 |

边界：

1. CAS 解决已有任务的抢占，不能保证同面板 Pending 行的并发创建唯一。
2. 当前没有数据库 Pending 唯一索引。
3. 精确发布范围与 Failed 人工回放仍有未合入设计。

### 4.2 任务、分类、面板使用不同粒度

真实规模：

```text
50 条任务
→ 976 action
→ 143 分类
→ 16 面板
```

选择：

1. 任务粒度保存状态、重试、结果和失败映射。
2. 分类粒度保序归并 add/remove，计算最终素材列表。
3. 面板粒度控制事务、固定锁序、失败隔离和正式发布。
4. 公共数据整批加载，不同面板并发限制为 4。
5. 每面板只登记一次 `publish_task`。

边界：

1. 新增操作采用 prepend，同分类 action 必须保留原始顺序。
2. 单面板失败只回滚该面板，再映射回原任务。
3. 单批性能数据不能外推到所有业务线和线上 P95。

### 4.3 用运行边界收口自动链路

| 问题 | 当前处理 |
|---|---|
| bulkCreate 后从库短暂不可见 | `useMaster: true` |
| 分类集合没有变化 | 入口返回 `ignored/no_changes` |
| 多实例抢占 | 查询候选后逐任务 CAS |
| `distribute_record` Processing 超时 | 3 小时租约恢复 |
| `publish_task` Processing 超时 | 10 分钟租约恢复 |
| 任务失败 | 最多三次，耗尽后进入 Failed |
| 积压和诊断 | 四类统计、阈值 500、飞书告警和失败原因 |

边界：

1. 方案中的 `SKIP LOCKED`没有进入当前主干。
2. 通知失败只记录日志，不修改发布状态。
3. Failed 回放仍依赖未合入 MR 2881。
