### 1.2 样本提供的组织选项

样本没有统一的第二章模板，至少存在以下方式：

1. 先给业务全景和个人工作定位，再展开核心建设。
2. 整体背景保持简短，把必要业务介绍放进每个主 Case。
3. 先按业务方向列代表交付，再在重点方向中解释上下游。
4. 用平台能力、业务应用和技术沉淀建立工作总览。

这些方式可以按内容需要组合。先确认业务、职责和交付的关系，再选择图、表或段落，不预设 VIMO 必须使用一张总图。

## 二、S1 的高评价信号

### 2.1 业务与工作放在同一张图里

样本没有先讲一大段抽象业务背景。业务方向、产品模块和个人工作区域在同一章节出现，评委能快速理解：

```text
这个业务在做什么
→ 作者负责哪一块
→ 做过哪些工作
→ 后面为什么展开这些重点
```

可复用原则：业务总览应同时说明相关业务、个人责任区和代表交付。全量工作索引可另作补充；当前答辩中业务总览属于第二模块。

### 2.2 先建立覆盖面，再分配重点

样本会列出完整工作范围，但没有平均展开。重点项目占主要篇幅，其他需求承担业务覆盖和交付密度。

对当前答辩的启发：商业化、小型素材能力和日常修复进入产出总览；重点 Case 根据判断密度决定篇幅。

### 2.3 技术内容有系统边界

较强的项目会说明分层、职责和模块关系，评委可以继续追问每层处理什么变化来源。

对当前答辩的启发：VIMO 的技术图需要突出真实对象和边界，如 Draft、Pre、Prod、`distribute_record`、`publish_task`、OpenAPI、Workflow，少画组件堆栈。

### 2.4 结果按类型拆开

样本会区分需求交付、质量和体验等结果，不用一个“整体提升”覆盖所有数据。

可复用原则：不同项目采用与其目标对应的结果，区分效率、质量、覆盖、采用情况和阶段验证。具体选哪些结果由事实和项目内容决定。

### 2.5 V1 到终版出现了明显收敛

稳定变化包括：

1. 工作范围更容易被快速理解。
2. 主项目更突出，次要信息被压缩。
3. 结果更靠近对应的方案。
4. 页面结构更统一。
5. 重复背景和解释减少。

这说明第一版无需追求每句话完美，但需要先锁定章节职责和证据位置。

## 三、S2 的补充信号

### 3.1 主 Case 自带所需业务背景

每个项目先说明用户问题和研发复杂度，再进入技术工作与收益。整体业务介绍可以保持简短。

可复用原则：业务总览建立必要的共同背景，各重点项目只补充理解本项目需要的信息。图不是强制形式。

### 3.2 复杂度由事实证明

样本使用代码体量、依赖关系、数据拉取方式和模块耦合说明复杂度。它没有依赖“复杂场景”“系统性难题”等判断词。

可复用原则：任务规模、展开后的操作量、涉及对象和依赖关系，比“链路复杂、性能压力大”更有解释力。当前项目的具体数字只在研究底稿维护。

### 3.3 技术机制附近直接放结果

方案和改造前后数据在同一个内容块中出现，读者不需要翻到章节结尾寻找收益。

可复用原则：性能机制旁放同口径前后数据，权限机制旁放对应身份和操作的验证结果，避免把数字集中堆在最后。

### 3.4 指标定义先出现

样本先解释页面展示成功率、耗时和支付成功率怎样计算，再展示变化。

可复用原则：人数说明身份去重方式，调用量说明事件口径，成功率说明分母，耗时说明起止点、环境和样本。

### 3.5 如实保留变差或受限结果

样本保留了变差的性能指标并解释原因。这比只展示正向结果更可信。

可复用原则：负向指标、阶段验证和受限路径直接说明，不用其他成功结果遮盖。本文件不保存当前项目的实时交付状态。

## 四、样本交叉观察后的可复用规律

这些是基于内容的研究判断，不是组织正式评分标准，也不能据此推断样本的实际评价。

### 4.1 自我介绍与业务总览的职责

自我介绍交代个人基本信息；业务总览回答：

1. 负责哪个业务方向。
2. 相关系统服务谁，管理哪些核心对象。
3. 我的工作落在链路哪些位置。
4. 交付了哪些代表工作，哪些在重点章节展开。

业务总览不承担完整技术介绍，也不提前总结一条宏大的成长路线。业务说明和个人工作尽量按相同分组组织，减少重复。

### 4.2 重点项目的职责

每个主 Case 应让读者理解以下信息，排列顺序和展开方式按项目确定，不是固定小标题：

```text
业务问题
→ 原链路或触发现象
→ 我的判断和方案
→ 真实落地机制
→ 结果与证据
→ 当前边界
```

可以有多个关键决策。数量依据项目投入和内容密度确定。

### 4.3 结果的职责

结果负责证明方案改变了什么。最有效的结果通常有四种：

1. 改造前后变化。
2. 真实规模或覆盖。
3. 可验证的风险消除。
4. 清楚标记成熟度的阶段结果。

代码量、Commit 数和文档数只能补充工作量，不能充当项目价值。

### 4.4 Ownership 的职责

有效写法会让评委看到具体动作：发现、定义、选择、推动、实现和收口。样本中的“主要负责”通常紧跟业务模块和结果。

当前材料可以直接说明用户是重点项目 Owner。协作者和团队基座仍要出现，用于解释系统边界和协作难度。

### 4.5 成长部分的职责

成长部分归纳认识和工作方式的变化，可以从以下问题选择：

1. 以前容易在哪里失误。
2. 哪次项目迫使自己改变方法。
3. 现在会提前做什么。
4. 下一阶段怎样验证这项改变。

具体项目在前文已有证据时，结尾不必再讲一次技术经过。不要要求每个总结点都绑定一个相同的案例。

## 五、比 S1 做得更好的具体目标

用户将 S1 设为质量基线。以下是努力方向，不代表对方存在对应缺陷，也不预先断言本材料能够获得更高评价：

| 项目 | S1 已经做到 | 当前答辩的增强目标 |
|---|---|---|
| 总体定位 | 业务和工作范围清楚 | 让实际责任、交付与判断自然可见，不提前写死能力口号 |
| 业务总览 | 产品模块完整 | 相关业务与个人工作对应，范围适度、详略清楚；图表形式后定 |
| 技术思考 | 有架构和治理内容 | 每个重点判断补触发现象、备选方案和失败边界 |
| 结果 | 有交付和量化信息 | 所有数字写明环境、窗口、样本和限制 |
| Ownership | 有主要负责范围 | 区分发现、决策、推动、实现和协作边界 |
| AI Native | 主要体现 AI 研发产出 | 明确模型、确定性工具和人工分别负责什么 |
| 不足与规划 | 有成长总结 | 使用真实行为变化和可验证动作 |
| 视觉 | 信息丰富 | 图表各有明确用途，总览和技术细节分开；实际呈现阶段再验证可读性 |

## 六、可以直接复用的结构 Case

### Case 1｜一句话交代工作范围

既有笔记中的 S1 表达示例（本轮未逐字复核，不作为原文引文）：

> 在 OTN 方向，我主要围绕 BONE 统一管控、故障与告警、资源与光层工具、网络规划与建设流程四条主线参与前端建设。

可学之处：直接说业务方向、真实模块和个人范围，后面马上接全景图。

### Case 2｜具体描述技术问题

既有笔记中的技术表达示例（本轮未逐字复核来源，不作为原文引文）：

> 部分存量代码在模块顶层、静态 schema、columns、route meta 等非响应式位置提前执行 `t()`，导致用户切换语言页面部分位置语言未生效。

可学之处：代码位置、触发动作和用户现象同时出现。

### Case 3｜用真实分层说明职责

本项目的表达示例，非外部答辩原文：

> 项目采用 Command → Handler → Service → API → HTTP 的单向分层。每层只处理一种变化来源，避免命令声明、业务编排和请求细节再次混杂。

可学之处：先给分层，再解释它解决的冲突。

### Case 4｜先定义指标

样本会先定义统计起止点，再展示 P90 或成功率。当前答辩应对每个数字采用同样规则。

### Case 5｜结果出现负向变化

样本保留旧值、新值、变化和归因。当前答辩遇到边界和未完成项时也应直接写清状态。

### Case 6｜具体说明不足

既有笔记中的不足表达示例（本轮未逐字复核来源，不作为原文引文）：

> 目前在数据量化上仍有不足，做完一件事往往只能凭感觉判断收益，缺少具体指标佐证。未来需在做事前预设量化指标，并熟练使用公司内的数据量化平台。

可学之处：不足对应日常行为，改进动作可以执行。

## 七、不采纳的做法

1. 按样本的业务模块数量复制章节。
2. 用代码行数、AI 贡献率或需求数量作为最高价值结果。
3. 每个项目统一套“背景—难点—方案—收益”长模板。
4. 为了显得完整而保留所有产品截图。
5. 画节点很多但没有阅读顺序的全景图。
6. 使用样本的标题、句式或自我评价。
7. 把对方的最终版当成当前第一版的页面上限。

## 八、稳定生产合同

正式架构和正文至少满足：

1. 业务总览说明相关业务、个人职责和代表交付，不要求展示所有任务；当前对应第二模块。
2. 主 Case 依据证据密度决定数量和篇幅。
3. 每个主 Case 至少有一条完整决策链。
4. 方案与结果尽量出现在相邻位置。
5. 每个数字旁都能看到口径或限定词。
6. 当 AI 进入重点产出时，说明具体使用、工具与人工分工及结果；不要求每一章都出现 AI。
7. 成长来自项目复盘，不写空泛能力词。
8. 正文负责讲判断，附录负责承接证据和完整链路。

局部内容明确后可以直接写局部草案，不以“全部样本研究完美”为正文前置条件。后续只围绕明确问题补查；新增样本记录不自动修改当前目录。

## 九、2026-09-09 新增五篇样本的具体记录

本节是对原材料的转述和分析。表头、技术名和图中标签用于定位，其他表述不作为逐字引文。

### 9.1 S3｜戴乐：连续项目、方案取舍和具体复盘

#### 整体逻辑

```text
个人履历 → 实习目标
→ 工作成果：业务概述、里程碑、工作概要
→ 商家任务新模型迁移 → 商家任务配置平台
→ 材料汇总 → 总结与规划
```

两个重点项目有真实承接：先迁移任务模型，再建设基于模型的配置平台。项目关系由模型与平台依赖说明，减少了另造“成长主线”的需要。

#### 内容上值得保留的做法

1. 职责写到具体项目和范围：直播任务迁移主要负责、开业任务部分负责；平台部分列产品设计、项目 POC 和后端开发职责。同一作者在不同项目中的角色不必相同。
2. 工作概要使用“重点事项｜目标&思路｜节奏｜阶段结果”，先让读者知道做什么、做到哪里。完整材料索引放在后部，不挤占重点解释。
3. 请求级缓存选型说明生命周期差异：全局缓存方案需要额外管理生命周期，当前需求集中在单次请求的数据复用，因此选择请求范围的容器和 Provider，并处理并发重复查询。值得学的是需求、候选、选择依据的关系。
4. 草稿存储比较不同方案对审批、历史记录和同版本修改的支持，选中方案仍承认实现成本更高。技术思考不依赖复杂术语数量。
5. 复盘写具体失误，包括顺手优化扩大测试影响面、兼容疏漏影响商家进组，再讨论需求边界和上线检查。
6. AI 使用出现在产品调研、交互原型比较和设计选择中，能看到应用环节；不单凭“用了 AI”证明能力。

#### 格式、画板与表格

1. 业务关系画板只保留平台、商家、顾客三个主体，连线标注触达、任务、反馈等关系。适合解释系统服务什么协作，而不是展示全部系统组件。
2. 里程碑同时记录时间、代表交付和职责变化。时间线有信息价值的前提是项目确有先后承接；不应将所有需求日期搬入正文。

### 9.5 S7｜甄诚：平台能力与业务采用相互对应

#### 整体逻辑

```text
个人介绍 → 工作总览
→ easy_agent 框架开发
→ 自建应用与业务方接入
→ 重点问题排查 → 知识沉淀

```

工作总览是一张思维导图，三个一级分支为 `golang agent sdk (easy_agent)`、`业务Agent`、`技术沉淀`。后文按这几类内容展开，平台、应用和推广材料有明确归属。

#### 内容上值得保留的做法

1. 平台能力与实际需求相互对应：业务方的存储、流式调用、上下文、飞书接入等要求，能回连到 SDK 补充的具体能力。
2. 区分“我的 Agent”“协助业务方”和“其他业务方反馈”。平台作者提供了什么、应用团队实现了什么，比笼统说“支撑多个业务”更清楚。
3. SDK 概念先定义 Runner、Agent、Tool、Event、Service、Session 的职责，再解释事件、记忆和接入机制。对于平台型工作，先建立少量核心概念有助于理解设计。
4. 飞书多轮对话从会话边界问题出发：私聊与群聊怎样隔离上下文，再说明卡片、用户与 Session 的关系。技术点与具体使用冲突相连。
5. 应用成果附近提供实际入口、使用记录、业务反馈和状态，不将联调、内部测试与已上线统一包装。
6. 问题排查逐段定位大数精度在哪一跳丢失；知识库问题则比较不同检索参数下的结果，再说明内层候选量与外层返回量的区别。排障能证明跨系统判断，不只是“修复问题若干”。
7. 分场景评测表同时保留样本数、正确数和准确率，可看出分母大小。业务侧应用的评测结果不能全部归为框架作者的个人收益。
8. 总结承认自己更熟悉 AI 基建、对广告业务理解仍不足，下一步与职责发展相连；不强行宣称已掌握全部业务。

1. 总览图二级分支进一步区分开发文档、使用文档、SDK 能力与功能、前端方案、应用团队和知识文章。链接附在对应节点，可作为材料导航。

### 10.3 格式与页面组织的使用原则

1. 标题形成导航：章节名表示业务或工作主题，内部标题根据内容选择。需要区分现状、已实施和规划时直接写明；不复制样本的深层编号。
2. 段落解释关系与判断：用途、问题、选择理由适合短段落，简单字段和同维度比较适合表格。整页表格并不天然比段落清楚。
3. 图文靠近：图片、机制图、数据和对应解释放在邻近位置，避免读者来回寻找。已核验的是内容顺序，实际显示效果留到排版时检查。
4. 分栏用于并看：改造前后、方案候选、多端效果适合分栏；因果链较长的说明保持连续阅读。
5. 提示块只强调局部：S3、S5、S6 使用浅橙提示块，S7 多用浅蓝提示块。可借鉴“重点与正文有层次”，不复制固定色号、表情密度或每段一个卡片的做法。
6. 颜色必须有含义：责任、系统归属和变更差异分别定义，图例随图出现。不能只给节点上色后让读者猜。
7. 链接就近、索引集中：关键判断附近提供证据入口，完整资料放后部；读者不点链接也应读懂正文。
8. 演示只选必要场景：视频适合完整交互，截图适合前后状态；播放前应说明要观察的行为。本轮没有播放样本视频，不把“有视频”直接评价为演示成功。
9. 不预设字体和留白结论：尚未逐页视觉核验，当前不从 XML 推导最优字体、字号、页面数和显示比例。
10. 形式服从内容：节点太多时可以拆图，比较维度少时可以用一句话。样本图表库是备选材料，不是必须完成的制作清单。

## 十一、业务总览怎样连接个人工作

### 11.1 不同组织方式分别解决什么问题

| 组织方式 | 样本依据 | 适用情况 | 容易出现的问题 |
|---|---|---|---|
| 业务关系与个人范围一起介绍 | S1、S5 | 多项工作分布在一条业务链或现有产品中 | 全景过大，责任图变成架构百科 |
| 简短业务介绍后给产出总览 | S4 | 先需要统一少量业务概念，产出跨多个主题 | 背景、总表、项目章节三次重复 |
| 按业务方向归组需求 | S6 | 日常工作较多，需要将小项聚合 | 用大标题掩盖工作之间缺少联系 |
| 平台能力与使用情况分组 | S7 | 主要投入是公共能力或基础设施 | 只讲组件，读者仍不知道谁在用 |
| 按连续项目演进展开 | S3 | 前一个项目确实成为后一个项目的基础 | 倒推一条不存在的成长路线 |

### 11.2 对当前第二模块的内容建议

以下是待用户确认的组织建议，不替代 `05` 中的章节决策，也不指定最终图表。

1. 总体范围用用户已确认的职责限定：素材业务、VIMO 基础设施、OpenAPI/vimocli，以及少量商业化工作。无需介绍整个 VIMO 的全部产品。
2. 同一内容组同时说明业务用途、本人范围与代表交付。素材日常开发和素材重点改造先按业务位置放在一起，避免先介绍一遍业务、再列一遍所有工作。
3. 平台和开放能力说明与素材业务的调用关系，不强行接成素材发布后的下一步。底层公共能力、CLI 和具体业务接口的职责分别写清。
4. 小项依据同一业务对象或用途聚合；重点项目在相关组内说明工作内容，后文沿用相同名称。无需增加一段“下面展开重点”的口头转场。
5. 商业化工作保留真实覆盖范围，篇幅与当前讲述重点相称；不因样本有两条业务线就平分篇幅。
6. AI 工作有明确采用、调用或研发关系时放入相应内容组；尚未决定的 Agent、Skill、Coco 不为追求齐全强行全部出场。
7. 新增大产出先判断业务归属，再决定是否成为重点项目。业务总览可以补代表交付，不需要每增加一个项目就重建整篇目录。
