# 优秀答辩样本与评分信号

> 文档职责：保存优秀答辩样本、版本变化、可比性、评分信号、反例和采纳状态，为北极星模型、答辩骨架和模拟评审提供研究证据。
>
> 唯一回答的问题：真实高评价答辩做对了什么、仍有哪些上限、当前答辩至少做到什么，以及怎样形成更强的转正证据。
>
> 所属阶段：`D0-A 的首个校准输入`。正式的多样本研究和评分规则校准仍属于 `D1`。
>
> 当前版本：`v0.1｜首个 M+ / SP 样本基线`
>
> 当前状态：`已完成首个双版本样本分析，证据尚未饱和`。
>
> 最近更新：`2026-08-25`

## 一、文档边界

### 1.1 本文保存什么

1. 优秀答辩文档的来源、版本、背景和可比性。
2. 同一文档不同版本之间的结构和表达变化。
3. 样本能够释放的高分信号，以及这些信号的证据强弱。
4. 样本的内容上限、潜在追问风险和不应复制的部分。
5. 从多个样本中逐步归纳出的最低生产合同和超越标准。
6. 结论进入北极星模型、答辩骨架和项目研究任务书的采纳状态。

### 1.2 本文不保存什么

1. 不把样本作者的项目事实复制为当前答辩的项目事实。
2. 不把一份高评价文档直接视为组织官方评分标准。
3. 不根据页面好看、内容很长或技术名词多，直接判断得分原因。
4. 不在这里编译当前答辩的最终主线和正文。
5. 不为每个样本创建独立 Markdown；后续样本继续进入本文。

### 1.3 与其他文件的职责关系

| 文件 | 唯一职责 | 与本文的关系 |
|---|---|---|
| `00-阶段地图.md` | 记录当前阶段、门禁和下一步 | 只引用当前样本研究状态，不复制研究正文 |
| `01-答辩北极星与能力证据模型.md` | 定义答辩要促成什么判断、什么能力证据有效 | 只吸收被样本支持的稳定结论，并链接本文 |
| `02-优秀答辩样本与评分信号.md` | 保存样本证据、比较、评分信号和反例 | 是样本研究的唯一真相源 |
| 后续答辩骨架 | 根据评分目标生成当前内容结构 | 读取 `01` 的稳定模型和本文的评分证据 |

## 二、当前研究问题

本轮不是评价文档“写得好不好”，而是回答以下决策问题：

1. 一个获得较高评价的内部转正答辩，最低具备哪些内容和证据？
2. V1 到最终版的变化，反映了哪些可能有效的改稿方向？
3. 哪些内容证明真实贡献，哪些内容只能证明工作量？
4. 哪些章节体现了系统思考，哪些章节仍停留在项目介绍？
5. 样本如何表达业务、技术、Ownership、结果、成长和 AI 能力？
6. 当前答辩如果只做到同等水平，会在哪些维度缺少差异化？
7. 哪些结论可以进入北极星稳定模型，哪些仍需更多样本或主管口径验证？

## 四、样本可比性

### 4.1 可复用的组织语境

1. 同属公司内部工程团队语境，语言、协作方式、飞书文档形态和工程证据具有较高参考价值。
2. 样本同时包含业务交付、工程治理、平台建设和 AI/CLI 能力，与当前答辩的问题地图存在较多交集。
3. 样本提供 V1 和最终版，能够观察内容压缩、系统抽象和证据补强的真实变化。
4. 用户明确提供了 `M+ / SP` 评价结果，因此它比无结果的公开模板更适合作为当前基线样本。

### 4.2 不能直接类比的部分

1. 样本属于网络基础设施前端，当前项目的业务、岗位边界、主管和评委可能不同。
2. 样本实习周期、项目机会、上线阶段和数据成熟度不能默认与当前答辩一致。
3. 文档中团队公共能力、导师输入和作者个人 Ownership 的真实边界，只能依据作者表述判断，不能外推到当前项目。
4. `M+ / SP` 的具体定义、权重和评审规则仍未获得正式来源确认。
5. 样本的调用量、代码量和 AI 贡献率属于该项目的数据，不构成当前答辩必须达到的数字门槛。

### 4.3 当前使用方式

```text
可以复用：
内容完整度、证据形态、系统抽象方式、结果表达方式、页面生产下限

不能复制：
项目主线、能力结论、指标规模、Ownership、技术机制和个人成长故事
```

## 五、V1 到最终版的关键变化

### 5.1 总体变化

V1 更接近一份工程实现和项目材料汇总，最终版明显向以下方向收敛：

```text
实现细节和工作记录
→ 系统问题与产品全景
→ 架构机制与贡献方式
→ 真实使用场景和量化结果
```

最终版没有完全摆脱项目式组织，但已经显著降低了代码细节对主叙事的干扰。

### 5.2 分章节变化

| 维度 | V1 | 最终版 | 可以提取的改稿信号 |
|---|---|---|---|
| OTN | 主要说明个人定位、承接 40 个需求和完成情况 | 增加产品建设目标、功能关系全景、统一模型、多厂商管控、资源治理和运行观测 | 先让评委理解业务系统和个人位置，再展示需求数量 |
| Starling | 按四个子问题展开大量代码、正则、边缘 Case 和脚本实现 | 压缩为问题分类、治理目标、核心策略和最终收益 | 主文档保留问题、判断和机制，代码细节下沉到技术文档或 Q&A |
| CLI 背景 | 说明 Agent 推动 CLI 成为标准调用接口，列出旧版问题 | 增加 Claude Code、Codex CLI、Gemini CLI 等趋势参照和旧版用户反馈 | 外部趋势只有和真实内部问题、已有验证连接后才有价值 |
| CLI 架构 | 有项目定位、分层和基础架构 | 增加标准化贡献流程、Agent 友好契约、迁移兼容、能力全景和真实调用数据 | 平台项目需要同时说明架构、贡献机制、迁移策略和用户结果 |
| 使用结果 | CLI 使用数据章节基本为空，Starling 结果分散 | 增加四类使用场景、累计调用、覆盖用户、周活和地区分布 | 强项目必须有使用证据，不能停留在“能力已建设” |
| 视觉 | 已有表格、代码块和画板，但实现材料较重 | 增加产品全景、架构图、流程图、使用截图和结果图 | 图应承担系统理解和结果佐证，不应只展示界面存在 |
| 成长 | 大段解释 ROI、D/C 端差异、数据能力和 AI | 压缩为四条感悟与四项规划 | 压缩能改善阅读，但成长仍需从具体决策和二次迁移中证明 |

### 5.3 最值得复用的版本演进规律

1. 从“我实现了什么”上升到“系统为什么需要这项能力”。
2. 从“代码怎样写”上升到“现实约束、架构边界和贡献机制是什么”。
3. 从“完成了功能”补充到“谁在什么场景使用，产生了什么变化”。
4. 把大段实现下沉，把主文档空间留给问题、判断、机制和结果。
5. 使用图、反馈、数据和文档链接组成证据，而不是只依赖自我评价。

## 六、为什么它可以作为高分基线

以下是依据文档内容和用户提供结果形成的评分原因假设，不是已获得评委确认的事实。

### 6.1 真实产出密度高

样本提供了大量可以快速建立可信度的活动与交付证据：

1. 有效代码新增 `9w+`。
2. `692` 次提交、`103` 个合并 MR、`121` 个评审 MR。
3. OTN 累计承接 `40` 个需求，完成 `20` 个缺陷修复和 `8` 轮厂商体验优化。
4. Starling 响应式治理包含 `65` 个修复 MR。
5. CLI 覆盖多个网络业务模块、多个站点和多种交互入口。

这些数字主要证明作者真实投入和交付广度，不能单独证明业务价值，但能够降低“是否真的做过”的不确定性。

### 6.2 至少两个项目完成了系统级抽象

1. Starling 没有只写成国际化 Bug 修复，而是归纳成本地缓存可靠性、响应式正确性、Key 注释准确性和 Fallback 资源完整性四类治理问题。
2. CLI 没有只写成命令开发，而是解释了平台无关分层、标准贡献机制、Agent 契约、兼容迁移、发布和质量体系。
3. 两个项目都从功能层进入了机制、边界和长期演进层，能够释放工程判断和系统设计信号。

### 6.3 结果证据不只停留在需求完成

1. CLI 提供线路中断分析、常规查询、高维统计报告和元数据巡检等具体使用场景。
2. CLI 截至文档窗口累计约 `143 万次`调用、覆盖 `192` 名用户，并提供最近一周调用和周活数据。
3. Starling 提供缓存容量分布、治理 MR、问题集合变化、注释覆盖率、同步准确率和运行耗时。
4. 文档通过产品截图、聊天反馈、技术方案、使用指南和数据图形成多种证据。

这些内容使系统设计能够连接真实使用和阶段结果，是它高于普通项目总结的重要原因。

### 6.4 内容覆盖了转正答辩的基本面

1. 个人背景和负责范围。
2. 整体工作产出。
3. 业务项目和产品全景。
4. 技术治理和平台架构。
5. 量化结果和真实反馈。
6. 个人成长、不足和下一阶段规划。
7. Q&A 入口和证据链接。

即使部分章节仍有上限，它已经覆盖了评委判断“做了什么、技术如何、结果怎样、未来做什么”的基本信息。

## 七、样本各维度评估

本表中的“强、中、弱”仅表示本文内部比较，不是官方分数。

| 维度 | 样本表现 | 当前强度 | 主要证据 | 上限或风险 |
|---|---|---|---|---|
| 真实交付 | 工作量和项目覆盖充分 | 强 | 需求、代码、MR、缺陷、模块覆盖 | 活动量较多，个人归因和业务价值需要继续拆分 |
| 业务理解 | OTN 最终版补充产品全景和闭环 | 中强 | 产品目标、统一模型、资源与观测关系 | 更像产品功能全景，缺少关键业务冲突和个人判断形成过程 |
| 问题建模 | Starling 四类治理问题较清楚 | 强 | 问题分类、目标、策略和结果 | 为什么优先这些问题、怎样从信号形成分类没有完全展开 |
| 技术判断 | CLI 分层、Agent 契约、迁移策略较完整 | 强 | Command 到 HTTP 分层、四类 Agent 能力、兼容矩阵 | 候选方案、反对意见和选择标准仍可更具体 |
| Ownership | 负责范围和贡献较多 | 中 | 完全负责 OneNet 前端、多个治理和平台建设 | “参与建设”“负责”与具体决策、推动、协作边界没有统一证据链 |
| 结果与验证 | CLI 和 Starling 数据丰富 | 强 | 使用场景、调用量、覆盖用户、治理指标 | 部分指标分母、窗口、自动调用占比和因果关系需进一步解释 |
| 成长 | 有 ROI、稳定性、数据和 AI 感悟 | 中弱 | 个人复盘与规划 | 多为总结性观点，缺少触发事件、行为变化、二次迁移和结果 |
| AI Native | CLI 和 Agent 契约有真实工程内容 | 中强 | Skill、结构化输出、错误恢复、贡献机制 | AI 代码贡献率本身价值弱，仍需说明质量门禁和个人独立贡献 |
| 视觉表达 | 图表、画板、截图和表格丰富 | 中强 | 产品全景、架构图、流程图和结果图 | 页面密度较高，部分截图只能证明界面存在，未必能十秒传递判断 |
| 整体定位 | 三个重点方向比较鲜明 | 中 | OTN、CLI、Starling | 缺少一句统领全篇的转正理由和能力演进结论 |
| Q&A 准备 | 文档具备较多深挖材料 | 中 | 代码、架构、指标和链接 | 正文只提供 Q&A 入口，未看到按业务、技术、Ownership、数据组织的问题库 |

## 八、样本最明显的内容上限

### 8.1 缺少一句统领全篇的转正判断

文档能够让评委得出“工作很多、工程能力较强、CLI 方向有亮点”，但没有主动回答：

1. 作者从什么角色成长成了什么角色？
2. 现在可以把哪类更大、更模糊的问题交给作者？
3. OTN、Starling 和 CLI 为什么共同证明同一条能力演进？
4. 继续投入培养后，未来最可预期的组织价值是什么？

### 8.2 OTN 仍偏产品功能和工作量介绍

OTN 最终版已经显著强于 V1，但主要篇幅仍在解释产品能力和承接数量。它没有集中还原：

```text
关键问题怎样被发现
→ 作者如何重新定义问题
→ 提出了什么不同策略
→ 与哪些角色形成或推动了决策
→ 哪个结果由该判断直接产生
```

### 8.3 Starling 有治理结构，但决策形成过程仍可更深

进一步追问时仍需要回答：

1. 四类问题分别来自用户反馈、线上埋点、代码审计还是发布事故？
2. 哪些是表面现象，哪些是共同根因？
3. 为什么采用两阶段缓存治理，而不是一次性迁移？
4. 响应式治理是否比较过刷新页面、编译期扫描、Lint、AST 或人工治理？
5. 如何控制 `65` 个 MR 的回归风险和协作成本？
6. `99%`、`99.99%`和 `100%`的统计分母、样本与失败定义是什么？

### 8.4 CLI 是最强 Case，但仍需要守住事实和指标边界

1. 多平台定位与当前已完成的平台接入范围需要严格区分。
2. Agent-assisted contribution 需要说明生成内容、人类 Review、测试和失败处理的真实比例。
3. 累计调用量需要解释用户调用、Agent 自动调用和单任务底层调用次数。
4. `143 万次`调用与业务价值之间需要通过任务成功率、用户留存或节省时间建立联系。
5. 分层架构、兼容迁移和 Skill 中哪些属于作者独立判断，哪些来自团队讨论，需要明确。

### 8.5 代码量和 AI 贡献率不适合作为最高价值指标

`9w+`代码和最高 `92.35%` AI 代码贡献率可以证明交付方式和工作强度，却也可能触发反向问题：

1. 更多代码是否意味着更多复杂度和维护成本？
2. AI 生成代码如何经过测试、Review 和真实链路验证？
3. 个人价值体现于输入代码数量，还是问题判断和系统结果？
4. AI 贡献率提高是否真的缩短周期、提高质量或扩大负责范围？

因此，AI 代码贡献率最多作为研发过程数据，不能单独成为 AI Native 的核心证明。

### 8.6 成长章节缺少行为和结果证据

当前成长主要表达 ROI、D/C 端差异、数据量化和 AI 学习。它的问题不是观点错误，而是缺少：

```text
原认知
→ 触发事件
→ 新判断
→ 后续行为变化
→ 第二次应用
→ 结果变化
```

其中“D 端对性能要求没那么高”和“使用 AI 要克服代码洁癖”属于容易被放大的概括，必须补充适用条件和质量边界。

### 8.7 视觉丰富，但并非每张图都降低解释成本

样本大量使用产品截图、聊天记录、架构图、流程图和数据图，整体完成度较高。但部分内容主要证明“这个页面或功能存在”，没有直接告诉评委：

1. 改造前后的核心差异是什么。
2. 个人 Ownership 在哪里。
3. 哪个节点是最大风险或关键判断。
4. 评委十秒内应该记住什么。

## 九、以该样本为基础的最低生产合同

“全面超过”首先意味着不能低于样本已经完成的基础建设。

### 9.1 内容最低线

1. 开头能够说明个人背景、真实负责范围和工作全景。
2. 选择两到三个重点方向，不把全部需求平均铺开。
3. 至少一个主 Case 同时具备业务问题、系统架构、关键机制和使用结果。
4. 至少一个治理类 Case 能把零散问题归纳为稳定问题体系。
5. 每个主 Case 都有真实截图、文档、代码/MR、请求或数据证据。
6. 包含量化结果、个人成长、当前不足和下一阶段规划。
7. 准备能够支撑技术、业务、Ownership 和数据追问的附录。

### 9.2 证据最低线

1. 活动量：需求、MR、接口、命令、素材、规则或其他真实交付数量。
2. 交付结果：完成状态、测试、灰度、发布、验收或风险关闭。
3. 使用结果：真实用户、调用、覆盖、反馈、复用或流程采纳。
4. 业务影响：效率、质量、稳定性、合规、成本或组织能力变化。
5. 每个核心数字都能说明定义、窗口、来源、计算方式和个人归因边界。

### 9.3 技术最低线

1. 不只展示最终架构，还要说明原系统为什么无法继续演进。
2. 能解释系统边界、分层职责、横切能力和关键失败语义。
3. 平台或 Agent 项目必须说明契约、权限、验证、错误和恢复。
4. 迁移项目必须说明兼容范围、迁移顺序、回归门禁和未兼容内容。
5. 实现细节进入附录，正文只保留影响判断的机制。

## 十、全面超过该样本的目标合同

| 维度 | 样本已经做到 | 当前答辩的超越目标 |
|---|---|---|
| 转正结论 | 展示大量真实工作和三个重点方向 | 开头直接给出一句转正理由，说明可托付范围和未来价值 |
| 整体结构 | 按 OTN、CLI、Starling 三个项目方向展开 | 用能力或业务演进统领项目，避免项目之间只有并列关系 |
| 业务理解 | 有产品全景和功能关系 | 进一步说明用户、业务冲突、原链路失效和价值优先级 |
| 问题发现 | 能把 Starling 归纳为四类问题 | 还原问题信号、根因建模和优先级形成过程 |
| 技术判断 | 有分层、Agent 契约和迁移策略 | 增加候选方案、选择标准、未采用方案、失败和演进边界 |
| Ownership | 有负责范围、工作量和感谢协作方 | 明确个人判断、决策权、推动对象、异议、协作边界和结果归因 |
| 结果 | 有活动量、治理指标、用户和调用数据 | 提升指标口径质量，建立活动量到业务影响的因果链 |
| 成长 | 有复盘观点和未来学习方向 | 用真实事件证明认知变化、行为变化、二次迁移和结果 |
| AI Native | 有 AI 代码贡献率、CLI、Skill 和 Agent 契约 | 证明上下文、工具、执行、评测、权限、兜底和组织复用的完整工作流 |
| 视觉 | 图表和截图丰富 | 每页只证明一个判断，图中标记冲突、变化、Ownership 和结果 |
| Q&A | 文档具备大量可深挖材料 | 为每个核心故事显式准备三层追问、证据入口和边界答案 |

### 10.1 开头必须比样本更强

当前答辩开头不能只展示代码量和项目列表，需要在两分钟内建立：

```text
我解决的核心问题是什么
→ 我的负责范围如何扩大
→ 哪三条以内的证据支持这个判断
→ 下一阶段为什么值得继续托付
```

### 10.2 每个主 Case 必须比样本多一条决策链

```text
观察到什么信号
→ 为什么判断它是关键问题
→ 现实约束和候选方案是什么
→ 为什么选择当前策略
→ 怎样推动协作和实现
→ 怎样验证判断
→ 哪个认知被带到下一个问题
```

### 10.3 结果必须从“数量”升级到“变化”

```text
做了多少
→ 完成到什么阶段
→ 谁真正使用
→ 流程、质量或风险发生什么变化
→ 哪些变化可以归因于我的判断和推进
```

### 10.4 AI Native 必须证明结果可控

1. 原工作流的瓶颈。
2. 为什么由 AI 处理这部分。
3. 人、模型和确定性系统的边界。
4. 上下文如何构建和保持正确。
5. 如何测试、评测、真实回读和处理失败。
6. 带来了什么效率、质量、负责范围或复用变化。
7. 哪些场景明确保留人工和传统系统。

## 十一、结果证据四层模型

| 层级 | 回答的问题 | 典型证据 | 正文使用方式 |
|---|---|---|---|
| R1｜活动量 | 做了多少工作 | 需求、MR、代码、接口、命令、文档 | 只用于证明投入和覆盖，不作为核心收益 |
| R2｜交付结果 | 事情是否完成并达到阶段门槛 | 测试、灰度、发布、验收、缺陷关闭 | 说明项目成熟度和交付质量 |
| R3｜使用结果 | 是否真的被目标用户或流程采用 | 用户、调用、留存、覆盖、反馈、复用 | 证明能力从产物进入真实使用 |
| R4｜业务影响 | 使用后发生了什么价值变化 | 时间、质量、稳定性、合规、成本、风险 | 作为正文最优先的结果证据 |

使用规则：

1. 不要求每个项目都达到 R4，但必须如实说明当前最高层级。
2. R1 不能替代 R3/R4；工作量大不自动等于价值高。
3. R3 的调用量需要拆分用户调用、自动调用和单任务放大系数。
4. R4 必须同时有基线、窗口、来源、计算方式和因果边界。
5. Demo 项目可以有 R1/R2，不得把预期的 R3/R4 写成已发生结果。

## 十二、从本样本提取的评分信号

| 编号 | 评分信号假设 | 样本证据 | 当前置信度 | 采纳位置 |
|---|---|---|---|---|
| SS-01 | 高评价答辩首先需要足够真实的交付和结果证据 | 需求、MR、缺陷、用户、调用、治理数据 | 中高 | `01` 的结果与验证模型 |
| SS-02 | 把零散功能抽象成稳定系统问题，比需求流水账更能体现工程能力 | Starling 四类治理问题、CLI 四类结构性问题 | 中高 | `01` 的问题发现与建模 |
| SS-03 | 平台项目需要同时证明架构机制、演进方式和真实使用 | CLI 分层、贡献流程、Agent 契约、迁移和调用数据 | 中高 | 项目故事合同和后续骨架 |
| SS-04 | 图、数据、反馈和技术文档共同出现，能显著降低自我评价的不可信感 | 多种图片、画板、指标和文档引用 | 中 | 证据包和视觉规则 |
| SS-05 | 活动量能够建立交付可信度，但不能代替使用和业务影响 | 文档同时展示代码/需求和调用/场景 | 中高 | 结果证据四层模型 |
| SS-06 | AI 相关能力只有连接契约、验证、恢复和真实使用时才有较强价值 | CLI 的可发现、可确定、可解析、可恢复 | 中 | AI Native 证据模型 |
| SS-07 | 成长章节如果只有观点和学习计划，即使文档整体高分，也仍然存在提升空间 | ROI、D/C 端、数据和 AI 感悟 | 中 | 成长证据链和反例 |
| SS-08 | 一句话总定位和跨项目能力演进不是高分文档的必备形式，但可能是进一步提高记忆点的关键 | 样本缺少明确总定位但获得高评价 | 低到中 | D2 骨架对比验证 |

## 十三、进入北极星模型的结论

本轮只把以下稳定程度较高的结论提升到 `01`：

1. 高分基础至少包括真实交付、系统级抽象、结果证据和完整答辩基本面。
2. 活动量、交付结果、使用结果和业务影响必须分层，不能混成一个“产出”。
3. 系统思考不仅是展示最终架构，还需要解释结构性问题、边界、演进和验证。
4. AI Native 不能由 AI 代码贡献率单独证明，更强证据是工作流、契约、评测、失败恢复和复用。
5. 当前答辩要形成差异化，应补足样本相对薄弱的问题发现过程、Ownership 决策链、成长迁移和一句话转正理由。

以下结论暂不升级为稳定标准：

1. 转正答辩必须使用三个一级项目方向。
2. 代码量、MR 数量和 AI 贡献率存在统一门槛。
3. `M+ / SP` 的正式评分权重可以从该文档反推出。
4. 网络基础设施前端的页面密度和技术比例适用于当前业务。
5. AI Native 必须成为所有高分答辩的一级方向。

## 十七、当前结论

周圣翔样本足以定义一个较高的生产底线：

```text
真实产出充分
+ 系统抽象完整
+ 技术机制可信
+ 使用与结果可见
+ 图、数据和文档证据丰富
```

当前答辩要全面超过它，不能只增加更多项目和技术细节，而要在四个位置形成明确优势：

```text
更早给出转正判断
+ 更完整地还原问题发现与决策过程
+ 更清楚地证明 Ownership 和成长迁移
+ 更严格地证明 AI Native 与业务结果的因果关系
```

当前停止点：本文已完成首个样本校准，但尚未形成正式评分规则；后续结论仍需更多优秀样本、主管口径和评委反馈交叉验证。
