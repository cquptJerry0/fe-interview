# 答辩北极星与质量门禁

> 这份文件是唯一评分基准。它负责决定什么值得讲、什么证据够用、什么内容必须降级。项目事实查 `10-项目研究底稿`，结构决策查 `05-答辩框架与模块决策.md`。

## 一、答辩要促成的最终判断

评委看完后，应能得出以下结论：

> 王子豪能够独立负责边界清楚的业务模块，理解真实用户和业务结果；遇到复杂链路时能发现问题、拆清约束、做出技术选择，并把方案推进到可验证的交付状态。他也在把 AI、CLI 和工程流程结合起来，形成可以继续放大的工作方式。

这句话包含六个判断，缺一项都可能让材料退化成需求流水账：

1. 知道业务为何存在。
2. 对结果负责，身份是 Owner。
3. 能发现问题并提出自己的判断。
4. 技术方案能处理真实边界。
5. 交付有结果、有证据、有状态。
6. 能复盘不足，并形成后续可复用的方法。

## 二、六个评分维度

| 维度 | 评委想确认什么 | 强证据 | 弱证据或反例 |
|---|---|---|---|
| 业务理解 | 用户是谁，链路为何这样设计，失败会影响什么 | 业务对象、上下游、风险、价值和取舍能对应 | 只讲页面、接口和需求数量 |
| Ownership | 是否主动发现、设计、推动、协调和收口 | 方案、MR、评审、联调、风险处理、结果回读 | 只说“参与”“支持”，或只靠 Commit 数量 |
| 技术判断 | 是否看到了冲突，为什么选当前方案 | 现象、约束、备选、选择、失败边界 | 只列中间件、状态机和架构名词 |
| 工程交付 | 方案能否在真实系统里运行 | 主干合入、真实请求、PPE、测试、监控、回滚 | Demo 冒充上线，单测冒充端到端结果 |
| 结果价值 | 改造后具体发生了什么变化 | 业务覆盖、效率、正确性、稳定性、复用或阶段结果 | 无口径百分比、预期收益、代码行数 |
| 成长潜力 | 是否形成更成熟的工作方法 | 复盘前后行为变化、可复用资产、下一步行动 | “认知提升”“继续深入业务”一类自评 |

六个维度无需平均分配。主 Case 重点证明 Ownership、技术判断和结果；业务全景负责业务理解与覆盖面；成长部分补足复盘和潜力。

## 三、如何证明“有思考”

思考不能依赖一句“我认为”。一条完整判断至少经过以下链路：

```text
观察到什么现象
→ 这个现象为什么值得处理
→ 当时有哪些现实约束
→ 考虑过哪些处理方式
→ 为什么选择当前方案
→ 具体落了哪些机制
→ 哪些边界仍然存在
→ 结果或验证改变了什么
```

### 3.1 可进入正文的思考

符合下列任意两项，通常值得进入正文：

1. 发现了原需求没有写清的风险。
2. 在多个方案之间做了有代价的选择。
3. 调整了系统职责、事务边界、状态或权限模型。
4. 根据真实日志、失败或联调结果修正了最初判断。
5. 主动补上了恢复、验证、审计、回读或兼容方案。
6. 让一个项目里的机制能被其他用户、脚本或 Agent 复用。

### 3.2 只适合快速展示的内容

1. 正常接口开发，没有新的业务或技术判断。
2. 需求很重要，但个人仅完成明确实现。
3. 有较多代码和 Commit，没有可解释的结果变化。
4. 只有规划、Demo 或预期收益。
5. 与主 Case 结论重复，继续展开只会增加篇幅。

### 3.3 思考表达检查

每个技术判断都要能回答：

```text
如果不这样做，会发生什么？
为什么当时没有选择另一种方式？
规模、并发或失败条件变化后，方案哪里先失效？
这项判断中哪部分由我提出或拍板？
```

答不上来时，先回到底稿补事实，不用架构词填空。

## 四、Ownership 证据模型

用户已确认自己是当前四项重点工作的 Owner。文档仍要说明协作边界，让 Owner 角色更可信。

| 动作 | 可以证明什么 | 常见证据 |
|---|---|---|
| 发现 | 主动识别问题、风险或机会 | 日志分析、Oncall、复盘、问题记录、评审评论 |
| 定义 | 把模糊需求变成边界和验收目标 | OnePage、技术方案、任务拆分、指标定义 |
| 决策 | 对方案、取舍和失败边界负责 | 方案比较、评审结论、关键 Commit、讨论记录 |
| 推动 | 协调依赖、环境、权限、上下游和排期 | 周报、群聊、联调记录、工单、发布清单 |
| 实现 | 完成关键工程内容 | 代码、MR、测试、配置和真实请求 |
| 收口 | 处理评审、验证、交付、风险和遗留项 | Review 关闭、PPE、主干、回读、复盘、后续治理 |

写作原则：

1. 直接写“我负责”或“我与 MT 共同负责”，无需习惯性弱化。
2. 同时交代团队已经提供的基座和协作者负责的系统。
3. MR 作者可以证明实现投入，方案归属还要结合文档和讨论。
4. Owner 也可以接续已有系统，关键在于是否对本轮目标、判断和交付负责。
5. 全球素材搬运固定写为：`我与 MT 共同 Owner，我负责 VIMO 侧方案和实现`。

## 五、技术深度门禁

一个技术点进入正文前，至少填写以下六项：

| 项目 | 必须回答 |
|---|---|
| 触发问题 | 哪个用户、链路、日志或失败暴露了问题 |
| 现实约束 | 兼容、状态、权限、并发、跨系统、交付周期中有哪些限制 |
| 备选方案 | 至少说明一个没有采用的合理方案 |
| 当前选择 | 选择了什么，代价是什么 |
| 落地机制 | 对象、状态、事务、接口、数据或执行链路怎样变化 |
| 失败边界 | 哪些情况仍需重试、人工处理或后续治理 |

技术深度优先看判断密度，少看名词密度。事务、CAS、Workflow、JWT、Codegen 只有在解决具体冲突时才有价值。

## 六、结果与证据等级

### 6.1 交付状态

| 状态 | 可用表述 | 不能扩写为 |
|---|---|---|
| 设计或规划 | 已形成方案、明确下一步 | 已落地、已验证 |
| Demo | 已跑通演示场景 | 生产可用 |
| 本地或单测 | 代码路径和局部机制通过 | 端到端稳定 |
| PPE 或联调 | 某环境、某样本已验证 | 线上长期指标 |
| 主干合入 | 工程交付完成 | 业务已经使用 |
| 线上运行 | 已进入真实环境 | 有规模、有收益 |
| 量化结果 | 在明确窗口和口径下观察到变化 | 可外推到所有场景 |

### 6.2 结果类型

项目不一定都有收入指标，可以使用以下结果：

1. 业务覆盖：覆盖哪些业务线、站点、对象和用户角色。
2. 正确性：状态、版本、审批、回读或数据一致性得到验证。
3. 风险：合规、越权、重复执行、旧数据或失败污染被控制。
4. 效率：耗时、人工步骤、调用成本或吞吐发生变化。
5. 稳定性：失败能被记录、恢复、重试、告警或人工处理。
6. 复用：独立用户、服务账号、脚本、Agent 或其他业务接入。
7. 阶段结果：Demo、PPE、主干合入、真实样本演练。

### 6.3 数字门禁

每个数字必须回答：

```text
统计对象是什么
时间范围是什么
环境是什么
样本有多少
数据从哪里来
能证明什么
不能证明什么
```

当前关键口径：

1. 自动链路 `1188 秒 → 约 12～24 秒`只代表 SG PPE 一批 50 条任务；三种计时范围仍需统一。
2. OpenAPI/vimocli 的 `208`是去重调用身份，包含个人、服务账号和自动化。
3. `442,078`是已验签请求事件，可能包含最终 `403`。
4. 全球搬运的 `19/19`来自阶段演练截图，输入材料记录为 20 个，MR 尚未合入。
5. Coco 的两次 Apply 证明人工采纳，不能直接证明长期正确率。

## 七、AI Native 评价标准

AI Native 关注职责分配和结果可控，不统计使用了几个模型。

### 7.1 五个检查点

1. 模型负责什么语义判断。
2. 哪些 contract 由代码、CLI 或 schema 固定。
3. 写操作在哪里经过人工确认。
4. 失败、重试、回读和审计怎样处理。
5. 是否有人工采纳、独立使用或任务结果。

### 7.2 当前可用证据

| 场景 | 可证明 | 当前边界 |
|---|---|---|
| Coco | 有限范围 Patch、越界还原、`git apply --check`、人工 Apply | 自动触发关闭，缺长期正确率和团队使用 |
| vimocli Skill | Skill 保存任务方法，CLI 固定真实站点、鉴权和请求 contract | CLI 使用量不能等同于 Skill 使用量 |
| VIMO Agent | 模型路由，`managed_cli_run`执行，通用脚本不持有 JWT | 写操作当前主要依赖软确认，缺真实运营任务数据 |

当前是否独立成章由 `05` 决定，不能因为“新时代 AI Native”预设篇幅。

## 八、内容筛选规则

候选内容按六项比较：

| 维度 | 问题 |
|---|---|
| 业务重要性 | 失败会影响谁，影响什么结果 |
| Ownership | 我对发现、定义、决策、推动、实现和收口承担多少责任 |
| 技术判断 | 是否有真实冲突、取舍和失败边界 |
| 结果强度 | 有什么可验证变化，成熟度如何 |
| 证据强度 | 是否有代码、MR、文档、请求或数据交叉支持 |
| 叙事区分度 | 是否与其他 Case 重复，是否能贡献新的评委判断 |

筛选结果只有四种：

```text
主 Case
快速产出
横向能力
附录或删除
```

主 Case 数量和关键决策数量都不预设。最终由时间预算和证据密度决定。

## 九、页面生产合同

每个正文模块至少有：

1. 一个直接表达判断的标题。
2. 一句业务或技术结论。
3. 一张链路图、机制图、对比表或证据表中的至少一种。
4. 清楚的个人职责。
5. 一个结果或阶段状态。
6. 一个必要的边界。

一页无法回答“评委看完要记住什么”时，说明页面职责还没有定清。

## 十、提交质量门禁

### 10.1 事实

- [ ] 业务主语、用户、对象和上下游准确。
- [ ] 已交付、PPE、Demo、未合入和规划分开。
- [ ] 数字有窗口、环境、样本和来源。
- [ ] 外部方案、理想架构没有写成实际落地。

### 10.2 Ownership

- [ ] 每个重点模块写清我负责什么。
- [ ] 团队基座和跨团队职责得到说明。
- [ ] Owner 身份没有被弱化，也没有把协作方工作据为己有。
- [ ] 个人判断有方案、代码、评审或推动证据。

### 10.3 技术

- [ ] 技术机制对应具体问题和失败后果。
- [ ] 至少说明一个替代方案或原方案缺陷。
- [ ] 当前方案的代价和剩余边界明确。
- [ ] 相邻 Case 没有重复讲同一段链路。

### 10.4 结果

- [ ] 结果紧跟方案出现。
- [ ] 没有数据时使用真实阶段结果。
- [ ] 测试数据没有扩成线上长期收益。
- [ ] 负向指标和遗留问题没有被隐藏。

### 10.5 表达与上场

- [ ] 遵守 `AGENTS.md` 的去 AI 味规则。
- [ ] 一句话只承担一个主要职责。
- [ ] 业务背景、技术选择和结果没有混写。
- [ ] 图中文字能在十秒内读懂。
- [ ] 正文可以自然口述，标题和口头表达一致。
