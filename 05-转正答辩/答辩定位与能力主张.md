# 答辩定位与能力主张

更新：2026-10-13。本文是后期精修 Review 的能力参考，不是起稿门槛，也不是展示正文。先定义一般工程师的能力维度，暂不映射本人项目，不预先认定本人已具备这些能力。

## 定位与使用时机

答辩最终帮助评委判断：这个人能够承担什么范围的工作，处理问题是否可靠，作出的选择是否合理，以及是否值得交付更复杂的任务。

这里采用八个观察维度，综合考察做事方向、技术能力、交付协作和持续成长。它们是写作与评审的通用参考，不是某家公司的官方评分表，也不存在大厂统一要求“证明八项能力”的规定。实际要求需要结合岗位、职级和公司的正式标准调整。

| 阶段 | 当前先做好什么 | 暂时不要求什么 |
| --- | --- | --- |
| 起稿 | 把事情、本人工作和目前结果说清楚，保持事实准确、职责边界清楚 | 不要求填满能力维度，不要求每段都有高级判断、完整数据或成图 |
| 组稿 | 理顺因果、合并重复，逐步确定主次与图文分工 | 不先给项目贴能力标签，不为了覆盖框架扩写普通交付 |
| 精修 Review | 从已有材料归纳真正有依据的能力主张，检查哪些表达值得保留、补充或降级 | 不把缺少展示机会等同于没有能力，不为凑维度编造经历或拔高贡献 |

框架现在可以建立，个人能力结论后置。所有阶段都遵守事实底线；延后的是表达精度和能力论证要求，不是真实性要求。

## 八个能力维度

| 能力 | 评委希望判断什么 | 什么表现更能说明能力 |
| --- | --- | --- |
| 业务理解与问题定义 | 是否理解服务对象、实际问题和预期效果，能否判断什么值得做 | 澄清模糊需求，识别真正的限制，结合业务目标确定范围、优先级与验收方式 |
| 问题分析与技术判断 | 是否能找到关键原因，在现实约束下选择合理方案 | 用证据定位问题，比较有实际差异的方案，说明选择依据、适用边界与接受的代价 |
| 工程实现与质量保障 | 是否具备扎实的实现能力，能让方案在真实环境中可靠运行 | 正确处理关键逻辑，写出可维护代码，根据风险安排测试、观测、异常处理、安全与发布保障 |
| 责任意识与端到端交付 | 是否对承担范围内的结果负责，能把事情推进到完成 | 管理依赖和风险，遇到阻塞及时调整或求助，跟进联调、上线与使用反馈，而非以提交代码作为终点 |
| 沟通协作与推动 | 是否能建立共同理解，推动多人协作中的问题解决 | 及时对齐目标、接口和分工，清楚解释方案，处理分歧与预期变化，让协作方能作出决定或继续执行 |
| 抽象复用与工程改进 | 是否能从一次性任务中识别共性，让后续工作更容易 | 选择适当的复用边界，改进工具、组件或流程，并通过实际采用说明收益；也能识别不值得抽象的情况 |
| 学习反思与成长 | 是否能进入陌生领域，并根据反馈改变方法 | 将新知识用于解决问题，复盘失误后调整行为，逐步减少对他人的依赖，同时保持对未知边界的认识 |
| AI Native：AI 使用与理解 | 是否能有效使用 AI、理解其限制，并将它组织成可信的工作方式 | 根据任务选择用法，组织上下文与工具，验证输出，处理失败，在质量、成本和效率之间作出判断，并沉淀有效实践 |

这些维度相互关联，但关注点不同：技术判断看选择是否合理，工程质量看实现是否可靠；交付看是否对结果负责，协作看如何与他人共同推进；复用看后续工作是否改善，成长看本人工作方式是否变化。

业务价值和个人贡献贯穿所有维度。能力回答“怎样处理问题”，结果回答“产生了什么变化”，个人贡献回答“其中哪些判断与行动由本人承担”。代码量、接口数量和项目规模可以提供背景，不能单独证明能力；业务结果很好也不自动说明全部收益来自本人。

## AI Native 的独立观察角度

AI Native 在本次框架中是重要的独立维度，不只作为工具兴趣或附加自评。这里关注工程师使用与理解 AI 的能力，不预设必须训练模型、开发 Agent 平台或使用某个特定产品。

| 层面 | 具体关注什么 |
| --- | --- |
| 有效使用 | 能根据任务选择 AI、常规工具或人工处理；提供必要上下文，合理拆分工作，将 AI 用于实际问题而非为了使用而使用 |
| 理解边界 | 理解输出的不确定性、上下文缺失、工具权限与执行环境等限制；能定位失败原因，判断何时补信息、换方法、采用确定性程序或交还人工 |
| 工程化与评估 | 用清晰接口、可复用流程、测试和结果核查约束执行；根据真实任务评估质量、效率与成本，并持续修正工作方式 |

三层共同观察，不必分别写成三个章节，也不是全部做完才算会用 AI。能够解释一次任务为何适合或不适合交给 AI、如何验证结果，通常比列出模型、工具或提示词数量更有说服力。

使用频率、生成代码比例、自动化步骤数量都不能单独证明效果。质量、人工复核成本、失败后的处理和安全边界同样需要考虑；保留人工判断或决定不用 AI，也可能体现成熟的理解。

## 对转正阶段的尺度

优秀工程师的能力方向可以相通，责任范围与证明深度不能跨职级照搬。转正材料重点看：是否能在合理支持下承担明确范围的工作，作出与经验匹配的判断，可靠交付并持续成长。独立承担不等于事事不求助。

- 基础可信度来自业务理解、技术实现、质量意识、责任心和协作；不能只靠某一项亮点替代。
- 更突出的表现可以是主动澄清问题、有依据的技术选择、跨环节推进、适度复用、成熟的 AI 用法，或反馈后的明显成长。不要求全部具备。
- 跨团队战略、全公司平台、大规模组织影响和完整技术路线规划，不默认作为转正要求。缺少这类工作机会不应成为扣分理由。

最终答辩不需要平均证明八项能力。成稿后选出最有支撑的少数主张，通常三到四项便于形成记忆，但数量不设硬指标；其他维度可由真实经历自然体现，无需单独占章。

## 后期精修怎样使用

精修时先读真实材料，再作能力判断。对一个值得保留的片段，考虑它能否让读者看见问题、本人判断或行动，以及相应结果；不要求每段重复完整链条。

1. 从材料归纳能力，而非拿能力名称倒推经历。一个项目可以支撑多个维度，同一维度也可以由多项工作共同支撑。
2. 区分有证据支持、表述尚不清楚、缺少材料三种情况。分别保留、改写或标为待了解，不全部变成补写任务。
3. 优先修复影响整体判断的缺口。没有量化数据时可用真实行为变化、采用记录或验证结果，不强行制造百分比。
4. 删除或下沉重复实现细节，保留能够改变读者判断的选择与边界。能力主张不必直接出现在标题和每段结尾。
5. 输出简短的整体评价与少量高收益修改建议，不制作八维打分表，不以全部覆盖作为通过条件。
