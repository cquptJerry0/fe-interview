# 转正答辩写作约定

更新：2026-10-18。依据本轮用户要求和 mentor 的“文字太多”反馈。这里保存当前协作要求，不保存项目事实或历史讨论流水。

## 内核

让评委快速理解三项代表贡献：解决了什么问题、最终做成什么、产生什么变化，以及本人作出了哪些判断、承担了哪些工作。

本轮重新定义内容、价值、组织形式和比重。结果应当是文字更少、业务与技术价值证据更充分、技术逻辑清楚、目录更浅。

整篇顺序已由用户确定：自我介绍 → 三个重点产出 → 总结与规划。各项目的内部结构、比重与形式仍待整篇确认。完整业务介绍不再单独占据一大章，必要背景进入对应项目。

## 分阶段使用

起稿先做到事实准确、事情说清楚、本人工作有边界。下列内容与格式要求用于逐步完善，不要求第一稿全部满足；允许数据、图和表达暂不完整，但不能用猜测填补事实。

组稿阶段重点理顺逻辑、去重和确定详略。后期精修再按 [答辩定位与能力主张](./答辩定位与能力主张.md) 判断材料实际支撑哪些能力，其中 AI Native 作为独立重要维度。能力框架先与项目解绑，不作为项目标签或八项必答题，也不提前认定个人优势。

## 内容要求

| 信息 | 应回答的问题 | 写作边界 |
| --- | --- | --- |
| 背景与判断 | 谁在什么场景遇到什么问题，为什么值得做 | 写到读者能理解贡献为止；可用业务图，避免公司业务百科 |
| 交付 | 本次建成或改变了什么 | 明确对象、能力和范围，区分已有基础与本人增量 |
| 业务产出 | 谁实际使用，业务供给、操作效率或业务结果发生什么变化 | 覆盖、采用、效率、转化分别说明；不能用接口数量代替收益 |
| 技术产出 | 执行、正确性、恢复、接入或维护成本发生什么变化 | 机制有何作用与实测效果分开；不编造节省人日或稳定性指标 |
| 个人贡献 | 负责哪一段，作出哪些选择、推动什么落地 | 不靠完整系统的规模替代本人贡献，协作边界不能省略 |

项目开场将交付与效果前置，背景和个人范围紧邻。先让读者知道这件事指什么、改变了什么，再展开设计；不能为了结果前置省掉必要概念。信息组织紧凑，但不把四件事硬塞进一个长句，也不强制四个小标题。

技术内容按 Why、What、How 检查：Why 说明问题、约束和选择理由；What 说明关键改动与边界；How 说明机制怎样成立，主要借助图。它们是内容检查，不是必须重复的标题模板。

保留真正影响选择的理由和关键约束，普通实现细节下沉。复杂关系不能为了少字删成几个空框，正确但与本节判断无关的细节也不必全部展示。

总结与规划补充工作覆盖、日常支持、成长和后续方向，不复述三个项目。工作总览可包括其他业务交付、工程沉淀、代码/MR、Oncall；完整产出清单是否保留仍待本人决定。

个人成长用认识或行为变化自然衔接简短经历，不机械分成“观点”和“例子”。规划分工作规划与个人规划，写清准备做什么、依托什么实践、希望补齐什么能力，不重复项目设计。

## 事实与数据

- 事实优先查原始文档、运行记录和本人确认；写作要求以当前用户决定为准。助手旧回复、修改时间和“最终稿”文件名都不能单独证明正确。
- 交付、采用、业务收益分别核对。功能上线、MR 合入、环境验证、长期运行不是同一状态。
- 数据保留最必要的时间、对象和范围；详细统计方法放来源。请求次数不等于成功任务数，调用身份不直接写成人数，候选素材不等于成功搬运或可用供给。
- 计时段不一致不直接相除成提速倍数；业务总体增长不能全部归因于单项改造。
- 资料冲突时标记待核验并保留来源，不挑更大或更新的数字填入正文。未知值不得伪装成已确认结论。
- 素材复制服务、Workflow/BPM、公共平台和同事工作保留真实分工；全球搬运使用与 MT 共同负责、本人承担 VIMO 侧方案和实现的口径。
- 不在答辩材料中保存 Cookie、JWT、密钥等凭证；截图和日志需检查敏感内容。

## 格式与图文分工

- 采用项目章与少量大块组织，通常两级标题足够。只有独立的阅读问题才增设下一层，不保留旧稿的五级编号。
- 背景可图示；并列内容可分栏；同维度比较可用表；机制关系用画板。三列表是候选，不要求三个项目使用同一模板。
- 表格单元格表达一项判断或少量要点，不承载整篇段落。宽表若必须缩字才能看清，拆为连续内容块。
- 分栏中的内容应有明确关系，如并列业务场景或连续建设阶段；不因为恰好有三个技术模块就平分三列。先确定扫读顺序和主次，再选载体。
- 图展示对象、边界、路径、前后差异与必要异常。正文解释判断和取舍，不逐节点复述；截图与数据证明真实交付或效果。
- 背景图、整体图、机制图各有独立任务，不把相同链路重复绘制。调用、依赖、代码生成和发布关系分别标注。
- 先确认图表达什么，再画。骨架中的图占位写明图名、问题、范围和关键变化；暂不强制 ASCII 或详细绘图 Prompt。获准制图后再补可编辑源码与实际预览。
- 日常同步保留正文已有的图片、画板和批注；需要说明时使用飞书资源原生描述，不以新增重复段落代替图注。2026-10-18 用户另行授权清空旧文重搭框架，本次已执行；后续新增内容仍按保留原则处理。
- 飞书重点使用句内蓝色加粗：`<b><span text-color="rgb(36,91,219)">关键结论</span></b>`。只标主要结果和决定性变化，不给每句添加关键词，不用整块浅蓝背景替代重点。
- 句与句、段与段需要有解释关系。技术名词首次出现时交代用途，不让读者依靠作者的内部知识补全含义。
- 优先自然、完整、具体的技术陈述。避免宣传式总结、对称排比和重复结尾；不能靠删主语、堆名词或把句子截断减少 AI 味。
- 当前骨架允许清楚标注待补图和证据；最终展示不包含写作指令、派发记录、旧 Prompt 和 Review 过程。

## 协作顺序

1. 模块会话返回推荐组织方案，不直接扩写全文；主协调收稿并处理重复、边界与比重。
2. 主协调搭出带开场短文、结论、证据位置和图占位的整篇骨架，由本人整体确认。
3. 本人逐标题打磨内容、布局和格式；AI 提供候选、核验和局部改写。
4. 按确认的表达任务补图，必要时局部修正文案，不重新扩大项目范围。
5. 成稿后按下方标准整篇 Review，再按能力参考进行精修；不用后期完整度要求阻塞起稿。工具执行成功和用户授权写入不等于内容通过。

本轮先实际研究本人指定的《工作总结-7.31》：介绍怎样展开、价值怎样定义、版面怎样组织、图表怎样分工。返回方案需引用具体片段，说明相对旧方案重做了什么，并提供开场试写和局部版面示意。不能只交“结果导向、多用图、精简文字”等原则，也不把参考全文当成模板；参考中的平台规模与他人产出不迁移到本人经历。

## Review

以下用于成稿后的内容与表达检查。早期只处理妨碍理解的主要问题，不要求一次通过所有项。能力层面的判断另见 [答辩定位与能力主张](./答辩定位与能力主张.md)，不把观察维度转换成强制篇幅、固定分数或每项目的证明清单。

| 检查 | 通过标准 |
| --- | --- |
| 第一眼 | 标题与开场能说明事情、交付、效果和本人范围 |
| 内容取舍 | 每个大块提供独立信息，主次明确，没有完整功能清单平均展开 |
| 价值 | 业务与技术产出清楚，证据状态和口径准确，没有拔高归因 |
| 技术 | Why、What、How 都能回答；关键判断有依据，必要边界没有丢失 |
| 图文 | 图解释关系，文字解释判断，证据支持结果；没有换载体重复讲解 |
| 目录与语言 | 层级浅，句段自然承接，术语可理解，高亮能区分重点 |
| 全篇 | 背景、项目、工作总览、成长与规划各有职责，项目之间没有抢讲同一贡献 |

Review 先报告影响理解和判断的问题，说明保留、合并、下沉或补证建议，再改措辞。没有按同一口径比较前，不宣称字数已经下降或数据更丰富。
