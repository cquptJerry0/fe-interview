# 转正答辩专用规则

## 1. 适用范围

1. 本文件适用于 `05-转正答辩` 目录内的全部工作。
2. 适用对象包括用户对话、澄清、进度汇报、研究结论、正文、口述稿、标题、图中文字、附录和 Q&A。
3. 当前目录的语言标准是：自然、直接、具体、克制，接近工程师本人正常说话。
4. 发现事实拔高、Ownership 越界、AI 味或文件职责混乱时，先修正再继续。
5. 本目录服务转正答辩，不生成简历，也不维护各项目的第二份完整事实库。

## 2. 文件职责

| 文件 | 唯一职责 | 不保存 |
|---|---|---|
| `00-阶段地图.md` | 阶段、当前热区、时间节点和下一步 | 项目技术事实、正文 |
| `01-答辩北极星与质量门禁.md` | 评分判断、证据标准和提交门禁 | 单项目长篇内容 |
| `02-优秀答辩样本与稳定结论.md` | 样本事实和已经验证的规律 | 当前答辩结构和项目事实 |
| `03-VIMO业务全景与个人产出.md` | VIMO 业务、用户、对象、个人职责和全部产出 | 最终章节和完整技术故事 |
| `04-答辩内容候选与证据矩阵.md` | 内容比较、证据强度、结果口径和缺口 | 正式文案 |
| `05-答辩框架与模块决策.md` | 结构候选、决策记录和模块卡 | 原始研究材料 |
| `10-项目研究底稿/` | R0～R5 的稳定事实、证据和新增变化 | 模型评分、90 秒稿、正式页面 |

新内容先判断属于哪个职责。无法归类时先说明用途，不立即创建文件。

## 3. 去 AI 味硬规则

### 3.1 默认禁用的句式

1. `不是……而是……`
2. `不仅……更……`
3. `从……走向……`
4. `通过……实现……提升……`
5. `围绕……打造……形成闭环`
6. `在……背景下，……应运而生`
7. 连续三组抽象排比
8. 用“本质上、真正需要的是、换句话说”替用户总结意图

确有对比时拆成两句，分别写原状态和当前变化。

差：

> 这不是一次简单的功能改造，而是一次面向未来的系统性升级。

好：

> 原链路已经能搬运素材，但任务依赖前端等待。页面超时后，运营看不到下游是否受理，也无法恢复逐素材结果。

### 3.2 慎用抽象词

下列词语必须落到具体对象、动作或数据，否则删除：

`赋能`、`抓手`、`闭环`、`关键断点`、`能力跃迁`、`全面提升`、`持续演进`、`系统性建设`、`降本增效`、`价值释放`、`业务牵引`、`认知升级`、`体系化沉淀`。

差：

> 完成平台能力沉淀，形成业务提效闭环。

好：

> 素材查询、面板操作和发布能力接入 OpenAPI 与 vimocli。脚本和 Agent 可以复用同一组接口，不再各自拼装页面请求。

### 3.3 一句话只承担一个职责

1. 业务背景、问题、选择、机制和结果分开写。
2. 一句话不同时承担价值拔高、能力总结和章节转场。
3. 连续出现多个逗号时优先拆句。
4. 图表已经表达的关系，不再补一段空泛说明。
5. 标题直接表达判断，少用“项目介绍”“技术方案”一类无信息标题。

### 3.4 使用真实业务语言

优先使用：素材、分类、面板、Draft、Pre、Prod、`distribute_record`、`publish_task`、OpenAPI、vimocli、Workflow、搬运任务、业务线、站点。

优先写真实动作：建单、计算目标分类、更新 Draft、创建发布任务、回读主库、跳过无变化任务、复用稳定 ID、统计失败任务。

每句话都要能回答“具体指什么”。答不上来就删除或回到底稿补事实。

## 4. 对话规则

1. 先直接回答用户的问题，随后给选择、理由和下一步。
2. 进度汇报使用`当前状态 → 已确认事实 → 下一步`。
3. 用户指出表达有 AI 味时，修正整类写法，不只替换当前一句。
4. 用户使用自然口语时，回复保持同等自然度。
5. 不在每次回复前重复一段“核心判断”。
6. 不用新术语掩盖阶段混乱。出现 D0、D1 等编号时必须同时写中文阶段名。

对话 Case：

| 场景 | 差 | 好 |
|---|---|---|
| 承认方案过重 | 你需要的不是更多控制面文档，而是真正进入内容生产 | 你说得对，前置文档已经够了。下一步直接做框架决策 |
| 说明下一步 | 接下来围绕业务全景构建候选故事雷达 | 下一步先定整篇结构，再确定四个项目各占多少篇幅 |
| 修正表达 | 这不是表述问题，而是叙事范式偏差 | 刚才那段写得太像模型总结，我按真实链路重写 |

## 5. 事实与交付状态

1. 合入主干可以写“已交付”。
2. Demo、单测、PPE、联调、主干合入、线上运行和量化结果分别表述。
3. 预期收益不能充当实际结果。
4. 数据必须说明时间、环境、样本和统计对象。
5. 测试数据不能扩写为线上长期指标。
6. 外部成熟方案只能标参考，不能写成项目已经落地。
7. 模型生成的结论需要代码、MR、文档、请求或数据交叉核验。
8. 事实发生变化时先更新研究底稿，再判断是否修改正文。

## 6. Ownership 规则

1. 用户已确认自己是 TTP、自动链路、OpenAPI/vimocli 等重点工作的 Owner。
2. 全球素材搬运为用户与 MT 共同 Owner，用户负责 VIMO 侧方案和实现。
3. 使用`我负责、我提出、我决定、我推动、我实现`时，紧跟具体对象和证据。
4. 团队基座用于说明协作和系统边界，不用于习惯性弱化用户角色。
5. MR 作者可以证明实现投入，不能单独证明需求和全部方案归属。
6. Owner 身份允许建立在存量系统或团队初版基座上，重点说明本轮目标、判断和交付责任。
7. 不把协作方的素材服务、Workflow、评测基座或平台能力归为个人建设。

推荐写法：

> 我与 MT 共同负责全球素材搬运。我负责 VIMO 侧方案和实现，包括任务持久化、预检、Workflow 接入、结果查询和后处理。

不推荐：

> 我主要参与并落地了部分搬运能力。

## 7. R0～R5 研究底稿规则

六份底稿只保存：

1. 当前事实摘要。
2. 业务、用户和真实链路。
3. 用户的 Ownership。
4. 已确认的技术判断，数量不限。
5. 结果、数据和统计口径。
6. 代码、MR 和飞书文档证据。
7. 新增变化和待确认项。

底稿不保存：

1. 模型生成的标题。
2. F1/F2/A2/E3 等内部标签。
3. 90 秒稿。
4. 正式页面结构。
5. 大段 Commit 流水。
6. 外部理想架构。

正式正文只从底稿抽取事实，重新按评委判断编译。

## 8. 重点项目的固定边界

1. TTP：讲合规最终写入、Pre／Prod、审批、Diff、事务和 TTP 环境。
2. 自动链路：讲事件、`distribute_record`、Draft、`publish_task`、任务粒度、性能和恢复。
3. `publish_task`始终属于自动执行链路，不单独漂移为另一项目。
4. OpenAPI/vimocli：讲 contract、资源权限、身份、多站点、CLI 语义和复用。
5. 全球素材搬运：按存量链路重构讲，先还原旧链路问题，再说明任务、恢复和后处理边界。
6. AI Native：Coco、Skill 和 Agent 的成熟度分别说明，不拼成已规模化的平台故事。
7. 商业化：当前快速展示，不强行编成独立主线。

## 9. 高评价样本中的好 Case

参考样本：

1. [【周圣翔】转正答辩](https://bytedance.larkoffice.com/wiki/UQJxwHxShigz1okFHgkcK5ATnwc)
2. [【周圣翔】转正答辩 V1](https://bytedance.larkoffice.com/wiki/I2hkwXbL4iXy3vkOgzbc5KXznfG?from=from_copylink)
3. [剪映商业化前端转正申请汇报](https://bytedance.larkoffice.com/docx/H0had3hlioudrpxsxZOcO2M4nqf)

这些 Case 只学习结构和语言，不复制业务事实。

### Case 1｜一句话说明工作范围

原文：

> 在 OTN 方向，我主要围绕 BONE 统一管控、故障与告警、资源与光层工具、网络规划与建设流程四条主线参与前端建设。

可取之处：直接说业务方向、真实模块和个人范围，后面马上接全景图。

### Case 2｜业务和工作放在同一结构

```text
业务方向
→ 产品全景与个人工作定位
→ 产品全景图
→ 核心功能建设
→ 工作产出与量化结果
```

可取之处：章节顺序已经完成转场，不需要另写宏大过渡。

### Case 3｜技术问题写到代码位置和用户现象

原文：

> 部分存量代码在模块顶层、静态 schema、columns、route meta 等非响应式位置提前执行 `t()`，导致用户切换语言页面部分位置语言未生效。

可取之处：一句话给出代码位置、触发动作和用户结果。

### Case 4｜直接写架构职责

原文：

> 项目采用 Command → Handler → Service → API → HTTP 的单向分层。每层只处理一种变化来源，避免命令声明、业务编排和请求细节再次混杂。

可取之处：先给真实分层，再说明它解决的冲突。

### Case 5｜复杂度由事实证明

```text
50 条任务
→ 976 个分类 action
→ 143 个分类
→ 16 个面板
```

可取之处：事实已经说明计算和事务粒度为何重要，不再补“高复杂度场景”。

### Case 6｜结果紧跟机制

```text
整批加载公共数据
→ 分类粒度归并
→ 面板粒度事务
→ 50 条 PPE 任务由 1188 秒降到约 12～24 秒
```

可取之处：读者能直接看到选择和结果的关系。数字旁必须保留 PPE 和单批样本限制。

### Case 7｜保留边界和负向结果

```text
I18N 个人 JWT：200
I18N 服务账号：验签后 403
```

可取之处：这能准确说明站点框架可用，服务账号仍需独立授权。

### Case 8｜具体说明不足

原文：

> 目前在数据量化上仍有不足，做完一件事往往只能凭感觉判断收益，缺少具体指标佐证。未来需在做事前预设量化指标，并熟练使用公司内的数据量化平台。

可取之处：不足对应行为，后续动作能够执行。

## 10. 正式写作流程

```text
读取阶段地图
→ 读取已确认的框架和模块卡
→ 从对应 R0～R5 底稿抽取事实
→ 按业务问题和评委判断组织
→ 检查 Ownership 和结果口径
→ 去掉研究标签与模型文案
→ 检查去 AI 味
→ 再进入排版和画图
```

不得把 R0～R5 的 90 秒稿、标题和结论段直接拼入正文。

## 11. 9 月 5 日后的增量规则

新工作先写入对应底稿的`新增变化`，至少记录：

```text
时间、业务问题、我的职责、技术判断、状态、证据、结果、影响模块
```

随后判断它属于：补强现有 Case、替换候选、进入产出总览、进入规划。

9 月 5 日后的新增工作不能直接插入最终正文，防止事实和结构反复漂移。

## 12. 提交前检查

1. 业务图能说明用户、对象、主链和个人责任区。
2. 每个主 Case 有真实问题、个人判断、落地机制、结果和边界。
3. 团队基座与个人 Owner 身份都清楚。
4. 数据口径紧邻数字。
5. 未合入和阶段验证没有写成上线。
6. 技术名词都能回答具体解决什么。
7. 相邻项目没有重复讲同一段链路。
8. 图表十秒内能看出核心判断。
9. 正文能自然口述，没有宣传稿语气。
10. 链接、权限、图片和敏感信息已经检查。
