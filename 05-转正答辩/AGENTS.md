# 转正答辩专用规则

## 1. 适用范围

1. 本文件适用于 `05-转正答辩` 目录内的全部工作。
2. 适用对象包括用户对话、澄清、进度汇报、研究结论、正文、口述稿、标题、图中文字、附录和 Q&A。
3. 对话自然、直接；正式文档采用客观、具体、克制的技术陈述。能口述不等于把聊天、串场和宣传文案写进正文。
4. 发现事实拔高、Ownership 越界、AI 味或文件职责混乱时，先修正再继续。
5. 本目录服务转正答辩，不生成简历，也不维护各项目的第二份完整事实库。
6. 本目录停用 `distill-work-summary`：用户已明确否定该 Skill。不调用、不读取后套用，也不沿用其固定叙事模板。项目应讲哪些内容、关键决策有多少，依据真实投入和本轮讨论确定。

## 2. 文件职责

| 文件 | 唯一职责 | 不保存 |

| `00-阶段地图.md` | 阶段、当前热区、时间节点和下一步 | 项目技术事实、正文 |

| `02-优秀答辩样本与稳定结论.md` | 样本事实和已经验证的规律 | 当前答辩结构和项目事实 |
| `03-VIMO业务全景与个人产出.md` | VIMO 业务、用户、对象、个人职责和全部产出 | 最终章节和完整技术故事 |
| `04-答辩内容候选与证据矩阵.md` | 内容比较、证据强度、结果口径和缺口 | 正式文案 |

新内容先判断属于哪个职责。无法归类时先说明用途，不立即创建文件。

## 3. 去 AI 味硬规则

### 3.1 默认禁用的句式

1. `不是……而是……`
2. `不仅……更……`
3. `从……走向……`
4. `通过……实现……提升……`
5. `围绕……打造……形成闭环`
6. `在……背景下，……应运而生`
7. 连续三组抽象排比
8. 用“本质上、真正需要的是、换句话说”替用户总结意图

确有对比时拆成两句，分别写原状态和当前变化。

差：

> 这不是一次简单的功能改造，而是一次面向未来的系统性升级。

好：

> 原链路已经能搬运素材，但任务依赖前端等待。页面超时后，运营看不到下游是否受理，也无法恢复逐素材结果。

### 3.2 慎用抽象词

下列词语必须落到具体对象、动作或数据，否则删除：

`赋能`、`抓手`、`闭环`、`关键断点`、`能力跃迁`、`全面提升`、`持续演进`、`系统性建设`、`降本增效`、`价值释放`、`业务牵引`、`认知升级`、`体系化沉淀`。

差：

> 完成平台能力沉淀，形成业务提效闭环。

好：

> 素材查询、面板操作和发布能力接入 OpenAPI 与 vimocli。脚本和 Agent 可以复用同一组接口，不再各自拼装页面请求。

### 3.3 一句话只承担一个职责

1. 业务背景、问题、选择、机制和结果分开写。
2. 一句话不同时承担价值拔高、能力总结和章节转场。
3. 连续出现多个逗号时优先拆句。
4. 图表已经表达的关系，不再补一段空泛说明。
5. 标题直接表达判断，少用“项目介绍”“技术方案”一类无信息标题。
6. 长段落及表格内的长句必须拆成分点。

### 3.4 使用真实业务语言

优先使用：素材、分类、面板、Draft、Pre、Prod、`distribute_record`、`publish_task`、OpenAPI、vimocli、Workflow、搬运任务、业务线、站点。

优先写真实动作：建单、计算目标分类、更新 Draft、创建发布任务、回读主库、跳过无变化任务、复用稳定 ID、统计失败任务。

每句话都要能回答“具体指什么”。答不上来就删除或回到底稿补事实。

### 3.5 正文默认使用客观技术陈述

这是用户明确要求的写作标准，适用于业务介绍、项目正文、表格和画板文字。

1. 直接描述业务用途、系统关系、负责范围、具体改动和结果。正文不使用“这段时间”“下面先介绍”“接下来展开”等串场句。
2. 不从假想用户的日常操作讲起，凑成一段“先做什么、再做什么、最后做什么”的故事。确实需要说明操作顺序时，写清对象和链路即可。
3. 业务介绍限定在理解个人工作所需的范围。既不介绍整个公司的业务，也不只列内部模块名和任务名。
4. 客观表达允许使用“我负责”“我决定”。不能靠删除主语、堆技术名词或把 Owner 改成“参与”制造客观感。
5. 开场的吸引力来自工作的重要性、清楚的责任范围和具体交付。不要用“复杂长链路”“关键断点”“面向未来”等词替代这些信息。
6. 内容应保留问题、选择和因果。去 AI 味不等于把文章压缩成没有关系的短句或功能清单。

用户否定的写法：

> 运营需要先把素材录入、维护好，再组织到分类和面板中，最后发布到客户端。我的日常开发覆盖素材管理、面板、版权与合同等模块，也负责自动化链路和跨业务素材搬运。
>
> 这段时间，我重点负责了自动化链路的整体重构优化，以及 vimocli 从零开始的基础设施建设。下面先介绍这些工作在素材业务中的位置，再展开具体项目。

问题：业务说明写成操作旁白，后半段重复职责并增加串场，仍未说明这些工作之间的关系。

客观表达示例（根据用户已确认范围整理，非最终正文、非外部样本原文）：

> VIMO 素材模块涵盖素材管理、版权与合同管理、分类与面板配置、自动分发、发布及跨业务搬运。OpenAPI 与 vimocli 提供相关业务的接口和命令行调用能力。
>
> 负责范围包括素材模块业务开发、VIMO 基础设施建设，以及 OpenAPI 与 vimocli 的基础设施和素材业务能力接入。重点工作包括自动化分发与发布链路重构、vimocli 0→1 建设；商业化方向主要承担审计相关开发。

这组句子只示范表达标准。正式第二模块还需要将代表交付放回对应业务位置，不能直接把它当成完整业务总览。

## 4. 对话规则

1. 先直接回答用户的问题，随后给选择、理由和下一步。
2. 进度汇报使用`当前状态 → 已确认事实 → 下一步`。
3. 用户指出表达有 AI 味时，修正整类写法，不只替换当前一句。
4. 用户使用自然口语时，回复保持同等自然度。
5. 不在每次回复前重复一段“核心判断”。
6. 不用新术语掩盖阶段混乱。出现 D0、D1 等编号时必须同时写中文阶段名。
7. 用户决定每块讲什么、真实判断和取舍；AI 应主动提供有事实依据的内容候选、关联方式和修改建议，承担整理、核验与执行，不要求用户先独自想好整篇。
8. 用户要求“先定内容，形式后议”时，先给可讨论的实际内容。不要只返回原则、问题清单或新增前置文档。

对话 Case：

| 场景 | 差 | 好 |
|---|---|---|
| 承认方案过重 | 你需要的不是更多控制面文档，而是真正进入内容生产 | 你说得对，前置文档已经够了。下一步直接做框架决策 |
| 说明下一步 | 接下来围绕业务全景构建候选故事雷达 | 下一步先定整篇结构，再确定四个项目各占多少篇幅 |
| 修正表达 | 这不是表述问题，而是叙事范式偏差 | 刚才那段写得太像模型总结，我按真实链路重写 |

## 5. 事实与交付状态

1. 合入主干可以写“已交付”。
2. Demo、单测、PPE、联调、主干合入、线上运行和量化结果分别表述。
3. 预期收益不能充当实际结果。
4. 数据必须说明时间、环境、样本和统计对象。
5. 测试数据不能扩写为线上长期指标。
6. 外部成熟方案只能标参考，不能写成项目已经落地。
7. 模型生成的结论需要代码、MR、文档、请求或数据交叉核验。
8. 事实发生变化时先更新研究底稿，再判断是否修改正文。

## 6. Ownership 规则

1. 用户已确认自己是 TTP、自动链路、OpenAPI/vimocli 等重点工作的 Owner。
2. 全球素材搬运为用户与 MT 共同 Owner，用户负责 VIMO 侧方案和实现。
3. 使用`我负责、我提出、我决定、我推动、我实现`时，紧跟具体对象和证据。
4. 团队基座用于说明协作和系统边界，不用于习惯性弱化用户角色。
5. MR 作者可以证明实现投入，不能单独证明需求和全部方案归属。
6. Owner 身份允许建立在存量系统或团队初版基座上，重点说明本轮目标、判断和交付责任。
7. 不把协作方的素材服务、Workflow、评测基座或平台能力归为个人建设。

推荐写法：

> 我与 MT 共同负责全球素材搬运。我负责 VIMO 侧方案和实现，包括任务持久化、预检、Workflow 接入、结果查询和后处理。

不推荐：

> 我主要参与并落地了部分搬运能力。

## 7. R0～R5 研究底稿规则

六份底稿只保存：

1. 当前事实摘要。
2. 业务、用户和真实链路。
3. 用户的 Ownership。
4. 已确认的技术判断，数量不限。
5. 结果、数据和统计口径。
6. 代码、MR 和飞书文档证据。
7. 新增变化和待确认项。

底稿不保存：

1. 模型生成的标题。
2. F1/F2/A2/E3 等内部标签。
3. 90 秒稿。
4. 正式页面结构。
5. 大段 Commit 流水。
6. 外部理想架构。

正式正文只从底稿抽取事实，重新按评委判断编译。

## 8. 重点项目的事实归属边界

下列内容用于避免项目事实混淆，不代表正文必须逐项展开。具体重点和内部结构逐块讨论。

1. TTP：相关事实包括合规最终写入、Pre／Prod、审批、Diff、事务和 TTP 环境。
2. 自动链路：相关事实包括事件、`distribute_record`、Draft、`publish_task`、任务粒度、性能和恢复。
3. `publish_task`始终属于自动执行链路，不单独漂移为另一项目。
4. OpenAPI/vimocli：相关事实包括 contract、资源权限、身份、多站点、CLI 语义和复用。
5. 全球素材搬运：按存量链路重构讲，先还原旧链路问题，再说明任务、恢复和后处理边界。
6. AI Native：Coco、Skill 和 Agent 的成熟度分别说明，不拼成已规模化的平台故事。
7. 商业化：当前快速展示，不强行编成独立主线。

## 9. 表达与结构 Case：区分外部样本和本项目示例

样本来源与完整研究见 `02-优秀答辩样本与稳定结论.md`。只有 S1 的 `M+ / SP` 来自用户确认，不能把所有参考材料称为高评价文档。

以下外部 Case 均为结构转述，不是逐字引文。只学习表达方法，不迁移他人的业务事实、数据或个人成绩。

### Case 1｜业务介绍中标明负责范围

S1 把业务方向、产品全景和个人建设放在同一节；S5 王文杰在存量飞鸽业务图中，用“负责模块”图例和对应色块标出个人责任区。

可取之处：介绍业务时已经说明作者做了什么。存量开发与重构同样能清楚呈现责任，不必包装成新建整个系统。

使用条件：职责图适合已有业务关系；若工作主要是平台能力建设，可以用能力分组。不能要求所有答辩都有一张完整业务图。

### Case 2｜多个小需求归到业务模块

S6 梁燕平将需求按账户、触达、主框架归组，同组中并列业务需求、技术文档和收益；S4 彭熠宁将多期标签建设作为同一个工作主题。

可取之处：分组有共同的业务对象或职责，组内工作仍可核对。不要给不相关的小任务套“平台化”“体系建设”等大标题。

### Case 3｜说明选择依据和接受的代价

S3 戴乐比较草稿存储方案时，将审批、历史保留和同版本编辑要求放在一起，并接受方案较高的实现成本。S5 比较定时扫描和延迟队列，结合几十个商家的规模、排期和查询复用需求选择定时扫描，同时说明分钟级延迟。

可取之处：思考体现在约束与取舍中。选中方案也可以有缺点，不需要将备选方案写成明显错误。

### Case 4｜画板和表格各自回答明确问题

S4 在表格中成对放改造前后的时序图，参与方顺序保持一致，变更调用使用不同颜色。S6 的能力地图以颜色区分两个系统与共有能力，并保留图例。

可取之处：图例说明颜色含义，对照结构减少读者寻找差异的成本。同一颜色不要同时表示个人贡献、完成状态和系统归属。

### Case 5｜平台建设接上实际使用

S7 甄诚先整理 SDK 能力，再区分本人开发的 Agent、协助业务方接入和其他业务反馈。具体业务需求能回连到 SDK 补充的功能，应用状态分别说明。

可取之处：平台价值由谁使用、如何接入、反馈了什么说明。AI 相关工作也要落到具体产品和采用情况；框架功能列表、演示和规模化收益不能混为一谈。

### Case 6｜复盘保留具体失误

S3 记录顺手优化扩大测试范围、配置兼容疏漏影响商家进组等失误；S5 记录未提前对齐 C 端文案引发返工。

可取之处：从发生过的问题推导后续做法。个人总结只归纳认识和行为变化，不重复整段技术方案，也不强行再次举 Coco 等已有案例。

### Case 7｜本项目的客观写法

以下是 VIMO 表达示例，不能标成外部答辩原文；引用事实前回读对应底稿。

1. 分层：先列 Command、Handler、Service、API、HTTP 的实际职责，再解释需要隔离哪类变化。
2. 复杂度：列任务展开后的 action、分类和面板规模，说明为何选择对应处理粒度。
3. 结果：将批量处理机制与同口径的改造前后耗时放在一起，保留 PPE、单批样本等限制。
4. 边界：区分个人身份和服务账号的真实返回，不把某一路径成功概括成全部身份可用。

## 10. 正式写作流程

先确定这一块要让评委知道什么、选哪些事实、事实如何关联，再决定使用段落、表格、画板或截图。

```text
确认当前模块和已决定的内容范围
→ 从对应 R0～R5 底稿抽取事实
→ 提出可讨论的内容草案与组织理由
→ 与用户逐块确认重点
→ 检查 Ownership 和结果口径
→ 去掉研究标签与模型文案
→ 检查去 AI 味
→ 内容明确后再定排版和画图
```

不得把 R0～R5 的 90 秒稿、标题和结论段直接拼入正文。

补充约束：

1. 局部内容明确即可写局部稿，不等待所有模块卡和全部形式决策齐备。
2. 第二模块将业务用途、个人负责范围和代表交付放在同一组内容中；避免一份业务介绍后再复制一份任务清单。
3. OpenAPI、CLI 等横向调用能力不能为了画流程图硬接在发布之后。分组关系与执行顺序分别判断。
4. 重点项目在总览中说明位置和工作内容，技术取舍留给对应重点章节；次要工作按业务归组简写。
5. 不从现有研究底稿直接锁定项目内部提纲，不提前规定必须有几张图、几项决策或几层标题。
6. 新样本的优点存入 `02`；只有适合本项目的稳定原则进入本文件。不把每个样本的章节、颜色和表头都变成强制规则。

### 画板交付方式

1. 本会话的画板交付以 `ASCII 图 + 绘图 prompt` 为主，供其他 Agent 绘制；未经用户要求，不主动派发或直接绘制飞书画板。
2. ASCII 图说明对象、链路和关联关系；绘图 prompt 补充节点文案、布局、阅读顺序、颜色与连线语义。
3. 绘图 prompt 必须区分流程步骤与对象关联，不允许绘图 Agent 为了布局擅自补充业务能力、改变关系或扩大个人职责。
4. ASCII 图和绘图 prompt 与对应内容放在一起，注明尚未完成实际绘制；绘图说明不进入正式答辩正文。

## 11. 9 月 5 日后的增量规则

新工作先写入对应底稿的`新增变化`，至少记录：

```text
时间、业务问题、我的职责、技术判断、状态、证据、结果、影响模块
```

随后判断它属于：补强现有 Case、替换候选、进入产出总览、进入规划。

9 月 5 日后的新增工作不能直接插入最终正文，防止事实和结构反复漂移。

## 12. 提交前检查

1. 业务总览能说明相关用户、业务关系和个人责任区；采用图、表或段落均可。
2. 每个主 Case 有真实问题、个人判断、落地机制、结果和边界。
3. 团队基座与个人 Owner 身份都清楚。
4. 数据口径紧邻数字。
5. 未合入和阶段验证没有写成上线。
