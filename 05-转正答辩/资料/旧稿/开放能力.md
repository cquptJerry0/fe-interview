# 3.1 VIMO CLI/Open API 开放能力

> 重构前素材快照，2026-10-13 留存，不再维护。旧目录、五级编号、逐项展开和图 Prompt 不约束本轮。只按需复用事实与资源；数据和代码状态不代表本轮已复验。当前稿件见 ../../正文/02-开放能力.md。

## 3.1.1 背景

【蓝字】业务诉求【/蓝字】

业务方已提出批量上传图片、获取资源地址后更新素材等需求，希望交给脚本或 Agent 执行。[VIMO CLI 诉求](https://bytedance.larkoffice.com/wiki/YjuJwZTydiZMcvko833cmlJFngg)还列出了面板与分类查询、素材信息修改、分级同步等操作，涉及醒图、Hypic 和醒图 PC。

业务方还希望脚本能交给其他人复用，并关心复用后以谁的身份执行、使用哪些权限。

【蓝字】外部环境【/蓝字】

lark-cli、bytedcli 已将业务操作组织成命令，Agent 可以读取说明、按任务调用，并根据结果继续执行。VIMO 可以采用同样的方式：已有操作能够覆盖的任务，由 Agent 组织执行，减少为不同任务单独开发页面入口或编写专用脚本的工作。

【蓝字】建设方向【/蓝字】

VIMO 已有一版[素材 OpenAPI](https://bytedance.larkoffice.com/wiki/Q0U5w7MS5ikSOLkv7YdcKd9AnVX)，部分业务操作已经可以由程序调用。面向 Agent 和更多业务接入，旧版仍有以下限制：

在复用已有业务处理的基础上，业务能力分为两个建设方向：

- 【蓝字】开放现有功能【/蓝字】：将查询、配置、分类维护等功能开放为接口和命令，复用原有业务规则，让 Agent、脚本及其他业务服务直接调用。
- 【蓝字】面向 Agent 开发新功能【/蓝字】：针对原页面没有覆盖的需求，补充批量处理、按指定素材或分类发布等能力，直接通过 Agent 提供给用户，不必先开发对应页面。

两类能力均配套命令和任务说明，供 Agent 调用。同时完善身份接入、权限申请与调用限流，减少手动签名和人工授权带来的接入成本。

## 3.1.3 建设开放基础设施

### 3.1.3.1 设计开放架构

【蓝字】建设目标【/蓝字】　用户、脚本和 Agent 都需要查询素材、调整面板分类、提交发布，只是组织任务的方式不同。我将这些入口共用的业务处理放在服务端，由 OpenAPI 提供调用能力，vimocli 将业务操作组织成命令，Skill 说明如何组合命令完成任务。

### 3.1.3.2 演进鉴权体系

【蓝字】降低接入成本【/蓝字】　早期道具包、分级等批量操作使用 HMAC 签名，接入方需要维护密钥、编写签名逻辑，并联系研发开通权限。面向 CLI 和 Agent 开放后，使用者既有运营人员，也有运行自动化任务的服务账号；继续沿用这套方式，每增加一个使用入口，都要重复准备身份和授权。

我接入字节云网关，复用其身份认证与路由能力，调用方不再自行处理 HMAC 签名。业务接口也有了统一的接入配置入口，国内、海外路由及鉴权配置可以集中管理。

<img name="image.png" height="1790" mime="image/png" scale="1.000000" src="F6PHbVwo5oWS5hxV9HEcELIqnvh" width="2824"/>

【蓝字】兼容个人与服务账号【/蓝字】　接入网关解决了请求如何进入服务的问题，业务侧仍需决定调用者可以执行哪些操作。当时 Kani 主要面向标准用户，开放平台的授权主要面向服务账号，单独采用任意一套都无法覆盖两类主体。因此，我保留业务侧 OpenAPI 权限，统一管理个人和服务账号的接口授权，素材操作再检查具体资源范围。

【蓝字】缩短商业化接入路径【/蓝字】　商业化希望将活动、资源位等能力快速接入 CLI，用于验证运营 Agent 流程。与素材自动化不同，这些调用与页面操作的业务差异较小，现有接口和 Kani 权限已经能够满足需求。如果每个接口都再走一遍 OpenAPI 接入，还要发布 BAM、配置网关并维护另一套授权，接入投入与这次新增能力并不相称。

<img name="image.png" height="446" mime="image/png" scale="1.000000" src="HZtVbUMgXobjD9xprqxcd7UPnog" width="1832"/>

这类需求需要补充的是程序调用入口，业务处理和授权规则都可以复用。我因此增加个人 JWT 直连：服务端识别 JWT 中的可信用户，再按原有 Kani 权限执行已有接口；客户端负责将这些接口组织成业务命令。

服务账号及需要独立开放授权的场景继续使用网关，个人直连只承接能够复用现有接口与用户权限的业务。两条路径并存，业务方按调用主体和授权需求选择。

### 3.1.3.3 细化素材权限

【蓝字】约束素材自动化的操作范围【/蓝字】　素材自动化会批量调整分类关联、更新素材配置，也会提交正式发布。接口能够处理多个面板和素材类型，而一次任务通常只需要操作其中一部分。直接授予接口调用权，无法表达这次任务究竟允许改到哪里。

【双栏开始】

【左栏】

【蓝字】限定面板与素材范围【/蓝字】　以面板分类整理为例，程序只需调整指定面板下的分类关联。即使调用的是同一个分类操作接口，也不应因此获得其他面板的操作权。

【右栏】

【蓝字】区分修改与正式发布【/蓝字】　分类调整、素材编辑与正式发布的影响不同。允许程序修改配置，不代表允许它将改动上线，修改权与发布权需要分别授予。

【双栏结束】

【蓝字】确定授权粒度【/蓝字】　我在接口权限之外增加资源授权。资源单位需要覆盖任务的主要操作范围，又不能随着每条素材的增减反复配置，因此选择业务线下的面板和素材类型，并分别设置新增、修改、发布权限。

#### 3.1.3.4.1 封装服务端接入组件

【蓝字】减少重复接入【/蓝字】　其他业务接入 OpenAPI 或个人直连时，都需要验证身份、适配现有用户上下文，并衔接业务权限。其中的验签和身份处理可以共用；如果各自实现，同一次站点适配或鉴权修复就需要在多个模块重复修改。我将公共逻辑封装进鉴权包，并配套[网关 OpenAPI 接入方案](https://bytedance.larkoffice.com/wiki/US3uwQ8XtiVtlWkgYItcg5qpnfe)和[个人直连快速接入方案](https://bytedance.larkoffice.com/wiki/GbcNwsuAzivvMakKOcxcuBBDnKc)，业务方按接入路径补充配置。

【蓝字】适配现有登录与授权【/蓝字】　个人 JWT 请求没有浏览器会话，直接进入原登录链路会被拦截；逐接口配置放行又需要持续维护。因此，身份验证安排在原登录检查之前：先验证凭证，再把可信用户转换为业务框架已有的用户上下文，让后续权限校验继续使用原来的规则。

【蓝字】核心代码【/蓝字】　中间件在业务处理前完成身份验证、授权分流、业务线处理与调用上报。以下核心逻辑省略框架注入和组件初始化，错误响应由统一函数返回。

身份验证、授权分流与调用上报（核心逻辑示意）

```typescript
async function handleRequest(request, response, next) {
  const config = appConfig.identityAuth;
  if (!config) return next();

  const authorizer = getGatewayAuthorizer(config);
  const openApi = authorizer?.resolveRequiredOpenApiTarget(request);
  const tokenHeader = (config.tokenHeader || "x-jwt-token").toLowerCase();
  const token = getHeaderValue(request.headers[tokenHeader]);

  if (!token) {
    return openApi ? reject(response, 401, "Missing JWT") : next();
  }

  const verifier = getJwtVerifier(config);
  let identity;
  try {
    identity = await verifier.verify(token);
  } catch (error) {
    logger.warn("JWT authentication failed", {
      path: request.path, error: error.message
    });
    const invalidIssuer = error instanceof IdentityJwtIssuerError;
    return reject(response, invalidIssuer ? 403 : 401,
      invalidIssuer ? "Invalid JWT Issuer" : "JWT Token Invalid");
  }

  const report = (bid, includeOpenApiEvent) => {
    const clientHeader = (config.clientHeader || "x-vimo-client").toLowerCase();
    void getTeaReporter(config).report({
      uid: identity.uid,
      path: request.path,
      bid,
      body: request.body,
      client: getHeaderValue(request.headers[clientHeader]),
      includeOpenApiEvent
    });
  };

  if (identity.identityType === "user") {
    const bid = getHeaderValue(request.headers["vimo-bid"]);
    if (openApi) {
      report(bid, false);
      return reject(response, 403, "Invalid JWT Issuer");
    }
    verifier.inject(identity, executionContainer);
    setIdentityAuthState(request, "direct_kani", identity.uid);
    report(bid, false);
    logger.info("User authenticated; Kani authorization pending");
    return next(); // 后续仍需执行 Kani
  }

  if (!authorizer) {
    logger.error("Gateway DB authorization config missing");
    return reject(response, 500, "Gateway DB authorization config missing");
  }

  let context;
  try {
    // 按方法、路径和业务线构造权限查询条件。
    context = authorizer.resolveContext(request);
  } catch (error) {
    if (error instanceof GatewayDbRequestError) {
      return reject(response, 400, error.message);
    }
    throw error;
  }

  // 先记录已验证身份的调用，缺权请求也可能进入统计。
  report(context.bid, true);
  if (!(await authorizer.hasPermission(identity.uid, context))) {
    logger.warn("No OpenAPI permission", { uid: identity.uid, ...context });
    return reject(response, 403, "No permission");
  }

  authorizer.writeBidToRequest(request, context);
  verifier.inject(identity, executionContainer);
  setIdentityAuthState(request, "gateway_db", identity.uid);
  logger.info("Gateway authenticated; OpenAPI authorization passed");
  return next(); // 后续沿用已完成的接口授权，业务仍校验资源权限
}
```

【蓝字】调用上报【/蓝字】　统一记录调用身份、接口路径、业务线和子应用。网关请求保留 OpenAPI 事件，标记为 vimocli 或 bytedcli 的调用另记 CLI 事件，两类事件分别统计。

```typescript

async function report(params) {
  const base = {
    uid: params.uid,
    url_path: params.path,
    sub_app: this.options.getPsm(),
    timestamp: Date.now().toString(),
    bid: params.bid
  };
  const events = [];

  if (params.includeOpenApiEvent) {
    events.push({
      eventName: "call_open_api",
      params: {
        ...base,
        req_body: JSON.stringify(params.body),
        auth_type: "jwt"
      }
    });
  }

  if (["vimocli", "bytedcli"].includes(params.client)) {
    events.push({
      eventName: "call_open_api_vimocli",
      params: base
    });
```

#### 3.1.3.4.2 封装 JWT 凭证工具

【蓝字】背景【/蓝字】　在建设接口自测页时，我发现字节云支持用浏览器已有登录态换取个人 JWT。利用这一能力，自测页可以直接以当前用户身份发起请求，省去手动获取、复制凭证的步骤。

【蓝字】抽取公共工具【/蓝字】　凭证获取只依赖用户登录态和目标站点，与具体测试接口无关。为了方便其他业务接入，并统一处理站点选择、凭证缓存与过期刷新，我将它抽取为 `@vimo/utils/browser`。业务方调用公共工具取得凭证，再组织自己的业务请求，无需从自测页复制一套实现。

【蓝字】对接字节云签发【/蓝字】　字节云负责登录校验和 JWT 签发，公共工具在浏览器侧携带登录态请求凭证，不自行生成 Token。

【蓝字】管理凭证有效期【/蓝字】　公共工具按国内、海外站点分别缓存 JWT，在使用时检查有效期。缓存缺失或距到期不足 60 秒时，重新向字节云请求凭证，业务入口不必自己维护刷新逻辑。

- 业务接口返回 401 时，跳过旧缓存，重新请求 JWT，并用新凭证重试一次。
- 若字节云的 JWT 获取接口返回 401，则说明字节云登录态已失效。工具将这一状态交给业务入口，由页面提供登录入口。

```typescript
async function getJwt(site, forceRefresh = false) {
  if (!forceRefresh && cacheValid(site, 60_000)) {
    return cache[site];
  }
  const response = await fetch(jwtEndpoint(site), {
    credentials: "include"
  });
  if (response.status === 401) throw loginRequired(site);
  if (!response.ok) throw jwtFetchFailed(response);
  return cacheJwt(site, response.headers.get("x-jwt-token"));
}

async function callWithJwt(site, request) {
  const result = await request(await getJwt(site));
  if (result.status !== 401) return result;
  return request(await getJwt(site, true));
}
```

### 3.1.5.3 管理并行任务

【蓝字】并行背景【/蓝字】vimocli 发展期，业务接入、鉴权、埋点和发布改造同时推进。不同任务的进度和产物分散在多个会话中，需要反复查找；将它们放进同一个长会话，又容易把上一项需求的假设带入下一项工作。

【蓝字】工作台建设【/蓝字】我基于 Mira 搭建工作台，将进度与任务入口集中展示，每项任务仍保留独立会话。

## 3.1.6 规划

【三栏开始】
【左栏】
【蓝字】优化用户 Skill【/蓝字】

结合使用记录和运营反馈，完善高频任务的操作示例、参数说明和结果检查方法。用典型任务和失败案例验证修改效果，减少 Agent 选错命令、遗漏步骤和反复询问的情况。

【中栏】
【蓝字】沉淀运营工作流【/蓝字】

与运营梳理日常重复操作，优先探索素材批量维护、分类整理、下发检查等高频流程。将已有接口组合成可复用的工作流，明确输入、操作顺序和结果核对方式，在真实任务中试用并调整。

【右栏】
【蓝字】扩展素材接口【/蓝字】

以素材业务为主，按实际需求补充查询、配置、分类维护等接口，优先解决现有能力无法完成、仍需人工处理的操作。新增接口同步提供 vimocli 命令和 Skill 说明，供后续同类任务复用。
【三栏结束】
