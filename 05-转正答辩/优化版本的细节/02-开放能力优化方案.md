# 开放能力优化方案（待讨论）

## 1. 本轮目标与边界

本专区只处理开放能力模块，不接管自我介绍、全球素材搬运、自动供给与总结规划。先保留当前大版本，再讨论目录、内容取舍、关键判断、字数和布局；这些约定确认后，才写正式优化正文并批量处理画板。

整篇答辩由用户描述的约 18000 字压到 6000–8000 字，优先 6000 多字。这是全篇目标，不是本模块字数，也不是本轮已经实测或完成的压缩结果。本模块建议暂以 **2100 字左右、2000–2400 字**设计，待全篇统筹时调整；原稿保留区、讨论记录和追问材料不计入最终主文。

本轮保留原文档、现有 WIP、本地 `正文/02-开放能力.md`，不覆盖它们。不优化、不新增画板；上一轮“8 张、正文 5 张”的建议不再作为配额，图的数量由确认后的表达任务决定。

**主线：让业务操作不只能够被程序调用，而是能在明确权限边界下，被不同环境中的脚本和 Agent 实际使用。**

沿用整体骨架的两项建设，但补足开场的业务问题、目标和结果。不是把旧稿逐段剪短，也不是把全部文字搬进图中。

最终目录暂推荐只有项目标题和两个二级标题：

- **2. VIMO 开放能力建设**
  - 章首不再细分标题：背景与目标、本人范围、代表产出、整体定位。
  - **2.1 开放业务操作**
    - 用行内小标题区分业务操作设计、接入路径选择、资源权限与公共复用。
  - **2.2 客户端与工程配套**
    - 用行内小标题区分业务命令与环境适配、云端接入、持续交付与使用观测。

暂不独立保留“背景、产出、横向复用、使用情况、公共组件、交付协作、规划”七套章节。它们的有效内容进入对应论点旁边，不等于删除这些贡献。

## 3. 分块内容、判断与布局

### 章首：业务问题、建设目标与结果

**阅读问题：为什么要做，交付了什么，谁在使用，你负责哪部分？**

- 背景保留批量运营与业务程序接入两个场景。原页面操作和早期接口不能完整满足任务组织、身份授权和多环境使用需求。
- 目标要同时包含“开放已有操作”和“补充页面未覆盖的批量／发布能力”，不能缩成给旧接口套一层 CLI。
- 交付用一段说明 OpenAPI、业务命令、用户 Skill 的分工；初始 CLI、接口生成和公共平台作为已有基础，个人增量单列一句。
- 结果只精选能体现不同价值的代表案例：老特效状态核查说明无需另建入口；分类关系批量调整说明重复操作变化。横向接入再用简短清单补覆盖，不给每个接入方都写小传。
- 总调用量、活跃身份、成功业务任务分开。当前原稿数字先留在原稿区，口径未对齐前不写进拟定成果条。

**布局建议：**通栏开场短段；两个案例并排，每例一条结果配原始证据；本人范围紧邻开场；整体图仅预留位置。案例截图不与长段落挤在狭窄表格里。

**建议篇幅：**背景、目标与范围约 250 字；代表产出与采用约 300 字。

### 2.1 开放业务操作

**阅读问题：为什么不是简单开放接口，服务端做了哪些重要判断？**

**业务目标怎样成为操作。**选择按素材或分类发布作为代表，说明调用方表达目标，服务端负责解析实际变更、校验对象并复用已有发布能力。详细解析机制需按既有方案与代码证据再核，不在本轮补造。

**不是所有业务都接同一条开放链路。**素材自动化需要独立开放授权；商业化等存量页面接口在业务语义和权限可复用时，采用个人 JWT 接入原授权链。保留“为什么不用所有接口再走一遍 OpenAPI”的成本与边界判断，而不是只摆两条路线。

**身份成立不等于有操作权。**把公共中间件的身份验证、接口授权，与业务层的资源授权区分开。素材操作限定业务线、面板／素材类型及操作，解释为什么比仅按接口更细、又不逐素材维护授权清单。

**共性抽取与业务规则的分工。**公共组件复用身份处理，素材鉴权服务复用权限查询与缺权提示；业务接口仍负责确定真实资源。创建、编辑、批量发布等是复用证据，不展开成长接口清单。

**布局建议：**少量行内小标题＋判断短段；接入路线用简短对照；鉴权和资源边界预留通栏图位；权限页面或业务接入证据就近放置。代码整体下沉到原稿／追问材料，主文最多保留解释关键判断所必需的局部，不展示整段中间件源码。

**建议篇幅：**约 750 字。重点是选择依据和职责边界，不逐项罗列组件文件。

### 2.2 客户端与工程配套

**阅读问题：为什么交付业务命令之后，还需要环境适配与持续交付？**

**稳定业务用法，集中处理接入差异。**业务命令对外表达任务，业务／协议适配负责系统差异，公共执行负责身份、站点、网络、请求与输出。接口生成保证覆盖与同步，手写命令负责语义和体验；不能把已有生成框架全归为个人新建。

**以云端 Agent 作为环境适配的代表。**页面已有身份如何随当前任务进入云端执行，是这部分的关键案例。解释沙箱可复用、身份按次注入、不落本地登录配置，以及“命令结束”和“凭证过期”不同；不再复述整条 SSO 签发流程。

**把能力交到用户手上。**用户 Skill 解决使用方法；开发 Skill 解决跨环节交付检查；流水线解决包、Skill、镜像的版本对应；自更新解决本地执行环境滞后。放成短配套区，不各占一整节，但保留必要人工确认和失败边界。

**用观测回答维护问题。**保留客户端与服务端统计范围不同，以及命令到实际请求的关联价值。看板作为已有交付证据；不把调用数据写成完整审计，不把请求数当任务完成数。

**布局建议：**客户端架构预留通栏图位；环境差异用短对照，云端接入原图与采用证据相邻；发布、更新、观测不平均分成三列长表。配套区保留最有解释力的一次交付记录，其余链接下沉。

**建议篇幅：**客户端与云端接入约 600 字；工程配套与观测约 200 字。

## 4. 旧内容如何处理

以下为建议，不是已经执行的删改。

- **背景：压缩。**保留真实业务需求与旧方式限制；lark-cli、bytedcli 的外部环境介绍压成参考依据，不另做行业科普。
- **能力交付：合并。**接口、命令、Skill 的完整说明不在开场、总览、客户端重复讲三次。接口数量只是覆盖，不代替收益。
- **业务支持与横向复用：精选＋就近放置。**章首先用代表结果，商业化接入放授权路径旁，云端运营 Agent 放环境适配旁；其他案例留原稿供追问。
- **鉴权演进、素材权限、服务端组件：按判断重组。**保留为什么采用两条路径、为什么细化资源权限、哪些共性可复用，删除同一链路的重复解释。
- **JWT 工具：归入云端接入。**主文解释凭证复用与任务身份边界；完整缓存、刷新代码及五类场景清单下沉。
- **客户端六层能力说明：收敛。**正文只解释分层的理由；接口生成、测试、观测和发布作为配套，不重复画运行链路。
- **发布、自更新、研发 Skill：保留但不平均展开。**围绕交付一致性串起作用，完整阶段列表、命令及流水线步骤下沉。
- **Mira 并行任务与长期规划：建议交全篇总结收口。**本会话不修改总结章节，只标记推荐去向；不把个人工作台自动计作开放能力业务收益。

## 5. 能力如何从材料中体现

不在标题上直接贴“架构能力、Owner 意识”等标签，而让评委从具体判断和结果中得到结论：

- 从临时业务任务识别可复用操作，而非每次新增页面入口，体现需求抽象与业务理解。
- 根据业务语义与授权需求选择不同接入路径，体现对成本、兼容性和边界的权衡。
- 分离身份、接口与资源权限，且以真实资源校验，体现正确性设计。
- 将环境差异集中在适配层，形成跨业务复用，体现架构与抽象能力。
- 同时考虑使用说明、发版、本地更新和观测，体现交付后的持续维护意识。

以上是待材料支撑的表达方向，不是已验证的能力评价；每项至少靠一个真实选择或采用证据落地，不补造收益。

## 6. 图、证据与字数的约定

- 本轮只保留图位的阅读问题、位置与范围，不锁定图数，不批量创图，也不优化原图。
- 图负责组成、边界、流程或差异，正文保留选择理由；不是把长句搬成节点来规避字数。
- 截图负责证明采用或结果；讨论方案里的图位不算已完成图。
- 主文字数包括标题、段落、列表、表格、图注，图内文字另计并检查读图负担；不把说明全部藏进图片或附录来虚假达标。
- 本轮原稿统计采用“每个汉字计 1、连续英文／数字词计 1”的工作口径，不等同飞书界面字数；图片／画板内部文字、资源名称和引用属性未计入。最终全篇须统一口径再验收。
