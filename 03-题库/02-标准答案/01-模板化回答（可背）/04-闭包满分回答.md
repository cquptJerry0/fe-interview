## Part 1｜技术讲解

### 1）一句话结论

- 闭包可以理解成：函数在定义时记住了它所在的词法作用域，所以即使外层函数已经执行结束，内部函数后续仍然能访问当时那层环境里的变量。
- 它解决的核心问题是“状态保留”和“私有封装”。
- 闭包本身不是性能问题，真正的风险在于你让闭包长期持有本来应该释放的大对象、DOM 引用或上下文，导致垃圾回收回不掉。

### 2）主链路图（ASCII）

```txt
源码写出来时
  -> 函数定义位置确定
  -> 词法作用域关系确定

运行 outer()
  -> 创建 outer 执行上下文
  -> 产生变量 count
  -> 返回 inner

只要 inner 还被外部引用
  -> inner 仍持有 outer 的词法环境
  -> count 就不会被释放
  -> 后续还能继续读写 count
```

```txt
outer()
  let count = 0
  return function inner() {
    count++
    return count
  }

inner 被外部保存
  -> outer 虽然执行结束
  -> 但 outer 环境没有立刻消失
  -> 因为 inner 还要继续访问它
```

### 3）结论证明材料

最小例子：

```js
function createCounter() {
  let count = 0

  return function () {
    count += 1
    return count
  }
}

const counter = createCounter()
console.log(counter()) // 1
console.log(counter()) // 2
```

关键不是“内部函数还能执行”，而是“它为什么还能读到上一次的 `count`”。

误判对比：

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0)
}
```

```txt
很多人会把这个坑直接背成“闭包有问题”。
更准确地说，这是闭包 + var 函数作用域共享绑定一起造成的结果。
如果改成 let，每轮循环有独立绑定，现象就不一样了。
```

### 4）工程视角

- 闭包在项目里并不稀有，防抖、节流、`once`、缓存函数、工厂函数、自定义 Hook 都会用到它。
- 所以面试高分点不是只背“函数加上它能访问的变量就是闭包”，而是能说出它为什么能保留状态，以及什么时候会带来内存压力。
- 真正危险的场景通常是事件监听、定时器、全局数组、缓存对象把闭包长期留下来，而闭包里面又抓着大对象或 DOM。
- 所以工程治理重点不是“避免闭包”，而是“避免不必要的长生命周期引用”。

### 5）常见误判点

- 不要把闭包和匿名函数画等号，命名函数一样可以形成闭包。
- 不要把调用位置和定义位置混淆，闭包依赖的是词法作用域，不是谁调用了它。
- 不要一听到内存泄漏就怪闭包，真正的问题通常是引用没有被释放。

## Part 2｜面试作答

### 1）20 秒快答

- 闭包本质上是函数记住了它定义时的词法作用域，所以外层函数结束后，内部函数仍然能访问那层环境里的变量。它的核心价值是保留状态和封装私有数据，真正的风险是长生命周期引用把本该释放的数据一直留住。

### 2）60-90 秒口语稿

- 我会把闭包讲成“词法作用域在运行时留下来的结果”。代码写出来时，函数的定义位置已经决定了它往哪层外部环境查找变量。等外层函数执行时，会创建对应的执行上下文和词法环境。如果内部函数被返回或者被外部继续引用，这个内部函数就还会持有外层环境，所以外层函数虽然执行结束了，那层环境也不会立刻释放，里面的变量后续还能被继续访问。它最常见的价值是保留状态和封装私有数据，比如计数器、防抖、节流、缓存这些都离不开闭包。闭包本身不是坏事，真正需要注意的是它如果长期持有不再需要的大对象、DOM 或上下文，就会让垃圾回收回不掉，最后表现成内存占用越来越高。

### 3）高频追问

#### 追问 1｜闭包和作用域链是什么关系？

- 作用域链回答的是“变量应该往哪找”。
- 闭包回答的是“为什么函数离开定义位置后，仍然能沿那条作用域链继续找”。
- 所以闭包的底层前提，就是 JavaScript 的词法作用域和作用域链规则。

#### 追问 2｜为什么循环里配合 `var` 容易出问题？

- 因为 `var` 是函数作用域，不会像 `let` 一样为每次循环创建独立块级绑定。
- 如果循环里注册回调，这些回调后面执行时，拿到的往往是同一个共享变量。
- 所以这不是“闭包错了”，而是你让多个闭包共享了同一个绑定。

#### 追问 3｜闭包为什么总和内存泄漏放在一起问？

- 因为闭包会延长某些变量的生命周期。
- 如果这些变量已经没用了，但外部仍然保留着闭包引用，它们就回收不了。
- 所以问题不在“闭包”这个词本身，而在“是不是存在不必要的长生命周期引用”。

#### 追问 4｜项目里哪些地方最常用闭包？

- 计数器、`once`、柯里化、防抖、节流、缓存函数、工厂函数、自定义 Hook 都很常见。
- 它们的共同点都是：需要在多次调用之间保留某个状态。

#### 追问 5｜闭包和 React 里的 stale closure 是什么关系？

- stale closure 本质上也是闭包现象。
- 回调拿到的是它创建那一刻的变量快照，如果依赖没处理好，它就可能一直读旧值。
- 所以 React 里的很多旧值问题，不是“闭包错了”，而是回调引用和依赖声明没有跟上状态变化。
