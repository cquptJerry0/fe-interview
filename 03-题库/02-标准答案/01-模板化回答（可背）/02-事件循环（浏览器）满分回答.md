## 模块 1｜主回答

### 1）一句话结论

- 浏览器事件循环可以理解成：先执行当前这轮宏任务里的同步代码，然后在当前宏任务结束时立刻清空微任务队列，之后浏览器才有机会做渲染，再进入下一轮宏任务。
- 常见宏任务有整段 `script`、`setTimeout`、I/O 回调；常见微任务有 `Promise.then`、`queueMicrotask`、`MutationObserver`。
- 面试里最关键的不是背名词，而是讲清“为什么 `Promise.then` 一定比下一轮 `setTimeout` 更早执行”。

### 2）原理图（ASCII）

```txt
一轮事件循环
  |
  +-- 取出一个宏任务
  |      |
  |      +-- 执行同步代码
  |      +-- 过程中把微任务放入队列
  |
  +-- 当前宏任务结束
  |      |
  |      +-- 清空微任务队列
  |
  +-- 浏览器获得一次渲染机会
  |
  +-- 进入下一轮宏任务
```

### 3）最小例子

```js
console.log(1)

setTimeout(() => {
  console.log(2)
}, 0)

Promise.resolve().then(() => {
  console.log(3)
})

console.log(4)
```

```txt
输出顺序：1 4 3 2

原因：
- `console.log(1)`、`console.log(4)` 属于当前宏任务里的同步代码
- `Promise.then` 进入微任务队列
- `setTimeout` 回调进入后续宏任务队列
- 当前宏任务结束后，先清空微任务，所以先输出 3，再到下一轮宏任务输出 2
```

### 4）面试口语稿

- 浏览器事件循环我会这样讲：整段 `script` 本身就是一个宏任务。执行这轮宏任务时，同步代码先跑；过程中如果遇到 `Promise.then` 这类微任务，它们不会立刻执行，而是先进微任务队列。等当前宏任务的同步代码结束后，会立刻清空微任务队列，然后浏览器才有机会去渲染页面，再进入下一轮宏任务。所以微任务的优先级不是“永远比所有任务高”，而是“在当前宏任务结束后，先于下一轮宏任务执行”。这也是为什么 `Promise.then` 通常会早于 `setTimeout(fn, 0)`。

## 模块 2｜深入展开

### 1）原理链路

```txt
题面：宏任务和微任务谁先谁后？
  -> 先分清当前执行的是哪一轮宏任务
  -> 再看这轮宏任务里产生了哪些微任务
  -> 当前宏任务结束后先清空微任务
  -> 微任务清空完，浏览器才可能渲染
  -> 然后进入下一轮宏任务
```

- 这题的关键不在“背出一张表”，而在“知道判断顺序时到底以什么为边界”。
- 这个边界就是“当前宏任务是否结束”。
- 只要当前宏任务还没结束，微任务就只是排队，不会抢占正在执行的同步代码。

### 2）业务化解释

- 项目里最常见的误判是：以为 `setTimeout(fn, 0)` 已经非常快了，但 `Promise.then` 还是会比它更早执行。
- 比如你先同步改了某些状态，又在 `Promise.then` 里读 DOM，再在 `setTimeout` 里打印日志，最终顺序往往和很多人直觉不一样。
- 另一个高频场景是“页面为什么不渲染”：如果当前宏任务很长，或者微任务队列被不断塞满，浏览器就迟迟拿不到渲染机会。
- 所以事件循环不是纯理论题，它直接关系到 UI 时机、数据更新时机和页面卡顿问题。

### 3）取舍 / 易错点

- 不要把“微任务优先于宏任务”背成绝对语句，更准确的说法是：当前宏任务结束后，先清空微任务，再进入下一轮宏任务。
- 不要忽略“渲染机会”这个环节。浏览器不是每条语句之间都渲染，而是要等当前执行栈和微任务清空后，才有机会绘制。
- 不要把浏览器事件循环和 Node 事件循环完全混为一谈，它们核心思想相通，但阶段划分并不完全一样。
- `setTimeout(fn, 0)` 也不是“立刻执行”，它只是尽快进入后续宏任务队列。

## 模块 3｜追问与详细回答

### 追问 1｜`requestAnimationFrame` 属于什么位置，为什么适合做动画？

- 它不该简单背成“宏任务”或“微任务”之一，更重要的是它的触发时机靠近浏览器下一次绘制前。
- 所以它特别适合做动画、逐帧更新和和渲染节奏相关的任务。
- 相比之下，`setTimeout` 只保证回调尽快进入后续任务队列，并不和浏览器绘制节奏强绑定。
- 这也是为什么动画类逻辑通常更推荐 `requestAnimationFrame`。

### 追问 2｜`async/await` 和微任务是什么关系？

- `async` 函数本质上是 `Promise` 语法糖。
- `await` 后面的代码，不会继续占着当前同步执行栈，而是等到对应 Promise 完成后，再以微任务的形式继续执行。
- 所以很多 `await` 的后续逻辑，本质上还是走进了微任务队列。
- 面试里如果能把它和 `Promise.then` 关联起来讲，通常会更稳。

### 追问 3｜为什么微任务太多会让页面看起来卡住？

- 因为浏览器通常要等当前宏任务执行完、微任务队列也清空后，才有机会做渲染。
- 如果微任务一直被塞进去，浏览器就会持续忙于执行它们，拿不到绘制机会。
- 用户看到的现象就是数据好像改了，但页面迟迟不刷新，或者滚动、点击变得卡顿。
- 所以微任务并不是越多越好，过度堆积一样会影响体验。

### 追问 4｜Node 里的事件循环和浏览器完全一样吗？

- 不完全一样。
- 两者核心思想类似，都是任务队列驱动，但 Node 有自己更细的阶段划分，比如 timer、poll、check 等。
- 所以面试里最稳妥的说法是：浏览器和 Node 都有事件循环，但具体阶段和某些 API 的调度细节不同。
- 不要把浏览器那套顺序原封不动套到 Node 上。

### 追问 5｜浏览器什么时候才会真正渲染页面？

- 通常要等当前这轮执行栈和微任务清空之后，浏览器才获得一次渲染机会。
- 这也是为什么同步长任务和微任务风暴都会拖慢页面刷新。
- 但“获得渲染机会”不代表每次都会立刻绘制，浏览器还会综合帧率、页面状态和内部策略决定。
- 面试里只要能讲清“渲染不会插进正在执行的同步代码中间”，基本就稳了。
