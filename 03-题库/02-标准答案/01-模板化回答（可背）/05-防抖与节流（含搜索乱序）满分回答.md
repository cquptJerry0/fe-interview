## 模块 1｜主回答

### 1）处理目标

- 这题不只是讲两个工具函数，而是要同时解决三件事：减少无效触发、保证交互流畅、避免旧请求覆盖新结果。
- 我的处理思路通常是 `触发控制 -> 请求顺序控制 -> 结果提交控制 -> 监控排查` 四层，而不是只说“我加个防抖”。
- 输入搜索框更适合防抖，滚动和拖拽这类持续高频事件更适合节流；而搜索请求乱序要靠 `AbortController`、请求序号或只提交最新响应来解决。

### 2）分层处理图（ASCII）

```txt
用户输入 / 滚动 / 拖拽
        |
        +-- 触发控制
        |      +-- 防抖：停下来再执行
        |      +-- 节流：固定间隔最多执行一次
        |
        +-- 发请求前
        |      +-- 取消旧请求 / 记录请求序号
        |
        +-- 响应回来
        |      +-- 只提交最新请求结果
        |
        +-- 上报监控
               +-- 请求次数、取消次数、失败率、耗时
```

### 3）兜底流程 / 最小方案

```js
function debounce(fn, wait) {
  let timer = null

  return function (...args) {
    clearTimeout(timer)
    timer = setTimeout(() => {
      fn.apply(this, args)
    }, wait)
  }
}

let currentController = null
let latestRequestId = 0

const search = debounce(async (keyword) => {
  latestRequestId += 1
  const requestId = latestRequestId

  currentController?.abort()
  currentController = new AbortController()

  const response = await fetch(`/api/search?q=${keyword}`, {
    signal: currentController.signal,
  })

  const data = await response.json()
  if (requestId !== latestRequestId) return

  renderList(data)
}, 300)
```

### 4）面试口语稿

- 我会先把这题拆成三个层次：第一层是触发控制，防抖适合输入搜索，等用户停下来再发；节流适合滚动、拖拽这类持续高频事件，固定间隔执行一次。第二层是请求顺序控制，搜索请求不能只靠防抖，因为网络快慢不一致，旧请求可能比新请求更晚回来，所以要么取消旧请求，要么给请求编号。第三层是结果提交控制，只允许最新请求更新页面。最后还要有监控，比如请求次数、取消次数、失败率和耗时。这样回答出来才像真实项目治理，而不是只会写一个防抖函数。

## 模块 2｜深入展开

### 1）问题拆解

```txt
高频输入 / 高频事件
  -> 会不会触发过多回调
  -> 会不会发出大量无效请求
  -> 旧请求会不会覆盖新结果
  -> 页面状态是否可恢复、可观测
```

- 防抖解决的是“不要在每次输入时都立即执行”。
- 节流解决的是“持续高频触发时，控制执行频率”。
- 搜索乱序解决的是“即使请求都发出去了，也不能让旧响应覆盖新结果”。
- 这三件事是相关但不同层次的问题，面试里要分开讲。

### 2）业务场景

- 搜索框联想词最典型：用户连续输入 `r`、`re`、`rea`、`react`，如果每次都发请求，浪费带宽，也容易乱序。
- 滚动加载、窗口缩放、拖拽移动更适合节流，因为这类交互需要“持续反馈”，不能像防抖那样等完全停下来。
- 实时筛选面板还可能混合两类问题：输入框用防抖，请求层再加取消或序号保护。
- 所以项目里很少是“只选一个词”，而是多层组合治理。

### 3）取舍 / 易错点

- 防抖不是节流的低配版，节流也不是防抖的加快版，它们服务的是不同交互目标。
- 只有防抖没有乱序保护，仍然可能出现旧请求覆盖新结果。
- 只有取消请求也不一定够，因为有些链路已经返回或不支持真正中断，这时还要做“只提交最新结果”的保护。
- 输入法组合输入、清空输入框、空关键词回退、错误态和 loading 态都要考虑，不能只写 happy path。
- 常见误区是：把这题只答成工具函数实现，而不讲用户体验和状态一致性。

### 4）专题判断

- 这题适合进入模板化回答。
- 如果继续追问 `AbortController`、React 里如何封装搜索 hook、列表加载与分页并发治理，建议补内部专题深挖卡。

### 难题加厚｜额外图

```txt
旧请求覆盖新结果的链路

输入 a   -> 请求1 -----------> 响应晚回来
输入 ab  -> 请求2 -----> 响应先回来
输入 abc -> 请求3 -------> 响应也回来

如果不做保护
  请求1 可能最后把页面覆盖成旧结果

正确做法
  只允许“最新 requestId”提交结果
```

### 难题加厚｜额外例子

```txt
搜索框
  -> 防抖 300ms
  -> 发请求前 abort 上一个
  -> 响应回来再比对 requestId

滚动监听
  -> 节流 100ms
  -> 不发请求也要保证滚动体验稳定
```

### 难题加厚｜精炼伪代码

```txt
onInput(keyword):
  debounce(runSearch, 300)

runSearch(keyword):
  currentId += 1
  id = currentId
  abort(previousRequest)
  response = fetch(keyword)
  if id != currentId:
    ignore(response)
  else:
    commit(response)
```

## 模块 3｜追问与详细回答

### 追问 1｜什么时候该用防抖，什么时候该用节流？

- 防抖更适合“停下来再做”的场景，比如搜索输入、表单校验、联想提示。
- 节流更适合“持续过程中也要有反馈”的场景，比如滚动、拖拽、resize。
- 区分它们最好的办法不是背定义，而是问自己：用户是在意“停下来后最准的一次”，还是“过程中持续有节奏的反馈”。
- 这个回答比单纯背“一个等最后一次，一个固定间隔”更像实战。

### 追问 2｜为什么搜索接口加了防抖，结果还是会乱？

- 因为防抖只控制“发请求的频率”，不控制“响应回来的先后顺序”。
- 网络快慢是不稳定的，旧请求完全可能比新请求更晚回来。
- 所以你还需要取消旧请求，或者至少给请求编号，只让最新响应更新页面。
- 这也是这题最容易丢分的点：只谈前半段，不谈结果一致性。

### 追问 3｜取消请求和忽略旧响应，哪个更重要？

- 最稳的是两者一起做。
- 取消请求可以减少无效带宽和服务端压力，但并不保证所有链路都已经真正中止。
- 忽略旧响应是最后一道状态保护，确保页面不会被旧结果污染。
- 所以工程上更推荐“双保险”，而不是二选一。

### 追问 4｜输入法组合输入要注意什么？

- 中文输入时会经历组合输入阶段，如果每个中间态都立刻触发搜索，体验通常很差。
- 实战里要结合组合输入开始和结束时机，避免把拼音中间态当成正式关键词。
- 否则你明明做了防抖，用户体验仍然可能很糟。
- 这类细节很能体现你是不是做过真实搜索框。

### 追问 5｜这题除了功能正确，还应该监控什么？

- 至少要看请求总次数、取消次数、平均耗时、错误率和空结果比例。
- 如果是核心搜索链路，还可以看用户输入到首个结果展示的时延。
- 这样你才能判断是防抖时间过短、过长，还是后端响应本身有问题。
- 所以这题不是只写函数，更是一次交互和链路治理题。
