## 模块 1｜主回答

### 1）一句话结论

- `key` 的作用不是单纯优化性能，而是给列表项一个稳定身份，让框架在 diff 时知道“这是原来的那个节点”，还是“应该新建 / 移除的节点”。
- 如果用 `index` 当 key，在中间插入、删除、排序时，后续项的 key 会整体漂移，框架就可能把旧节点状态错误复用到新位置上。
- 所以 `index` 只有在列表完全静态、不增删、不排序、没有本地状态依赖时才勉强可接受；只要列表会变，优先用稳定业务 id。

### 2）原理图（ASCII）

```txt
旧列表
index: 0   1   2
key:   0   1   2
item:  A   B   C

头部插入 X 后
index: 0   1   2   3
key:   0   1   2   3
item:  X   A   B   C

问题：
框架看到 key=0 还在，就可能把旧 A 的节点复用给新 X
后面节点也跟着整体错位
```

### 3）最小例子

```jsx
{list.map((item, index) => (
  <InputRow key={index} defaultValue={item.value} />
))}
```

```txt
如果每一行都有自己的输入状态，在头部插入一项后：
- 原来第二行的状态可能跑到第三行
- 光看列表内容也许没问题
- 但输入框值、选中态、动画态会出现明显错位
```

### 4）面试口语稿

- `key` 不能随便用 `index`，根因不是“React 不喜欢”，而是框架在 diff 列表时需要一个稳定身份。`key` 稳定，框架才知道哪个节点该复用，哪个该新建；如果用 `index`，一旦中间插入、删除、排序，后面所有项的 key 都漂了，旧节点状态就可能被错误复用到新位置上，最典型的就是输入框值、组件内部状态、动画状态错位。所以 `index` 只有在完全静态列表里才勉强能用；只要列表会变，优先用业务唯一 id，实在没有就自己生成稳定 id，也不要用位置当身份。

## 模块 2｜深入展开

### 1）原理链路

```txt
为什么 key 很重要？
  -> 列表 diff 不是只看内容
  -> 还要识别节点身份
  -> 身份稳定才能正确复用旧节点
  -> index 漂移会让身份判断失真
  -> 最终表现成状态错位
```

- 这题如果只答“因为性能不好”，其实是不够的。
- 更本质的是：框架的 diff 需要用 `key` 把旧节点和新节点对上号。
- 一旦对号关系错了，错误就不只是多渲染几次，而是状态被复用到错误的位置。

### 2）业务化解释

- 最典型的业务场景是表单列表、可编辑表格、拖拽排序、Todo 列表。
- 这些场景里的每一行通常都有内部状态，比如输入值、展开态、选中态、动画态。
- 如果 key 用 `index`，在列表头部插入一项或者拖拽排序后，这些状态就很容易串位。
- 所以这题最好的讲法不是抽象概念，而是直接举“输入框串位”的例子。

### 3）取舍 / 易错点

- `key` 问题不是纯性能问题，它首先影响正确性。
- 静态列表、纯展示、没有内部状态依赖时，用 `index` 才有可能问题不大。
- 只要有插入、删除、排序、筛选、局部状态，`index` 就不稳。
- 如果没有后端 id，可以在数据进入前端时生成并持久化一个稳定 id，而不是每次渲染时临时算位置。
- 常见误区是：只会背“不要用 index”，但举不出任何具体 bug 表现。

### 4）深挖判断

- 这题可以进入模板化回答。
- 如果继续追问 diff 细节、节点复用策略、受控 / 非受控输入状态错位，建议补内部专题深挖卡。

### 难题加厚｜额外图

```txt
稳定 key
old: [A(id=101), B(id=102), C(id=103)]
new: [X(id=999), A(id=101), B(id=102), C(id=103)]

框架知道：
- X 是新增
- A/B/C 是原节点平移复用

index key
old: [A(0), B(1), C(2)]
new: [X(0), A(1), B(2), C(3)]

框架误以为：
- 0 还是旧节点
- 1 还是旧节点
- 2 还是旧节点
-> 状态错位
```

### 难题加厚｜额外例子

```jsx
const list = [
  { id: 'temp-1', value: 'React' },
  { id: 'temp-2', value: 'Vue' },
]

{list.map((item) => (
  <InputRow key={item.id} defaultValue={item.value} />
))}
```

- 就算后端暂时没给 id，也可以在前端入库时生成稳定 id，只要它在这条数据生命周期内不变就行。

### 难题加厚｜精炼伪代码

```txt
oldMap = map oldChildren by key

for each newChild in newChildren:
  if oldMap has newChild.key:
    reuse old node
  else:
    create new node

old nodes not matched:
  remove
```

## 模块 3｜追问与详细回答

### 追问 1｜什么时候用 `index` 勉强还能接受？

- 当列表完全静态、不插入、不删除、不排序，也没有依赖节点身份的局部状态时，问题通常不明显。
- 比如一组固定文案纯展示，且顺序永远不变，这种场景影响会小很多。
- 但只要列表一旦可能变化，`index` 就不再稳。
- 所以更好的表达不是“绝对不能用”，而是“动态列表里不要用”。

### 追问 2｜`key` 问题只是性能问题吗？

- 不是，首先是正确性问题。
- 性能只是其中一个侧面，更严重的是状态可能错位复用。
- 输入框值串位、动画状态跑错、组件内部 state 对不上，都是典型表现。
- 这也是为什么这题不能只背成“性能优化”。

### 追问 3｜React 和 Vue 在 `key` 上的思路一样吗？

- 具体实现细节不完全一样，但核心思想很接近：列表 diff 需要稳定身份来正确复用节点。
- 所以这不是某个框架独有的怪规矩，而是虚拟 DOM / 列表 diff 普遍要解决的问题。
- 面试里这样回答更稳，不会把问题说窄。
- 真正要深挖时，再分别讲各自实现细节。

### 追问 4｜如果后端没有给 id，该怎么生成稳定 key？

- 可以在数据进入前端时生成一个稳定 id，并跟着这条数据一起存活，而不是每次 render 时临时重新生成。
- 比如在本地新增一行待提交数据时，先生成一个 `temp-id`。
- 关键不是 id 来自哪里，而是它在这条数据生命周期里不能变。
- 位置索引之所以不行，就是因为它会随列表结构变化而变化。

### 追问 5｜如果 key 变了，会发生什么？

- 对框架来说，key 变了往往就意味着“这不是原来的节点了”。
- 那它更可能卸载旧节点、再挂载新节点，而不是复用原节点。
- 所以 key 不稳定，不仅会让状态错位，还可能导致组件重复挂载、动画重置、输入焦点丢失。
- 这也是为什么 key 一定要稳定，而不是随手拼一个会变的值。
