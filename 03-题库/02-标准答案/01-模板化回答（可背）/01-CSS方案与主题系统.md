## 模块 1｜主回答

### 1）选择结论

- 这题不能答成“哪种 CSS 方案最好”，而要答成“什么场景怎么选”。
- 如果目标是开发效率、规范统一、主题切换稳定，我会优先用 `Tailwind + CSS Variables`。
- 如果目标是样式隔离清晰、组件边界明确，我会优先用 `CSS Modules`。
- 只有在确实需要运行时动态样式、主题与 props 强绑定时，我才会考虑 `CSS-in-JS`。
- 多主题系统不要直接在组件里写颜色判断，而是要走 `设计令牌 -> 语义变量 -> 组件消费` 三层结构。

### 2）选择图 / 决策树（ASCII）

```txt
先看项目目标
  |
  +-- 要高效开发、统一规范、低运行时成本
  |      -> Tailwind / 原子类方案
  |
  +-- 要样式隔离清晰、组件本地维护简单
  |      -> CSS Modules
  |
  +-- 要运行时根据 props 动态生成复杂样式
         -> CSS-in-JS（谨慎用）
```

```txt
主题系统不要直接落到组件判断

品牌色 / 灰阶 / 间距 / 圆角
          |
          v
      设计令牌
          |
          v
  主题映射（light / dark / brandA）
          |
          v
  语义变量（--color-text-primary）
          |
          v
  组件消费（Button / Card / List）
```

### 3）最小对比表 / 最小例子

```txt
Tailwind
  关键词：效率高、约束强、运行时成本低

CSS Modules
  关键词：局部作用域、边界清晰、心智稳定

CSS-in-JS
  关键词：动态强、表达力高、运行时成本更高
```

```css
  --color-bg-page: #ffffff;
  --color-text-primary: #111111;
  --space-page-x: 16px;

[data-theme='dark'] {
  --color-bg-page: #111111;
  --color-text-primary: #f5f5f5;
}

.page {
  background: var(--color-bg-page);
  color: var(--color-text-primary);
  padding-inline: var(--space-page-x);
}
```

```txt
Tailwind + CSS Variables 的常见组合：
布局 / 间距 / 原子类 -> Tailwind
主题色 / 语义色 / 品牌切换 -> CSS Variables
```

### 4）面试口语稿

- 我不会上来就说哪种 CSS 方案绝对最好，而是先看团队规范、样式隔离需求、运行时动态程度和主题扩展成本。中后台或者设计规范强的项目，我更倾向 `Tailwind + CSS Variables`，因为开发效率高、统一性强，而且主题切换稳定。组件边界清晰、需要本地样式隔离时，我会用 `CSS Modules`。`CSS-in-JS` 不是不能用，但我只会在确实需要运行时动态样式时再用，因为它通常会带来额外运行时成本。多主题系统我一定会抽成 `设计令牌 -> 主题映射 -> 语义变量 -> 组件消费` 这条链路，组件里不直接写具体颜色值，这样后面新增主题时不用重写组件。

## 模块 2｜深入展开

### 1）对比维度

- 隔离性：样式是不是容易串。
- 运行时成本：样式是在构建时确定，还是运行时生成。
- 动态能力：能不能方便表达基于状态和 props 的动态样式。
- 团队协作：规范是否统一，新成员是否容易接手。
- 主题扩展：新增主题时，是不是只改变量映射就行。

```txt
方案差异不要只看“写法像不像”

构建期更重
  Tailwind / CSS Modules
    -> 运行时更轻

运行期更重
  CSS-in-JS
    -> 动态表达更强
    -> 但也更吃运行时、调试链路和注入顺序
```

### 2）选项本体拆解

- `Tailwind` 本质是原子类和设计约束体系。优势是统一和高效，缺点是类名容易变长，对抽象能力有要求。
- `CSS Modules` 本质是构建时做局部作用域映射。优势是样式边界清晰、运行时几乎没负担，缺点是主题和动态样式表达不如变量体系自然。
- `CSS-in-JS` 本质是把样式表达拉到 JavaScript 里。它适合强动态样式，但如果大量运行时生成样式，会增加性能和调试成本。
- `CSS Variables` 不是完整 CSS 方案，而是主题系统的核心载体。真正好用的主题切换，关键不在“选哪个库”，而在变量层是否抽得对。

```txt
错误做法：主题判断散落在组件里

Button -> if (dark) 用 #fff else #111
Card   -> if (dark) 用 #222 else #fff
List   -> if (dark) 用 #333 else #f8f8f8

结果：
  主题一多
    -> 组件里到处是判断
    -> 改色要全仓搜
    -> 很难保证口径一致
```

```txt
推荐做法：组件只消费语义变量

Button / Card / List
        |
        v
color: var(--color-text-primary)
background: var(--color-bg-surface)
        |
        v
切主题时只改变量映射，不改组件实现
```

### 3）取舍 / 易错点

- 不要把“主题”理解成一组颜色表，真正稳定的是语义变量，不是直接改十几处具体颜色。
- 不要在组件里写 `isDark ? '#fff' : '#111'` 这种判断，否则主题一多，组件层会迅速失控。
- `Tailwind` 和 `CSS Modules` 不是互斥关系，完全可以 `Tailwind` 负责布局原子类，`CSS Modules` 负责局部复杂样式。
- `CSS-in-JS` 的问题不只是性能，还包括调试链路、样式注入顺序和运行时依赖。
- 主题切换不仅要“颜色变了”，还要验证暗色模式下对比度、禁用态、hover 态和图标资源是否都对齐。
- 首屏主题切换还要考虑闪烁问题；如果主题应用得太晚，用户会先看到默认主题，再看到目标主题。

## 模块 3｜追问与详细回答

### 追问 1｜`Tailwind` 和 `CSS Modules` 是二选一吗？

- 不是。
- `Tailwind` 适合快速表达布局、间距、字号、颜色等通用原子能力。
- `CSS Modules` 适合承接局部复杂样式、伪元素、动画和难以拆成原子类的结构样式。
- 工程上很常见的做法就是两者结合，而不是强行站队。

### 追问 2｜为什么多主题更推荐 `CSS Variables`？

- 因为主题切换本质上是“变量映射切换”，不是“组件逻辑切换”。
- `CSS Variables` 可以让组件层保持稳定，只在根节点或作用域节点切换变量值。
- 这样新增主题时，主要改变量表，不需要逐个翻组件。
- 这比在组件里写主题判断更容易维护，也更适合设计令牌体系。

### 追问 3｜什么时候才值得用 `CSS-in-JS`？

- 当样式和组件状态、运行时 props、主题对象强绑定，而且这种动态能力真的高频使用时，才值得用。
- 如果只是为了“把样式写进 JS”，通常收益并不高。
- 很多场景用 `CSS Variables`、类名切换、`CSS Modules` 就已经能解决问题。
- 所以关键不是它能不能用，而是它带来的额外成本是否值得。

### 追问 4｜设计令牌和语义变量有什么区别？

- 设计令牌更偏基础能力，比如品牌主色、灰阶、圆角、间距等级。
- 语义变量更偏业务和组件消费语义，比如 `--color-text-primary`、`--color-bg-surface`。
- 基础令牌负责“原材料”，语义变量负责“组件到底应该拿什么用”。
- 真正稳定的主题系统，组件层应该尽量依赖语义变量，而不是直接依赖基础色值。

### 追问 5｜怎么避免页面首屏主题闪烁？

- 关键是尽早确定主题，并在首屏渲染前把对应主题标记挂到根节点，比如 `data-theme`。
- 如果主题来自本地存储或用户设置，应尽量在应用挂载前读取并应用。
- 否则就会先按默认主题渲染一遍，再切到目标主题，用户看到的就是闪烁。
- 所以主题系统不只是样式问题，也涉及初始化时机。
