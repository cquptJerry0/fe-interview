## 这题在问什么

这题表面在问“你喜欢哪种 CSS 写法”，本质在问两件事：
- 你有没有一套清晰的 CSS 方案选择标准
- 你能不能把“多主题”做成稳定的设计令牌系统，而不是零散改颜色

## 60 秒直答

我不会一上来就说某个方案最好，而是先看团队和业务约束。中后台追求开发效率和统一规范，我更偏向 `Tailwind + CSS Variables`；组件隔离要求强时会用 `CSS Modules`；确实需要运行时样式表达和强动态性时才考虑 `CSS-in-JS`。多主题我不会直接改组件里的颜色值，而是先抽设计令牌，再映射成 CSS Variables，通过 `data-theme` 或根节点 class 切主题。这样组件层只消费语义变量，不关心主题细节。

## 核心机制

- 方案选择看 4 个维度：隔离性、运行时成本、团队协作、主题扩展
- 主题系统看 3 层：设计令牌 -> 语义变量 -> 组件消费
- 组件层只用 `var(--color-text-primary)` 这种语义变量，避免写死具体颜色

## 最小例子

```css
:root {
  --color-bg-page: #ffffff;
  --color-text-primary: #111111;
}

[data-theme='dark'] {
  --color-bg-page: #111111;
  --color-text-primary: #f5f5f5;
}

.page {
  background: var(--color-bg-page);
  color: var(--color-text-primary);
}
```

## 业务 / 验证

如果是后台系统，我会强调：主题切换成功不是“颜色变了”就算完，还要验证：
- 组件有没有漏用硬编码颜色
- 新增主题时需不需要改组件代码
- 暗色模式下对比度和可读性是否达标

## 常见追问

- `Tailwind` 和 `CSS Modules` 是二选一吗？
- 为什么我不推荐“组件里直接写主题判断”？
- 运行时切主题为什么 CSS Variables 比重新生成样式更稳？
- 设计令牌和语义变量有什么区别？

## 易错点

- 把“主题”理解成一组颜色表，而不是一套令牌系统
- 组件里写死颜色值，后面主题扩展非常痛苦
- 方案选择只谈个人偏好，不谈团队约束
