## 模块 1｜主回答

### 1）选择结论

- 这题不能答成“哪个命令更高级”，而要答成“什么协作场景怎么选”。
- `merge` 适合保留真实分叉历史，尤其是多人共享分支、公共分支协作时更稳。
- `rebase` 适合个人分支整理历史，让提交线性化，但因为会改写提交历史，不适合在多人共用远端分支上乱用。
- `stash` 适合临时切任务时快速收起未完成改动，不适合把它当长期存储区。

### 2）选择图 / 决策树（ASCII）

```txt
你要解决什么问题？
  |
  +-- 我要把两条分支合到一起，且保留真实历史
  |      -> merge
  |
  +-- 我要在个人分支整理提交，让历史更线性
  |      -> rebase
  |
  +-- 我现在代码写到一半，临时要切任务
         -> stash

另一个关键判断
  这是不是多人共享远端分支？
    |
    +-- 是 -> 优先 merge，谨慎 rebase
    +-- 否 -> 个人分支可用 rebase 整理历史
```

### 3）最小对比表 / 最小例子

```txt
merge
  关键词：合并两条历史、可能产生 merge commit、历史完整

rebase
  关键词：改写提交基底、重放提交、历史更线性

stash
  关键词：临时收起工作区 / 暂存区改动、短期切换任务
```

```bash
git fetch origin

git merge origin/main
# 或

git rebase origin/main

git stash push -m "half-done search panel"
git stash pop
```

### 4）面试口语稿

- 我会先把分支讲成“指向 commit 的引用”，再讲 `merge`、`rebase`、`stash`。`merge` 是把两条历史合并在一起，通常会保留真实分叉关系，所以多人协作和公共分支更稳。`rebase` 是把当前分支的提交搬到新的基底上重新播放，历史会更线性，但提交哈希会变，所以更适合个人分支整理历史，不适合在别人也在用的远端分支上随便做。`stash` 我把它当短期临时工作栈，适合突然要切任务时先把没做完的改动收起来，但不建议长期堆很多条，不然最后自己也容易忘。

## 模块 2｜深入展开

### 1）对比维度

- 历史形态：是否保留真实分叉。
- 提交哈希：是否改写已有提交。
- 协作风险：是否会影响别人已拉取的历史。
- 冲突处理时机：是在一次合并点解决，还是在重放过程中逐个解决。
- 使用目标：是整合历史，还是临时收起未提交改动。

### 2）选项本体拆解

- `merge` 的本质是把两个分支头对应的历史整合起来，必要时生成一个新的 merge commit。优点是历史真实，缺点是提交图可能更分叉。
- `rebase` 的本质不是“合并”，而是“把提交换个基底重新应用一遍”。因此新的提交和旧提交虽然内容可能一样，但哈希已经不是同一个对象了。
- `stash` 的本质是把当前工作区和暂存区状态压到一个临时栈里，让工作目录回到相对干净状态，方便你切分支或切任务。
- 所以这三者不是同级替代关系，而是解决不同问题的三把工具。

### 3）取舍 / 易错点

- `merge` 不是“更笨”，它的价值是保留真实协作历史。
- `rebase` 不是“绝对更高级”，它只是更适合整理个人分支历史。
- 如果在多人共享远端分支上 `rebase` 之后强推，别人本地历史就会和远端产生明显冲突。
- `stash` 很适合短期切换，但不建议长期堆很多条，否则很容易丢上下文。
- 面试里不要把分支说成“代码副本”，更准确地说，它是指向某个 commit 的引用。

## 模块 3｜追问与详细回答

### 追问 1｜为什么 `rebase` 之后提交哈希会变？

- 因为 Git 的 commit 哈希不只和代码内容有关，还和父提交、时间、元数据等一起参与计算。
- `rebase` 的过程本质上是把原提交基于新的父提交重新创建一遍。
- 所以即使你觉得“改动内容没变”，它也已经是新的 commit 对象了。
- 这也是为什么 `rebase` 会被归类为改写历史。

### 追问 2｜为什么多人共享远端分支上不要随意 `rebase`？

- 因为别人已经基于旧历史开发和拉取了代码。
- 你一旦改写并强推，远端历史就和大家本地历史不一致，后续拉取和合并会变得很混乱。
- 这不是 `rebase` 不能用，而是它更适合你独享的那条分支。
- 所以面试里最稳的说法是：个人分支整理历史可以 `rebase`，公共分支协作更谨慎。

### 追问 3｜`merge` 冲突和 `rebase` 冲突处理思路有什么差别？

- `merge` 更像在一个合并点上把两边差异统一解决。
- `rebase` 则是在“重放提交”的过程中，可能每重放一个提交就要解决一次冲突。
- 所以 `merge` 冲突更集中，`rebase` 冲突更偏过程化。
- 你选哪种，不只是看命令偏好，也看你希望怎么理解和处理冲突。

### 追问 4｜`stash` 和临时 commit 怎么选？

- 如果只是短时间切任务，而且这批改动还不值得形成明确提交，`stash` 很方便。
- 如果这批改动已经有阶段性意义，或者你希望它能进入正式历史、可回顾、可分享，那临时 commit 往往更稳。
- 所以 `stash` 更像短期工作栈，不应该承担长期存档职责。
- 面试里这样答，会比单纯说“`stash` 就是临时保存”更完整。

### 追问 5｜`stash pop` 出问题了还能找回吗？

- 先不要慌，很多时候 `stash` 记录并没有立刻彻底消失。
- 可以先看 `git stash list`，确认记录是否还在；如果是 `pop` 后出冲突，也要先解决冲突，不要误以为内容没了。
- 就算列表里看不到，某些情况下也还能通过 reflog 或底层对象排查回收，但那已经偏进阶。
- 所以最稳妥的实践还是：重要改动不要长期只放在 `stash` 里。
