## 模块 1｜主回答

### 1）一句话结论

- 事件委托就是不把监听器绑在每个子节点上，而是绑到共同父节点上，利用事件冒泡统一处理子元素事件。
- 它最适合列表、表格、动态增删节点这类场景，因为节点新增后不用重新逐个绑定监听器。
- 事件委托之所以常和冒泡一起问，是因为它成立的核心前提之一，就是事件能从目标节点冒泡到父节点。

### 2）原理图（ASCII）

```txt
ul.list 绑定一个 click 监听器
  |
  +-- li[data-id='1']
  +-- li[data-id='2']
  +-- li[data-id='3']

点击某个 li
  -> 事件先发生在 li
  -> 再冒泡到 ul.list
  -> 父节点监听器里根据 event.target / closest 判断点到了谁
```

### 3）最小例子

```js
const list = document.querySelector('.list')

list.addEventListener('click', (event) => {
  const item = event.target.closest('[data-id]')
  if (!item || !list.contains(item)) return

  console.log('clicked id:', item.dataset.id)
})
```

### 4）面试口语稿

- 事件委托我会这样讲：不是给每个子节点都绑监听器，而是把监听器绑在共同父节点上，利用事件冒泡统一处理。这样做有两个直接好处：第一，减少重复绑定；第二，动态新增节点时不用重新一个个挂监听器。它和冒泡一起问，是因为委托的核心基础就是事件能从真正点击的子节点冒泡到父节点。实际写代码时，我不会直接信任 `event.target`，而是会结合 `closest` 找到符合条件的目标节点，避免点到内部图标、文字时判断错位。

## 模块 2｜深入展开

### 1）原理链路

```txt
为什么父节点能处理子节点点击？
  -> 因为点击事件先发生在子节点
  -> 然后沿 DOM 树往外冒泡
  -> 父节点监听器拿到事件对象
  -> 再反查真正命中的子项
```

- 事件委托本质不是“偷懒少绑几个事件”，而是利用传播模型做统一入口处理。
- 这也是为什么它跟事件流题天然连在一起。
- 如果你不知道事件怎么冒泡，就很难把委托讲完整。

### 2）业务化解释

- 列表、表格、树组件、菜单、标签流都很适合事件委托。
- 这些场景里的子项数量可能很多，而且会动态增删，如果每个都单独绑定，维护成本会更高。
- 事件委托还能让交互入口更集中，比如整张卡片点击、按钮点击、删除图标点击都可以在一个地方统一分发。
- 所以它的价值不只是性能，还包括动态性和维护性。

### 3）取舍 / 易错点

- 委托不是所有事件都适合，前提是这个事件要能冒泡，或者你知道替代方案。
- 不要直接拿 `event.target` 当最终目标，真实点击点可能是图标、文字、子元素，通常要配合 `closest`。
- 也不要把委托说成“绝对性能更好”，更准确地说，它在大量同构节点和动态节点场景下更有工程价值。
- 如果某个子节点内部调用了 `stopPropagation`，父节点委托逻辑就可能收不到事件。

### 4）深挖判断

- 这题可以进入模板化回答。
- 如果继续追问非冒泡事件怎么处理、合成事件系统怎么做委托，建议补内部专题深挖卡。

## 模块 3｜追问与详细回答

### 追问 1｜为什么事件委托通常依赖冒泡，而不是捕获？

- 因为最常见的委托模式，是让事件先在真正的目标节点上发生，再一路冒泡到父节点统一处理。
- 这样父节点拿到事件时，更容易基于最终命中的子元素做判断。
- 捕获阶段也不是完全不能做，但大多数列表点击类场景并不需要这么早介入。
- 所以日常说事件委托，默认就是基于冒泡在讲。

### 追问 2｜动态新增节点为什么特别适合委托？

- 因为监听器绑在父节点上，子节点增删不影响父节点监听器本身。
- 新节点只要符合 DOM 结构和选择规则，天然就能被同一套逻辑接住。
- 这比你每次新增节点后都重新手动绑定一次更省心。
- 所以它在列表、树、菜单这种动态结构里很常见。

### 追问 3｜哪些事件不适合直接这么委托？

- 核心要先看这个事件是不是适合靠冒泡往上带。
- 像 `focus`、`blur` 这类就不能简单照搬点击事件那套理解。
- 所以当某个事件委托失效时，第一步不是怀疑代码，而是先确认这个事件本身的传播特性。
- 这就是边界意识。

### 追问 4｜为什么要配合 `closest`，不能只看 `event.target`？

- 因为用户点到的往往不是你定义的那个“整块业务节点”，而是里面的图标、文字、图片。
- 如果只看 `event.target`，很容易把这些内部元素误认为最终业务目标。
- `closest` 能帮你沿着 DOM 往上找最近的符合条件节点，判断会稳很多。
- 这也是事件委托实战里最常见的小细节。

### 追问 5｜事件委托的价值只是减少监听器数量吗？

- 不只是。
- 减少重复绑定当然是一个好处，但更重要的是动态节点天然可接入，以及交互逻辑入口更集中。
- 当一个列表项里有多种点击动作时，委托还能让你在一个地方统一分发。
- 所以它的工程价值常常大于“省几个监听器”这件事本身。
