## 这题在问什么

核心不是背定义，而是看你知不知道：
- 为什么列表场景常用事件委托
- 它依赖的是哪个传播阶段
- 如何准确定位到真正被点击的子元素

## 60 秒直答

事件委托就是把原本绑在多个子节点上的事件，统一绑到它们的公共父节点上，利用事件冒泡在父节点里统一处理。它适合列表、多动态节点场景，优点是减少监听器数量、方便处理新增节点。实现时不能只看 `event.target` 就结束，最好配合 `closest()` 找到真正符合条件的元素。

## 核心机制

- 子节点点击后，事件会沿着冒泡链往父节点传
- 父节点收到事件后，根据 `target` / `closest` 判断点的是谁
- 因为监听绑在父级，所以后续新增子节点通常也能复用逻辑

## 最小例子

```js
list.addEventListener('click', (event) => {
  const button = event.target.closest('[data-action="delete"]')
  if (!button) return
  const item = button.closest('[data-id]')
  console.log('delete item', item.dataset.id)
})
```

## 业务 / 验证

在消息列表、表格、菜单项很多的页面里，事件委托很适合。验证时我会看两件事：
- 新增节点后是否不用重新绑事件
- 是否会误点到父容器里别的元素，导致逻辑串掉

## 常见追问

- 事件委托为什么通常依赖冒泡，不依赖捕获？
- `event.target` 和 `currentTarget` 有什么区别？
- 什么场景不适合事件委托？
- React 里还需要手写很多委托吗？

## 易错点

- 把 `target` 和 `currentTarget` 混淆
- 不用 `closest()`，导致嵌套元素点击判断失真
- 忽略某些不冒泡事件的限制
