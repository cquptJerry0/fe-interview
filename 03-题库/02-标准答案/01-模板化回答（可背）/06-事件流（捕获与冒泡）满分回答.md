## 模块 1｜主回答

### 1）一句话结论

- DOM 事件传播通常分三段：捕获阶段、目标阶段、冒泡阶段。
- 捕获阶段是事件从外往里走到目标节点，冒泡阶段是事件从目标节点再往外层节点返回。
- 大多数业务逻辑写在冒泡阶段，捕获阶段更适合做提前拦截、埋点或某些全局控制。
- 面试里不要只背“先捕获后冒泡”，而要讲清楚代码为什么会按这个顺序执行。

### 2）原理图（ASCII）

```txt
window
  -> document
    -> html
      -> body
        -> div.parent
          -> button.target

捕获阶段：window -> ... -> div.parent -> button.target
目标阶段：button.target
冒泡阶段：button.target -> div.parent -> ... -> window
```

### 3）最小例子

```js
const parent = document.querySelector('.parent')
const button = document.querySelector('.target')

parent.addEventListener('click', () => {
  console.log('parent bubble')
})

parent.addEventListener('click', () => {
  console.log('parent capture')
}, true)

button.addEventListener('click', () => {
  console.log('button bubble')
})
```

```txt
点击 button 时，常见输出顺序：
parent capture -> button bubble -> parent bubble
```

### 4）面试口语稿

- 事件流我会分成捕获、目标、冒泡三段来讲。事件发生后，不是直接只在目标节点执行，而是先沿着 DOM 树从外往里走一遍捕获阶段，到目标节点后进入目标阶段，然后再从里往外冒泡。大部分业务监听器默认都写在冒泡阶段，所以我们平时更容易感知到冒泡。捕获阶段一般用在更早的拦截、埋点或者某些全局控制。面试里我会顺手补一句：`stopPropagation` 阻止的是继续传播，`preventDefault` 阻止的是默认行为，这两个不要混。

## 模块 2｜深入展开

### 1）原理链路

```txt
为什么一个点击会触发多层监听？
  -> 因为事件不是只待在目标节点
  -> 它会沿 DOM 路径传播
  -> 先捕获到目标
  -> 再从目标冒泡回外层
```

- 传播路径的存在，决定了父节点也能感知子节点上的事件。
- 这也是事件委托、全局埋点、外层统一拦截这类模式的基础。
- 如果只会背“捕获和冒泡”，但讲不出它为什么重要，答案就会很空。

### 2）业务化解释

- 列表点击、弹窗关闭、菜单收起这类逻辑，常常依赖冒泡把事件带到父节点。
- 全局埋点、路由切换前的拦截、某些容器级行为控制，则可能会用到捕获阶段。
- 实战里更常见的是：你明明只点了子元素，为什么父元素也响应了？这本质就是冒泡行为。
- 所以这题跟真实项目非常接近，不是纯概念题。

### 3）取舍 / 易错点

- 默认监听器大多工作在冒泡阶段，所以日常业务代码通常先从冒泡理解起。
- 不要把 `stopPropagation` 和 `preventDefault` 混成一件事，一个管传播，一个管默认行为。
- 也不要以为所有事件都会完整冒泡，像 `focus`、`blur` 这类就有特殊性。
- 捕获阶段不是更“高级”，只是更早；要不要用，取决于你是否需要在事件到目标前介入。

## 模块 3｜追问与详细回答

### 追问 1｜`event.target` 和 `event.currentTarget` 有什么区别？

- `event.target` 是真正触发事件的那个节点。
- `event.currentTarget` 是当前正在执行监听器的那个节点。
- 在事件委托里，这两个值往往不一样：子元素触发，父元素处理。
- 面试里能举出这个例子，通常就说明你不是只会背传播顺序。

### 追问 2｜`stopPropagation` 和 `preventDefault` 有什么区别？

- `stopPropagation` 阻止事件继续沿传播路径往下走。
- `preventDefault` 阻止浏览器默认行为，比如链接跳转、表单提交。
- 一个控制传播链路，一个控制浏览器默认动作。
- 它们经常一起出现，但语义完全不同。

### 追问 3｜为什么大多数业务监听器默认写在冒泡阶段？

- 因为冒泡更符合“子元素触发，父容器统一处理”的常见业务模式。
- 事件委托也依赖冒泡，所以很多列表、表格、菜单场景天然适合冒泡阶段。
- 相比之下，捕获阶段更偏提前介入，不是大多数业务的默认需求。
- 所以你平时更常接触到冒泡，并不奇怪。

### 追问 4｜什么时候会主动用捕获阶段？

- 当你需要在事件到达目标前更早拦截，或者做更外层的统一处理时，会考虑捕获。
- 比如某些全局埋点、全局手势、容器级行为判断，捕获阶段会更早拿到事件。
- 但它不是为了“更强”，而是为了“更早”。
- 没有这个需求时，没必要强行用捕获。

### 追问 5｜不是所有事件都会冒泡，这句话怎么理解？

- 这句话是在提醒你：事件传播有通用规律，但具体事件还有各自特性。
- 例如 `focus`、`blur` 的行为就和常见点击事件不完全一样。
- 所以项目里遇到“为什么委托没生效”，第一反应应该是先确认这个事件是否适合用冒泡处理。
- 也就是说，传播模型要会背，更要知道边界。
