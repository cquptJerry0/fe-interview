## 逐题答案

### 1. 高德 SDK 提供的地图插件是由什么绘制的

#### 思维导图关键点

```txt
高德地图 SDK
├─ 地图底图 / 矢量图层：SDK 内部渲染引擎
├─ 路线 / 点标记 / 面：通过 SDK 覆盖物能力绘制
├─ 新版 JSAPI 常见会使用 WebGL 图形能力
└─ 工具条 / 比例尺等控件：表现上多是 DOM + CSS
```

#### 60-90 秒口语稿

高德地图不是业务代码手动用 DOM 一个个画出来的，而是由 SDK 内部的地图渲染引擎完成。面试里我会分层回答：地图底图、矢量线、路线和一些覆盖物，通常由 SDK 内部基于 Canvas/WebGL 等图形能力绘制，尤其新版 JSAPI 更偏 WebGL；但工具条、比例尺、搜索框这类控件插件，表现上很多是 DOM 和 CSS。业务开发时更重要的是使用 SDK 暴露的 `Map`、`Marker`、`Polyline`、路线规划这类 API，不应该依赖它内部到底用了几个 canvas 或几个 DOM 节点。真实项目里如果要排查性能，我会先区分是地图渲染层的问题，还是业务覆盖物和 DOM 控件的问题。

#### 高频追问

1. 能不能直接操作 SDK 内部 DOM  
不建议。可以操作自己创建的自定义覆盖物或容器，但不要依赖 SDK 内部结构。

2. 为什么地图渲染适合 WebGL  
因为地图涉及大量瓦片、矢量点线面、缩放和平移，WebGL 更适合利用 GPU 做图形绘制。

### 2. 请求线路是远端数据吗

#### 思维导图关键点

```txt
路线规划
├─ 输入：起点、终点、途经点、策略
├─ 请求：调用地图路线规划服务
├─ 返回：距离、时间、路径点、导航步骤
└─ 前端：把结果渲染成路线和说明
```

#### 60-90 秒口语稿

是的，路线规划一般是远端数据。前端传入起点、终点、交通方式和策略，比如驾车、步行、骑行，SDK 或 WebService 会向高德服务请求路线规划结果。服务端根据道路网络、实时路况、距离、限行和策略计算路线，再返回路径点、距离、时间和步骤说明，前端负责把这些结果渲染成折线和导航信息。也就是说前端通常不是自己在本地算路网最短路径，而是调用服务并做展示。真实项目里要注意接口配额、失败兜底、定位权限、坐标系转换和 loading 状态。

#### 高频追问

1. 路线是否实时  
取决于路线规划能力和策略，通常会结合服务端路网与路况信息。

2. 前端能否缓存路线  
可以缓存相同起终点的结果，但实时路况会变化，所以缓存要有过期策略。

### 3. 组合式 API 如何在页面加载时挂载地图

#### 思维导图关键点

```txt
Vue3 Composition API
├─ ref 保存 DOM 容器
├─ onMounted 初始化地图
├─ shallowRef 保存第三方实例
├─ nextTick 确保 DOM 完成渲染
└─ onUnmounted 销毁实例和事件监听
```

#### 60-90 秒口语稿

Vue3 组合式 API 里挂载地图，一般会在模板里准备一个容器 `div`，用 `ref` 拿到 DOM，然后在 `onMounted` 里初始化地图，因为这时组件已经挂载到真实 DOM 上了，第三方 SDK 才能拿到容器尺寸。地图实例我会用 `shallowRef` 或普通变量保存，避免 Vue 对复杂第三方对象做深层响应式代理。组件卸载时在 `onUnmounted` 里销毁地图、清理事件监听和定时器，避免内存泄漏。真实业务里像订单地址选择页、门店地图页，都要保证地图初始化发生在 DOM 可用之后，并且离开页面时清理 SDK 资源。

#### 原始题干延展代码

```vue
<template>
  <div ref="mapContainer" class="map-container"></div>
</template>

<script setup>
import { nextTick, onMounted, onUnmounted, ref, shallowRef } from 'vue'

const mapContainer = ref(null)
const mapInstance = shallowRef(null)

onMounted(async () => {
  await nextTick()

  mapInstance.value = new AMap.Map(mapContainer.value, {
    zoom: 12,
    center: [116.397428, 39.90923]
  })
})

onUnmounted(() => {
  if (mapInstance.value) {
    mapInstance.value.destroy()
    mapInstance.value = null
  }
})
</script>

<style scoped>
.map-container {
  width: 100%;
  height: 400px;
}
</style>
```

#### 高频追问

1. 为什么不用 `setup` 里直接初始化  
`setup` 执行时 DOM 还没挂载，地图 SDK 拿不到真实容器。

2. 为什么用 `shallowRef`  
地图实例是第三方复杂对象，不需要 Vue 深层追踪，避免额外代理成本和潜在兼容问题。

### 4. Vue 的其他可用的生命周期，什么时候调用

#### 思维导图关键点

```txt
Vue 生命周期
├─ 创建：beforeCreate / created
├─ 挂载：beforeMount / mounted
├─ 更新：beforeUpdate / updated
├─ 卸载：beforeUnmount / unmounted
├─ 缓存：activated / deactivated
└─ 错误：errorCaptured
```

#### 60-90 秒口语稿

Vue 生命周期可以按创建、挂载、更新、卸载来理解。创建阶段里，`created` 已经能访问响应式数据和方法，但还没有真实 DOM；挂载阶段里，`mounted` 表示组件已经挂到 DOM 上，适合初始化地图、图表、DOM 监听这类第三方库；更新阶段里，数据变化后会触发重新渲染，`beforeUpdate` 能看到更新前 DOM，`updated` 是 DOM 更新后，但不建议在 `updated` 里无条件改状态，否则容易死循环；卸载阶段里，`beforeUnmount` 和 `unmounted` 适合清理定时器、事件监听、WebSocket、地图实例。还有 `activated/deactivated` 用在 `keep-alive` 缓存组件切入切出时。真实项目里生命周期不是死背名字，而是把“数据可用”“DOM 可用”“资源该清理”这几个时机对应起来。

#### 高频追问

1. 请求数据放哪里  
如果不依赖 DOM，`created` 或 `setup` 就可以；如果依赖 DOM 容器，放 `mounted` 或 `onMounted`。

2. 第三方库初始化放哪里  
通常放 `mounted` 或 `onMounted`。

3. 资源清理放哪里  
放 `beforeUnmount/onBeforeUnmount` 或 `unmounted/onUnmounted`。

### 5. Vue 父子组件创建卸载生命周期的顺序

#### 思维导图关键点

```txt
创建挂载
父 beforeCreate
父 created
父 beforeMount
子 beforeCreate
子 created
子 beforeMount
子 mounted
父 mounted

更新
父 beforeUpdate
子 beforeUpdate
子 updated
父 updated

卸载
父 beforeUnmount
子 beforeUnmount
子 unmounted
父 unmounted
```

#### 60-90 秒口语稿

父子组件生命周期可以记成一句话：创建时父先开始、子先挂完、父最后挂完；卸载时父先发起、子先卸完、父最后卸完。具体来说，父组件先走创建阶段，然后父组件进入 `beforeMount`，这时开始渲染子组件，所以子组件会完成自己的创建和挂载，等子组件 `mounted` 后，父组件才 `mounted`。卸载时正好是父组件先进入卸载流程，然后递归卸载子组件，子组件 `unmounted` 完成后，父组件才 `unmounted`。真实业务里这个顺序会影响父组件能否拿到子组件 DOM、子组件事件监听清理时机，以及异步请求是否会在组件卸载后继续回写状态。

#### 高频追问

1. 父 `mounted` 时子 DOM 可用吗  
一般子组件已经 `mounted`，所以父 `mounted` 时子 DOM 通常可用。

2. 父卸载时谁先完成  
父先进入卸载流程，子先完成卸载，父最后完成卸载。

### 6. Vue 数据的监听和联动

#### 思维导图关键点

```txt
Vue 数据联动
├─ computed：由已有状态派生新状态
├─ watch：监听指定数据，做副作用
├─ watchEffect：自动收集依赖
├─ v-model：表单 / 组件双向绑定
└─ props + emit：父子组件联动
```

#### 60-90 秒口语稿

Vue 数据联动核心是响应式系统。模板、`computed`、`watch` 都会依赖响应式数据，当数据变化时，Vue 会触发依赖更新。面试里我会区分 `computed` 和 `watch`：`computed` 适合做同步派生值，比如总价、筛选后的列表，它有缓存；`watch` 适合做副作用，比如监听关键词变化后请求接口、监听地图中心点变化后更新地址；`watchEffect` 会自动收集用到的响应式依赖，适合依赖比较直接的场景。父子组件之间常见是父传 `props`，子通过 `emit` 通知父更新，表单场景可以用 `v-model` 做双向绑定。真实项目里不要滥用深度 `watch`，大对象深监听会有性能成本。

### 7. 如何理解异步绘制

#### 思维导图关键点

```txt
异步绘制
├─ JS 改状态 / 改 DOM
├─ 浏览器不一定立刻绘制
├─ 当前 task 和 microtask 处理完
├─ 进入 style / layout / paint / composite
└─ 下一帧屏幕才看到变化
```

#### 60-90 秒口语稿

异步绘制可以理解为：JS 修改状态或 DOM 后，浏览器不会每改一次就马上同步把像素画到屏幕上，而是会把这些变化合并，在合适的渲染时机统一处理。通常当前宏任务执行完，还要清空微任务队列，然后浏览器才有机会进入样式计算、布局、绘制和合成流程。所以你会看到“数据已经变了，但界面还没立刻刷新”的现象。框架里的 `nextTick` 也是类似思路，它等的是 DOM 更新批处理完成，而不是等屏幕一定完成绘制。真实业务里如果一次性执行大量 JS 或塞太多微任务，浏览器就迟迟没有机会渲染，用户会感觉页面卡住。

#### 高频追问

1. `nextTick` 后一定已经绘制到屏幕了吗  
不一定。`nextTick` 更偏 DOM 更新完成，真正屏幕绘制还要等浏览器渲染帧。

2. 想等下一帧怎么办  
可以用 `requestAnimationFrame`。

### 8. JS 单线程的一次生命周期（事件循环）

#### 思维导图关键点

```txt
一轮事件循环
├─ 执行一个 task
├─ 跑完同步代码
├─ 清空 microtask
├─ 浏览器选择是否渲染
└─ 进入下一轮 task
```

#### 60-90 秒口语稿

JS 主线程一次事件循环可以按“宏任务、同步代码、微任务、渲染、下一轮”来理解。浏览器先取出一个任务，比如整体 script、点击事件、定时器回调，然后执行里面的同步代码。执行过程中遇到 `Promise.then`、`queueMicrotask` 这类会进入微任务队列，遇到 `setTimeout` 会进入后续任务队列。当前任务的同步代码执行完后，浏览器会做 microtask checkpoint，把微任务尽量清空，然后才有机会进行渲染，最后进入下一轮任务。重点是微任务不会打断当前同步代码，它只是比下一轮宏任务更早执行。真实业务里日志顺序、状态更新时机、DOM 读取时机、页面卡顿，都和这个调度边界有关。

### 9. 大数据渲染如何基于事件循环优化，如何处理大量数据的

#### 思维导图关键点

```txt
大数据渲染
├─ 不一次性塞进 DOM
├─ 分片渲染
│  ├─ setTimeout
│  ├─ requestAnimationFrame
│  └─ requestIdleCallback
├─ 虚拟列表
├─ DocumentFragment
└─ Worker 做计算，主线程做渲染
```

#### 60-90 秒口语稿

大数据渲染的核心原则是不要在一个任务里做太多事，否则 JS 长时间占住主线程，浏览器没法响应用户输入，也没法渲染。常见优化有几类：第一是虚拟列表，只渲染可视区域附近的数据，而不是几万条 DOM 全部创建；第二是分片渲染，把大数组拆成小批次，用 `setTimeout`、`requestAnimationFrame` 或 `requestIdleCallback` 分多轮事件循环执行，让浏览器中间有机会处理输入和绘制；第三是减少 DOM 操作，比如使用 `DocumentFragment` 合并插入；第四是把纯计算放到 WebWorker，主线程只负责最终渲染。真实业务里像订单列表、埋点日志表格、商品搜索结果页，通常会组合使用分页、虚拟滚动、骨架屏和分片渲染。

#### 高频追问

1. 为什么 `requestAnimationFrame` 适合渲染  
它在浏览器下一次绘制前执行，适合把 DOM 更新和渲染节奏对齐。

2. 虚拟列表解决什么问题  
解决 DOM 数量过多导致的内存、布局和绘制压力。

### 10. WebWorker 优势，如何新建和通信，劣势

#### 思维导图关键点

```txt
WebWorker
├─ 优势：独立线程，不阻塞主线程
├─ 创建：new Worker('./worker.js')
├─ 通信：postMessage / onmessage
└─ 劣势：不能操作 DOM，通信和调试有成本
```

#### 60-90 秒口语稿

WebWorker 的优势是可以把耗时计算放到主线程之外执行，避免阻塞页面交互和渲染。比如大数据过滤、复杂排序、图片处理、加密压缩这类 CPU 密集任务，都适合放到 Worker。创建时主线程通过 `new Worker('worker.js')` 创建，双方通过 `postMessage` 发消息，通过 `onmessage` 接收消息。它的劣势也很明显：Worker 不能直接操作 DOM，和主线程通信有结构化克隆或 transferable 的成本，调试和错误处理更复杂，还要注意 Worker 的创建、终止和资源释放。真实业务里我会把 Worker 用在“计算重、DOM 轻”的任务上，而不是把普通接口请求都搬进去。

#### 示例代码

```js
// main.js
const worker = new Worker('./worker.js')

worker.postMessage({ type: 'sum', payload: [1, 2, 3, 4] })

worker.onmessage = event => {
  console.log('worker result:', event.data)
}
```

```js
// worker.js
self.onmessage = event => {
  const { type, payload } = event.data

  if (type === 'sum') {
    const result = payload.reduce((total, item) => total + item, 0)
    self.postMessage(result)
  }
}
```

### 13. JS 中判断数组

#### 思维导图关键点

```txt
判断数组
├─ 首选 Array.isArray
├─ instanceof 有跨 iframe 问题
├─ Object.prototype.toString.call 可兜底
└─ constructor 不稳定
```

#### 60-90 秒口语稿

JS 判断数组最推荐用 `Array.isArray(value)`，语义最清楚，也能处理跨 iframe 或多 realm 的场景。`value instanceof Array` 在普通场景可以用，但如果数组来自不同 iframe，它的构造函数不是当前环境的 `Array`，就可能判断失败。老一点的通用写法是 `Object.prototype.toString.call(value) === '[object Array]'`。`constructor === Array` 不推荐，因为 `constructor` 可能被改写。真实业务里我一般直接用 `Array.isArray`。

### 14. 原生 DOM 如何实现 TodoList，要求动态添加、完成、删除

#### 思维导图关键点

```txt
TodoList
├─ 状态数组维护任务
```

#### 60-90 秒口语稿

原生 DOM 实现 TodoList，我会用一个数组维护状态，而不是只操作零散 DOM。添加时读取输入框内容，生成一条 todo 放进数组，然后重新渲染列表。完成和删除可以用事件委托，把点击事件绑在 `ul` 上，根据按钮的 `data-id` 判断操作哪一项。完成就是切换 `done`，删除就是过滤掉对应 id。这样动态添加出来的节点也不需要重复绑定事件。真实业务里这其实就是框架状态驱动 UI 的简化版，只是这里我们手动维护状态和渲染。

### 18. 字符串加法，不能直接转换成数字相加，按位相加

#### 思维导图关键点

```txt
字符串加法
├─ 双指针从末尾开始
├─ 每位转数字
├─ sum = x + y + carry
├─ 当前位 sum % 10
├─ 进位 Math.floor(sum / 10)
└─ 最后反转结果
```

#### 60-90 秒口语稿

字符串加法不能直接转数字，因为可能超过 JS 安全整数范围。正确思路是模拟竖式加法，从两个字符串末尾开始，用两个指针分别指向当前位，再加上进位 `carry`。每轮计算当前位之和，结果位是 `sum % 10`，新的进位是 `Math.floor(sum / 10)`。两个字符串都遍历完后，如果还有进位也要补上。最后因为我们是从低位到高位收集结果，所以要反转再拼成字符串。真实业务里这种题考的是边界处理，比如长度不同、最后进位、前导零和大数精度。
