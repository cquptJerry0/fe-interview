## SOP 回写（A / B / C / D + BFC）

### A. `aaa - bbb` 垂直高度计算（结合 `BFC` 深讲）

#### 模块 1｜主回答

##### 1）一句话结论

- 这题最稳的答法不是上来报数字，而是先确认测量口径。
- 如果问的是 `aaa` 这一行文本内容区和 `bbb` 这一行文本内容区之间的垂直间距，答案是 `15px`。
- 如果把上下两行文本本身的行高也一起算进去，那么总高度就是 `16 + 15 + 16 = 47px`。
- 核心原因不是中间有 3 个空 `p` 就把高度堆起来了，而是这些块级盒子处在同一个 `BFC` 里，垂直 `margin` 发生了折叠；同时空块级元素自己的上下 `margin` 也会继续参与整条折叠链。

##### 2）原理图（ASCII）

```txt
很多人的错误直觉：把所有 margin 全加起来

aaa.mb(15)
+ p.mt(10)+p.mb(15)
+ p.mt(10)+p.mb(15)
+ p.mt(10)+p.mb(15)
+ bbb.mt(10)
= 100px（这是错的）
```

```txt
真实发生：这些“相邻的垂直 margin”在同一个 BFC 里折叠

┌──────────────┐
│ aaa 这一行   │  line-height = 16
└──────────────┘
margin-bottom: 15

<p></p>  margin-top: 10, margin-bottom: 15
<p></p>  margin-top: 10, margin-bottom: 15   -> 连成一整条 adjoining margin chain
<p></p>  margin-top: 10, margin-bottom: 15

margin-top: 10
┌──────────────┐
│ bbb 这一行   │  line-height = 16
└──────────────┘

整条链上的 margin 都是正值
=> 折叠后只保留最大值 15
```

```txt
空块级元素为什么能“把折叠传过去”

margin-top: 10
┌─────────────────────┐
│ no border           │
│ no padding          │
│ no content / line   │
│ height: auto / 0    │
│ min-height: 0       │
└─────────────────────┘
margin-bottom: 15

=> 这个空 p 自己的 top / bottom margin 先可折叠
=> 再和前后兄弟块级元素继续折叠
```

##### 3）最小例子

```html
<style>
  p {
    font-size: 16px;
    line-height: 1;
    margin-top: 10px;
    margin-bottom: 15px;
  }

  .break {
    border-top: 1px solid transparent;
  }
</style>

<p>aaa</p>
<p class="break"></p>
<p></p>
<p></p>
<p>bbb</p>
```

```txt
给第一个空 p 加一条透明 border 后：
- 这个空块的“空盒自折叠”条件被打断
- 中间间距就不再是单纯的 15px
- 这就是验证 A 题原理最直接的方法
```

##### 4）面试口语稿

- 这题我会先确认口径。如果问 `aaa` 和 `bbb` 两行文本内容区之间的垂直间距，我会答 `15px`；如果把两行文本自身高度也算进去，就是 `47px`。原因不是中间 3 个空 `p` 把高度累加了，而是这些块级元素在同一个 `BFC` 里，垂直方向发生了 `margin collapse`。再加上空块级元素没有边框、没有内边距、没有内容、没有高度时，它自己的上下 `margin` 也会折叠，所以整条链最终只保留最大正值 `15px`。这也是为什么面试官后面会顺着追问 `BFC`。

#### 模块 2｜深入展开

##### 1）原理链路

- 先看行高：`line-height: 1` 不是 `1px`，而是 `font-size × 1`，这里等于 `16px`。
- 再看空 `p`：空块级元素没有实际文本行盒，高度不会因为 `line-height` 自动变成 `16px`。
- 真正决定中间距离的是 `margin`，而不是空 `p` 的“内容高度”。
- 在普通文档流中，这几个 `p` 都参与同一个块级格式化上下文，也就是同一个 `BFC` 的排版规则。
- `BFC` 这层概念在这里不是为了炫技，而是为了说明：相邻块级盒子的垂直外边距折叠，讨论前提就是“它们在同一个块级格式化上下文里”。
- 这题里有两种折叠同时存在：
  - 兄弟块级元素之间的垂直 `margin` 折叠。
  - 空块级元素自身 `margin-top` 和 `margin-bottom` 的折叠。
- 因为整条链上的值都是正数，所以最终结果不是相加，而是“取最大值”，也就是 `15px`。

##### 2）业务化解释

- 项目里最常见的坑是：设计稿上看起来是“很多块叠起来，间距应该越来越大”，结果页面实际只剩一小截空白。
- 这种情况高发在：富文本、文章详情页、CMS 输出的 `p` 标签、评论区、卡片列表里的段落块。
- 你如果不知道 `margin collapse`，就会以为是浏览器算错了，或者误以为 `line-height` 把空元素撑开了。
- 实际排查时最有效的方法不是盯着代码算，而是打开浏览器 DevTools 看 box model，再故意加一条 `border` 或一点 `padding` 做 A/B 验证。
- 如果你想要“稳定可控的块间距”，现代布局里很多时候用 `flex/grid + gap` 会比靠一串 `margin` 更直观，也更不容易被折叠规则坑到。

##### 3）取舍 / 易错点

- 不要把 `line-height: 1` 理解成 `1px`，它是倍数。
- 不要看到 3 个空 `p` 就默认有 `3 × 16px` 的高度，空块没有文本行盒，不会这么算。
- 不要把 `BFC` 理解成“每个块元素都有自己的独立世界”。更准确地说，是这些普通流中的块级盒子共同参与某个 `BFC` 的排版规则。
- 不要把“兄弟元素 margin 折叠”和“父子元素 margin 折叠”混成一件事；A 题主要是兄弟链 + 空块自身折叠。
- 如果题目继续追问“怎么验证自己判断没错”，最好的回答不是背定义，而是说：我会加 `border / padding / 内容 / height` 去打断空块折叠，再对比页面变化。

##### 4）深挖判断

- 这题本身适合保留在模板化回答里。
- 如果后面继续追问 `margin collapse` 的完整分类、父子折叠、浮动与 `BFC` 隔离、`flow-root` 和现代布局的取舍，建议单独补一张 `BFC / margin collapse` 专题深挖卡。

### 追问：A 题为什么会追到 `BFC`

#### 模块 1｜主回答

##### 1）一句话结论

- 因为 A 题不是单纯算数题，它本质在考：同一个 `BFC` 内，块级元素的垂直 `margin` 为什么不会老老实实相加。

##### 2）原理图（ASCII）

```txt
同一个 BFC

[块 1] margin-bottom: 15
[块 2] margin-top: 10, margin-bottom: 15
[块 3] margin-top: 10

这些相邻垂直 margin 不是独立结算
而是按 BFC 里的 margin collapse 规则统一结算
```

##### 3）最小例子

```css
.wrapper {
  overflow: hidden;
}
```

```txt
面试里不要把这句背成“加 overflow 就不会折叠”。
更准确的口径是：BFC 影响块级盒子的排版边界；
A 题提 BFC，是在提醒你从“格式化上下文 + margin collapse 规则”去理解，不是机械记修复手法。
```

##### 4）面试口语稿

- 面试官追 `BFC` 很正常，因为 A 题真正考的是块级排版规则。你如果只会说“答案是 15”，但说不出为什么 15，不知道同一 `BFC` 下相邻块级元素的垂直 `margin` 会折叠，那这题其实没答透。

#### 模块 2｜深入展开

##### 1）原理链路

- `BFC` 可以粗糙理解成一块独立的块级排版区域。
- 块级盒子在这个区域里如何摆放、浮动怎么影响、垂直 margin 怎么交互，都受它约束。
- A 题之所以会提到 `BFC`，就是因为 `margin collapse` 不是随便在任何地方都一样发生，它和块级格式化上下文有关。

##### 2）业务化解释

- 真实项目里你经常会遇到：列表项之间的间距不符合直觉、富文本首尾多了一段空白、父子块级元素间距“漏到外面去了”。
- 这些问题如果不从 `BFC + margin collapse` 的角度看，排查会很乱。

##### 3）取舍 / 易错点

- `BFC` 不是只有背触发条件；真正重要的是“它隔离了什么排版影响”。
- 不要把 `overflow: hidden` 当万能药，它会顺手带来裁剪、副作用和滚动行为变化。
- 现代布局能用 `gap` 的时候，很多块间距问题没必要硬抗 `margin collapse`。

##### 4）深挖判断

- 这块建议后续单独补专题卡，因为它会同时牵出：浮动包裹、父子外边距折叠、块格式化上下文、现代布局替代方案。

### B. 对象方法 + `this` 指向（深讲箭头函数、编译/运行、词法环境）

#### 模块 1｜主回答

##### 1）一句话结论

- 在浏览器普通脚本、非严格模式下，这段代码输出依次是：`obj`、`obj`、`window`、`window`。
- `fn1` 里的箭头函数没有自己的 `this`，它不会在调用时重新绑定，而是去外层词法环境里拿 `this`。
- 但这个“拿外层”的规则是静态的，真正拿到的具体值不是编译时写死的 `obj`，而是外层函数这一次运行时创建执行上下文时得到的 `this`。

##### 2）原理图（ASCII）

```txt
第一层：语法 / 编译视角

fn1() {
  const fn = () => {
    console.log(this)
  }
}

这里能确定的是：
- 这是箭头函数
- 箭头函数没有 own this
- 里面的 this 要向外层词法环境取

这里还不能确定的是：
- 将来具体会是 obj / window / undefined
- 因为那取决于 fn1 运行时怎么被调用
```

```txt
第二层：运行 obj.fn1() 时

创建执行上下文 EC(fn1)

EC(fn1)
  this = obj
  LexicalEnvironment = LE_fn1
  VariableEnvironment = VE_fn1

执行到 const fn = () => { console.log(this) }
  -> 创建箭头函数对象
  -> 这个箭头函数没有自己的 this binding
  -> 它把 [[Environment]] 指向当前 LE_fn1

后面无论：
  fn()
  fn.apply(window)

箭头函数都会沿 [[Environment]] 回到 LE_fn1
读取那里的 this
=> 都是 obj
```

```txt
对比普通函数 fn2 里的 fn

function fn() {
  console.log(this)
}

fn()               -> this 看调用方式，普通调用 => window（非严格模式）
fn.apply(window)   -> this 被显式绑定为 window
```

##### 3）最小例子

```js
const base = {
  make() {
    return () => this.name;
  },
};

const obj1 = { name: 'obj1', make: base.make };
const obj2 = { name: 'obj2', make: base.make };

const f1 = obj1.make();
const f2 = obj2.make();

console.log(f1()); // obj1
console.log(f2()); // obj2
console.log(f1.call({ name: 'x' })); // 还是 obj1
```

```txt
这个例子证明两件事：
1. 箭头函数的 this 不是“编译时永远绑定 obj1”
2. 同一份源码，每次在不同外层执行上下文里创建箭头函数，捕获到的 this 可以不同
```

##### 4）面试口语稿

- 这题浏览器非严格模式下输出是 `obj、obj、window、window`。`fn1` 里的箭头函数没有自己的 `this`，它不是调用时再决定 `this`，而是沿外层词法环境去拿。所以真正关键点不是“箭头函数永远指向定义时对象”，而是：箭头函数的 `this` 解析规则是静态的，但具体值取决于外层函数这次运行时的 `this`。`obj.fn1()` 调用时，`fn1` 执行上下文里的 `this` 是 `obj`，箭头函数创建时把这个环境记住了，所以后面 `fn()` 和 `fn.apply(window)` 都还是 `obj`。而 `fn2` 里的普通函数 `this` 看调用方式，所以两次都是 `window`。

#### 模块 2｜深入展开

##### 1）原理链路

- 这题要拆成两层：
  - 语法 / 编译视角：建立词法作用域关系，知道箭头函数里的 `this` 不在当前函数内解析，而是向外层找。
  - 运行视角：真正执行 `obj.fn1()` 时，才创建 `fn1` 的执行上下文，并确定这次调用的 `this = obj`。
- 你可以把 JavaScript 里的函数执行想成“每调一次，就新开一个上下文抽屉”。
- 这个抽屉里至少有两类你面试里常说的东西：
  - 词法环境 `LexicalEnvironment`：更偏 `let / const / class / 块级作用域` 这类绑定。
  - 变量环境 `VariableEnvironment`：更偏 `var / function declaration` 这类老式绑定。
- 实际引擎会做优化，但你面试里可以先这么理解。
- 对这题最重要的是：函数执行上下文还会带着 `this binding`。
- 普通函数的 `this` 是调用时按调用方式决定的；箭头函数没有自己的 `this binding`，它会沿自己的 `[[Environment]]` 去读外层函数环境记录中的 `this`。
- 所以更准确的话不是“箭头函数编译时绑定 this”，而是：
  - 编译 / 语法阶段确定了解析规则：向外层拿。
  - 运行时在箭头函数创建那一刻，把“向哪一层外部环境拿”固定下来。
  - 那一层环境里的 `this` 具体是多少，又由外层函数这次调用方式决定。

##### 2）业务化解释

- 这就是为什么很多人喜欢在回调里用箭头函数：它能稳定继承外层 `this`，避免普通函数在回调里把 `this` 丢掉。
- 比如对象方法里开一个 `setTimeout(() => {})`，箭头函数通常能拿到外层方法调用时的 `this`。
- 但反过来，如果你做的是事件系统、库回调、DOM 监听，恰好想让回调里的 `this` 代表当前调用者或当前元素，那箭头函数反而不合适。
- 所以箭头函数不是“更高级的函数”，而是“适合继承外层上下文的函数”。

##### 3）取舍 / 易错点

- 最大误区：把“词法 this”理解成“编译时把 obj 写死了”。不是的。
- 更准确的说法是：`this` 的查找规则静态，具体值由创建它时的外层运行环境决定。
- 如果你写：
  - `const detached = obj.fn1; detached()`
  - 那么这次外层 `fn1` 自己的 `this` 就可能不是 `obj` 了；非严格模式下通常是 `window`，严格模式或模块里则可能是 `undefined`。
- `apply / call / bind` 改不了箭头函数的 `this`，但可以改普通函数的 `this`。
- 箭头函数不只有 `this` 特性，它也没有自己的 `arguments`，不能当构造函数 `new`。

##### 4）深挖判断

- 这题表面看是 `this` 输出题，实际底层会牵出：执行上下文、词法环境、变量环境、闭包、普通函数与箭头函数的内部差异。
- 很适合后续补成一个 `this / 箭头函数 / 执行上下文` 专题深挖卡。

##### 难题加厚｜额外图

```txt
“规则静态，值运行时”可以压成一句图

代码写出来时：
  this 向外找   <- 规则确定

真正执行 obj.fn1() 时：
  外层 this = obj   <- 值确定

创建箭头函数时：
  记住“去这个外层环境找 this”

之后怎么 call/apply：
  都不会改成别的值
```


#### 模块 3｜追问与详细回答

##### 追问 1｜箭头函数继承外层 `this` 到底是编译时决定，还是运行时决定？

- 最稳的回答是：规则是静态的，值是运行时确定的。
- “静态”指的是：代码一写出来，箭头函数就决定了自己没有 `own this`，以后一定向外层词法环境拿 `this`。
- “运行时”指的是：外层函数到底是用 `obj.fn1()` 调、还是被摘出来单独调，这次调用产生的外层 `this` 是什么，要等真正执行那次调用时才知道。
- 所以不要把它说成纯编译时，也不要说成纯调用时重绑；更准确是“静态解析规则 + 运行时外层上下文值”。

##### 追问 2｜为什么 `fn.apply(window)` 对箭头函数不生效？

- 因为 `apply / call / bind` 能做的事，本质是给“有动态 `this` 的函数”传一个新的 `this`。
- 箭头函数没有自己的动态 `this` 槽位，它内部直接走外层环境查找。
- 所以你给它传 `window`，它也不会用；它还是回外层环境里拿原来的那个 `this`。

##### 追问 3｜如果写成 `const detached = obj.fn1; detached()` 会怎样？

- 非严格模式浏览器普通脚本里，`detached()` 这次调用通常会让 `fn1` 的 `this` 变成 `window`，那么里面新创建的箭头函数就会捕获 `window`。
- 严格模式或 ES Module 里，这个 `this` 往往会是 `undefined`。
- 所以箭头函数不是永远指向“定义时左边那个对象”，而是取决于它创建时外层函数这次怎么被调。

##### 追问 4｜普通函数的 `this` 和箭头函数的 `this` 最大区别是什么？

- 普通函数：`this` 看调用方式，`obj.fn()`、`fn()`、`fn.call(x)` 都可能不同。
- 箭头函数：没有自己的 `this`，只继承外层。
- 所以普通函数更适合需要“由调用者决定上下文”的场景；箭头函数更适合“稳定拿住外层上下文”的场景。

##### 追问 5｜这题和词法作用域、闭包是什么关系？

- 关系非常近。
- 词法作用域说的是：变量和 `this` 这类绑定应该沿什么环境往外找。
- 闭包说的是：函数把外层环境记住了，之后离开原位置仍然能访问那个环境里的绑定。
- 箭头函数这里本质上也是记住了外层环境，所以你完全可以把它理解成“词法作用域规则 + 函数记住外层环境”的一个具体表现。

### C. `Promise + setTimeout` 执行顺序

#### 模块 1｜主回答

##### 1）一句话结论

- 这题输出顺序是：`1`、`4`、`2`、`3`、`success`。

##### 2）原理图（ASCII）

```txt
宏任务 1：整段 script

同步执行 Promise 执行器 -> 打印 1
注册 setTimeout            -> 回调进入后续宏任务队列
继续同步代码               -> 打印 4

当前宏任务结束
微任务队列为空
```

```txt
宏任务 2：setTimeout 回调

打印 2
res('success')   -> then 回调进入微任务队列
打印 3

当前宏任务结束
清空微任务队列 -> 打印 success
```

##### 3）最小例子

```js
console.log('start');
setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('then'));
console.log('end');
```

```txt
输出：start -> end -> then -> timeout
```

##### 4）面试口语稿

- 这题我会按事件循环来判断。`Promise` 的执行器本身是同步代码，所以先输出 `1`；`setTimeout` 只是注册一个后续宏任务；主线程继续往下执行，输出 `4`。等脚本这轮宏任务结束后，进入下一轮执行定时器回调，先输出 `2`，然后 `res('success')` 会把 `then` 放进微任务队列，但不会立刻执行，接着同步输出 `3`。等当前这个定时器回调结束，才清空微任务，所以最后输出 `success`。

#### 模块 2｜深入展开

##### 1）原理链路

- `new Promise(executor)` 里的 `executor` 是立刻同步执行的。
- `setTimeout` 不会打断当前调用栈，只会注册后续宏任务。
- `res('success')` 也不会让 `then` 立刻插队执行，而是把对应回调放进微任务队列。
- 判断顺序时最关键的边界是：当前宏任务有没有结束。
- 只有当前宏任务结束后，微任务才会被清空。

##### 2）业务化解释

- 项目里最常见的误判就是：以为 `setTimeout(fn, 0)` 已经是“马上执行”，但 `Promise.then` 还是会比它更早。
- 这直接影响 loading 消失时机、日志顺序、状态更新时机和 DOM 读取时机。

##### 3）取舍 / 易错点

- 不要把“微任务优先级更高”背成死句，准确说法是：当前宏任务结束后先清空微任务。
- `res()` 调用本身是同步执行的，但它触发的 `then` 回调是异步排进微任务队列的。
- `setTimeout(fn, 0)` 不是立刻执行，只是尽快排队。

##### 4）深挖判断

- 这题已有现成题卡，后续直接复用即可：[事件循环（浏览器）](../../../03-题库/02-标准答案/01-模板化回答（可背）/02-事件循环（浏览器）满分回答.md)

#### 模块 3｜追问与详细回答

##### 追问 1｜为什么 `res('success')` 之后不是立刻打印 `success`？

- 因为 `then` 回调不是同步执行，而是排进微任务队列。
- 当前定时器回调这个宏任务还没结束，所以要先把后面的同步代码 `console.log(3)` 跑完。

##### 追问 2｜如果把 `then` 换成 `await`，本质会变吗？

- 本质不变。
- `await` 后续逻辑底层也是走 `Promise` 微任务恢复执行。

##### 追问 3｜为什么这题里 `2` 先于 `success`？

- 因为 `2` 在定时器回调同步代码里，`success` 在这个回调内部新塞进去的微任务里。
- 先跑完当前宏任务同步代码，再清空微任务。

##### 追问 4｜浏览器渲染会插在 `2` 和 `3` 中间吗？

- 一般不会。
- 浏览器通常要等当前调用栈和微任务清空后，才获得渲染机会。

##### 追问 5｜Node 里也一定完全一样吗？

- 核心思想相通，但具体阶段划分不同。
- 面试里最稳的是先把浏览器这套说清，再补一句 Node 阶段更细，不完全一模一样。

### D. 作用域链

#### 模块 1｜主回答

##### 1）一句话结论

- 这题输出 `10`。
- 因为 JavaScript 查找变量看的是词法作用域，也就是“函数定义在哪里”，不是“函数在哪里被调用”。

##### 2）原理图（ASCII）

```txt
代码书写位置决定外层作用域关系

Global
  a = 10
  fn = function ...
  test = function ...   <- test 定义在全局

fn 内部
  a = 20
  test()
```

```txt
真正执行时

调用 fn()
  创建 EC_fn
  里面有局部 a = 20
  然后调用 test()

调用 test()
  test 自己内部没有 a
  向它“定义时”的外层找
  -> Global 里的 a = 10

所以输出 10
```

##### 3）最小例子

```js
const a = 10;

function fn() {
  const a = 20;
  function test() {
    console.log(a);
  }
  test();
}

fn();
```

```txt
这里输出就会变成 20。
区别不在“谁调用了 test”，而在“test 定义在什么位置”。
```

##### 4）面试口语稿

- 这题输出是 `10`。因为 `test` 是在全局作用域里定义的，所以它查找 `a` 时，不会因为自己在 `fn` 里面被调用，就去拿 `fn` 作用域里的 `a = 20`。JavaScript 变量查找走词法作用域，外层链路在代码写出来时就确定了，运行时只是沿这条既定链路往外找，所以最终找到的是全局的 `a = 10`。

#### 模块 2｜深入展开

##### 1）原理链路

- 这题底层和 B 题其实是同一类能力：都在考“编译时确定规则、运行时按规则查找”。
- 写代码时，`test` 的外层作用域就已经固定为全局作用域。
- 运行时调用 `fn()` 只会让它进入调用栈，不会改写 `test` 原本的外层作用域指向。
- 所以要分清两条链：
  - 调用栈：谁先调谁，谁后调谁。
  - 作用域链：变量从哪一层往哪一层找。
- 很多人把这两条链混了，才会误判成 `20`。

##### 2）业务化解释

- 真实项目里常见表现就是：回调被传来传去，很多人以为“在哪调用就用哪层变量”。
- 但实际上，只要函数定义位置没变，它访问外部变量的路径就没变。
- 这也是闭包能成立的根基：函数把定义时那条外层作用域关系记住了。

##### 3）取舍 / 易错点

- 不要把调用位置和定义位置混淆。
- 不要把“作用域链”和“原型链”混淆；一个是变量查找，一个是属性查找。
- `var / let / const` 会影响块级作用域和暂时性死区，但不会改变“词法作用域按定义位置决定”这个根规则。

##### 4）深挖判断

- 这题可以直接挂到已有闭包卡上复习：[闭包（含常见坑与排障）](../../../03-题库/02-标准答案/01-模板化回答（可背）/04-闭包满分回答.md)
- 如果后续想把“作用域链、闭包、执行上下文、变量对象”一口气打通，建议补一张专题深挖卡。

#### 模块 3｜追问与详细回答

##### 追问 1｜如果把 `test` 写到 `fn` 里面，结果会怎样？

- 会输出 `20`。
- 因为这时 `test` 的定义位置已经变成 `fn` 内部，它的外层作用域也跟着变了。

##### 追问 2｜为什么 `fn` 调用了 `test`，`test` 却拿不到 `fn` 里的 `a`？

- 因为调用关系不会改写词法作用域关系。
- `test` 能不能看到 `fn` 里的变量，取决于它是不是定义在 `fn` 里面，而不是是不是在 `fn` 里被调。

##### 追问 3｜作用域链和调用栈最大的区别是什么？

- 调用栈回答“现在谁在执行”。
- 作用域链回答“变量往哪找”。
- 一个看执行顺序，一个看变量解析路径。

##### 追问 4｜这题和闭包是什么关系？

- 闭包成立的底层前提就是词法作用域。
- 如果函数不能记住自己定义时的外层作用域，也就谈不上闭包。

##### 追问 5｜这题和 B 题有什么共同点？

- 共同点都是：代码写出来时先确定“向哪一层外部环境找”。
- B 题是箭头函数的 `this` 沿外层环境找，D 题是普通标识符 `a` 沿外层作用域链找。
- 两题都在考你是否分得清“定义位置决定查找规则”和“运行时只是按规则去取值”。
