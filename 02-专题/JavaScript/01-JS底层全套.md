# JS 底层全套

副标题：编译时、运行时、执行上下文、环境记录、词法作用域、`this`、箭头函数、原型、闭包、`Promise Job`、事件循环

口径说明：这篇以当前公开官方资料为准，主线参考 ECMAScript 规范、WHATWG HTML event loop 和 MDN。面试里不必把规范术语一字不差背出来，但链路不能断。

## 原始题干 1｜对象方法 + `this`

```js
const obj = {
  fn1() {
    const fn = () => {
      console.log(this);
    };
    fn();
    fn.apply(window);
  },

  fn2() {
    function fn() {
      console.log(this);
    }
    fn();
    fn.apply(window);
  },
};

obj.fn1();
obj.fn2();
```

```js
function Person(name) {
  this.name = name;
}

Person.prototype.say = function () {
  return this.name;
};

const p = new Person("alice");

console.log(p.say());
console.log(Object.getPrototypeOf(p) === Person.prototype);
console.log(Object.getPrototypeOf(Person.prototype) === Object.prototype);
```

```js
const counter = createCounter();

```

## Part 1｜技术讲解

### 1. 一句话结论

`this`、作用域链、原型、闭包、`Promise`、事件循环这些题，不是几块互不相干的八股，它们都落在同一条底层链上：

源码进入引擎后，先经过解析和声明实例化，规则在这一阶段被固定；真正执行时，引擎再创建执行上下文、环境记录和函数对象；变量按词法作用域查找，普通函数 `this` 由调用形式决定，箭头函数 `this` 取外层环境；对象属性沿原型链查找；函数若继续持有外层环境就形成闭包；`Promise` 回调再通过宿主的事件循环和微任务机制被调度。

一句更适合面试的说法是：

规则先静态确定，值在运行时按规则取，最后再由宿主调度把异步结果结算出来。

### 2. 总链路图

```txt
源码进入引擎
  ->
解析 / Early Errors / 声明实例化
  ->
创建 Script 或 Function 执行上下文
  ->
建立 Lexical Environment / Variable Environment
  ->
Environment Record 记录当前绑定
  ->
变量查找沿 [[OuterEnv]] 形成的词法链向外找
  ->
普通函数 this 由调用形式决定
箭头函数 this 从外层词法环境捕获
  ->
对象属性查找沿 [[Prototype]] 向上找
  ->
函数对象如果继续持有外层环境，就形成闭包
  ->
Promise reaction 变成 Job
  ->
宿主把 Job 放进微任务队列
  ->
当前 task 结束后做 microtask checkpoint
  ->
浏览器获得渲染机会，再进入下一轮 task
```

### 3. 先把几个最常混掉的概念拆开

#### 3.1 编译时和运行时不是二选一

前端面试里经常把这两个词说得很散。更稳的理解是：

1. 编译时或更准确地说，解析和声明实例化阶段，决定的是规则。
2. 运行时决定的是这次执行具体拿到什么值。

比如：

1. `test` 定义在全局，这条词法关系是静态的。
2. 箭头函数没有 own `this`，这个规则是静态的。
3. 某次调用里普通函数 `this` 到底是不是 `obj`，要到运行时看调用方式。
4. 某层环境里的变量当前值是多少，也要到运行时看。

所以“箭头函数的 `this` 是定义时决定的”这句话只能算半对。更准确的说法是：它的取值规则在定义时固定，具体值在创建那次外层执行上下文里确定。

#### 3.2 调用栈、作用域链、原型链是三条不同的链

1. 调用栈决定谁先执行。
2. 作用域链决定变量往哪找。
3. 原型链决定对象属性往哪找。

这三条链经常被混成一团，尤其是 `this` 题和作用域题一起出现的时候。面试里只要你主动把这三条链分开，回答就会立刻显得更清楚。

### 4. 编译时到底先做了什么

规范层面不会要求你背引擎的 AST 或字节码实现细节，但现代引擎大体都会经历下面几步：

1. 词法分析和语法分析，把源码变成可执行结构。
2. 发现 Early Errors，也就是有些错误在真正运行前就会直接报掉。
3. 进入声明实例化，为当前脚本或函数创建绑定。

真正和面试关系最密切的是第 3 步，因为它解释了“提升”到底是什么。

#### 4.3 规范视角和引擎实现视角怎么对齐

这也是一个很容易被追问的点。

1. 规范描述的是抽象执行模型，比如执行上下文、环境记录、声明实例化、Job。
2. 真正的引擎实现通常会落成 AST、字节码、解释执行、热点优化和去优化。

面试里不要把两层话术混着说。更稳的口径是：

规范告诉我们“语言语义必须长什么样”，引擎再用自己的实现把这套语义跑出来。

所以你可以说 V8、SpiderMonkey 这类引擎实现里通常会有 parse、bytecode、JIT，但在解释 `this`、作用域链、闭包时，最好还是用规范模型来说明语义。

#### 4.1 什么是声明实例化

可以把它理解成：

在这段代码真正逐行执行前，引擎先为当前执行上下文把该有的绑定准备好。

常见结果是：

1. 函数声明通常在这一阶段就完成绑定，所以可以先调用后定义。
2. `var` 也会创建绑定，但初始化行为和 `let`、`const` 不一样。
3. `let`、`const` 会先创建绑定但保持未初始化状态，所以会出现 TDZ。

#### 4.2 为什么说“提升”是现象，不是机制名

工程上大家会说“变量提升”“函数提升”，但底层更接近“声明实例化导致的绑定可见性差异”。

面试里如果被追问，不要停在“提升就是提前到顶部”这种说法。更好的说法是：

源码顺序没变，是引擎在真正执行前先为这层上下文建立了绑定。

### 5. 运行时的核心：执行上下文

每次执行全局脚本、函数、模块、`eval`，都对应某个执行上下文。你可以把它理解成“这次执行的运行容器”。

一个执行上下文里，最值得你在面试里记住的是这些东西：

1. 当前代码对应的词法环境。
2. 当前代码对应的变量环境。
3. 当前这次调用的 `this` 绑定。
4. 当前上下文的外层引用。

规范名词会更细，但面试里核心不是把槽位背全，而是知道“变量为什么能找到”“`this` 为什么是这个值”“闭包到底留住了什么”。

#### 5.1 Lexical Environment 和 Variable Environment

这两个词很多人知道名字，但不知道为什么会有两个。

简单理解可以先这么记：

1. 它们都和“当前可访问绑定集合”有关。
2. 词法环境更强调这层环境本身和它的外层引用。
3. 变量环境在历史上和 `var`、函数声明这类绑定关系更密。

面试里如果不被深追，你可以先说：

当前执行上下文会关联一套环境对象，用来保存绑定，并且通过外层引用形成词法链。

但如果面试官明显追底层，就要能说出 `Lexical Environment`、`Variable Environment` 和 `Environment Record` 这些术语。

#### 5.2 Environment Record 是什么

它可以理解成“这层作用域里到底存了哪些绑定”的那层记录结构。

常见可以粗分成：

1. Declarative Environment Record
2. Object Environment Record
3. Global Environment Record

你不需要把每个子类型的所有细节背下来，但至少要知道：

1. 变量不是飘在空气里。
2. 函数查找变量时，本质上是在一层层 Environment Record 里找名字。
3. 这些 Environment Record 会通过 `[[OuterEnv]]` 串起来。

#### 5.3 函数对象本身还记住了什么

如果你想把闭包和箭头函数讲得更底层，函数对象本身也要进入视野。

函数对象至少和这些信息密切相关：

1. 它在哪个外层环境里被创建，也就是后面闭包会用到的那条环境引用。
2. 它的 `this` 模式，是 lexical 还是 non-lexical。
3. 它是不是可以被当构造函数调用。

面试里不必把所有内部槽背全，但至少要知道：

1. 闭包不是运行到后面临时拼出来的。
2. 函数在被创建那一刻，就已经和某条外层环境关系绑定上了。

### 6. 词法作用域和作用域链

#### 6.1 作用域为什么叫“词法”作用域

因为它看代码定义位置，而不是看运行时从哪里调用。

这就是为什么：

```js
const a = 10;

function fn() {
  const a = 20;
  test();
}

function test() {
  console.log(a);
}
```

最后输出 `10`。

`test` 定义在全局，所以它的 `[[OuterEnv]]` 指向全局环境，而不是 `fn` 那次调用现场。

#### 6.2 为什么调用位置改不了查找路径

因为：

1. 调用位置决定这次是谁在执行。
2. 定义位置决定当前函数创建时记住的外层环境是谁。

也就是说，调用栈会变，词法链不因为“换了个地方调用”就被重写。

#### 6.3 作用域链底层到底在找什么

可以把它想成：

1. 先在当前环境记录里找名字。
2. 找不到就顺着 `[[OuterEnv]]` 往上一层找。
3. 一直找到全局。
4. 还找不到，就抛 `ReferenceError`。

所以变量查找是一条“按环境记录逐层向外”的链，而不是在所有活动函数里乱扫。

### 7. `this` 到底是怎么定的

#### 7.1 普通函数的 `this` 不是看定义位置

普通函数的 `this` 看调用形式。

最常见的几种情况：

1. `obj.fn()`：`this` 通常是 `obj`。
2. `fn()`：在浏览器非严格模式普通脚本里通常是 `window`；严格模式或模块里通常是 `undefined`。
3. `fn.call(x)` / `fn.apply(x)`：`this` 是显式传入的 `x`。
4. `new Fn()`：`this` 是新创建的实例对象。

#### 7.2 为什么 `obj.fn()` 和 `const f = obj.fn; f()` 不一样

高分说法不该只停在“看调用者是谁”，因为这句很容易误导。

更准确的理解是：

1. 成员访问 `obj.fn` 会产生一个带 base object 的引用。
2. 紧接着调用时，这个 base object 会参与 `this` 绑定。
3. 一旦你把函数先取出来，再单独调用，原来的 base object 信息就丢了。

所以：

```js
const f = obj.fn;
f();
```

这里和 `obj.fn()` 的关键区别不是“调用者变了”这么口语，而是“引用里的基对象丢了”。

#### 7.3 严格模式和模块为什么也值得一提

因为很多人背 `fn()` 等于 `window`，这在现代前端里并不稳。

1. ES Module 顶层默认就是严格模式。
2. class 内部方法也按严格模式处理。

所以更稳的面试口径是：

浏览器非严格模式普通脚本里，普通函数裸调用常见是 `window`；严格模式或模块中通常是 `undefined`。

#### 7.4 `this` 绑定为什么和成员访问关系这么大

如果面试官继续追到底层，最值得补的一句是：

成员访问和调用不是一个动作。先得到一个引用，再基于这个引用发起调用，这个引用里是否保留了 base object，会直接影响普通函数的 `this`。

所以：

```js
obj.fn();
```

和：

```js
const f = obj.fn;
f();
```

差别的本质，不是表面上的“调用者长得不一样”，而是前者在调用时仍然携带对象基底，后者已经退化成单纯的函数值。

### 8. 箭头函数为什么是另一套规则

箭头函数的关键不是“更简洁”，而是它没有自己的一些绑定。

最重要的有：

1. 没有 own `this`
2. 没有 own `arguments`
3. 没有 own `super`
4. 没有 own `new.target`
5. 不能作为构造函数使用

这就解释了为什么：

```js
const obj = {
  fn1() {
    const fn = () => {
      console.log(this);
    };
    fn();
    fn.apply(window);
  },
};
```

`fn()` 和 `fn.apply(window)` 结果一样。

因为 `apply` 能影响的是普通函数那种动态 `this` 绑定，而箭头函数根本不走这套绑定过程。它只会回外层环境里找当前那次 `fn1` 执行时的 `this`。

#### 8.1 箭头函数和普通函数最值得记的对比

1. 普通函数：`this` 看调用形式。
2. 箭头函数：`this` 看外层词法环境。
3. 普通函数：可 `new`。
4. 箭头函数：不可 `new`，也没有自己的 `prototype` 属性用于实例化。

#### 8.2 为什么箭头函数不能当构造函数

因为它本来就不是为“实例化一批对象”设计的那套函数对象。

更实用的记法是：

1. 普通构造函数那套机制，需要和 `new`、实例对象、`prototype` 以及 `[[Prototype]]` 建立关系。
2. 箭头函数没有走这条路，所以也就没有构造器那套能力。

这也是为什么你在工程里用箭头函数做回调很顺手，但不会拿它去承担“构造实例”的职责。

### 9. 原型和原型链

这一块经常被和作用域链混掉，但它们完全不是一回事。

#### 9.1 原型链解决的是“属性从哪来”

当你访问：

```js
p.say
```

浏览器不会去查词法作用域，而是：

1. 先看 `p` 自己有没有 `say`。
2. 没有就顺着 `p.[[Prototype]]` 往上找。
3. 找到 `Person.prototype`。
4. 再找不到就继续到 `Object.prototype`。

这条链是“对象属性查找链”，不是变量查找链。

#### 9.2 `prototype`、`[[Prototype]]`、`__proto__` 别混

面试里最容易乱的是这三个词。

1. `Fn.prototype`：函数对象默认带的一个普通属性，通常用于给实例共享方法。
2. `obj.[[Prototype]]`：对象内部的原型指针，决定对象属性沿哪条链找。
3. `__proto__`：访问内部原型的历史 getter/setter 入口，不建议当规范主术语背。

一句口语化的记法：

函数的 `prototype` 常用来“放给实例继承的方法”；实例对象的 `[[Prototype]]` 会指向构造函数的 `prototype`。

#### 9.3 为什么说属性查找和变量查找不是一回事

这是 `JS 底层` 里特别值得主动强调的一点。

1. `a` 这种标识符查找，走作用域链。
2. `obj.a` 这种属性查找，走原型链。

所以 `test()` 里为什么拿不到 `fn` 里的 `a`，和 `p.say()` 为什么能找到 `Person.prototype.say`，底层根本不是同一套机制。

#### 9.4 `new` 到底把原型链做了什么

面试里如果从原型追到 `new`，至少要讲清下面这条主线：

1. 创建一个新对象。
2. 把这个新对象的 `[[Prototype]]` 指向构造函数的 `prototype`。
3. 用这个新对象作为 `this` 去执行构造函数。
4. 如果构造函数显式返回对象，就按显式返回值走；否则返回这个新对象。

这条链能把“构造函数”“实例方法”“原型链”三个常被分开背的点一下串起来。

### 10. 闭包到底保留了什么

闭包不是“匿名函数”或者“函数套函数”，而是函数对象继续持有外层环境引用导致的结果。

更底层一点说：

1. 函数被创建时，会记住当时所在的外层词法环境。
2. 如果这个函数在外部继续被引用，它对应的那条环境链就不会立刻释放。
3. 后续再调用这个函数时，仍然能通过那条环境链拿到旧的绑定。

所以：

```js
function createCounter() {
  let count = 0;
  return function () {
    count += 1;
    return count;
  };
}
```

这里真正被“留下来”的，不是一份神秘的变量快照，而是那个函数还能访问到原来那层环境记录。

#### 10.1 为什么 `var` 循环容易踩坑

因为多个回调很可能共享的是同一个函数级绑定，而不是每轮循环一个新绑定。

这不是“闭包有 bug”，而是多个闭包共同引用了同一个环境里的同一个名字。

#### 10.2 React 里的 stale closure 为什么老被提到

因为闭包拿到的是某次渲染时那条环境链上的绑定。如果你在异步回调里继续用旧闭包，它当然可能读到旧值。

所以 React 里的 stale closure 本质上不是 React 发明的新问题，而是 JS 词法作用域和闭包在异步场景下的自然表现。

#### 10.3 为什么说闭包保留的是“绑定能力”，不是“值快照”

这个说法能直接区分你是真懂还是只会背定义。

如果闭包保留的只是值快照，那么同一个计数器函数连续调用时，不会一直看到更新后的 `count`。但事实恰恰相反，它每次都会读到那层环境里当前最新的绑定值。

所以更准确的说法是：

闭包保留的是“继续访问那层环境记录”的能力，不是把某个值在创建时静态拷贝了一份。

### 11. `Promise`、Job 和事件循环

#### 11.1 `Promise` 在 ECMAScript 里和宿主是分工的

ECMAScript 规范定义了 `Promise` 状态流转、reaction 和 Job 的抽象模型，但“什么时候真正去执行这些 Job”要依赖宿主环境。

前端面试里最值得记住的是：

1. `new Promise(executor)` 的执行器是同步执行的。
2. `then`、`catch`、`finally` 的回调不会同步执行。
3. 它们会以 Promise Reaction Job 的形式排队，交给宿主结算。

#### 11.2 浏览器里为什么说是“微任务”

因为 HTML 标准的事件循环模型里，浏览器会在合适的时机做 microtask checkpoint，把微任务队列清空。

所以：

```js
new Promise((res) => {
  console.log(1);
  setTimeout(() => {
    console.log(2);
    res("success");
    console.log(3);
  }, 0);
}).then(console.log);

console.log(4);
```

输出顺序是：

```txt
1
4
2
3
success
```

因为：

1. Promise 执行器同步执行，所以先打印 `1`。
2. 脚本继续同步执行，打印 `4`。
3. `setTimeout` 回调属于后续 task。
4. 在这个 task 里调用 `res`，只是把 Promise reaction 排进微任务。
5. 当前 task 结束后才做 microtask checkpoint，所以最后才打印 `success`。

#### 11.3 为什么“微任务优先”这句话不够准

更准确的说法是：

当前 task 结束后，宿主会先结算微任务，再进入下一轮 task。

这意味着微任务不会抢占正在执行的同步代码。它只是比“下一轮 task”更早结算。

#### 11.4 事件循环和渲染有什么关系

浏览器通常要在当前 task 和 microtask checkpoint 都处理完之后，才更有机会推进渲染。

所以工程上常见的问题就都串起来了：

1. 为什么一堆同步逻辑会卡界面。
2. 为什么微任务塞太多也会让页面迟迟不刷。
3. 为什么有时数据已经变了，但用户还没看到新的像素。

#### 11.5 一轮浏览器事件循环最值得背的版本

如果你想把口语稿讲得稳一点，可以记成下面这条线：

1. 取一个 task 来执行。
2. 跑完这轮同步代码。
3. 做 microtask checkpoint，把微任务尽量清空。
4. 浏览器获得渲染机会。
5. 再进入下一轮 task。

这版说法比单纯背“宏任务、微任务谁优先”更像真正理解了宿主调度。

### 12. 把面经题串回总图

#### 12.1 `this` 题在考什么

它在考：

1. 普通函数 `this` 的运行时绑定。
2. 成员引用的基对象会不会丢失。
3. 箭头函数 lexical `this`。

#### 12.2 作用域链题在考什么

它在考：

1. 词法作用域看定义位置。
2. 标识符查找走环境记录和 `[[OuterEnv]]`。
3. 调用关系改不了查找路径。

#### 12.3 `Promise + setTimeout` 题在考什么

它在考：

1. Promise 执行器同步。
2. Promise reaction 不是同步执行，而是 Job。
3. Job 在浏览器里通常落到微任务结算点。
4. `setTimeout` 是后续 task，不会插队当前同步代码。

#### 12.4 闭包题在考什么

它在考：

1. 函数对象记住了哪条外层环境。
2. 为什么外层函数结束后变量还能被访问。
3. 为什么异步回调和事件监听容易带出旧值和生命周期问题。

### 13. 关键误判点

1. 不要把“编译时”简单理解成“引擎已经把所有值都算好了”。
2. 不要把“提升”说成代码真的被搬到了顶部。
3. 不要把调用栈和作用域链混为一谈。
4. 不要把作用域链和原型链混为一谈。
5. 不要把“看调用者是谁”当成 `this` 的完整答案。
6. 不要把箭头函数理解成“永远指向定义时左边那个对象”。
7. 不要把 `Promise` 整体背成“异步”，执行器是同步的。
8. 不要把“微任务优先”理解成能打断当前同步代码。
9. 不要把闭包理解成一份变量值的静态快照。
10. 不要把所有内存问题都归咎于闭包，真正的问题常常是无意义的长生命周期引用。

### 14. 工程/业务例子

这条链在真实业务里几乎每天都会遇到：

1. 对象方法传给事件系统后，为什么 `this` 丢了。
2. 异步回调为什么拿到旧状态，本质上往往是 stale closure。
3. 某个实例方法为什么能在实例上调用到共享方法，本质是原型链查找。
4. Promise 回调为什么总比你以为的“立刻执行”慢一步，本质是 Job 和宿主调度。
5. 页面为什么“状态改了但 UI 还没刷新”，底层常常和事件循环结算边界有关。

如果你能把这些工程现象倒推回执行上下文、环境记录、原型链和事件循环，这个专题就算真的吃透了。

### 1. 思维导图关键点

```txt
JS 底层全套
├─ 解析 / 声明实例化
├─ 执行上下文
├─ Lexical Environment / Variable Environment
├─ Environment Record + [[OuterEnv]]
├─ 词法作用域 / 作用域链
├─ 普通函数 this
├─ 箭头函数 lexical this
├─ prototype / [[Prototype]] / 原型链
├─ 闭包 = 函数继续持有外层环境
├─ Promise Reaction Job
├─ task / microtask checkpoint
└─ 浏览器渲染机会
```

### 2. 60-90 秒口语稿

如果面试官从 `this`、作用域链、闭包或者事件循环往下追，我会把它们统一到一条底层链来讲。源码进入引擎后，先经过解析和声明实例化，所以函数定义位置、词法作用域关系、箭头函数没有 own `this` 这些规则先被固定；真正执行时，每次调用会创建执行上下文，里面带着 `this`、Lexical Environment、Variable Environment 和对应的 Environment Record。变量查找会沿 `[[OuterEnv]]` 往外找，所以定义在全局的 `test` 最后拿到的是全局 `a = 10`；普通函数 `this` 看调用形式，而箭头函数 `this` 走外层词法环境；对象属性不是沿作用域链找，而是沿原型链找。再往后，如果函数继续持有外层环境，就形成闭包；`Promise` 的 reaction 会变成 Job，交给宿主在当前 task 结束后的 microtask checkpoint 里结算，所以 `Promise + setTimeout` 那道题最后才会输出 `success`。真实业务里像回调丢 `this`、异步拿旧值、实例共享方法、日志顺序和 UI 刷新时机，这些问题底层都能落回这条链。

### 3. 高频追问

#### 追问 1｜箭头函数的 `this` 到底是编译时决定，还是运行时决定

规则是静态固定的，具体值是运行时拿到的。箭头函数一写出来，就确定没有 own `this`，以后只能沿外层环境取；但具体取到的是哪个值，要看它创建时外层那次执行上下文里的 `this`。

#### 追问 2｜为什么 `obj.fn()` 和 `const f = obj.fn; f()` 差别这么大

因为前者保留了成员访问产生的 base object，后者把函数值取出来后，这个基对象信息丢了，普通函数的 `this` 绑定自然也变了。

#### 追问 3｜作用域链和原型链怎么一句话区分

变量查找走作用域链，属性查找走原型链。一个是名字绑定问题，一个是对象属性继承问题。

#### 追问 4｜闭包到底保存的是值还是环境

更准确地说是保存了访问那层环境的能力，不是简单把某个值复制了一份。

#### 追问 5｜为什么 `Promise` 明明是异步的，执行器却先跑了

因为异步的是 reaction 回调，不是 `new Promise(executor)` 这个构造动作本身。执行器在创建 Promise 时就同步执行了。

#### 追问 6｜为什么微任务不会插到同步代码中间

因为宿主通常是在当前 task 结束后做 microtask checkpoint，它不会抢占当前还在运行的这段同步逻辑。
