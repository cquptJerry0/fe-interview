# SKILL 写作：怎么写好一个 SKILL

## Part 1｜技术讲解

### 1. 一句话结论

好的 SKILL 能让 Agent 少猜、少误操作、做完能验证。写好 SKILL 的核心是五条原则：**触发要准、路径要清、风险要前置、细节要分层、结果要可验**。

### 2. 五条写作原则

#### 原则一：触发要准

`description` 里要写清楚"什么时候用"，也要隐含边界，避免误触发。

```yaml
# ❌ 模糊
description: "vimo 相关操作"

# ✅ 准确
description: |
  vimo 素材管理能力。支持素材的查询、创建、更新、上传、分级、自定义字段管理。
  当用户提到"素材"、"物料"、"自定义字段"时触发。
  注意：实验管理请使用 vimocli-experiment，权限管理请使用 vimocli-admin。
```

关键点：
- **正面触发词**：明确写什么关键词命中
- **反面排除**：明确写什么不命中，避免抢其他 SKILL 的活
- **能力边界**：写清楚能做什么和不能做什么

#### 原则二：路径要清楚

不要只列命令，要告诉 Agent **用户说 A 走哪条路径，用户说 B 切到哪个子能力**。

```markdown
# ❌ 只列命令
- vimocli material list
- vimocli material create
- vimocli material update-custom-info

# ✅ 按用户意图组织路径

## 用户说"查素材" / "素材列表"
→ vimocli material list --biz {biz} --site {site}

## 用户说"创建素材"
→ 先确认素材类型（图片/视频/文档）
→ vimocli material create --name {name} --type {type}

## 用户说"改自定义字段" / "改 biz_extra"
→ **必须先 get 再改再回写**
→ vimocli material get {id} → 局部修改 biz_extra → vimocli material update-custom-info {id} --biz-extra '{完整json}'
```

关键点：
- **用用户语言做索引**：Agent 要把用户的话翻译成操作，你要帮它建好映射
- **标注关键决策点**：哪里需要确认、哪里有条件分支、哪里必须先做另一步

#### 原则三：风险要前置

涉及删除、权限、发布、覆盖写入这类操作，要写确认、预览、备份、回滚。

```markdown
## ⚠️ 高风险操作

### 分级操作（不可逆）
1. 操作前必须预览：vimocli material preview-grade --ids {ids}
2. 用户确认后才能执行
3. 建议先在测试环境验证

### 批量操作
1. 先列出影响范围：vimocli material list --filter {condition}
2. 用户确认范围后才能批量操作
3. 保留操作记录，必要时可回滚

### 权限变更
1. 撤权前确认影响：vimocli admin check-permission --user {userId}
2. 撤权后通知当事人
```

关键点：
- **按风险等级分级**：不可逆 > 批量 > 单条，不同等级不同确认策略
- **给具体操作**：不是写"注意安全"，而是写"先 preview 再 confirm"
- **考虑回滚**：能回滚的写回滚步骤，不能回滚的强调不可逆

#### 原则四：细节要分层

主文件只放核心判断和高频路径，复杂内容拆到 references，稳定流程沉到 scripts。

```
vimocli-material/
├── SKILL.md                    # 核心流程 + 决策规则 + 风险提示（≤200行）
├── references/
│   ├── material-api-spec.md    # 完整 API 文档（按需读取）
│   ├── biz-extra-schema.json  # biz_extra 字段枚举（按需读取）
│   └── grade-rules.md         # 分级规则详细说明（按需读取）
├── scripts/
│   └── batch-update.sh        # 批量更新（稳定流程，不让 LLM 手写）
└── assets/
    └── material-template.json # 素材创建模板（填充比生成更可靠）
```

为什么分层？

```
不分层：
  SKILL.md 2000 行 → Agent 全加载 → 上下文爆炸 → 核心规则被淹没

分层：
  SKILL.md 150 行 → Agent 快速理解核心 → 需要细节时按需读取
```

关键判断标准：

| 内容类型 | 放哪里 | 为什么 |
|---------|--------|--------|
| 流程、规则、决策点 | SKILL.md | Agent 必须一开始就知道 |
| API 完整参数说明 | references/ | 只在具体操作时才看 |
| 枚举值、字段定义 | references/ | 按需查询，不占初始上下文 |
| 稳定重复的脚本 | scripts/ | 直接执行比让 LLM 写更可靠 |
| 模板、结构体 | assets/ | 填充模板比让 LLM 生成更准确 |

#### 原则五：结果要可验证

写清楚执行后看什么字段、回读什么结果、怎么判断真的成功。

```markdown
## 创建素材后的验证

1. 命令返回 success 不一定真成功
2. 验证步骤：
   - 回读素材：vimocli material get {id}
   - 检查字段：name、type、status 是否符合预期
   - 检查 biz_extra：自定义字段是否写入成功

## 更新自定义字段后的验证

1. update-custom-info 返回 success
2. 验证步骤：
   - 回读：vimocli material get {id}
   - 对比 biz_extra：确认修改的字段值正确，其他字段未被覆盖
   - **重点检查**：是否有字段被意外清空（整体覆盖的坑）
```

关键点：
- **不要相信命令的返回值**：success 不一定真成功
- **给具体验证步骤**：看哪个字段、对比什么值
- **标注容易出错的验证点**：比如整体覆盖导致的意外清空

### 3. 常见反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 把所有内容塞进 SKILL.md | 上下文爆炸，核心被淹没 | 分层，主体 ≤200 行 |
| 只列命令不写路径 | Agent 不知道什么场景用什么命令 | 按用户意图组织路径 |
| 不写风险提示 | Agent 直接执行高风险操作 | 分级标注，前置确认 |
| 不写验证步骤 | 操作结果不可信 | 写回读和对比步骤 |
| description 太模糊 | 误触发或漏触发 | 写正面触发词 + 反面排除 |

### 4. 一句话总结

> 写好 SKILL 的五条原则：触发要准（description 写清边界）、路径要清（按用户意图组织）、风险要前置（不可逆操作必须确认）、细节要分层（主体精简、按需加载）、结果要可验证（回读对比，不信返回值）。

## Part 2｜面试答题稿

### 题型判断

问"怎么写好 SKILL / SKILL 写作最佳实践"→ 解决型八股

### 思维链

```
痛点（写不好会怎样）→ 五条原则 → 反模式
```

### 口语化输出

> "写好 SKILL 我会重点看五件事。
>
> 第一，触发要准。description 里要写清楚正面触发词，也要写反面排除，避免误触发。比如'素材管理'和'实验管理'是两个 SKILL，要明确边界。
>
> 第二，路径要清楚。不要只列命令，要按用户意图组织——用户说'改自定义字段'，Agent 要知道走 get → 局部改 → 回写这条路径。
>
> 第三，风险要前置。不可逆操作必须预览确认，批量操作必须先列出范围，权限变更必须通知当事人。不是写'注意安全'，而是写具体的确认步骤。
>
> 第四，细节要分层。SKILL.md 主体控制在 200 行以内，只放核心流程和规则。API 文档放 references，稳定脚本放 scripts，模板放 assets，按需加载。
>
> 第五，结果要可验证。不能信命令的返回值，要写回读步骤——操作后再 get 一次，对比字段值，确认真的成功。特别是整体覆盖类的操作，要重点检查有没有字段被意外清空。"

### 追问预判

| 追问 | 应对 |
|------|------|
| "SKILL.md 多长合适？" | 主体 150-200 行，核心流程+规则+风险提示。超了就拆 references |
| "怎么判断什么放主体什么放 references？" | Agent 必须一开始就知道的放主体，具体操作时才看的放 references |
| "scripts 和直接让 LLM 写有什么区别？" | 稳定重复的逻辑放 scripts 更可靠（不让 LLM 手写容易出错的逻辑），一次性/灵活的让 LLM 写 |
