# AI Coding 满分心智模型：复杂页面如何被 Agent 化交付

副标题：以百度搜索页为例

## Part 1｜技术讲解

### 1. 一句话结论

这题如果只答“搜索框、结果列表、分页器怎么写”，层次是不够的。

更高阶的答法应该是：

当需求本身来自截图、竞品和产品基准时，真正要解决的不是“一个页面怎么写出来”，而是“如何把复杂需求编译成 AI 可执行的任务序列，再把这些任务组织成一个可交付、可验证、可扩展的系统”。

所以这题真正考的是三层能力：

1. AI 驾驭力：你会不会把需求转成 Spec、把任务拆给 Agent、把模型按阶段分工。
2. 业务穿透力：你能不能看出搜索页背后是结果分发、模块编排和商业化系统。
3. 工程架构力：你能不能把这个页面做成可扩展、可实验、可维护的前端系统。

一句话概括就是：

不是“用 AI 写页面”，而是“组织 AI 交付系统”。

### 3. 分阶段展开

#### 阶段 1｜这不是页面题，而是参考驱动的 Agent 题

“类似百度搜索页”这句话本身就说明，这不是一道自由发挥的页面题。

它至少隐含了三层基准：

1. 视觉基准：布局、密度、留白、信息层级、搜索框位置、结果区节奏要接近某个现成产品。
2. 产品基准：要考虑 Suggestion、翻页、状态切换、AI 回答、相关搜索等真实产品能力，而不是一个静态列表。
3. 业务基准：搜索页不是展示页，它承载用户意图满足、点击率、停留时长和商业化混排。

所以这题第一步不应该是“新建组件”，而应该是“确认参考物”和“确认成功标准”。

这也是为什么 AI Coding 在这题里的首要价值不是代码生成，而是需求理解。多模态模型先读截图和参考页，往往比直接吐 JSX 更有价值。

#### 阶段 2｜先把截图编译成 Spec，而不是让 AI 直接吐代码

拿到截图之后，先让 AI 做视觉解构和需求收敛，而不是直接让它产出页面。

我会先让它回答下面这些问题：

1. 页面有哪些一级区块。
2. 首页态和结果态是不是两个不同状态机。
3. 搜索框、Tab、结果流、右侧知识区、分页区分别承担什么职责。
4. 页面里有哪些显式状态：`query`、`page`、`loading`、`error`、`list`、`total`、`tab`。
5. 哪些行为是主链路，哪些是边界场景。

比如它至少应该产出下面这种 ASCII：

```txt
+------------------------------------------------------+
| Logo | [ 搜索输入框                       ] [搜索]    |
+------------------------------------------------------+
| Tab: 全部 / 视频 / 图片 / AI 答案                    |
+------------------------------------------------------+
| AI 回答面板 / 知识卡 / 自然结果 / 广告结果混排       |
| Result Card 1                                        |
| Result Card 2                                        |
| Result Card 3                                        |
+------------------------------------------------------+
| 相关搜索                                             |
+------------------------------------------------------+
| < 上一页 > 1 2 3 4 5 < 下一页 >                     |
+------------------------------------------------------+
```

这一层做完，才算把自然语言需求编译成工程语言。

Anthropic 官方提示工程文档强调，要把任务目标、成功标准、上下文和示例说清，再考虑更复杂技巧；这恰好说明复杂页面需求必须先做 Spec，再谈生成。

#### 阶段 3｜双重组件化：页面要拆，需求也要拆

普通前端的组件化，只是把 UI 拆成：

1. `SearchHeader`
2. `SearchInput`
3. `SuggestionDropdown`
4. `ResultCard`
5. `Pagination`
6. `AIAnswerPanel`
7. `EmptyState`
8. `ErrorState`

这只是第一层。

更重要的是第二层，也就是把“需求和开发任务”本身做组件化：

1. 视觉骨架任务：搭 Layout、搜索区、结果区、分页区。
2. 搜索交互任务：处理输入、联想词、防抖、键盘导航、提交。
3. 结果承载任务：支持多种 `card_type` 卡片。
4. AI 回答任务：流式接收、Markdown 渲染、引用溯源。
5. 埋点实验任务：曝光、点击、停留、A/B 开关。
6. 异常兜底任务：空态、错误态、加载态、重试。
7. 回归验收任务：视觉比对、主链路回归、边界用例。

Claude Code 官方把 sub-agents 定义成处理特定任务的小型专精 agent，并建议它们使用独立上下文窗口。这正适合复杂页面需求，因为这类需求本来就不应该交给一个大 prompt 一把梭。

#### 阶段 4｜模型与 Agent 编排：真正值钱的是 workflow，不是单次 prompt

这题如果只说“我会选一个最强模型”，还远远不够。

更合理的做法是按阶段分工：

1. 强推理模型负责需求澄清、Spec 产出、架构决策、代码 review。
2. 快速模型负责样板代码、样式铺设、测试草案、Mock 数据。
3. 多模态模型负责截图解构、视觉还原比对、结构对齐。

OpenAI 官方的 model selection 指南强调，模型选择应该先围绕准确率建立 eval，再去权衡时延和成本。也就是说，模型选择不是“哪一个最强”，而是“在哪个阶段需要什么能力”。

如果把这件事再往工程化推一步，它其实就是一条 workflow：

```txt
参考图
  ->
Spec Agent
  ->
任务拆解 Agent
  ->
页面实现 Agent
  ->
交互与数据 Agent
  ->
Review / Eval Agent
  ->
人工拍板
```

#### 阶段 5｜业务穿透力：搜索页本质是结果分发与模块编排系统

把百度搜索页理解成“十条蓝链”已经是旧口径了。

根据百度在 2025 年 8 月 20 日发布的 Q2 2025 公开财报口径，移动搜索结果页中 AI 生成内容占比已经在 2025 年 6 月底超过 50%，并在 2025 年 7 月达到 64%；公开表述里还明确提到，搜索结果页正在从传统网页链接转向更结构化、更智能化、更多模态优先的答案。

这至少说明三件事：

1. 搜索页已经不是单一结果列表，而是异构结果混排页。
2. AI 回答面板不是附属模块，而是核心产品形态。
3. 前端不再只是“渲染十条结果”，而是承担结果编排、模块插槽和实验承载。

所以更合理的业务定义应该是：

搜索页 = 用户意图分发页 + 异构模块编排页 + 商业化承载页。

这也是为什么你在答题时必须主动提 `card_type`、编排层、插槽、实验开关和 AI 回答流。

#### 阶段 6｜工程架构力：不是几层组件树，而是四层系统

这类页面更适合按四层来建模：

```txt
页面编排层
  决定本次 query 该出现哪些模块、模块顺序和插槽位置

业务能力层
  搜索请求管理
  URL 状态管理
  埋点管理
  实验开关
  card_type 分发

UI 组件层
  SearchHeader
  SearchInput
  ResultCard
  Pagination
  AIAnswerPanel
  EmptyState
  ErrorState

基础能力层
  防抖
  取消请求
  缓存
  Streaming
  错误兜底
```

这里最核心的是页面编排层。

因为搜索页天然不是固定内容流，它会随着 query 类型、用户意图和实验配置而变化。今天是“自然结果 + 广告 + 相关搜索”，明天可能是“AI 答案 + 知识卡 + 视频轮播 + 自然结果”。如果没有编排层，前端很快会被各种 if-else 拉垮。

这部分不是百度官方公开披露的前端架构，而是基于其公开业务口径和现代 React/Next.js 工程实践做的工程推断。答题时最好明确这一点。

#### 阶段 7｜交互主链路与高风险边界：真正难的不是页面，而是搜索行为

这题真正容易拉开差距的地方，在于交互链路。

至少有 7 类能力要主动讲出来：

1. Suggestion 需要防抖，否则用户快速输入会把后端打爆。
2. 请求需要竞态取消，否则旧请求可能覆盖新结果。
3. URL 要同步 `query/page/tab`，否则刷新和分享都不稳定。
4. 分页必须保留查询条件，否则上下文会丢。
5. 键盘导航要支持上下选择、Enter 提交、Esc 关闭。
6. AI 回答面板如果是流式输出，要处理中断、重连、局部渲染。
7. 空态、错误态、加载态、Skeleton 都不能缺。

这部分的现代实现，也有非常明确的官方一手资料可以借：

1. Next.js 官方 `useSearchParams` 文档说明，查询参数天然适合作为页面状态的一部分。
2. React 官方 `useDeferredValue` 和 `startTransition` 文档说明，搜索类 UI 应该把昂贵更新做成非阻塞或延迟感知。
3. TanStack Query 官方文档说明，查询函数可以接到 `AbortSignal`，从而处理取消和过期请求。

所以这题不要只答“防抖 + 分页”，而要答成“搜索行为链路的稳定性设计”。

#### 阶段 8｜安全、评测与交付：AI 不是终点，而是流水线中的一环

AI Coding 最容易掉进的坑，就是把“生成”当成“交付”。

真正可上线的流程至少还要补 4 层东西：

1. 人工审批：高风险工具调用、架构决策、外部依赖接入需要人工拍板。
2. 结构化输出：Spec、任务拆解、验收清单、测试点要结构化，不能只有大段自然语言。
3. 评测闭环：先做 eval 数据集和检查项，再比较不同模型和不同 prompt。
4. 最终交付物：不只有页面代码，还包括 Spec、ASCII、主链路图、风险点、测试点和复盘。

MCP 官方文档里，tools 明确支持工具调用暴露与审查，elicitation 还专门处理“执行中向人要关键信息”的场景。这背后说的就是一件事：

复杂任务里的 Agent，本质上要与人协作，而不是把人踢出回路。

### 4. 工程/业务例子

可以把百度搜索页理解成一个很典型的“从传统蓝链到 AI-native 编排”的工程案例。

早期理解里，搜索页更像：

```txt
SearchInput
  ->
ResultList
  ->
Pagination
```

但今天更像：

```txt
SearchInput / Suggestion
  ->
Query Understanding
  ->
页面编排层
  ->
AI Answer Card
  + Knowledge Card
  + Ad Card
  + Natural Result Card
  + Related Search
  ->
Pagination / 二次搜索
```

这带来三个工程变化：

1. UI 不再是固定列表，而是动态插槽和多态卡片。
2. 状态不再只是一组本地 state，而是 URL、请求、流式结果、实验配置共同驱动。
3. 交付不再只是“把页面写出来”，而是“把复杂业务编译成 Agent 可执行的流水线，再稳稳交到线上”。

这里要特别说明：

上面关于前端分层、`card_type` 映射、编排层和插槽的部分，是基于百度公开业务口径和现代前端官方实践做的工程推断，不是百度官方公开披露的内部实现。

### 3. 高频追问

#### 追问 1｜为什么这题是 Agent 题，不是页面题

因为“类似百度”说明你面对的是一个参考驱动、业务复杂、结果异构的需求。真正难的是如何把它拆成可执行任务并组织 AI 协作，而不是单独写一个页面。

#### 追问 2｜为什么一定要先看截图和 ASCII

因为复杂页面最怕误解需求。截图和 ASCII 的作用，是先把结构和状态边界确认出来，减少 AI 和人的误差传递。

#### 追问 3｜需求组件化和前端组件化有什么区别

前端组件化是拆 UI，需求组件化是拆工作单元。前者让代码更清晰，后者让 Agent 协作更可控。

#### 追问 4｜为什么搜索页天然需要编排层

因为搜索结果不是固定列表，它会随着 query 类型、实验策略和业务模块变化。没有编排层，所有混排逻辑都会烂在页面组件里。

#### 追问 5｜模型选择为什么不能只看最强模型

因为不同阶段需要的能力不同。需求分析和 review 更看重推理质量，样板代码和测试草案更看重速度，多模态对齐则需要视觉理解能力。

#### 追问 6｜AI Coding 为什么必须要有 eval 和人工审批

因为复杂任务里“生成”不等于“可交付”。没有评测和人工边界，模型只是在输出文本，不是在稳定产出系统。

### 2. 这题最容易答浅的地方

#### 容易答浅 1｜把题目降级成输入框加分页

这会让整道题退化成一个初级页面实现题，体现不出 Agent 方法论和系统思维。

#### 容易答浅 2｜只讲页面组件化，不讲任务组件化

页面拆组件只能证明你会写前端，任务拆组件才能证明你会指挥 AI 协作。

#### 容易答浅 3｜只讲模型强弱，不讲模型分工和上下文装配

复杂任务里，最值钱的是 workflow 设计，不是模型品牌崇拜。
