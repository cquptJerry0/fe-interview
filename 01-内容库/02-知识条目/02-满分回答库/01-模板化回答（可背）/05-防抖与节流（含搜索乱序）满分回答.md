## 一句话结论

防抖是“停下来再执行”，节流是“持续触发也按固定频率执行”；搜索框除了防抖减少请求量，还必须解决请求乱序（旧请求晚回覆盖新结果），推荐 AbortController 取消旧请求或用递增序号只接收最新响应。

## 解释（从零到一）

最底层视角：高频事件会在短时间内触发大量回调，导致主线程压力、重复请求、状态抖动；防抖/节流本质是用闭包保存“时间与定时器状态”，控制回调执行时机。

防抖（debounce）语义：
- 多次触发只执行最后一次（等待用户停下来）
- 典型：输入框联想、窗口 resize 结束后计算布局

节流（throttle）语义：
- 一段时间最多执行一次（过程采样）
- 典型：scroll/mousemove/resize 过程中的计算、曝光上报

搜索框乱序（竞态）为什么会发生：
- A 请求先发不代表先回
- 如果“谁先回就 setState”，旧请求晚回会覆盖新结果

最小修复（AbortController）：

```js
let controller = null;

async function search(q) {
  if (controller) controller.abort();
  controller = new AbortController();
  try {
    const res = await fetch(`/api/search?q=${encodeURIComponent(q)}`, {
      signal: controller.signal,
    });
    const data = await res.json();
    render(data);
  } catch (e) {
    if (e.name === "AbortError") return;
    throw e;
  }
}
```

备用修复（递增序号，只接收最后一次）：

```js
let latestId = 0;
async function search(q) {
  const id = ++latestId;
  const res = await fetch(`/api/search?q=${encodeURIComponent(q)}`);
  const data = await res.json();
  if (id !== latestId) return;
  render(data);
}
```

## 图解

```text
输入：a -> ab -> abc（连续触发）

只有防抖：
  请求次数减少，但仍可能并发

并发乱序：
  req#1(abc) 先回 -> UI=abc
  req#0(ab)  后回 -> UI=ab（错误覆盖）

解决：
  abort 旧请求 或 只接收 latestId
```

## 对比与取舍

- AbortController vs 序号校验
  - abort：语义清晰、旧请求不再落 UI，网络/服务端压力更小（是否真正中断取决于链路）
  - 序号：兼容任意请求库，但旧请求仍会占资源

- setTimeout 节流 vs rAF 节流
  - rAF：更贴合渲染帧，适合 scroll/mousemove 这类 UI 相关场景
  - setTimeout：适合接口限频/上报节流

## 实践与验证

- 验证乱序修复：
  - Network：能看到并发请求，但旧请求的响应不会再更新 UI
  - 关键埋点：记录 `requestId/query/applied(是否落 UI)`，确认只落最新
- 排障顺序：
  1) 是否存在并发请求
  2) 是否在旧请求回调里仍然 setState
  3) abort 是否被当成错误弹窗

## 常见追问

- 只用防抖能解决乱序吗？为什么不行？
- 节流的副作用是什么（丢中间状态）？怎么缓解（rAF）？
- loading 状态为什么也会乱？怎么让它只由最新请求控制？

## 易错点

- 把 abort 当失败处理，导致用户看到错误提示
- 只做防抖不做乱序治理，线上仍会偶发错误覆盖
- 在 scroll 回调里直接做重布局读取，导致卡顿
