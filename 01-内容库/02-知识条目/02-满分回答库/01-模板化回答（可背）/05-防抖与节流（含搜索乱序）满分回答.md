## 一句话结论

防抖解决“触发太密”问题，节流解决“持续触发”问题；搜索场景仅做防抖不够，还要处理请求乱序。工程上推荐“防抖 + 取消旧请求（AbortController）或序号门禁”组合，否则旧响应晚回会覆盖新结果。

## 技术解释

### 1) 防抖与节流的语义差异

- 防抖（debounce）：在最后一次触发后等待一段时间才执行，适合输入联想。
- 节流（throttle）：固定时间窗口内最多执行一次，适合滚动、拖拽。

### 2) 为什么搜索会乱序

- 请求 A 先发，不代表先回。
- 如果你直接“谁回就渲染谁”，就会出现旧结果覆盖新关键词。

### 3) 解决乱序的两种主流策略

策略 A：AbortController 取消旧请求。

```js
let controller;

async function search(keyword) {
  if (controller) controller.abort();
  controller = new AbortController();
  const res = await fetch(`/api/search?q=${encodeURIComponent(keyword)}`, {
    signal: controller.signal,
  });
  return res.json();
}
```

策略 B：请求序号门禁（只接收最新序号）。

```js
let reqId = 0;

async function search(keyword) {
  const id = ++reqId;
  const data = await fetchData(keyword);
  if (id !== reqId) return;
  render(data);
}
```

### 4) 细节取舍

- 防抖可配置 `leading/trailing`，面试时要讲清用户体验差异。
- 节流建议支持 `cancel/flush`，便于页面切换和强制触发。
- 取消请求要区分“主动 abort”与“真实异常”，避免错误上报污染。

## 对比与取舍

- 防抖：减少请求量效果好，但反馈会延迟。
- 节流：反馈更连续，但请求量控制不如防抖。
- AbortController：语义清晰；序号门禁：兼容性和可控性更强。

## 实践与验证

- 记录每次输入触发请求数，确认防抖确实生效。
- 记录“响应序号 < 当前序号”的丢弃次数，验证乱序被拦截。
- 在弱网与高延迟环境压测，观察结果稳定性。

## 业务举例

### 背景与约束

- 搜索框日均调用量高，用户连续输入时请求风暴明显。
- 线上出现“输入了新关键词却看到旧结果”的投诉。
- 约束：不能改后端排序逻辑，需要前端先止血。

### 方案与取舍

- 输入层加防抖，降低请求频率。
- 请求层加 AbortController，取消旧请求。
- 渲染层保留序号门禁兜底，防止极端情况下覆盖。

### 实施与验证

- 埋点统计“输入次数/请求次数”比值。
- 监控乱序覆盖告警（旧响应命中新关键词页面）。
- 灰度观察搜索成功率与用户二次输入率。

### 结果与复盘

- 请求量明显下降，乱序覆盖问题消失。
- 复盘发现某些 SDK 请求不可取消，序号门禁成为关键兜底。
- 后续把“搜索组件并发策略”沉淀为公共库能力。

## 面试口述版（60-90秒）

我会先区分语义：防抖是停下来再执行，节流是持续触发也按频率执行。搜索框场景通常先防抖降请求量，但高分点是你要补充“仅防抖不够”，因为网络返回会乱序，旧请求可能晚回覆盖新结果。我的落地做法是三层：输入层防抖、请求层用 AbortController 取消旧请求、渲染层加序号门禁只接收最新结果。最后用埋点验证请求量和乱序覆盖率，确保不是只改代码不看效果。
