## 一句话结论

浏览器事件循环可以记成“一轮内先跑同步、再清空微任务、再给渲染机会、再取下一个宏任务”。`Promise.then` 属于微任务，优先于下一轮 `setTimeout`。真正高分点是能讲清“为什么微任务过多会卡渲染”。

## 技术解释

### 1) 一轮事件循环的基本顺序

```text
执行一个宏任务 -> 清空微任务队列 -> 渲染机会 -> 进入下一轮
```

- 同步代码属于当前宏任务的一部分。
- 当前宏任务结束后，会把微任务队列清空。
- 清空后浏览器才有机会做布局、绘制和合成。
- 下一轮再取新的宏任务（如 `setTimeout` 回调）。

### 2) 常见任务分类（面试高频）

- 微任务：`Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`。
- 宏任务：`setTimeout`、`setInterval`、I/O 回调、UI 事件回调。
- `requestAnimationFrame`：不是普通宏任务，它在渲染前回调，和帧节奏绑定。

### 3) 为什么会“卡”

- 微任务必须在本轮被清空。
- 如果你在微任务里继续塞微任务，会形成长链。
- 渲染机会会被推迟，用户看到输入后界面不刷新，体感就是卡顿。

```js
console.log("sync-1");
Promise.resolve().then(() => {
  console.log("micro-1");
  Promise.resolve().then(() => console.log("micro-2"));
});
setTimeout(() => console.log("macro-timeout"), 0);
console.log("sync-2");
```

预期顺序：`sync-1 -> sync-2 -> micro-1 -> micro-2 -> macro-timeout`。

### 4) 工程实践里的用法

- 重计算不要全部塞微任务，必要时拆到宏任务或空闲时段。
- 动画相关更新优先考虑 `requestAnimationFrame`。
- 输入联想、滚动等高频交互要避免“微任务洪水”。

## 对比与取舍

- `queueMicrotask`：时序更早，但容易饿死渲染。
- `setTimeout(0)`：时序更晚，但能把控制权还给浏览器，利于渲染。
- `requestAnimationFrame`：适合视觉更新，不适合做大量业务计算。

## 实践与验证

- 在 Performance 面板观察输入事件到下一帧绘制间隔。
- 关注 Long Task 数量和微任务链长度。
- 对重计算拆分前后做 A/B，比较交互延迟。

## 业务举例

### 背景与约束

- 搜索联想页面在高频输入时，字符已经出现，但结果列表更新明显滞后。
- 目标是在不改后端接口的前提下，降低输入到渲染延迟。
- 约束：同一页面还有埋点与日志任务，不能直接删逻辑。

### 方案与取舍

- 把低优先级统计从微任务链移到宏任务批处理。
- 关键渲染路径仅保留必要微任务，避免链式 `then` 过长。
- 列表重排相关逻辑放到 `requestAnimationFrame`，和帧同步。

### 实施与验证

- 埋点记录“输入时间戳 -> 首次列表绘制时间戳”。
- 通过 Performance 对比改造前后主线程切片。
- 灰度期间观察输入抖动投诉与交互失败率。

### 结果与复盘

- 输入响应体感明显改善，列表刷新更贴近输入节奏。
- 复盘发现部分第三方 SDK 仍在微任务里做重逻辑，后续做隔离调度。
- 结论：事件循环题不只背顺序，核心是“调度策略影响交互体验”。

## 面试口述版（60-90秒）

浏览器事件循环我会先给顺序：执行一个宏任务后，会清空微任务，然后浏览器才有渲染机会，再进入下一轮宏任务。所以 `Promise.then` 一定先于下一轮 `setTimeout`。但我会补一个高分点：微任务不是越多越好，如果你在微任务里持续塞微任务，会推迟渲染，用户体感就是输入后界面不刷新。工程上我会把低优先级逻辑移到宏任务，把视觉更新放 `requestAnimationFrame`，并用 Performance 和输入到绘制时延来验证改动效果。

- `requestAnimationFrame` 在事件循环中处于什么位置？
- 如何识别线上是“事件循环调度问题”还是“后端慢”？

## 易错点

- 只记“微任务先于宏任务”，不解释渲染机会。
- 把所有异步都当成宏任务，概念混乱。
- 在微任务链里做大计算，导致主线程长期占用。
