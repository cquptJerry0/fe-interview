## 一句话结论

这题不是“站队题”，是“交付能力验证题”。高分回答路径是：先给真实主力栈和产出，再给跨栈可迁移证据，最后回到岗位匹配和落地计划。重点是让面试官相信你“入职后能稳定交付”，而不是“你懂流行观点”。

## 技术解释

### 1) 面试官真正关心什么

- 你在目标岗位主栈上能否快速产出。
- 你是否具备框架无关的工程能力（性能、排障、协作、观测）。
- 你面对新栈时是否有可执行上手路径。

### 2) 推荐回答框架（固定四步）

1. 事实：主力栈是什么，做过哪些核心模块。  
2. 证据：给具体指标或问题闭环，不说“我都用过”。  
3. 迁移：讲另一栈的关键机制和你的落地经验。  
4. 匹配：明确入职后 30/60 天如何补齐并交付。

### 3) 可迁移能力怎么讲

- 状态管理：不是背库名，而是讲状态边界、更新链路、可调试性。
- 异步与竞态：如请求取消、乱序门禁、错误恢复。
- 性能与可观测：渲染瓶颈定位、指标建设、回归验证。

### 4) 不同岗位的强调点

- 偏 React 团队：重点讲 Hooks、渲染机制、生态实践。
- 偏 Vue 团队：重点讲响应式边界、组合式 API、迁移经验。
- 平台团队：重点讲工程化和跨团队协作，不拘泥框架偏好。

## 对比与取舍

- 站队式回答：表达态度强，但容易被追问打穿。
- 交付式回答：风险低且更贴近招聘目标。
- 面试场景下，优先“可交付可信度”而不是“技术审美偏好”。

## 实践与验证

- 准备 2 个跨栈案例：一个性能问题，一个稳定性问题。
- 每个案例至少有一条量化结果或故障闭环证据。
- 准备 30/60 天补齐计划，避免空泛承诺。

## 业务举例

### 背景与约束

- 面试岗位主栈为 React，而候选人过去项目以 Vue 为主。
- 面试官担心入职初期学习成本高，影响交付节奏。
- 目标是在面试中消除“上手风险”疑虑。

### 方案与取舍

- 先明确 Vue 主力经验和实际产出，建立可信度。
- 再给 React 落地案例（如 Hooks + 竞态处理），证明迁移能力。
- 最后给短期上手计划，承诺可验证的交付节点。

### 实施与验证

- 面试中用 STAR 结构讲 1 个 Vue 项目和 1 个 React 实践。
- 重点展示问题、方案、指标，不讲泛泛学习经历。
- 通过追问展示对两栈底层机制的理解一致性。

### 结果与复盘

- 对话焦点从“你是不是 React 人”转到“你能否解决复杂问题”。
- 面试官更愿意深入讨论业务场景和交付路径。
- 复盘结论：框架偏好题本质是风险评估题。

## 面试口述版（60-90秒）

这个问题我一般不站队。我会先说事实：我主力在哪个栈，做过哪些核心模块，并给一个量化结果。然后我会给跨栈证据，比如在另一栈里如何处理状态、竞态和性能问题，证明我不是“只会写页面”。最后回到岗位匹配，说明如果团队主栈和我过往不完全一致，我会怎么在 30/60 天内补齐并交付。我的目标是让面试官看到可迁移的工程能力，而不是技术立场。

## 追问

- 如果你主力栈不是岗位主栈，前三周如何安排学习与交付？
- 你在 React/Vue 中各自踩过的一个坑是什么，怎么解决的？
- 如何证明你的能力是“框架无关”的？
- 如果团队同时维护 Vue 和 React，你如何做技术债治理？

## 易错点

- 把问题答成“谁更好用”的口水战。
- 只说“都用过”，不给任何成果证据。
- 没有落地计划，无法消除面试官风险担忧。
