## 一句话结论

事件委托是把子节点事件统一交给父容器处理，核心依赖冒泡。`closest` 的价值是从真实点击点向上定位业务目标元素，避免点到内部 `span/svg` 就匹配失败。高分点不是“省监听器”，而是能讲清动态列表、边界节点和排障策略。

## 技术解释

### 1) 原理

- 子节点触发事件后会冒泡到祖先节点。
- 父容器绑定一次监听即可处理后续新增子节点。
- 这样能减少大量重复绑定和解绑逻辑。

### 2) 推荐写法

```js
const list = document.getElementById("list");

list.addEventListener("click", (e) => {
  const btn = e.target.closest("[data-action='remove']");
  if (!btn || !list.contains(btn)) return;
  removeItem(btn.dataset.id);
});
```

### 3) 为什么要 `closest`

- `event.target` 是最深点击点，不一定是你真正关心的业务元素。
- 按钮里经常嵌 `icon/span`，直接比类名会漏判。
- `closest` 可以稳定回溯到最近命中节点。

### 4) 常见边界

- 不是所有事件都冒泡，例如 `focus/blur` 默认不冒泡（可用 `focusin/focusout`）。
- 嵌套委托时要防止父子都命中导致重复执行。
- Shadow DOM、Portal、跨 iframe 场景事件路径要单独验证。

## 对比与取舍

- 逐项绑定：直观但在大列表和动态增删下维护成本高。
- 事件委托：性能与维护更优，但需要更严谨的命中判断。
- 混合策略：关键高频节点直绑，其余走委托。

## 实践与验证

- 统计页面监听器数量，验证委托后是否收敛。
- 对动态新增节点做自动化点击测试，确认无需额外绑定。
- 检查事件命中日志，防止误命中上层元素。

## 业务举例

### 背景与约束

- 订单列表支持无限滚动，节点数量可达数千。
- 旧实现为每个按钮单独绑定点击事件，导致性能抖动且漏绑问题多。
- 需求要求不改 UI 结构，短周期上线。

### 方案与取舍

- 删除逐项绑定，改为列表容器统一委托。
- 命中规则统一用 `data-action + closest`，避免类名耦合。
- 对不冒泡事件单独处理，不强行纳入委托。

### 实施与验证

- 对关键操作增加点击路径日志，校验命中准确率。
- 对新增页数据做回归，验证不需要二次绑定。
- 观察主线程事件处理耗时与内存占用。

### 结果与复盘

- 监听器数量显著下降，动态新增漏绑问题消失。
- 复盘发现个别场景因嵌套委托触发两次，后续加命中边界判断修复。
- 结论：事件委托是“维护性优化 + 性能优化”双收益。

## 面试口述版（60-90秒）

事件委托的核心是利用冒泡，把子节点事件统一交给父容器处理。它的价值不只是在性能上减少监听器，更重要是动态节点天然可用，不需要反复绑定。落地时我会强调 `closest`，因为真实点击点常在按钮内部元素上，直接用 `event.target` 很容易漏判。工程上要补边界：不是所有事件都冒泡，嵌套委托要防重复命中。我做过大列表改造，委托后监听器数量和漏绑问题都明显下降。

## 易错点

- 直接用 `event.target` 做判断，忽略嵌套节点。
- 忽略不冒泡事件，导致“委托失效”误判。
- 委托范围过大，反而增加无关节点判断成本。
