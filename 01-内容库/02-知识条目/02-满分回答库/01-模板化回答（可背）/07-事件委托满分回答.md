## 一句话结论

事件委托是把子元素事件统一交给父容器处理，依赖冒泡让父容器收到事件，再用 `event.target + closest` 定位实际命中的子元素，适合“列表项多且动态增删”的场景。

## 解释（从零到一）

最底层视角：
- click 会从目标节点冒泡到父节点
- 父节点只绑定一次监听，就能接到所有子节点的 click

最小例子（推荐写法）：

```js
const list = document.getElementById("list");

list.addEventListener("click", (e) => {
  const btn = e.target.closest(".del");
  if (!btn || !list.contains(btn)) return;
  removeItem(btn.dataset.id);
});
```

为什么要 `closest`：
- 实际点击点可能落在按钮内部的 `<span>/<svg>` 上，`event.target` 不一定就是按钮
- `closest(".del")` 能从 target 往上找到最近的匹配元素

## 图解

```text
button.del (target)
  ↑ 冒泡
li
  ↑
ul#list (listener 在这里)
```

## 对比与取舍

- 委托 vs 逐个绑定
  - 委托：监听器数量少、动态新增无需重新绑定；缺点是需要写 target 判定逻辑
  - 逐个绑定：直观；缺点是大量节点初始化成本高、动态增删容易漏绑/忘解绑

## 实践与验证

业务例子：商品列表（1000 行）每行有“删除/收藏/跳详情”，并支持无限滚动追加
- 逐个绑定会造成大量监听器与维护成本
- 委托只在列表容器绑定一次，新增节点天然可用

排障：点击没反应
1) 打印 `event.target` 确认命中元素
2) 检查 selector 是否匹配，`closest` 是否返回 null
3) 是否有 stopPropagation 阻断冒泡
4) 是否有遮罩层导致 target 不是预期元素

## 常见追问

- 哪些事件不适合委托（不冒泡/语义问题）？如何绕过（捕获/focusin）？
- 如何在委托里区分多种按钮（data-action）？

## 易错点

- 只判断 `e.target.className`，点到子节点导致失效
- 忘了做 `list.contains(btn)`，导致跨层级误命中
