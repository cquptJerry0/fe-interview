## 一句话结论

这题不要只讲“我喜欢哪套 CSS”，而要讲清楚三件事：规则如何生成、主题值如何切换、团队如何治理。我会先把常见方案逐个说明，再给一个可落地的默认组合：规则层偏静态（Tailwind/CSS Modules），值层走 CSS Variables + 语义 token。

## 技术解释

### 先给总框架：为什么会有这么多 CSS 方案？

因为“样式问题”其实是两类问题：
- 规则层问题：样式规则是构建时产出，还是运行时注入？
- 值层问题：主题切换是复制规则，还是只切 token 值？

所以选型时不要混在一起讲。先定规则层，再定值层，最后补治理与验证。

### 10 种常见方案逐项讲清楚

#### 1) BEM + SCSS

- 是什么：BEM 约束命名结构（Block/Element/Modifier），SCSS 提供变量、嵌套、mixin。
- 怎么用：每个组件先定义 Block，再拆 Element，用 Modifier 承载状态差异。
- 好处：无运行时成本，产物稳定，老项目容易接受。
- 代价：命名与维护成本高，团队容易出现“伪 BEM”。
- 适用：传统业务、稳定迭代、对工具链改造意愿低的团队。
- 易错点：SCSS 嵌套过深导致选择器权重失控，后期只能靠覆盖补丁。

#### 2) CSS Modules

- 是什么：构建时把 class 名哈希化，默认局部作用域。
- 怎么用：组件内 `import styles`，模板中使用 `styles.xxx`，减少全局污染。
- 好处：冲突少、迁移平滑、和 React/Vue 工程化契合。
- 代价：跨组件复用和全局主题要额外设计。
- 适用：中大型业务系统，强调模块边界。
- 易错点：把主题逻辑硬塞到每个 module，导致 token 重复与维护分裂。

#### 3) Tailwind（utility-first）

- 是什么：原子化 utility class 体系，不是组件库。
- 怎么用：在模板/JSX 直接组合 `flex p-4 text-sm`；JIT 扫描源码后按需产出 CSS。
- 好处：开发快、协作一致性高、产物通常可控。
- 代价：class 变长；动态拼接 class 容易漏扫描；规范弱时会出现 arbitrary value 滥用。
- 适用：多人协作、交付节奏快、强调设计一致性的项目。
- 易错点：写 ``text-${size}`` 这类动态字符串，线上会出现“有 class 没样式”。

#### 4) Runtime CSS-in-JS（运行时注入）

- 是什么：在运行时根据 props 生成 CSS 并插入 style 标签。
- 怎么用：样式写在 JS/TS，动态状态直接由 props 驱动。
- 好处：表达力强，组件封装体验好。
- 代价：运行时开销、SSR/hydration 一致性和注入顺序问题更复杂。
- 适用：高动态组件库或局部复杂组件。
- 易错点：首屏链路变重、样式闪烁排障复杂。

#### 5) Compile-time CSS-in-JS（编译时提取）

- 是什么：开发体验接近 CSS-in-JS，但在构建阶段提取成静态 CSS。
- 怎么用：在 TS 中定义样式与 token，构建时输出 CSS 文件。
- 好处：兼顾类型能力与运行时性能。
- 代价：构建链路更复杂，对工程能力要求高。
- 适用：组件库、平台化前端团队。
- 易错点：工具链升级时兼容成本高，需提前锁定版本策略。

#### 6) 纯 CSS Variables 主题

- 是什么：把主题值放进 `--token`，规则复用，运行时切变量值。
- 怎么用：组件只消费语义 token（如 `--color-text-primary`），不直接写品牌色。
- 好处：主题扩展线性增长，切换成本低。
- 代价：前期 token 体系设计要求高。
- 适用：多主题、多租户、白标场景。
- 易错点：token 没分层（global/semantic/component），后期很难治理。

#### 7) class 切主题（`.theme-dark` 等）

- 是什么：根节点切 class，按选择器覆盖不同主题规则。
- 怎么用：每个主题维护一组覆盖规则。
- 好处：实现简单，初期改造快。
- 代价：主题数量增加后规则膨胀非常快。
- 适用：主题少（2-3 套）且生命周期短的系统。
- 易错点：把它用于 10+ 主题场景，最终变成维护灾难。

#### 8) Design Token 平台化

- 是什么：把设计值抽成统一资产，并建立发布与校验流程。
- 怎么用：通常分 `global -> semantic -> component` 三层映射。
- 好处：跨端一致、可审计、可扩展。
- 代价：建设成本高，需要设计与研发共同维护。
- 适用：中大团队、长期产品线。
- 易错点：只有 token 文件，没有门禁流程，最终仍被业务绕过。

#### 9) 混合方案（最常见落地）

- 是什么：规则层用 Tailwind/CSS Modules，值层用 CSS Variables + token。
- 怎么用：离散状态走 class，连续主题值走变量。
- 好处：效率、性能、治理三者平衡。
- 代价：需要明确团队规范，否则会多套风格混用。
- 适用：绝大多数中后台、增长业务和 SaaS 项目。
- 易错点：没有“何时用哪套”的准则，代码风格快速碎片化。

#### 10) 内联样式 / 临时覆盖（兜底）

- 是什么：直接 `style` 或局部高优先级覆盖。
- 怎么用：只用于紧急修复或极小范围动态值。
- 好处：见效快。
- 代价：难复用、难治理、技术债增长快。
- 适用：临时止血，不应成为主路径。
- 易错点：临时方案长期化，后续重构成本陡增。

## 对比与取舍

我在面试里会给一个清晰决策顺序：
1. 先看 SSR 与性能预算，决定能否接受运行时注入。
2. 再看主题规模（2 套还是 20 套），决定 class 覆盖还是变量切值。
3. 再看团队阶段，决定是否投入 token 平台化治理。
4. 最后看交付周期，决定是一步到位还是分阶段迁移。

默认推荐路径：
- 小团队短期项目：CSS Modules + 少量变量。
- 中大型业务：Tailwind/CSS Modules + CSS Variables + 语义 token。
- 组件平台化团队：编译时提取 + token 工程化发布。

## 实践与验证

- 产物验证：构建后检查 CSS 体积、重复规则比例、无效选择器比例。
- 主题验证：切换主题时只改变量值，不触发大面积样式重算。
- 体验验证：关注 FCP/LCP、样式闪烁率、主题切换耗时。
- 可维护验证：lint 约束禁止硬编码品牌色，CI 校验 token 完整性与对比度。

## 业务举例

### 背景与约束

- 场景：B 端中后台做多租户白标，共 12 个租户，要求支持品牌主题切换。
- 约束：两周上线，旧页面不能大规模重写；SSR 页面要求首屏不闪。
- 风险：如果每租户一套 class，CSS 体积会膨胀，回归范围无法控制。

### 方案与取舍

- 规则层：保留 Tailwind + CSS Modules，避免引入运行时注入链路。
- 值层：新增 token 三层映射（global/semantic/component），主题通过 CSS Variables 切值。
- 取舍：放弃“每主题复制规则”的方案，改为“规则复用 + 值替换”。

### 实施与验证

- 实施：把品牌色和间距收敛到语义 token，组件只允许消费语义 token。
- 校验：CI 增加 token 完整性检查、对比度检查（AA 门槛）。
- 验证指标：主题切换耗时、样式回归缺陷数、构建产物体积、线上样式错误率。

### 结果与复盘

- 结果：主题切换稳定且无明显闪烁，新增租户成本从“复制一套样式”变为“维护映射表”。
- 复盘：早期图表模块绕过 token 导致颜色不一致，后续通过 adapter 层统一修正。
- 结论：主题系统的关键不是“能切色”，而是“可治理、可验证、可回滚”。

## 面试口述版（60-90秒）

这题我会先分层讲。第一层是规则层，决定样式规则是构建时产出还是运行时注入；第二层是值层，决定主题是复制规则还是只切 token 值。常见方案有 BEM+SCSS、CSS Modules、Tailwind、运行时和编译时 CSS-in-JS、CSS Variables、class 主题、token 平台化和混合方案。  
我的默认落地是规则层偏静态，值层用 CSS Variables 加语义 token。原因是这套方案在 SSR 一致性、性能和团队协作之间最平衡。  
我做过 12 租户白标项目，最终通过 token 分层和 CI 校验把主题切换做成“只改值不改规则”，上线后新增租户主要改映射表，回归成本明显可控。如果面试官追问，我会展开讲动态 class 漏扫、SSR 样式闪烁和 token 治理门禁这三个高频坑。

## 追问

- Tailwind 的动态 class 漏扫为什么发生？你如何避免？
- 什么时候必须选运行时 CSS-in-JS？什么时候不该选？
- 为什么多主题场景更推荐 CSS Variables 而不是 class 穷举？
- token 三层（global/semantic/component）具体怎么分？如何避免语义漂移？
- SSR 场景下怎么避免主题切换导致的首屏闪烁？
- 如果线上出现“某租户主题错色”，你的排障路径是什么？

## 易错点

- 把“规则层选型”和“主题值策略”混成一个问题，导致论证混乱。
- 只谈开发体验，不谈 SSR 一致性、性能预算和治理成本。
- 没有校验与回滚机制，主题上线后只能人工排查。
