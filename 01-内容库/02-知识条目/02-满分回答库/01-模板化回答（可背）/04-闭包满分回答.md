## 一句话结论

闭包是“函数 + 创建时词法作用域”的组合，允许函数在外层执行结束后仍访问外层变量。它是封装状态的核心工具，但也会让对象被意外保活，导致状态串扰或内存泄漏。面试高分点是能把“闭包好处”和“引用链排障”一起讲清。

## 技术解释

### 1) 闭包为什么成立

- 函数创建时会记录词法环境引用。
- 只要函数对象还可达，相关环境就不会被回收。
- 所以外层函数结束后，内部函数仍可访问外层变量。

```js
function makeCounter() {
  let n = 0;
  return function inc() {
    n += 1;
    return n;
  };
}

const inc = makeCounter();
inc(); // 1
inc(); // 2
```

### 2) 工程里的典型用途

- 防抖/节流：保存 `timer/lastTime`。
- 缓存：保存 `Map` 或计算结果。
- 模块私有状态：隐藏不希望外部直接改的变量。

### 3) 为什么会出问题

- 闭包里引用了大对象（DOM、列表数据、上下文），且函数长期挂在全局事件上。
- 组件卸载后监听没解绑，闭包环境一直可达。
- 结果是内存无法回收，甚至旧状态影响新页面。

### 4) 排障思路

- Heap Snapshot 看 Detached DOM 和 Retainers。
- 沿引用链找“谁还持有回调函数”。
- 检查定时器、事件监听、全局缓存是否在销毁时清理。

## 对比与取舍

- 闭包封装 vs class 实例字段：闭包私有性强，class 可读性更高。
- 闭包缓存 vs 全局缓存：闭包作用域清晰，但生命周期要管理。
- 使用闭包不是问题，无法释放才是问题。

## 实践与验证

- 给关键页面做进入/离开循环压测，观察内存基线。
- 在销毁流程里统一调用 `removeEventListener`、`clearTimeout`。
- 通过 Performance + Memory 验证回收是否发生。

## 业务举例

### 背景与约束

- 筛选面板模块频繁打开关闭，长时间使用后页面内存持续上升。
- 业务要求不影响当前交互逻辑，优先快速止血。
- 模块中存在多个闭包回调和全局事件监听。

### 方案与取舍

- 保留闭包结构（便于状态封装），重点治理生命周期。
- 新增统一销毁函数，集中解绑监听和定时器。
- 对大对象引用改为按需读取，避免被闭包长期持有。

### 实施与验证

- 用 Heap Snapshot 对比改造前后 Retainers 链路。
- 加自动化回归：反复进入/退出页面 50 次看内存曲线。
- 监控线上长会话用户的内存告警比例。

### 结果与复盘

- 内存曲线回归稳定，长会话卡顿明显减少。
- 复盘发现最关键问题不是“用了闭包”，而是“闭包生命周期未收口”。
- 后续在代码评审中增加“闭包引用链检查项”。

## 面试口述版（60-90秒）

闭包本质是函数在创建时绑定词法作用域，所以即使外层函数执行完，内部函数仍能访问外层变量。工程上我会用它做防抖节流、私有状态和缓存，但会特别关注生命周期，因为闭包很容易把对象意外保活。排障时我通常从内存快照入手，看 Retainers 链，定位是谁还持有回调，再清理事件监听和定时器。我的经验是闭包本身不是问题，问题是没有配套销毁策略。

## 追问

- 为什么闭包会导致内存泄漏，而普通局部变量不会？
- 如何判断某个闭包是否“意外保活”了大对象？
- 闭包做缓存时如何设计失效策略？
- 在 React/Vue 组件中，闭包生命周期如何和组件生命周期对齐？

## 易错点

- 把“闭包”直接等同于“内存泄漏”。
- 只讲概念，不讲引用链和实际排障步骤。
- 忽视卸载阶段清理，导致历史页面状态残留。
