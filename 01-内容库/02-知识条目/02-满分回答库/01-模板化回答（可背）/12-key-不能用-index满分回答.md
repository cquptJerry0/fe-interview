## 一句话结论

key 是列表节点的稳定身份标识，用来让 diff 正确复用真实 DOM/组件实例；用 index 做 key 在插入/删除/排序时会导致身份跟着位置变，产生错误复用与状态错位（例如 input 内容/焦点跑到别的行）。

## 技术解释

底层机制：
- diff 在同层对比时用 key 把“旧节点”和“新节点”匹配起来
- 匹配成功就复用 DOM/组件实例，只更新差异；匹配失败才新建/删除/移动

index 做 key 为什么会错：
- 列表发生插入/删除后，元素的 index 改了，但你用 index 当 key，相当于“身份证跟着座位号变化”

最小反例（语义推演）：

```text
旧：[0:A, 1:B, 2:C]
删 A 后新：[0:B, 1:C]

diff（按 key 匹配）会把：
key=0 的 DOM(A) 复用给 B
key=1 的 DOM(B) 复用给 C
key=2 的 DOM(C) 删除
```

一旦 DOM 里有非受控状态（input 值、焦点、动画中间态），就会出现“状态串台”。

## 图解

```text
key 是身份，不是位置
稳定 key：节点搬家但身份不变 -> 正确复用
index key：位置变导致身份变 -> 错误复用/状态错位
```

## 对比与取舍

- 何时可以用 index key（非常有限）
  - 列表永不插入/删除/排序
  - 列表项无内部状态，纯展示
- 何时不能用
  - 任何动态列表（增删改排序）
  - 列表项含输入框/局部状态/动画

## 实践与验证

推荐 key：
- 后端稳定 id（如 todo_id）
- 前端生成并绑定到数据上的稳定 uuid（不要在 render 时随机生成）

验证是否错位：
- 在列表第一项输入文字后在头部插入新项，观察输入是否“跑行”

## 追问

- 用随机数当 key 行不行？为什么？
- Vue 和 React 的 diff 细节不同，但为什么这个结论一样？

## 易错点

- render 时生成 uuid 导致每次 render 都重挂载（性能差、焦点丢）
- 把“key 唯一”当成唯一要求，忽略了“稳定”更关键

## 业务举例

- 场景：可排序列表中输入框值错位，用户编辑 A 项后内容跑到 B 项。
- 做法：把 index key 改为业务稳定 id，确保重排时节点身份不变。
- 验证：插入/删除/排序后输入值与选中状态始终绑定正确项。

## 面试口述版（60-90秒）

`key` 的作用是给 diff 提供稳定身份，index 在插入、删除、排序时会变化，导致节点被错误复用，出现状态错位和输入框串值。正确策略是用业务稳定 id 作为 key。只有完全静态、无本地状态、无重排的列表，index 才可能勉强可用。验证时我会给一个“列表头部插入”最小例子，现场演示 index key 的问题。
