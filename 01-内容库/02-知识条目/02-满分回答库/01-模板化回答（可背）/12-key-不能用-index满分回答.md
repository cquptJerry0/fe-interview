## 一句话结论

`key` 代表列表节点的稳定身份，不是当前位置编号。用 `index` 作为 key 在插入、删除、排序后会让身份错位，导致错误复用 DOM/组件实例，典型现象是输入框值、焦点、勾选状态串到别的行。

## 技术解释

### 1) key 在 diff 里的作用

- 同层节点比较时，框架先按 key 建立新旧节点映射。
- key 命中表示“这是同一业务实体”，可复用实例和 DOM。
- key 不命中才会新建、删除或移动节点。

### 2) index 为什么危险

- index 本质是“位置”，不是“身份”。
- 一旦头部插入或中间删除，后续所有 index 都变化。
- diff 会把旧节点错误复用给新业务项，状态随之错位。

```text
旧: [0:A, 1:B, 2:C]
新: [0:X, 1:A, 2:B, 3:C]

index key 下会把旧 A 复用给 X，后续连锁错位
```

### 3) 什么时候可以用 index

- 列表严格静态：不增删、不排序、不过滤。
- 子项无本地状态、无动画、无输入焦点等“实例状态”。
- 实战里这种场景很少，默认不建议。

### 4) 稳定 key 的来源

- 后端业务主键（推荐）。
- 前端生成并持久化的唯一 id（如本地草稿 id）。
- 禁止用随机数每次重算，否则每轮都强制重建。

## 对比与取舍

- 稳定业务 id：正确复用，状态安全，性能更稳。
- index：写起来快，但动态列表风险高。
- 随机 key：看似唯一，实则每次都变，性能最差。

## 实践与验证

- 用“插入/删除/排序/过滤”四类操作做回归。
- 检查输入框值、选中态、焦点是否跟随正确业务项。
- 在性能面板观察节点重建数量，验证复用是否合理。

## 业务举例

### 背景与约束

- 可编辑列表支持拖拽排序和插入，线上频繁出现“输入内容串行”。
- 旧实现使用 index key，问题在复杂操作后高频触发。
- 需要在不改交互的前提下快速修复。

### 方案与取舍

- 将 key 从 index 改为后端返回的业务 id。
- 本地临时项生成稳定 uuid，提交后与后端 id 对齐。
- 保留旧数据兼容逻辑，避免历史记录失配。

### 实施与验证

- 针对插入/删除/排序路径补自动化用例。
- 录制用户操作回放，验证输入和焦点不串行。
- 灰度期间监控编辑失败率和异常反馈。

### 结果与复盘

- 状态错位问题消失，列表编辑稳定性显著提升。
- 复盘确认根因就是“把位置当身份”。
- 后续在 lint 和 code review 中禁止动态列表使用 index key。

## 面试口述版（60-90秒）

我会先定义：`key` 是列表节点的稳定身份，不是数组下标。diff 会根据 key 复用旧节点，如果你用 index，插入或删除后身份会整体漂移，DOM 和组件实例会被错误复用，所以会出现输入值和焦点串台。正确做法是用业务主键或稳定生成的本地 id。只有在完全静态且无本地状态的列表里，index 才勉强可用。我在项目里处理过这类问题，把 key 改为业务 id 并补四类操作回归后，串台问题就消失了。

## 易错点

- 把 key 理解成“让警告消失”的语法占位。
- 动态列表偷懒用 index，后续状态问题难定位。
- 使用不稳定 key（如 `Date.now()`）导致整表重建。
