# Answer Question

在用户要求回答一道题、写答案稿、写专题稿、优化口语稿或判断是否值得深挖时使用这个 skill。

## 先做什么

1. 先判断题型。
2. 只有当专题明确涉及现代实现、版本演进、框架 / 浏览器 / 运行时内部机制，或者用户明确要求最新资料时，才先搜索官方或一手资料。
3. 如果只是代码题、输入输出题、手写题汇总型专题，默认先做归纳总结，不要求复杂搜索。
4. 如果是系统专题题，先到 `deep-topic.md` 判断它属于标准单链专题、聚合型专题，还是专题案例 / 样板专题。
5. 再选对应参考材料。
6. 最后决定输出为面经正文答案稿，还是专题文章。

## 题型判断补充

1. 题目核心如果是“实现一个”“手写一个”“设计一个函数 / 类 / 机制”“写出代码”“补全代码”，优先判为编程题，不要因为题目使用 JavaScript 就误判成代码输出题。
2. 像事件总线、列表 diff、请求去重、缓存、超时控制、Promise 封装、组件 / 页面实现，这类默认都按编程题处理。
3. 只有题目核心是在判断“最终输出是什么”或解释 `this`、作用域链、闭包、事件循环、原型链执行结果时，才走代码输出题。
4. 如果用户明确提到“笔试”“手写”“先输出在聊天框”“先给简单版”“先给最短可写版”，编程题默认先给最小可用版，再补进阶版。

## 统一输出要求

1. `20 秒快答` 不再使用，统一改成 `思维导图关键点`。
2. `60-90 秒口语稿` 结尾默认补 1 句工程或业务例子。
3. 如果题目本身明显值得长期复用，优先产出专题文章。
4. 用户已经认可过的高质量回答，落盘版本不得降级，不得为了压缩篇幅把专题写回泛化八股。
5. 各题型专属要求下放到对应 reference 文件：简单题看 `simple-question.md`，代码输出题看 `code-output.md`，编程题看 `coding-question.md`，系统专题题看 `deep-topic.md`。
6. 系统专题题不要默认套同一模板；先按 `deep-topic.md` 判断专题类型，再决定写法。
7. 系统专题题里的 `结论证明材料`、`关键误判点` 默认按需使用，不要求每篇都单独成节；如果证据已内嵌到正文、误判点没有新增信息，可以省略或压缩。
8. 文档可读性优先；如果某些内容更适合作为科普补充、资料依据或防错提醒，可以后置到附录，不要打断正文主线。
