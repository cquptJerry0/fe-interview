# 编程题写法

适用范围：

1. 算法题
2. 页面实现题
3. 组件题
4. 手写函数题、机制题、工具题

## 默认原则

1. 第一版先给笔试最小可用版，不要一开始就写很多。
2. 代码量以 3-5 分钟可手写完成为准，先保证能过题、能讲清。
3. 默认不要先写工程化封装、泛型设计、完整容错、过多扩展参数。
4. 如果用户说“笔试”“手写”“先在聊天框输出”“先给简单版”，优先进一步压缩到最短可用解。
5. 只有用户明确要“满分版”“工程版”“可复用版”，再补第二版代码。
6. 手写题默认优先用 `for`、`for...of`，尽可能少用 `forEach`。
7. 如果需要提前结束循环、跳过当前项、边遍历边调试，优先不用 `forEach`。
8. 主版本先保证题意完整和结果正确，再追求短；不要为了少几行而默认接受漏字段、漏删除、漏异常。
9. 在不牺牲正确性和可讲性的前提下，可以优先使用 `Set`、`Map`、`find`、`Object.keys` 这类常见内建方法来压代码量。
10. 如果 `Map` 能明显降低复杂度、同时代码仍然顺、短、好讲，就可以直接放进主版本，不必机械地等到“进阶版”再提。
11. 非必要不要使用正则；如果普通字符串方法、循环、下标计算就能更直白地解决问题，优先不用正则。

## 固定输出

1. 原始题干
2. 思维导图关键点
3. `60-90 秒口语稿`
4. 最小可用版代码
5. 关键边界 / 高频追问
6. 如果需要，再给进阶版或满分版

## 关键边界 / 高频追问必选项

1. 时间复杂度必写。
2. 空间复杂度必写。
3. 再根据题目补主键选择、边界条件、异常情况、是否需要深比较、是否要取消订阅、是否要真取消请求等追问点。
4. 不要把复杂度单独漏在外面；默认并到“关键边界 / 高频追问”里统一输出。

## 最小可用版要求

1. 优先使用最直接的数据结构和最少的辅助函数。
2. 能内联就先内联，能少一层封装就少一层。
3. 注释只保留必要的一两句，不要把答案写成教程。
4. 先满足题目主目标，再在“关键边界”里补充未展开的工程点。
5. 如果某些优化会明显拉长代码，先口头点到即可，不要默认写进第一版。
6. 数组方法如 `forEach`、链式 `map/filter/reduce` 默认克制使用，除非它比循环明显更短且不影响讲解。
7. 像商品列表 diff 这类题，如果题意包含字段增删改，主版本就要完整覆盖；可以直接用 `Map` 建索引、用 `Set` 合并新旧 key，优先保证正确，再兼顾简洁。

## 口述顺序模板

1. 先说最直接可行的思路
2. 再给思维导图关键点，先把主线讲顺
3. 再把最小可用版快速写出来
4. 再说指针、状态或数据结构怎么变
5. 再说关键边界、时间复杂度、空间复杂度
6. 最后说还能怎么优化
