# 专题题写法

适用范围：

1. 输入 URL 到页面显示
2. 浏览器渲染链路
3. RenderNG / Viz
4. SSR
5. JS 执行机制全链路
6. React 渲染与调度
7. 工程化底层原理题

## 先判断专题类型

1. 标准单链专题：
   适用于一条明确技术主链可以讲清的题，比如浏览器导航与渲染、React Hooks、Vue 响应式、SSR、工程化运行时。
   仓库里的代表例子：
   - `02-高收益八股/浏览器/01-输入URL到页面显示-导航-RenderNG-Viz.md`
   - `02-高收益八股/框架/React/01-React-Hooks-底层与规则.md`
   - `02-高收益八股/框架/Vue/01-Vue2-vs-Vue3-响应式.md`
   - `03-Agent与Codex/01-AI-Coding-复杂页面-Agent化交付-以百度搜索页为例.md`
2. 聚合型专题：
   适用于代码题、输入输出题、手写题、同类面经题汇总，重点不是一条现代实现链，而是先归纳“这组题在考什么”，再逐题展开，最后讲这些题如何串起来。
   仓库里的代表例子：
   - `04-高收益手写题/JavaScript/01-发布订阅-列表Diff-请求去重缓存与超时.md`
3. 专题案例 / 样板专题：
   适用于示范“如何从多道题抽一条总链”，重点是教 AI 学会构造专题，而不是给所有专题提供统一硬模板。
   仓库里的代表例子：
   - `02-高收益八股/JavaScript/01-JS底层全套.md`

## 输出模板

### 模板 1｜标准单链专题

```txt
Part 1｜技术讲解
- 一句话结论
- 主链路图
- 分阶段展开
- [按需] 结论证明材料 / 资料校准说明
- [按需] 关键误判点 / 面试里最容易答浅的地方
- 工程/业务例子

Part 2｜面试作答
- 思维导图关键点
- 60-90 秒口语稿
- 高频追问
- 复习标记

[按需] Part 3｜附录
- 科普补充
- 主要资料依据 / 资料校准说明
- 面试里最容易答浅的地方
- 版本差异 / 延伸阅读
```

### 模板 2｜聚合型专题

```txt
Part 1｜这组题在考什么
- 一句话结论
- 总套路图 / 共性主线

Part 2｜逐题展开
- 原始题干
- 思维导图关键点
- 60-90 秒口语稿
- 最小可用版代码 / 最终结论
- 关键边界 / 高频追问

Part 3｜怎么把这组题串起来
- 共性考点
- 易错点对照
- 面试时如何主动拔高
```

### 模板 3｜专题案例 / 样板专题

```txt
Part 0｜原始题干集合
- 多道原始题干或代表面经题

Part 1｜技术讲解
- 一句话结论
- 总链路图
- 把概念拆开
- 按链路分段展开
- 把原始题干挂回总图
- 关键误判点
- 工程/业务例子

Part 2｜面试作答
- 思维导图关键点
- 60-90 秒口语稿
- 高频追问
- 复习标记

Part 3｜资料
- 官方资料
```

## 通用专题要求

1. 深题必须讲链路、现代实现和工程落地，不能只回到传统八股。
2. 要把“规则链路”和“真实工程意义”一起讲清。
3. 口语稿最后必须落到一个真实业务例子。
4. 不能为了压缩篇幅牺牲说服力，专题稿默认比普通题更厚。
5. 如果用户已经明确认可过某一版回答，落盘版本必须以那一版为下限，不能简化回普通八股。
6. 不要默认把所有专题都写成同一种形状，先判断它是标准单链专题、聚合型专题，还是专题案例 / 样板专题。
7. 普通专题参考样板专题的“组织能力”，不要机械照抄样板专题的篇幅、字段数和展开体量。
8. `结论证明材料` 不是每篇专题都必须单独成节；如果证据已经在分阶段展开里顺手讲清，正文末尾保留参考资料即可。
9. `关键误判点` 也不是每篇专题都必须单独成节；如果只是重复正文主旨，可以压成更短的“面试里最容易答浅的地方”，或者直接并入对应阶段。
10. 如果某些内容更偏科普、补充说明、资料汇总或防错提醒，但会打断正文主链，可以统一后置到 `Part 3｜附录`，优先保证正文顺、短、好理解。

## 搜索与资料使用

1. 只有当专题明确涉及现代实现、版本演进、框架 / 浏览器 / 运行时内部机制，或者用户明确要求最新资料时，才先搜索官方或一手资料。
2. 如果专题是在汇总代码题、输入输出题、手写题这类内容，默认侧重题目归纳、共性总结、口语稿沉淀和题型对比，不需要为了每道题都做复杂的 web search。
3. `web search` 只负责校准，不负责替你写答案；如果搜出来的大段英文不能变成清晰中文主线，那这次搜索就是过度了。
4. 搜索前先明确要校准的具体问题；如果搜完不能让答案更准、更现代，说明这次搜索价值不高。
5. 搜索时优先顺序：官方文档 -> 官方博客 -> 规范或维护者资料 -> 论文或源码文档。
6. 官方 guide / overview / blog 优先于大段规范原文；规范和源码资料主要用于兜底校准，不要把英文原文大段搬进正文。
7. 不要把旧版本实现、历史文章结论、过时八股，写成当前口径。
8. 如果搜索后发现资料之间存在版本差异，要在答案里明确“这是当前官方公开口径”。

## 专项专题约束

1. 如果是浏览器架构题，至少要明确 `browser process`、`renderer process`、`commit`、现代渲染流水线、Viz 或最终出像素路径。
2. 浏览器题优先看 Chromium / Chrome for Developers / MDN。
3. React 题优先看 react.dev。
4. Vue 题优先看 vuejs.org。

## 专题案例 / 样板专题

1. `JS 底层` 更适合作为高复用专题案例，用来辅助 AI 理解：
   - 什么叫“值得做成专题”
   - 专题应该展开到什么粒度
   - 怎么从零散面经题抽出一条总链路
   - 最后成稿应该长什么样
2. `JS 底层` 的定位是“参考答案风格样板”，不是“所有专题都必须满足的硬编码清单”。
3. 写 `JS 底层` 总专题时，优先看 ECMAScript 规范、WHATWG HTML event loop、MDN 对应条目。
4. `JS 底层` 总专题不能只写 `this + 闭包`，至少要串起：编译时、运行时、执行上下文、Lexical Environment、Variable Environment、Environment Record、词法作用域、作用域链、Reference Record、普通函数 `this`、箭头函数、函数对象的 `[[Environment]]`、原型、原型链、`new`、属性查找 vs 变量查找、闭包、`Promise Reaction Job`、微任务、宿主事件循环。
5. `JS 底层` 总专题必须产出：原始题干、总链路图、关键误判点、把面经题串回总图、官方资料链接。
6. 后续如果沉淀出 `浏览器渲染专题案例`、`React 调度专题案例` 等，也应放在这一层，作为“专题如何构造”的样板，而不是继续堆进通用规则。
