# 模块写作与交付

用于把业务需求、技术资料和个人工作整理为总结或答辩模块，并按授权交付正文。普通说明、指南或局部改写不必套用完整路径。

## 从当前阶段推进

```text
业务目标与事实材料
→ 模块主线与收益边界
→ 关键词大纲
→ 带格式、图表职责的详细大纲
→ 连贯正文
→ 本地文件与目标平台交付
→ 回读核对与用户验收
```

这些阶段用于识别当前缺口，不要求逐级审批或建立对应文件。沿用已确认内容，只处理仍需决策的部分；用户只要聊天稿就不落盘，只授权本地就不发布线上。

| 阶段 | 需要解决的判断 | 可以继续的条件 |
|---|---|---|
| 资料整理 | 业务缺口是什么，旧方案为何不足，当前机制与结果有哪些依据 | 已区分事实、目标、交付状态和待补数据 |
| 主线设计 | 哪些工作属于同一目标，各自解决什么问题、产生什么收益 | 子块有独立职责，联系来自共同对象或真实依赖 |
| 关键词大纲 | 每个技术点为何值得写，前后如何承接 | 大纲能说明问题、判断与依据，不只有模块名 |
| 格式大纲 | 每部分适合短段、分点、表格、画板还是截图 | 每种载体有独立信息，必要的图与截图已定义范围 |
| 正文 | 句间是否有解释关系，技术细节是否服务本节问题 | 脱离聊天可读，写作过程不混入正文，缺证据部分明确限定 |
| 交付 | 哪些位置获得写入授权，如何保留现有内容与样式 | 只修改目标范围，按实际可观察条件核对内容与格式 |

## 整体设计的取舍

业务背景优先说明需求对象、已有办法及其剩余限制。PRD 帮助理解为什么要做，代码、方案与运行记录验证具体机制；调查顺序和开发顺序不直接决定文章顺序。

业务接入与公共能力改造可以在共同目标下分块，但分别交代问题、负责范围和结果。总体结构与总览、详述的分工见[主线与章节职责](../逻辑与语言/主线与章节职责.md)；交付能力、业务收益与技术收益的归属见[结果价值与贡献](../内容指导/结果价值与贡献.md)。不将需求整体的业务结果单独归因于其中一项重构。

复杂改造先交代共同问题和整体处理方式，再展开有独立理由的机制；简单接入可以只解释条件、链路和边界。标题优先写动作及具体对象，不固定技术点数量，也不将每节都套成“背景、改造内容、关键设计”。

关键词大纲用于确定内容取舍，格式大纲才明确段落、分块与图表职责。用户已要求直接写正文时，将这些判断用于内部组织，不再交付“这里准备写什么”的大纲。

## 局部内容与形式

技术机制出现前，先让读者知道它解决的问题；同段相邻句需有原因、条件、解释或证据关系。章节转场应指出共同对象或前置依赖，不能依靠连接词或假设的实施顺序。具体改写见[段落展开与承接](../逻辑与语言/段落展开与承接.md)。

丰富格式时，仍先保留完整论证。并列信息可分点，对照关系可分栏，成行成列的数据用表格；长段落不能仅搬进单元格。图、截图、正文分别提供路径关系、真实证据与设计理由，不要求每部分都同时具备这些形式。

画板先定义类型与范围，截图先定义证明对象；只要求占位时保留文字及插入位置，不扩大执行范围。分别读取[图的必要性与选型](../格式与图表/图的必要性与选型.md)、[代码示例与截图](../格式与图表/代码示例与截图.md)。

## 交付与复用

获授权后再执行文件或平台写入。Markdown 特殊标记与飞书原生块的对应、保留线上新改动及回读检查，见[飞书块与重点标记](../格式与图表/飞书块与重点标记.md)。平台命令和接口参数由对应文档技能或工具说明维护，不在本流程复制。

交付时报告实际内容变化、数据缺口和验证范围，不把写入成功等同于正文认可。用户只要求局部改动时，保持其余主线、图表和已确认信息；不要重新生成整篇以绕过精确编辑。

复用时提供读者与用途、资料、已确认内容、当前阶段及本次授权范围即可。章节数量、图表配置、颜色与附录安排按目标和用户约定决定，不能将单篇事实或版式照搬到其他模块。
