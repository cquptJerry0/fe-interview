## 1. 中文优先

中文负责解释问题、机制和因果关系。英文只保留无法准确替代的协议名、框架名和行业术语。

不要把英文翻译成另一个同样难懂的中文名词。注释应说明它在系统中做什么。

推荐：

```text
Harness(智能体运行支撑环境)
Trace(完整执行轨迹)
Checkpoint(执行检查点)
Holdout Set(不参与优化的保留评测集)
```

少用：

```text
Harness(线束)
Trace(追踪)
Checkpoint(检查点)
```

## 2. 英文术语

### 第一次出现

较难术语第一次出现时写成：

```text
英文(精简通俗注释)
```

注释控制在能说明职责的短语，不写完整百科定义。

### 后续出现

同一文档后续直接使用英文或已经确定的中文名，不反复加括号。

### 常用词

Agent、API、RAG、MCP、HTTP、CLI、SDK、SQL、UI、JSON、Git 等常用词可以直接保留。

### 密度控制

一句话出现三个以上较难英文术语时，优先拆句或改成中文。

坏例子：

```text
通过 Memory Consolidation、Skill Discovery、Harness Adaptation 和 Holdout Set 形成 Improvement Loop。
```

改写：

```text
系统先归并零散记忆，再从成功轨迹中提取可复用 Skill。产生新的 Harness 候选后，必须使用未参与优化的保留评测集验证，避免只对历史失败样本有效。
```

## 3. 分点完整性

分点不是关键词容器。每个核心分点必须形成独立句义。

坏例子：

```text
- Memory Consolidation。
- Skill Discovery。
- Harness Adaptation。
```

改写：

```text
- Memory Consolidation(记忆归并)：把多次任务产生的零散经验合并成稳定知识，同时处理重复、冲突和过期内容。
- Skill Discovery(技能发现)：从成功轨迹中识别可复用的方法，并生成能够独立测试和版本化的 Skill。
- Harness Adaptation(运行支撑环境适配)：根据失败证据调整上下文、工具、权限或验证器，而不是直接训练模型。
```

重要分点优先包含：

```text
问题 + 机制 + 边界
```

必要时追加失败或例子，不要求每个分点写成小论文。

## 4. 段落结构

解释型段落采用：

```text
核心判断
→ 工作机制
→ 边界或失败
→ 具体例子
```

设计型段落采用：

```text
现实约束
→ 产生的冲突
→ 关键取舍
→ 结果变化
```

一个段落只推进一个判断。出现两个独立转折时拆段。

## 5. 标题规则

标题负责导航，不承担整段解释。

推荐：

```text
- Agent 执行循环
- 长任务恢复
- Skill 的生成与淘汰
- 权限边界
```

少用：

```text
- 从 Loop 到 Graph 再到 Harness 的全新范式跃迁
- M8.4 Skill
- 核心能力与体系化闭环建设
```

不用字母编号代替自然语言。编号只表示阅读顺序，不表示掌握等级。

## 6. 例子与心智图

抽象概念第一次出现后，优先给一个最小例子：

```text
用户要求发布配置
→ Agent 生成变更
→ 程序校验字段
→ 人工审批
→ 写入外部系统
→ 回读确认
```

图只在能降低理解成本时使用。不要用大图掩盖正文无法说清的逻辑。

## 7. 禁止写法

- 只列术语，不解释问题和机制。
- 连续堆框架名证明“前沿”。
- 使用“形成闭环、赋能业务、全面提升”等抽象结论代替实际动作。
- 使用“如图所示”后逐节点复述。
- 同一段同时解释背景、架构、实现、收益和未来规划。
- 为了显得完整，每个章节使用相同的模板句。
- 把英文首字母缩写继续解释成英文。

## 8. 可读性审计

交付前逐段询问：

- 不认识这个英文词的人能否通过括号知道它做什么？
- 删除术语后，句子是否仍然存在完整逻辑？
- 每个分点能否单独回答一个问题？
- 这一段是在解释机制，还是只在评价价值？
- 是否有一个具体失败或例子帮助理解？
- 图和表是否减少了正文负担，而不是重复正文？
- 是否可以在不损失技术含量的情况下再短一点？
