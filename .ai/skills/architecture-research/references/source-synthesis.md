## 1. 研究问题

先把用户的宽泛目标改写成可验证的决策问题。

例如：

```text
宽泛目标：
研究现在 Agent 应该怎么学。

决策问题：
哪些机制构成当前 Agent 工程的稳定主干？
哪些内容只属于特定框架、课程或前沿研究？
第一轮学习应该投入到什么深度？
```

研究问题至少包含：

- 需要作出的决策。
- 决策影响的对象。
- 时间和版本边界。
- 不属于本次研究的内容。
- 能证明结论的证据。

## 2. 来源选择

按证据强度分层：

| 层级 | 来源 | 主要作用 |
|---|---|---|
| 一级 | 正式协议、官方 API、正式论文、真实请求 | 确认事实、契约和原始结论 |
| 二级 | 官方源码、RFC、架构文档、维护者文章 | 确认实现机制和工程取舍 |
| 三级 | 独立复现、Benchmark、工程复盘 | 检查泛化能力和失败边界 |
| 四级 | 系统课程、书籍、教程、专业博客 | 建立连续知识和发现遗漏 |
| 五级 | 推特、播客、演讲、社区讨论 | 发现线索和争议 |
| 限制使用 | 来源不明的泄漏代码、反编译材料 | 只能提出待验证假设 |

重要结论至少需要：

1. 一个一级或二级来源确认机制真实存在。
2. 一个源码、实验、复现或独立来源确认它解决了真实问题。

## 3. 证据卡片

每份来源先转换成统一卡片：

```text
来源名称：
来源类型：
发布日期或版本：
最后核对日期：
它解决的问题：
核心结论：
关键机制：
适用前提：
已知限制：
失败案例：
与其他来源的关系：
可以进入哪个主题：
证据状态：
仍待确认：
```

证据状态使用：

- 真实运行已验证。
- 代码和配置已确认。
- 官方资料已确认。
- 多来源交叉验证。
- 合理推断。
- 待确认。

不要把“项目 README 声称支持”写成“生产能力已经成熟”。

## 4. 四类中间产物

### 问题地图

列出领域中长期存在的问题，不使用框架名做一级分类。

```text
Agent 长任务
├── 状态如何保存
├── 中断后如何恢复
├── 外部副作用如何避免重复
├── 人工审批如何暂停和继续
└── 如何观察当前进度
```

### 概念归一表

| 原始术语 | 统一概念 | 相同点 | 真实差异 | 主归属 |
|---|---|---|---|---|
| 不同来源中的名称 | 总纲使用的名称 | 共同问题 | 机制或边界差异 | 唯一章节 |

归一不是强行合并。名字相似但控制权、状态或失败语义不同的概念必须拆开。

### 覆盖矩阵

| 稳定问题 | 来源 A | 来源 B | 源码/实验 | 当前结论 | 证据缺口 |
|---|---|---|---|---|---|

覆盖矩阵用于发现：

- 只有单一来源支持的结论。
- 多个来源反复讨论的稳定问题。
- 原始材料已经覆盖但新结构遗漏的内容。
- 热门术语很多但缺少实际机制的方向。

### 冲突矩阵

| 争议点 | 来源 A | 来源 B | 差异原因 | 当前处理 |
|---|---|---|---|---|

优先检查差异是否来自：

- 目标用户不同。
- 系统规模不同。
- 版本或发布日期不同。
- Workflow 与 Agent 定义不同。
- 研究环境与生产环境不同。
- 宣传口径与实际实现不同。

## 5. 合订规则

最终文档按下面的顺序组织：

```text
稳定问题
    ↓
最小工作机制
    ↓
相邻概念边界
    ↓
常见实现模式
    ↓
框架和项目样本
    ↓
失败与验证
```

不要按下面的方式组织：

```text
文章 A 摘要
文章 B 摘要
框架 C 功能
框架 D 功能
```

多份来源重复一个机制时，只保留一处定义，其他来源作为证据或案例引用。

## 6. 冲突处理

- 事实冲突：核对版本、源码和真实行为。
- 术语冲突：回到输入、状态、控制权和输出定义。
- 价值判断冲突：同时保留观点及适用条件。
- 证据不足：标记待确认，不为保证文档完整而编造结论。
- 前沿结论：进入前沿雷达，不直接进入稳定主干。

允许输出“不确定”。高质量研究的目标是缩小未知范围，不是消灭所有未知。

## 7. 完成门槛

来源收集在满足下面条件后停止扩张：

- 主要问题已经由多个独立来源覆盖。
- 新来源不再产生新的稳定问题或关键反例。
- 争议点已经能解释其适用条件。
- 每个主干结论都有足够证据。
- 剩余内容主要是框架 API 和重复案例。

不要因为还能继续搜索就无限增加资料。
