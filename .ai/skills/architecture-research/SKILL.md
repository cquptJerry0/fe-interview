# 知识体系调研与文档架构

## 目标

把分散资料编译成一套可解释、可验证、可维护的知识或架构体系，并让文档数量随独立职责增长，而不是随写作次数增长。

最终体系应满足：

```text
稳定结构
  +
动态状态
  ↓
按当前任务生成视图
```

## 强制原则

1. 先定义要解决的问题和用户工作流，再决定目录与文件。
2. 一个问题只有一个真相源；其他位置只保留定位和链接。
3. 每个产物必须归入`稳定结构`、`动态状态`或`生成视图`。
4. 稳定结构定义长期边界，动态状态记录当前事实，生成视图不得反向成为新的主干。
5. 方法、授课合同、生成规则和质量门禁优先进入 Skill、脚本或自动化，不散落在内容文档中。
6. 固定课表、季度计划、项目路线图等只表示某一时刻的快照；除非业务本身要求固定排期，否则不能成为长期真相源。
7. 先合订知识架构，再设计多文档职责；不按文章来源、文件类型或框架品牌机械拆分。
8. 官方资料、源码、论文和真实系统证据优先于课程与社交媒体。
9. 不用删减知识点换取表面清爽；通过主归属、引用和生成视图消除重复。
10. 不把推断、规划、宣传和待验证方向写成已落地事实。

## 三层产物模型

### 稳定结构

回答长期不随一次任务变化的问题，例如：

- 完整知识边界和概念关系。
- 稳定架构、协议和职责。
- 题库中的真实问题及来源。
- 资料索引和证据等级。

### 动态状态

回答此刻发生了什么，例如：

- 学习进度、薄弱点和掌握证据。
- 项目状态、风险、决策和待办。
- 当前版本、最近实验和待验证假设。

### 生成视图

由稳定结构和动态状态临时编译，例如：

- 当前课程单元。
- 某次评审稿、周报、面试训练或执行计划。
- 针对一个角色、项目或时间窗口的摘要。

生成视图可以被保存以便审计，但必须标明生成依据和时间，不能独立改写稳定结构。

## 任务路由

| 类型 | 目标 | 默认交付 |
|---|---|---|
| 方向调研 | 判断某个领域应该怎么理解和建设 | 研究设计、问题地图、推荐方向 |
| 体系盘点 | 检查现有知识或架构是否完整、现代、重复 | 覆盖矩阵、缺口、重构建议 |
| 多资料合订 | 将多篇文章或多个项目统一成一个心智 | 概念归一表、统一架构、总纲 |
| 多文档重构 | 解决入口混乱、职责重叠和规则散落 | 三层分类、职责表、迁移台账 |
| 动态系统设计 | 用稳定事实和当前状态生成任务视图 | 真相源、状态模型、生成合同 |
| 正式方案写作 | 需求、目标和主要方案已经确定 | 转交`technical-document-writing` |

## 与双轨 CU 的交接

`course-delivery-orchestrator` 与 `technical-document-writing` 是可选的后续能力，不随本 Skill 分发。研究与知识架构整理可以独立完成；需要交接时先确认使用端已安装对应 Skill，未安装则交付材料并说明边界，不假定它们可用。

本 Skill 负责建立稳定知识架构，不负责长期授课。完成技术学习体系时，至少向`course-delivery-orchestrator`交付：

```text
唯一知识总纲
知识点名称与主归属
前置依赖和概念边界
每个知识域的掌握标准
资料索引与证据等级
可选题库或能力目标
学习进度的初始字段
```

`course-delivery-orchestrator`只根据这些稳定输入和当前状态生成 CU，不重新定义知识树。CU 学习中发现的新问题先写成待核实缺口；只有经过来源核实后，才由本 Skill 更新总纲。

## 工作流

### 第一步：读取规则与现状

- 读取适用的`AGENTS.md`、项目规则和业务背景。
- 识别真实仓库根、现有入口、链接、来源、未提交改动和运行约束。
- 盘点每份文档实际回答的问题，不按文件名猜职责。
- 用户只要求调研时，不创建、修改或删除文件。

### 第二步：设计研究

读取[来源合订](references/source-synthesis.md)和[评审门禁](references/review-gates.md)。

先确定：

- 核心决策问题和非目标。
- 需要验证的关键假设。
- 来源类型、版本和证据要求。
- 预期稳定结论、动态状态和生成视图。
- 需要用户确认的高风险取舍。

默认先让用户评审；用户明确要求一步到位时可以继续，但仍需完成内部评审。

### 第三步：标准化来源

为来源建立证据卡片，并形成：

```text
问题地图：领域中有哪些稳定问题
概念归一表：同义词、近义词和真实差异
覆盖矩阵：每个问题有哪些来源和证据
冲突矩阵：来源在哪些结论上不一致
```

涉及当前版本、最新项目状态或前沿方向时，必须核对发布日期、版本和官方来源。

### 第四步：建立统一架构

读取[文档架构](references/document-architecture.md)。

1. 先为每个问题指定唯一真相源。
2. 再将全部产物归入稳定结构、动态状态或生成视图。
3. 按用户完成任务的工作流设计入口和引用关系。
4. 将方法与运行规则迁移到 Skill、脚本或自动化。
5. 为旧内容建立迁移映射，证明没有遗漏。

多文档体系至少明确：

- 唯一主入口。
- 唯一知识或架构主干。
- 每份文档只回答的问题。
- 动态状态怎样更新。
- 生成视图读取哪些输入、何时失效。
- 冲突时由谁拥有定义权。

### 第五步：写一个完整样章或样例视图

读取[中文表达](references/writing-quality.md)和[产物模板](references/output-patterns.md)。

样例必须验证：

- 稳定结论是否足够支撑任务。
- 动态状态是否能改变生成结果。
- 生成视图是否只引用而不复制主干。
- 核心机制、边界、失败和验证是否完整。

先根据样例反馈修正架构，再批量落地。

如果目标是学习体系，样例视图优先使用`course-delivery-orchestrator`生成一个真实双轨 CU，验证总纲是否足以支撑选课、推导、实验和面试训练。

### 第六步：批量落地

- 先写唯一主干，再写状态与索引。
- 最后按需要生成视图，不预建大量空文件。
- README 只负责导航，不承担第二份知识正文。
- 每完成一份文档，重新确认它是否仍只回答一个独立问题。

### 第七步：质量审计

先运行：

```bash
python3 "${CODEX_HOME:-$HOME/.codex}/skills/architecture-research/scripts/validate_doc_system.py" \
  <文档根目录> --entry README.md
```

再人工审计：

- 每个重要问题是否只有一个真相源。
- 所有文档是否能归入三层模型。
- 生成视图是否声明输入、时间和失效条件。
- 运行规则是否仍散落在内容文档中。
- 原有知识点是否全部迁移或明确降级。
- 重要结论是否有原始来源和版本。
- 推断、快照、计划和已落地事实是否区分清楚。
- 本地链接、绝对路径和孤立文档是否清理完成。

脚本只检查结构问题，不能代替语义审计。

## 资源读取规则

- 合订多来源、处理证据冲突时读取[来源合订](references/source-synthesis.md)。
- 设计三层产物、真相源和多文档职责时读取[文档架构](references/document-architecture.md)。
- 写正文、解释术语和检查可读性时读取[中文表达](references/writing-quality.md)。
- 需要暂停等待用户确认时读取[评审门禁](references/review-gates.md)。
- 需要输出研究设计、职责表、迁移台账或生成视图合同时读取[产物模板](references/output-patterns.md)。

## 禁止事项

- 不按“资料一、资料二、资料三”组织最终架构。
- 不让总纲、课程、知识模块、项目目录各自维护一套知识树。
- 不按 README、教程、模板、计划等文件类型先建目录再填职责。
- 不把固定未来计划当成稳定事实。
- 不把生成视图中的临时分组回写为永久知识边界。
- 不让内容文档重复保存 Skill 已定义的方法和质量门禁。
- 不在架构尚未经过样例验证时批量生成大量正文。
- 不把动态选课、授课模板和面试答案重新维护在架构研究 Skill 中。
