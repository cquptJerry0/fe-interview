## 1. 存量链路重构

### 适用判断

项目已有完整业务链路，但随着规模、入口或复杂度增长，旧模型出现超时、积压、状态不一致、重复计算或演进困难。

### 推荐编排

```text
项目标题：重构了哪条完整链路

项目简介：
旧链路由哪些分散机制组成
+ 这些机制共同造成什么系统问题
+ 新架构把链路收敛为什么模型

贡献一：入口或执行模型
贡献二：状态、发布或可靠性模型
贡献三：性能、容量或成本治理

业务收益：仅在存在跨项目结果时单列
```

### 关键心智

- 项目简介必须站在全局视角，不能成为贡献一的重复版本。
- 子故事按架构层次拆，不按事件产生、消费、写库、发布的时间顺序拆。
- 旧链路只介绍理解新架构所需的最小背景。
- 每条技术收益跟随对应故事，不单独汇总成数字清单。

## 2. 0→1 系统建设

### 适用判断

此前没有标准系统，候选人从业务目标出发定义对象、流程、边界和核心能力。

### 推荐编排

```text
项目标题：建设了什么新系统或核心能力

项目简介：
业务为什么需要这套能力
+ 候选人负责的范围
+ 系统由哪些核心层次组成

贡献一：核心领域模型或主流程
贡献二：最难的技术基础设施
贡献三：可靠性、扩展性或工程化

业务收益：
采用规模、转化、效率、收入或组织影响
```

### 关键心智

- 0→1 不需要虚构“原链路混乱”。
- 架构难度来自如何划边界、定义稳定对象、确定最小闭环以及为增长预留扩展点。
- “开发了页面、接口、BFF”不是三个故事，应围绕领域模型和系统能力重新组织。
- 首次落地的业务结果通常很重要，足够大时可以独立成行。

## 3. 平台与基础设施

### 推荐编排

```text
平台主语与服务对象
→ 重复建设或能力分散的根因
→ 稳定内核和扩展协议
→ 可靠性、版本、分发或治理机制
→ 覆盖范围和提效结果
```

可拆成：

- 内核与扩展模型。
- 可靠执行或数据链路。
- 版本、分发与兼容治理。
- 观测、诊断与采用门槛。

避免把插件、缓存、日志、打包分别列成贡献，它们需要归属于一个可记忆的系统能力。

## 4. 复杂技术专项

### 推荐编排

复杂主题可以使用“小标题 + 2～3 个支撑点”，不必强压成单句：

```text
流式传输与状态管理
1. 协议限制如何推动传输层重构。
2. 生命周期模型如何解决乱序、工具调用和 UI 同步。
3. 失败、取消或断线如何恢复。
```

支撑点必须共同证明标题，不能把所有技术亮点收进一个“大杂烩”主题。

## 5. 故事形态选择器

### 架构 Ownership

```text
系统范围
→ 旧边界为何失效或 0→1 如何划界
→ 新分层与核心能力
→ 整体价值
```

### 性能治理

```text
规模与现象
→ 非线性放大根因
→ 计算、存储或调度模型变化
→ 核心性能结果
```

### 可靠性闭环

```text
关键失败场景
→ 原状态边界为何无法恢复
→ 新状态、补偿或回查机制
→ 故障收益
```

### 架构演进与迁移

```text
旧模型在新规模下为何失效
→ 目标模型
→ 兼容、灰度或双写迁移
→ 长期收益
```

### 平台抽象

```text
重复建设的共同根因
→ 稳定内核
→ 差异承接和扩展机制
→ 采用范围或接入收益
```

### Agent 系统

```text
模型不确定性带来的业务风险
→ 工具契约、状态和执行边界
→ 评估、回查和人工兜底
→ 自动化结果
```

## 6. 结果位置选择器

### 写在当前句子

结果只由当前技术贡献产生：

```text
20 分钟 → 24 秒
渲染峰值 120 次/秒 → 40 次/秒
扫描数百面板 → 查询待发布任务
核心包体积控制在 10KB
```

### 单独成行业务收益

结果跨越多个贡献，证明整个项目价值：

```text
首单完成率与转化率提升
覆盖多个国家、业务线或团队
显著降低履约损失或人工运营成本
形成组织级标准能力
```

### 不写

- 无法说明测量方法的数字。
- “提升体验、提高稳定性”等泛化结果。
- 动作数、文件数、接口数等不能证明价值的工作量。
- 与当前技术方案没有直接因果关系的指标。
