# 协作与版本接续

只处理本轮目标，用可见成果换取有效反馈。五步是工作顺序，不是五次审批。

## 进入哪一步

| 用户当前需求 | 行为 |
|---|---|
| 想画图但目的未明 | 提一个推荐主题与范围；只问影响结构的关键问题 |
| 先给骨架 | 做主题和骨架，交付后停，不提前填满细节 |
| 骨架可以，继续后面几块 | 沿用结构和样式，成批补齐约定内容 |
| 只改一处术语或布局 | 只读相关规则，修改节点及受影响邻接区域 |
| 直接快速完成或覆盖 | 内部按五步连续完成，保留写入安全与实际检查 |
| 只要 ASCII + prompt | 交付可直接使用的方案，不创建或更新远端画板 |

一个推荐方案通常足够。有本质不同的取舍才提供备选，不把字体、色值、转换命令等日常工作交给用户选择。用户已给参考时沿用有效规律，不重新问风格问卷。

## 案例与 ASCII 是设计的必经产出

新复杂图和结构重绘必须先按入口匹配好案例、实际读预览和说明，给出完整 ASCII。它同时包含真实分区、组件/颜色/线型图例、完整主链和必要支撑关系。禁止让用户逐项提醒组件，或拆成几段让用户自己拼。

只交设计时停止远端动作；用户已明确直接完成时先给简洁完整设计再连续执行，不额外审批。局部参数反馈保留已有成图与案例，不为一处改词重做全图 ASCII。源码沉淀时把最终修正合入制作链，不留下依赖聊天的手工补丁。

## 最小进度记录

从会话、当前画板及已有源文件恢复，不要求每轮新建文件。长任务可以沿用一份 decisions.json 或简短记录，包含：图的目的、当前步骤、已认可选择、本轮范围、待确认事实、当前版本与验证状态。

这不是强制 schema。已有案例脚本需要 decisions.json 时遵循它实际读取的字段，不为统一记录破坏脚本输入。无需同时维护 normalized、selection、route、plan、layout 等无人使用的文件。

确认可以稳定当前结构，但不代表永远不能改。新事实要求改变已认可边界时，说明原因、影响范围和推荐调整；不要悄悄换一张图。

## 局部更新

先读远端当前图，识别用户改动。保留未涉及节点的身份、位置、配色和文字；只重算受影响容器、连线及标签。整体重排确有必要时先说明。

逻辑上改一个节点不表示接口支持局部 patch。若接口整板替换，基于当前完整结构合并变化，保留备份并 dry-run。写前再次核对本轮涉及区域；发现并发编辑冲突时先协调，不能用旧快照覆盖。回读比较不能代替服务端原子版本保护，不宣称它消除了所有并发窗口。

已有授权覆盖明确目标与范围时不逐轮重复索取；范围扩大、目标改变或删除无关内容时重新确认。参考画板不是写入目标。

## 本轮交付

给当前图或草图，简短说明本轮变化、保留的选择及真实缺口。需要用户判断时只问影响最大的具体问题；无关键问题就完成约定工作，不用“是否满意”“是否继续优化”制造空转。

得到正向反馈后保留版本，后续修改从该版本接续。只有用户要求沉淀时才更新案例与模板；记录具体认可内容，不把一个案例推广为所有图的通用真值。
