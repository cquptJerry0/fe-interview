# 1. 定主题

这一轮先回答：这张图给谁看，主要想体现什么，让读者看完理解什么？从已有上下文提取，不给用户发一套必填问卷。

## 确定范围与表达

用一句话写目的，再明确本图包含与不包含的内容。先核实影响主结构的事实，不为起稿遍历整个代码库；涉及关键机制时继续定向调查。没有依据的推断保留为待确认，不画成事实。

| 想让读者理解 | 合适的表达 | 不要混淆 |
|---|---|---|
| 先做什么，条件变化怎么办 | 流程图：动作、判断与结果 | 系统分层不表示执行顺序 |
| 谁负责什么，如何协作 | 架构图：职责边界、组件与依赖 | 不能按节点数量凑层级 |
| 谁在何时调用谁 | 时序图：参与者、生命线与消息 | 不能用一串说明卡替代时序 |
| 对象如何改变状态 | 状态图：状态、事件和迁移 | 操作名不等于状态 |
| 设计为什么减少成本 | 同口径的旧新对照 | 不能只把新链路换成亮色 |
| 对象如何归属、数据如何分布 | 树、关系图或数据图 | 不给所有关系都加执行箭头 |

图型服务于目的，默认仍用原生组件实现，不在这里选择渲染技术。

一图有多个维度时，先指定主线，其他维度只解释它。例如流程为主，平台和认证作为依赖层。两个问题需要不同讲解顺序且无法建立清楚联系时，建议拆图，并说明各自回答什么，不强行拼成大图。

## 必须先匹配案例

定主题后按 SKILL.md 的案例路由选择最相关成功案例，必须查看真实预览和读取设计说明，再形成骨架。多入口、任务汇合与数据读写优先读 [素材供给案例](../references/material-supply-case.md)；流程与必要依赖层读 [自动发布案例](../references/four-lane-case.md)。案例只提供表达与实现起点，业务事实重新核实。

返回时说明参考哪个案例、沿用什么、本次调整什么。不得只读案例名后从零猜组件，也不得把参考图结构、组件和配色绑成不可拆分模板。

## 本轮交付

给出“本图用于……，重点让读者看懂……，范围到……”，同时提出一个推荐图型。目的已清楚可直接进入骨架；仍有决定整图方向的分歧时，只问最关键的问题。

例如发布图的目的可以是“解释功能合入如何变成可用版本，以及包发布与模板更新为什么分开”。这是目的示例，具体发布机制须核实，不能从这个句子推导系统已实现哪些保障。
