# 3. 填内容

逐块确定节点、文案和连接，让读者不看正文也能沿主体理解系统。先形成完整主线，再挑内部机制展开。

## 按对象写节点

| 对象 | 写法 | 示例 |
|---|---|---|
| 流程动作 | 执行主体：具体动作 | 编排 CI：创建 vX.Y.Z Tag |
| 平台或组件 | 名称，必要时加一句职责 | AgentBuddy；模板平台 |
| 产物或记录 | 对象名与代表的结果 | 本次包与 Skill 发布成功记录 |
| 判断 | 可回答的条件，结果写在线上 | 模板构建成功？ |
| 认证身份 | 身份类型与使用方 | 模板平台服务账号；不展示凭据值 |

“主体：动作”用于需要定位执行方的流程节点，不给平台、数据库和每个图标强行添加两行小字。多次出现同一执行方时，可用清楚的职责区域承接，避免机械重复。

文案用讲解时会说的话：对象明确、动作具体，缩写先交代作用。比如只写“回执门禁”看不出谁等待什么；应依据真实实现表达为“模板 CI：等待本次包与 Skill 发布成功”。版本可配 vX.Y.Z 或已核实的具体示例。

## 补全主体关系

每个动作检查输入、结果和下游，但只把理解本图必需的对象画出来。写记录的节点与读记录的节点都要能找到；平台和认证分开，不把服务账号当作平台。

主步骤不能被子流程吞掉。“创建正式版本 → 发布包 → 发布变更 Skill → 更新模板”是不同动作，不能为了省空间只留下一个“发布”。实际先后、并行、条件执行均以证据为准。

国内与海外行为相同时用站点参数；真实流程或权限边界不同才拆通道，不为两个名字复制整套图。PSM、函数、任务标识只在确有定位价值且已核实的边界出现，不做代码库清单。

## 本轮交付

检查主体能否顺着讲完、区域交接有没有断点、节点名称能否直接读懂。缺事实的地方明确待确认，不靠命名习惯补齐。骨架已认可时成批补内容，只有需要改变结构或发现真实冲突才再次确认。
