# 2. 搭骨架

骨架相当于图的目录与版面。要同时看出讲哪些内容、在哪里讲、如何关联；几个彩色空框或一串标题不足以判断方向。

## 四类骨架

| 类别 | 要定什么 | 完成标志 |
|---|---|---|
| 内容 | 真实区域、各区职责、主要角色、跨区关系 | 能说清每块为什么存在 |
| 位置 | 阅读起点与终点，横纵方向含义，主线、旁路与展开位置 | 能按一个顺序讲下来 |
| 颜色 | 颜色区分阶段、模块还是状态，区域标题与主体的层级 | 同色含义稳定，标题清楚 |
| 图形与图标 | 动作、判断、平台、数据、身份的形状，必要图标和图例 | 形状帮助识别对象，无装饰配额 |

关系是骨架的一部分。先标清执行、调用、读写、依赖或包含，再决定线型与箭头。真实包含可以用空间表达，不额外画执行线；分叉与合流要有业务依据。

## 位置与阅读顺序

流程默认优先单向推进。用户指定“左到右是流程，上到下是架构关系”时，横向承载执行顺序，纵向仅承载归属、依赖或展开；同一流程不得向下折行续写。独立任务可以平行排列，但不能用平行排版暗示实际并发或先后。

这条约定不覆盖标准时序图的纵向时间或用户明确选择的其他方向。内容太长时优先调整粒度或拆图，不通过折行、缩字号隐藏问题。

先预留主线、分支与标签的空间，再放节点。并排区域不必机械等宽；区域有真实边界才加框，简单链路不必套泳道。

## 颜色与符号

从用户参考或已认可的案例取合适参数，允许为当前内容调整。色值集中维护即可，不必取历史样本频率最高的颜色。

颜色主要承担一种分类，必要状态用独立且少量的强调色；不能同一颜色既表示某平台又表示失败。去掉颜色仍应能看懂关键分支，不要求额外生成黑白稿。

图标只在识别参与者或平台有帮助时加入。优先原生形状，例如动作矩形、判断菱形、存储圆柱、产物文档形。短图例只解释本图实际使用且容易混淆的符号。

## 本轮交付

交付包含真实区域名、主要节点、带含义的关联及必要色彩说明的草图。ASCII 适合讨论结构；用户要求在画板搭骨架时，按授权写入原生骨架并验证，不能只发文字代替。

新复杂图有高返工风险时，在这里取得方向反馈。用户已给明确结构或要求直接完成时继续填内容，不强制多轮审批。

需要“细节展开 / 主流程 / 平台 / 认证”布局时，参考 [四通道案例](../references/four-lane-case.md)，不把四通道当作默认所有图型。
