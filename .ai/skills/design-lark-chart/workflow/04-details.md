# 4. 展开细节

细节的用途是解释设计。每项展开都要回答具体问题，并与主图中一个明确的节点或区域关联。

## 选择值得展开的机制

优先选择决定正确性、执行顺序、隔离或成本的机制。问自己：删掉这个细节后，读者是否会误解设计，或无法解释一个重要取舍？如果不会，就留在正文或不画。

| 读者的问题 | 可以怎样展开 |
|---|---|
| 版本从哪里来 | 读取来源 → 选择规则 → 计算结果；配一个核实过的例子 |
| 哪些对象需要发布 | 对比基线 → 筛选变更 → 发布并回查 |
| 为什么不能立刻执行下一步 | 查询状态 → 等待后再查；成功继续，失败或超时转人工 |
| 两个任务同时来会怎样 | 明确竞争范围、取得执行权的条件和未取得时的去向 |
| 为什么性能会改善 | 画出重复范围、共享数据或合并粒度，不只列优化后步骤 |

上述机制只是表达候选，不意味着目标系统具有锁、轮询、超时或自动重试。先核实触发条件、对象身份和失败行为；没有证据时不替系统设计默认值。

## 画成局部关系

局部展开可以是小流程、判断分支、状态变化或少量读写关系。靠近被解释的主节点，用独立边界和有含义的连接说明“展开”而非执行下一步。

主图保留必经步骤。展开不会把“制品 CI 发布 Skill 到 AgentBuddy”缩成“发布”，也不能在下面铺两大块说明文字冒充子流程。

并发要区分“同时触发”“等待某次成功”“同一范围互斥”。一条无名称的虚线不足以同时表达三种关系。异常通道标明停止、跳过、重试或人工处理；不要把错误线混入正常路径。

性能对照保留一致的输入、输出和计时范围。标出成本实际减少的位置；没有测量依据不填写倍数，循环范围、事务边界与部署边界要区分。

## 本轮交付

按图的目的补足必要机制，不按模块平均分配细节。有的区域只需一个节点，有的值得展开三四步。细节挤满画布时重新取舍或拆局部图，不能靠缩字号解决。
