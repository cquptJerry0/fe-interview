# design-lark-chart

先让读者看懂这张图要讲什么，再逐步把内容画实。追求从需求到满意成图的最短路径，保留已认可的选择；不一次堆满细节，也不把五步变成五轮审批。

## 唯一主流程

根据已有进度进入对应步骤，只读本轮需要的文件。

| 步骤 | 定义与产出 | 按需读取 |
|---|---|---|
| 1. 定主题 | 给谁看、主要体现什么、看完应理解什么；确定图型与范围 | [定主题](workflow/01-purpose.md) |
| 2. 搭骨架 | 内容、位置、颜色、图形图标四类骨架，连同跨区关系形成可判断方向的草图 | [搭骨架](workflow/02-skeleton.md) |
| 3. 填内容 | 逐块定义节点、对象、动作、产物与连接；形成完整主体 | [填内容](workflow/03-content.md) |
| 4. 展开细节 | 只展开解释关键设计的计算、判断、等待与异常机制 | [展开细节](workflow/04-details.md) |
| 5. 整体优化 | 检查图能否顺着讲，再处理文案、形状、留白、走线与实际效果 | [整体优化](workflow/05-refinement.md) |

新复杂图先交付能判断方向的主题与骨架。结构已明确或用户要求直接完成时，可以连续执行。用户说“先骨架”就停在骨架；说“后面几个模块继续”就成批补齐，不逐节点请示。

## 接续与确认

- 已有图从当前版本和最近反馈开始，不重新起稿。先识别用户手工修改，保留未涉及区域。
- 主题、边界、阅读方向等高返工成本选择值得确认；工具命令、间距和端口由 agent 处理。
- 仅在真实歧义、授权缺失或必须推翻已认可结构时提问。给一个推荐方案，不默认生成多套风格让用户筛。
- 多轮协作和覆盖已有画板时，按 [协作规则](guides/collaboration.md) 管理范围、进度和局部变更。

## 默认用飞书原生组件

绘制沿用已验证的方式：生成节点和布局 → 转成飞书原生结构 → 必要的属性修正 → 检查、写入、回读和真实导图。DSL 是批量构建的中间格式，用户得到的是可以继续编辑的图形与连接线。

实际画图时读 [原生绘制](guides/native-drawing.md)。不要在每次设计前让用户选择 DSL、代码图或 SVG。仅用户明确指定，或查证原生组件无法满足关键表达时，才读该指南链接的特殊格式说明。

分工：本 skill 管内容与协作；lark-whiteboard-cli 提供组件和转换语法；lark-whiteboard 执行查询、备份、dry-run、更新和导图。需要操作文档容器时再读 lark-doc。不要各启动一遍完整创作流程。

## 内容与权限边界

- 节点与关系来自用户输入或核实过的代码、配置、文档。现状、方案和待确认事实分开，不为丰富画面补造机制。
- 只要 ASCII / prompt 时就交付设计，不为了验收调用远端写入。
- 写入前明确目标与范围，保留用户改动并备份、dry-run；写入后回读和检查真实导图。不能以静态检查或本地预览冒充远端验证。
- 不强制每张图生成一套规划 JSON、黑白稿、测试画板或评分文件；工具实际需要的输入与本轮验证证据仍需保留。
- 默认当前 agent 完成检查，不主动委托子代理；本轮约定完成且无具体阻断问题就交付。
