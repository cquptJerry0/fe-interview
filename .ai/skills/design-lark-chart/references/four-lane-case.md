## 结构怎么用

横向是业务阶段，纵向是信息类型。阶段数量由业务决定，与四条通道数量无关。

| 通道 | 放什么 | 不放什么 |
|---|---|---|
| 细节展开 | 必要的版本计算、增量选择、等待与失败分支，局部流程用虚线框包围 | 凑数的说明卡片、完整代码库映射 |
| 主流程 | 完整的“执行主体：具体动作”，从左到右 | 把必要步骤藏进子流程，再只留下“发布”一个框 |
| 平台 | 平台服务、执行环境，以及与步骤有关的数据或制品 | 服务账号和 Token 冒充平台 |
| 认证 | 真实使用的身份类型及用途 | 凭据值、为对齐而虚构的账号 |

两个独立任务可在主流程通道内使用两个平行基线，但不得将同一条流程折到下一行继续。纵向连线说明局部展开、数据读写或依赖，不冒充执行顺序。共同 Tag 触发两条任务，和后一个任务等待前一个成功，是两种不同的关系，都应保留。

国内与海外重复流程用站点参数表达；只有行为真正不同时才拆通道。图例的形状含义要与业务节点一致，不能用形状丰富度代替真实分类。

## 文案怎么改

先说清动作和对象，再决定是否需要技术名词。读者应能拿着节点直接讲，不需要翻译缩写。

| 难懂的写法 | 本案例的表达 |
|---|---|
| 读取 main、正式 Tag、bnpm | 汇总 main 的 package.json、Git 正式版本 Tag、bnpm 已发布版本 |
| patch + 1 | 版本末位加一；配 0.2.77 → 0.2.78 示例 |
| 阶段互斥（Git CAS） | 同一发布范围一次只运行一个任务；取得占用权后执行 |
| 发布变更 Skill | 制品 CI：发布变更 Skill 到 AgentBuddy；展开“对比上次成功发布 → 筛选变更目录 → 发布并回查” |
| 检查活动工单 | 确认实例没有正在进行的发布；已有任务则停止 |
| 本次成功记录：版本 / Tag / SHA | Git 发布结果：本次包与 Skill 均已发布；画出谁写入、谁读取 |

CAS 的准确解释：先读远端状态，只有它仍等于刚读到的值，才允许更新并取得占用权。另一个任务先更新后，本次抢占失败并重新观察。这里用 Git 引用的按预期 OID 更新实现，不是 Git 自带的业务“锁服务”；不保证 FIFO，失败保留现场，不能画成锁自动过期或无条件抢占。

技术事实来自本案例当时的 main 提交 `1e0fd15a76c8c2145f5636292c55ad2e17b984b2`，不是其他项目的默认规则。正式版本、Skill 基线、命名空间及平台身份在复用前都要重新核实。

## 图形、字体与走线

1. 本案例原生映射：动作 `round_rect`、人工或起止 `round_rect2`、判断 `diamond`、平台 `predefined_process`、执行环境 `hexagon`、存储 `cylinder`、认证 `parallelogram`、版本文件 `note_shape`。正文放在节点内部，不拆成漂浮文字。
2. 形状外框不等于文字区域。平行四边形、菱形、胶囊、圆柱和折角纸张要预留额外内边距。优先改短句、加宽或增高，不能靠把字号缩小来塞文字。英文产品名不得拆成单独尾字母。
3. 本案例字号：标题 48、阶段标题 40、主节点 30、细节 28、连线标签 26。它们是案例参数，不是任何画布通用值。
4. 常规主节点间距 80，阶段间距 144，阶段内边距 32。跨阶段实际空隙还包含两侧内边距。文字为“触发”的线，必须给文字、箭头与两端节点各留出空间；标签长时重新布局，不按固定 gap 硬塞。
5. 本案例保留四区浅蓝、浅青、浅绿、浅灰。颜色表示阶段，形状表示对象身份，不能混成一套不一致的状态编码。
6. 虚线标签也必须占据独立留白。上排主节点向平台的依赖线可能经过下排任务触发线，不能把标签放在交叉点。没有节点的虚实线相交不表示合流；密集交叉需重新布线或拆图。
7. 不为填满单元格添加无用组件。平台名已足够时只写 bnpm、AgentBuddy。不要恢复用户手动删除的地址、长注释或说明框。

## 复现与迁移

先将案例文件复制到当前任务自己的输出目录，所有后续命令在输出目录运行。不要直接修改 skill 中的案例快照。

```bash
node build.cjs
npx -y @larksuite/whiteboard-cli@^0.2.12 -i board.json --check
npx -y @larksuite/whiteboard-cli@^0.2.12 -i board.json --to openapi -o converted.json --format json
node finalize.cjs
```

复用时重新填写执行主体、步骤、阶段、目标平台、数据对象及认证关系。源文件中的颜色和布局参数可以作为起点，不能照抄 vimocli 的任务、命名空间、锁范围或站点。

目标画板 token 不随案例自动复用。写入必须针对本次用户确认的画板，先备份当前节点、保留用户改动、dry-run，再按已有授权更新。

## 本案例验证过的原生细节

- 转换器先产生 DSL 可表达的形状，再修正 SDK 明确支持的原生类型；换形状后重新增加高度并居中，不能只改 type。
- 先定义所有节点，最后定义 connector。写入前检查所有端点引用都属于本次节点集合。
- 显式设置递增 `z_index`，背景和子流程边界先放底层；否则远端可能遮住正文。
- 高 Tag 节点使用不同位置的右侧绑定端口，使两条触发线分别保持水平。
- 调整原生高度后重新计算 connector 的端点、包围盒与相对 turning_points。
- 标签用原生 captions；必要时调整 caption_position，使其离开其他连线交叉点。
- `--check` 通过不代表原生换形状后的文字一定安全。必须回读类型、文字及端点，并检查真实导出图。
- 写后短暂 `2890007` 或加载占位图可有界等待再读，不能立即重建或声称完成。

交付前至少检查：四条通道对齐、主流程未折行、主步骤未被子流程吞掉、平台与认证分开、标签不被夹住、无截字与孤立英文尾字母、执行箭头及数据关系含义正确。
