## 1. 案例一：按技术主题组织复杂项目

原始样例：[优秀简历-技术主题编排.jpg](images/优秀简历-技术主题编排.jpg)

优秀之处：

- 不写“完成 AI 对话应用”，而是提炼“流式传输与状态管理”“渲染与性能优化”“认证与安全”等主题。
- 标题先提供追问钩子，支撑点再解释协议限制、生命周期模型、性能策略和安全边界。
- 多个实现机制共同服务一个技术主题，能够形成连续追问。
- 关键位置使用性能数据，证明技术选择产生了结果。

可复用结构：

```text
技术主题
→ 关键约束
→ 核心架构或模型
→ 2～3 个协同机制
→ 技术结果
```

不能照搬：

- 技术点过多时会变成 API 和框架清单。
- 同一标题下塞入虚拟列表、服务端渲染、布局稳定等不同主题，会削弱主线。
- 单个基础 API 或库名不能直接证明技术难度。

## 2. 案例二：按项目主语建立 Ownership

原始样例：[优秀简历-项目Ownership编排.png](images/优秀简历-项目Ownership编排.png)

优秀之处：

- 先写“参与项目、简介、核心贡献”，读者先理解候选人负责的业务链路。
- 一个项目下的贡献围绕流程、领域对象、服务能力和运行时保障展开，具备总分结构。
- 大项目可以单列“取得收益”，让业务价值与具体实现分层。
- 0→1 建设不会强行套历史性能问题，而是突出主流程建设和能力覆盖。

可复用结构：

```text
项目主语
→ 业务简介与负责范围
→ 正交核心贡献
→ 项目级业务收益
```

不能照搬：

- “使用 Go 开发服务”“使用 Zod 校验”等描述只有技术栈，没有解释为什么构成关键贡献。
- 工作量、接口和字段不能代替架构故事。
- “提高效率、提升健壮性”需要指标或具体失败场景支撑。

## 3. 融合后的编排原则

两份案例分别解决不同问题：

```text
项目级：
用项目主语、简介、核心贡献和业务收益建立 Ownership。

技术级：
用技术主题、关键约束、架构模型、协同机制和技术结果建立深度。
```

最终不要机械套模板，而要让不同层级承担不同职责：

```text
标题负责记忆点
简介负责总览和架构主语
贡献标题负责抛钩子
正文负责难点和设计判断
句内数据负责证明技术结果
独立收益负责证明项目价值
```

## 4. 自动分发链路示例

### 推荐版本

```text
自动分发与发布链路重构

项目简介：负责自动分发、面板同步至正式发布的全链路重构，将同步回调、定时扫表和逐任务写入的分散逻辑，收敛为任务驱动的执行与增量发布链路，解决回调超时、发布半成功和长期任务积压问题。

1. 执行链路任务化：将自动分发、面板同步和素材状态同步从事件回调内直接执行，改为事件建单、消费者异步处理；任务中固化源版本与变更计划，避免重复事件和执行期间配置变化导致结果不一致。

2. 增量发布架构：原定时任务需要遍历数百个面板并逐个比较 Draft 与线上版本，完整扫描耗时约 20 分钟；改为在事务内 upsert 发布任务并合并同一面板的连续变更，定时器只消费真实待发布面板，将变更发现耗时降低至 10 秒内。

3. 批量执行与积压治理：面对生产速度长期高于消费速度造成的 5000+ 任务积压，将逐任务查询和写入改为整批计算最终分类状态，再按面板聚合事务提交；单批耗时由约 20 分钟降至 24 秒，处理效率提升约 50 倍。
```

为什么成立：

- 项目简介建立整条链路的总览和 ownership。
- 三条分别证明执行模型、发布模型和性能模型，互相正交。
- 第一条重点是语义一致性，不强塞性能数据。
- 第二、三条的技术收益直接写在对应句子内。
- 没有足够大的跨项目业务指标，因此不硬加“业务收益”。

## 5. 常见失败写法

### 所有信息塞进一句

```text
在近等量负载下，将 976 个动作、965 个动作、183 个分类和 24 个面板事务……
```

问题：过程数据抢占注意力，面试官反而看不到“改变执行模型”和“解决积压”。

### 抽象词代替技术判断

```text
通过业务幂等键建立幂等边界，统一可靠执行语义。
```

问题：没有说明什么会重复、哪一步需要幂等、如何判断已经生效。

### 项目简介与贡献重复

```text
简介：建设统一发布任务。
贡献：新增 publish_task 统一正式发布。
```

问题：简介没有全局视角，只是提前复述一条贡献。

### 为了格式硬加收益

```text
项目收益：提升系统稳定性与用户体验。
```

问题：没有新增信息，应删除。技术收益留在对应贡献中，业务收益只有足够具体和重大时才单列。
