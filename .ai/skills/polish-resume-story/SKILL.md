# 简历技术故事编排

## 核心目标

简历首先展示一个人的问题定义、逻辑组织和架构判断，其次才是措辞。不要把本 Skill 降级成逐句润色器。

最终项目段落要共同完成五件事：

```text
抛出值得追问的钩子
讲清真正的重难点
呈现系统架构或模型变化
透露关键设计判断与取舍
用结果证明方案成立
```

这五件事由整段项目分层承担，不要求每条贡献同时塞满五项。

## 与上游 Skill 的边界

`extract-resume-stories` 负责业务建模、外部技术调研、多方案选型、架构重建和答辩自洽。

本 Skill 负责把已经成立的项目故事编辑成简历：

```text
确定项目记忆点
→ 选择项目母版
→ 组合正交技术故事
→ 分配每层的信息职责
→ 配置结果证据
→ 压缩为自然表达
```

如果输入只有零散业务背景，且还无法回答“为什么选这个架构”，先调用上游 Skill；不要靠润色虚构技术深度。

## 默认交付原则

简历正文是第一优先级。除非用户要求分析过程，默认先给可直接使用的版本，再用极短说明列出待确认数据或关键取舍。

默认输出：

```text
项目标题
项目简介
2～4 条核心贡献
业务收益（仅在值得单列时出现）
```

不要默认输出长篇方法论、架构分析、评分表或面试稿。

## 工作流

### 1. 锁定项目记忆点

先用一句内部判断回答：

```text
面试官看完这段，只记住候选人 ownership 了什么系统？
```

记忆点应是完整系统能力，例如：

- 自动分发与发布链路重构
- 面向 AI 对话的流式交互与观测体系
- 商家首次入库 0→1 核心能力建设
- 多业务组件与依赖治理平台

不要用函数、页面、接口、工具名或泛化能力词充当项目主语。

### 2. 选择项目母版

先判断项目属于哪种叙事，不要所有经历套同一种句式。

#### A. 存量链路重构

适用于自动分发、发布、同步、审核、交易、数据处理等已有链路改造。

```text
旧链路如何运转且为何开始失控
→ 新架构如何重新划分边界
→ 执行、可靠性、性能等正交子故事
→ 整体业务结果
```

项目简介必须建立全局视角，子故事按系统层次拆分，不能按调用链步骤写流水账。

#### B. 0→1 系统建设

适用于新平台、新业务、新基础设施或首次形成标准能力。

```text
业务机会或能力空白
→ 定义了什么系统边界
→ 搭建哪些关键能力
→ 解决了哪些从无到有的工程难题
→ 采用规模或业务结果
```

不要为了套“旧系统问题”虚构历史包袱。0→1 的难度来自边界定义、核心模型、关键取舍和可持续演进能力。

#### C. 平台与基础设施

适用于 SDK、CLI、组件库、开放平台、治理平台。

```text
重复建设或能力分散
→ 抽象稳定内核
→ 设计扩展与差异承接机制
→ 建立可靠性、版本或分发能力
→ 覆盖范围与提效结果
```

#### D. 复杂技术专项

适用于流式交互、渲染性能、编译工具、监控回放等单一领域足够深的项目。

```text
技术主题标题
→ 关键约束
→ 核心模型或架构
→ 2～3 个协同机制
→ 性能、稳定性或边界结果
```

详细母版和选择条件见 [references/story-layouts.md](references/story-layouts.md)。

### 3. 设计故事组合

从候选内容中选择 2～4 个正交故事。每条应回答不同问题，例如：

```text
执行模型：任务如何创建、执行和保持语义一致
发布模型：变更如何被发现、合并和可靠发布
性能模型：计算与写入如何避免放大
治理模型：规则、权限和版本如何统一演进
观测模型：问题如何定位、回放和归因
```

禁止按以下方式拆分：

- 按开发时间或 Commit。
- 按接口、表、页面、消费者。
- 把同一性能优化拆成“批量查询、缓存、事务”三条。
- 每条都重复“统一、任务化、提高可靠性”。

### 4. 分配信息职责

用层级解决信息密度，不要靠超长句：

```text
项目标题：系统主语和第一记忆点
项目简介：业务范围、旧问题或 0→1 机会、整体架构
贡献标题：面试钩子和技术主题
贡献正文：重难点、关键架构变化、设计判断
句内结果：该技术故事直接产生的技术收益
独立收益行：跨越整个项目的重大业务收益
```

例如“20 分钟降至 24 秒”属于性能故事，应写在该贡献中；“首单完成率提升”“覆盖多个业务线”“减少整体履约损失”属于项目级业务结果，足够重要时再单列。

### 5. 写出技术难度

技术难度通过模型变化与工程约束体现，不靠堆高级名词。

优先表达：

```text
同步回调执行 → 冻结任务异步消费
全量扫描发现变更 → 真实变更增量建单
逐事件重复写入 → 合并计算最终状态
组件内隐式状态 → 显式生命周期模型
人工规则迁移 → 结构化识别与自动门禁
```

每个核心故事至少显露一种判断：

- 普通方案为什么失效。
- 根因位于哪一层。
- 为什么改变执行或数据模型。
- 哪些事件可以合并，哪些必须保持顺序。
- 一致性、失败恢复、兼容或迁移边界如何处理。
- 方案引入了什么代价，为什么可以接受。

“幂等边界、可靠执行语义、增量控制面”等抽象词只有在具体解释后才能使用。

### 6. 配置结果证据

结果必须与当前故事存在直接因果关系。

#### 技术收益

默认写在当前贡献句内，包括：

- 延迟、吞吐、扫描范围、事务数量、资源成本。
- 成功率、重复执行、故障恢复时间。
- 包体积、渲染次数、内存占用。
- 接入时间、构建时间、发布次数。

一条通常只保留最有冲击力的一组数据。不要用动作数、分类数、面板数等过程指标淹没主结果。

#### 业务收益

只有满足以下条件时才单独成行：

- 结果跨越多个技术贡献。
- 能证明整个项目的业务价值。
- 指标对面试官有明确意义。

例如转化率、履约效率、业务覆盖、收入、成本、事故损失或组织采用。泛泛的“提升用户体验和系统稳定性”不单列。

未经确认的线上数字标记为 `待确认`；可以提出合理包装口径，但用户确认后才能进入无标记正文。

### 7. 选择表达形态

不要固定使用“一条只讲一个冲突、一项改造、一组结果”。根据故事复杂度选择：

- 单句闭环：适合边界清楚的性能或可靠性故事。
- 标题 + 两句：第一句讲架构变化，第二句讲关键边界或结果。
- 主题 + 2～3 个支撑点：适合流式系统、监控 SDK、平台基础设施等复杂技术主题。
- 项目简介 + 正交贡献 + 独立业务收益：适合完整链路和 0→1 大项目。

一条内容可以包含多个协同机制，但这些机制必须共同证明同一个技术主题。

### 8. 去除 AI 味

最终逐句检查：

- 是否连续使用“针对、通过、实现、支持、提升”。
- 是否一句话塞入三个以上并列机制。
- 是否为了显得高级加入无解释的抽象词。
- 是否使用“统一、完善、全面、有效”等没有信息量的形容词。
- 是否把开发步骤写成流水账。
- 是否把技术栈或基础 API 当作贡献。
- 是否重复项目简介中的信息。
- 删除后不影响第一遍理解的词，全部删除。

优先使用具体主语和动作：

```text
定时器扫描全部面板
事件侧登记真实变更
消费者合并同面板任务
整批计算最终分类状态
事务只提交发生变化的面板
```

句子应该像工程师复盘自己的项目，而不是像架构术语生成器。

## 人工决策点

只在以下节点需要用户决定：

1. 项目存在两个同样合理的记忆点，且会影响整段定位。
2. 用户需要在严格事实与合理包装之间确定边界。
3. 线上规模、性能数据或业务结果需要确认。

其他工作，包括故事分组、母版选择、信息压缩和自然语言校准，由 Skill 自动完成，不把编辑工作返还给用户。

## 质量门禁

交付前必须通过：

1. 十秒记忆：能否用一句话说出候选人 ownership 的系统？
2. 总分结构：项目简介和子故事是否存在明确的总分关系？
3. 正交性：每条贡献是否证明不同能力？
4. 技术难度：是否看得到普通方案失效和系统模型变化？
5. 架构心智：是否至少透露一个边界、取舍或关键判断？
6. 因果关系：技术手段是否真的能解释结果？
7. 结果配置：技术收益是否就地收口，业务收益是否只在值得时单列？
8. 表达自然：是否像真实工程师，而非模板拼接？
9. 面试可守：每个钩子能否继续回答“为什么、难在哪里、还有什么代价”？

任一核心门禁失败，先重组故事，不要继续润色词语。

## 案例校准

生成最终正文前按需读取 [references/good-cases.md](references/good-cases.md)。学习案例的编排和信息职责，不复制案例中的业务名词、技术栈和数字。
