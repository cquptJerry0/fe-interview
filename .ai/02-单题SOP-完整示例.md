## 完整示例｜`useEffect` 的依赖是浅比较还是深比较？

### Part 1｜技术讲解

#### 1）一句话结论

- `useEffect` 不是深比较。
- 更准确地说，React 会在前后两次渲染之间，对依赖数组的每一项按 `Object.is` 语义比较。
- 基本类型主要看值，引用类型主要看是不是同一个引用。
- 所以对象、数组、函数即使内容看起来一样，只要本次 `render` 产生了新引用，`effect` 还是会重跑。

#### 2）主链路图（ASCII）

```txt
render(n-1)
  deps_prev = [dep1, dep2, dep3]

render(n)
  deps_next = [dep1, dep2, dep3]

逐项比较：
  Object.is(prev[0], next[0]) ?
  Object.is(prev[1], next[1]) ?
  Object.is(prev[2], next[2]) ?

只要有一项不同
  -> 依赖变化
  -> 清理上一次 effect
  -> 执行这一次 effect
```

```txt
函数组件重新 render
        |
        v
函数体重新执行
        |
        v
对象 / 数组 / 函数重新创建
        |
        v
引用变化
        |
        v
effect 重跑
```

#### 3）结论证明材料

最小例子：

```tsx
function Demo({ id }) {
  const query = { id }

  useEffect(() => {
    console.log('effect rerun')
  }, [query])

  return null
}
```

```txt
第 1 次 render: query -> ref A -> { id: 1 }
第 2 次 render: query -> ref B -> { id: 1 }
Object.is(ref A, ref B) === false
=> effect 重跑
```

反例：

```tsx
function Demo({ id }) {
  const query = useMemo(() => ({ id }), [id])

  useEffect(() => {
    console.log('effect rerun')
  }, [query])

  return null
}
```

```txt
第 1 次 render: query -> ref A
第 2 次 render: query -> ref A
Object.is(ref A, ref A) === true
=> effect 不重跑
```

#### 4）工程视角

- 真实项目里最常见的问题，不是“不会背浅比较”，而是接口请求、筛选对象、回调函数在每次 `render` 时都变成了新引用。
- 这样页面看起来“数据没变”，`effect` 却一直重跑，最终表现成重复请求、重复订阅或日志刷屏。
- 工程上优先解法不是先上 `useMemo` / `useCallback`，而是先拆成真正需要的原子依赖。
- 只有当对象或函数必须作为整体复用，而且稳定引用确实有价值时，才考虑 `useMemo` / `useCallback`。

### Part 2｜面试作答

#### 1）20 秒快答

- `useEffect` 不是深比较，而是对依赖数组逐项按 `Object.is` 比较。基本类型主要看值，引用类型主要看引用是不是同一个，所以对象、数组、函数很容易因为新引用导致 effect 重跑。

#### 2）60-90 秒口语稿

- 我不会直接把这题答成“浅比较”三个字。更准确的说法是，React 会在前后两次渲染之间，对依赖数组逐项按 `Object.is` 去比较。基本类型主要看值，引用类型主要看是不是同一个引用。函数组件每次重新渲染都会重新执行函数体，所以如果依赖里放的是对象、数组、函数，这些值往往会在每次 `render` 里生成新引用。这样即使内容看起来一样，也会被判定成依赖变化，effect 就会重跑。工程上我会优先把依赖拆成真正需要的原子值，只有确实需要稳定对象或函数引用时，才会用 `useMemo` 或 `useCallback`。

#### 3）高频追问

##### 追问 1｜为什么 React 不做深比较？

- 深比较成本高，组件渲染频繁时会带来额外性能负担。
- 深比较语义也不稳定，框架无法替你猜“你依赖的是整个对象，还是对象里的某几个字段”。
- React 更希望开发者显式声明依赖边界，而不是由框架隐式推断。

##### 追问 2｜依赖里放函数为什么也容易重跑？

- 因为函数本质上也是引用类型。
- 函数组件每次 `render`，函数体里的函数声明都会重新创建。
- 如果把这个函数直接放进依赖数组，它每次都可能是新引用，effect 就会重跑。

##### 追问 3｜是不是所有对象依赖都应该改成 `useMemo`？

- 不是。
- 第一选择永远是依赖真正需要的原子值。
- `useMemo` 适合的是“这个对象必须整体复用，而且稳定引用真的有价值”的情况。

##### 追问 4｜线上发现 `useEffect` 老是重跑，你怎么排查？

- 先看依赖数组里有没有对象、数组、函数。
- 再确认是不是父组件频繁 `render` 带下来的。
- 再把每一项依赖单独打印出来，看究竟是谁变了。
- 能拆成原子值就拆，必须保留引用类型时再考虑 `useMemo` / `useCallback`。

##### 追问 5｜为什么开发环境里有时会执行两次？

- 这不一定是依赖比较的问题。
- 在 React 18 开发环境下，如果开启了 `StrictMode`，某些副作用会被额外执行一次，用来帮助发现不安全副作用。
- 所以要先区分：到底是依赖真的变了，还是开发环境的额外检查行为。

#### 4）关联专题 / 复习标记

- 复习标记：`可展开`
- 继续深挖：`Hooks` 规则、`useLayoutEffect` 时机、stale closure、StrictMode 双执行，这些应该进入系统专题，而不是继续在单题里硬塞。

## 完整示例｜`BFC 是什么？margin collapse 怎么判断？怎么打断？`

### Part 1｜技术讲解

#### 1）一句话结论

- BFC 可以理解成独立的块级排版区域，内外布局边界彼此隔离。
- `margin collapse` 是垂直方向相邻块级盒子的 `margin` 合并规则，不是浏览器 bug。
- 打断折叠的核心不是背触发点，而是让两个 `margin` 不再满足“可以相邻合并”的条件。

#### 2）主链路图（ASCII）

```txt
先判断当前是不是普通块级文档流
  -> 再看两个 margin 是否在垂直方向相邻
  -> 再看中间是否被 border / padding / 内容 / 新格式化上下文打断
  -> 满足时才会发生折叠
```

```txt
兄弟元素折叠

块 A   margin-bottom: 30
  |
  |  垂直相邻
  v
块 B   margin-top: 20

最终间距不是 50
而是 30
```

```txt
父子折叠

parent
  └─ child margin-top: 20

如果 parent 没有 border / padding / 内容
child 的 margin-top 可能直接顶到 parent 外面
```

#### 3）结论证明材料

主方案 vs 打断方案：

```txt
主方案：普通块级流里直接相邻
  -> 发生折叠

打断方案 A：给 parent 加 padding-top
  -> margin 不再直接接触

打断方案 B：给 parent 建立新的格式化上下文
  -> 常见写法：display: flow-root / overflow: hidden
```

最小样式例子：

```css
.parent {
  display: flow-root;
}

.child {
  margin-top: 20px;
}
```

```txt
这里的重点不是记住某个属性名，
而是知道它为什么能把这块布局边界隔开。
```

#### 4）工程视角

- 项目里最常见的误判是：你以为自己给子元素加了 `margin-top`，结果视觉上像是父元素整体往下掉。
- 另一个高频坑是为了“顺手解决折叠”直接写 `overflow: hidden`，最后把阴影、超出内容也一起裁掉。
- 所以工程上我会先区分：我是只想打断折叠，还是顺便还要处理浮动、裁剪、滚动等问题。

### Part 2｜面试作答

#### 1）20 秒快答

- BFC 是独立的块级排版区域，`margin collapse` 是垂直相邻块级盒子的 `margin` 合并规则。判断关键看它们是不是处在可合并的普通块级流里，打断的核心思路就是让两个 `margin` 不再相邻，比如加 `padding`、`border`、内容，或者新建 BFC。

#### 2）60-90 秒口语稿

- 我会把这题拆成两层讲。第一层，BFC 可以理解成一块独立的块级排版区域，里面和外面的布局边界是隔离的。第二层，`margin collapse` 不是 bug，而是普通块级流里垂直方向相邻盒子的 `margin` 合并规则。最常见的是兄弟块之间的 `margin-bottom` 和 `margin-top` 合并，父子之间如果父元素没有 `border`、`padding`、内容，也会出现子元素的 `margin-top` 顶到父元素外面的现象。打断折叠的核心就是让这两个 `margin` 不再满足“可相邻合并”的条件，所以常见做法是加 `padding`、`border`、插入内容，或者让父元素建立新的格式化上下文。工程上我会特别注意副作用，比如 `overflow: hidden` 虽然能打断折叠，但也可能把阴影和溢出内容裁掉。

#### 3）高频追问

##### 追问 1｜为什么父子元素也会发生折叠？

- 因为如果父元素顶部没有边框、没有内边距、也没有内容把它们隔开，子元素的 `margin-top` 就可能和父元素外侧发生折叠。

##### 追问 2｜为什么 `overflow: hidden` 能打断折叠？

- 因为它会让元素建立新的格式化上下文，内外布局边界被重新隔开。
- 但它不只是“打断折叠”，还会带来裁剪等副作用。

##### 追问 3｜`flex` / `grid` 里还会按原来方式折叠吗？

- 常见的普通块级流折叠规则，在 `flex item`、`grid item` 场景下不会原样套用。
- 所以判断前要先确认当前讨论的是哪一种布局上下文。

#### 4）关联专题 / 复习标记

- 复习标记：`可快答`
- 继续深挖：这题当前先挂在布局 / 格式化上下文这条线，没有单独专题时不要把它硬写成 CSS 大全。

## 完整示例｜`大图加载失败怎么处理？`

### Part 1｜技术讲解

#### 1）处理目标 / 一句话判断

- 大图加载失败不是简单的“裂图不好看”，而是一个可用性、稳定性和可追踪性问题。
- 我不会只写一个 `onError` 换默认图，而是按 `预防 -> 降级 -> 恢复 -> 监控` 四层处理。

#### 2）主链路图（ASCII）

```txt
请求原图
  |
  +-- 成功 -> 展示原图
  |
  +-- 失败
        |
        +-- 降级到低清图 / 缩略图 / 备用 CDN
        |      |
        |      +-- 成功 -> 展示降级图
        |
        +-- 仍失败 -> 展示占位图 / 错误态 / 重试入口
                         |
                         +-- 上报监控
```

#### 3）结论证明材料

最小兜底链路：

```txt
加载前
  -> 预留尺寸，避免布局抖动

加载失败
  -> 先切备用资源
  -> 再失败则展示占位图
  -> 高价值图片给重试按钮
  -> 上报失败信息
```

最小伪代码：

```txt
load original
  -> fail ? try fallback : show original
fallback fail
  -> show placeholder
  -> report error
```

#### 4）工程视角

- 真实项目里，不同图片价值不同：商品主图、封面图、头像图的容错策略不能一样。
- 高价值图片更强调恢复能力和重试入口；列表缩略图更强调整体页面可用和布局稳定。
- 所以不能把这题答成一个统一技巧点，而要体现业务分层和取舍。

### Part 2｜面试作答

#### 1）20 秒快答

- 大图加载失败我不会只写 `onError` 换默认图，而是按 `预防 -> 降级 -> 恢复 -> 监控` 四层处理：先固定尺寸避免抖动，失败后优先切低清图或备用资源，再失败就展示占位图或错误态，高价值图片给重试入口，最后把失败信息上报出来。

#### 2）60-90 秒口语稿

- 这题我会按四层处理。第一层是预防，图片在加载前就要预留尺寸，比如固定宽高或者 `aspect-ratio`，避免加载失败后页面抖动。第二层是降级，原图失败后优先切低清图、缩略图或者备用 CDN，而不是直接空白。第三层是恢复，如果这是用户强关注的图片，比如商品详情主图，我会给重试入口；如果只是列表缩略图，就优先保证整体页面可用。第四层是监控，要上报图片 URL、业务 ID、网络环境、失败类型和重试次数，方便区分到底是资源失效、CDN 异常还是前端加载策略有问题。这样回答能体现我不是只会前端技巧，而是有完整的稳定性思路。

#### 3）高频追问

##### 追问 1｜为什么不能只在 `onError` 里换默认图？

- 因为那只是“最后一层兜底”。
- 如果前面不做尺寸预留、资源降级和监控，页面仍然可能抖动、空白，而且问题不可追踪。

##### 追问 2｜什么场景需要重试，什么场景直接降级？

- 用户强关注、单张价值高的图片更适合给重试入口。
- 列表缩略图这类低价值资源，通常优先保证整体页面可用，不需要频繁打断用户操作。

##### 追问 3｜监控里至少要带哪些字段？

- 图片 URL、业务 ID、失败类型、网络环境、是否走了备用资源、重试次数。
- 这样后面才能区分资源失效、网络波动还是 CDN 异常。

#### 4）关联专题 / 复习标记

- 复习标记：`可展开`
- 继续深挖：如果后续要把图片懒加载、失败降级、曝光统计、CDN 策略打通，再单独建“图片稳定性链路”专题。

## 完整示例｜`CSS Modules、Tailwind、CSS-in-JS 怎么选？`

### Part 1｜技术讲解

#### 1）选择结论

- 我不会把这题答成“哪种方案绝对最好”，而会答成“什么场景怎么选”。
- 团队规范强、追求统一和低运行时成本时，我更偏向 `Tailwind + CSS Variables`。
- 组件边界清晰、希望样式局部隔离时，`CSS Modules` 很稳。
- 只有在确实需要高频运行时动态样式时，我才会考虑 `CSS-in-JS`，因为它通常会带来更高的运行时和调试成本。

#### 2）主链路图（ASCII）

```txt
先看项目诉求
  |
  +-- 要统一规范、开发效率、低运行时成本
  |      -> Tailwind + CSS Variables
  |
  +-- 要组件本地隔离、语义 class、构建期处理
  |      -> CSS Modules
  |
  +-- 要根据 props / 运行时状态动态生成复杂样式
         -> CSS-in-JS
```

#### 3）结论证明材料

最小对比表：

| 方案 | 优势 | 代价 |
| --- | --- | --- |
| `Tailwind + CSS Variables` | 统一、开发快、运行时轻 | 类名多，约束感强 |
| `CSS Modules` | 局部隔离、构建期处理、稳定 | 动态主题表达不如变量体系自然 |
| `CSS-in-JS` | 动态能力强、和 JS 状态贴近 | 运行时成本更高、调试链路更重 |

选项本体拆解：

- `CSS Modules` 更像“构建时做局部作用域映射”。
- `Tailwind` 更像“用一套约束化原子类提升一致性”。
- `CSS-in-JS` 更像“把样式表达拉到 JS 运行时里”。

#### 4）工程视角

- 选型不能只看写法喜好，还要看团队协作、主题系统、运行时性能、调试成本。
- 如果业务里大量样式是静态的，却为了少量动态场景全盘上 `CSS-in-JS`，通常得不偿失。
- 反过来，如果组件样式和运行时状态强绑定很深，完全拒绝动态方案也会让代码变得别扭。

### Part 2｜面试作答

#### 1）20 秒快答

- 这题我不会答成谁绝对更好，而会看场景：统一规范和低运行时成本优先时，我更偏 `Tailwind + CSS Variables`；组件隔离更重要时用 `CSS Modules`；只有确实需要复杂运行时动态样式时，才考虑 `CSS-in-JS`。

#### 2）60-90 秒口语稿

- 我不会上来就说哪种 CSS 方案绝对最好，而是先看团队规范、样式隔离需求、运行时动态程度和主题扩展成本。中后台或者设计规范强的项目，我更倾向 `Tailwind + CSS Variables`，因为开发效率高、统一性强，而且运行时比较轻。组件边界清晰、需要本地样式隔离时，我会用 `CSS Modules`。`CSS-in-JS` 不是不能用，但我只会在确实需要根据 props 或运行时状态动态生成复杂样式时再用，因为它通常会带来额外运行时成本和更重的调试链路。所以这题的高分点不是背方案名，而是能讲清每个方案本体是什么、适用边界是什么、为什么在这个团队和项目里这么选。

#### 3）高频追问

##### 追问 1｜为什么你不是默认推荐 `CSS-in-JS`？

- 因为它的动态能力很强，但代价通常是更高的运行时成本、更复杂的注入顺序和调试链路。
- 如果业务大部分样式是静态的，这个代价未必划算。

##### 追问 2｜为什么 `Tailwind` 常和 CSS Variables 一起说？

- 因为 `Tailwind` 负责统一表达和开发效率，CSS Variables 更适合承接主题和语义变量。
- 两者配合后，既有统一性，也能保留主题扩展能力。

##### 追问 3｜`CSS Modules` 的核心价值是什么？

- 它最稳的价值是“局部作用域隔离”和“构建期处理”。
- 如果你希望组件样式边界清晰，又不想引入额外运行时负担，它通常是很稳的选择。

#### 4）关联专题 / 复习标记

- 复习标记：`可展开`
- 继续深挖：如果后续把设计令牌、主题映射、CSS 方案选型和运行时成本统一打通，再单独建“CSS 方案与主题系统”专题。

## 结构变体速览

不同题目，`Part 1` 的讲法可以不同，但都要保留“结论 + 图 + 证明 + 工程视角”的外壳：

- JS 原理题：适合按 `编译时 -> 创建环境 -> 运行时绑定 / 查找 -> 输出结果` 讲。
- CSS 图解题：适合按 `约束关系图 -> 失败原因图 -> 主方案 / 打断方案 -> 最小样式例` 讲。
- 场景题：适合按 `问题拆解 -> 分层处理 -> 恢复 / 降级 -> 监控排查` 讲。
- 对比题：适合按 `选择结论 -> 决策树 -> 最小对比表 -> 适用边界` 讲。
