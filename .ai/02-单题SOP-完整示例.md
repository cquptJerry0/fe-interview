## 八股题完整示例

### 完整实例｜`useEffect` 的依赖是浅比较还是深比较？

#### 模块 1｜主回答

##### 1）一句话结论

- `useEffect` 不是深比较。
- 更准确地说，React 会在前后两次渲染之间，对依赖数组每一项按 `Object.is` 语义比较。
- 基本类型主要看值，引用类型主要看是否还是同一个引用。
- 所以对象、数组、函数即使内容一样，只要本次 `render` 产生了新引用，`effect` 就会重新执行。

##### 2）原理图（ASCII）

```txt
render(n-1)
  deps_prev = [dep1, dep2, dep3]

render(n)
  deps_next = [dep1, dep2, dep3]

逐项比较：
  Object.is(prev[0], next[0]) ?
  Object.is(prev[1], next[1]) ?
  Object.is(prev[2], next[2]) ?

只要有一项不同
  -> 依赖变化
  -> 清理上一次 effect
  -> 执行这一次 effect
```

```txt
函数组件重新 render
        |
        v
函数体重新执行
        |
        v
对象 / 数组 / 函数重新创建
        |
        v
引用变化
        |
        v
effect 重跑
```

##### 3）最小例子

```tsx
function Demo({ id }) {
  const query = { id }

  useEffect(() => {
    console.log('effect rerun')
  }, [query])

  return null
}
```

```txt
第 1 次 render: query -> ref A -> { id: 1 }
第 2 次 render: query -> ref B -> { id: 1 }
Object.is(ref A, ref B) === false
=> effect 重跑
```

##### 4）面试口语稿

- `useEffect` 不是深比较。更准确地说，React 会在前后两次渲染之间，对依赖数组逐项按 `Object.is` 做比较。基本类型主要看值，引用类型主要看是不是同一个引用。函数组件每次重新渲染都会重新执行函数体，所以如果依赖里放的是对象、数组、函数，这些值往往会在每次 `render` 时生成新引用。这样即使内容没变，也会被判定为依赖变化，`effect` 就会重跑。工程上处理这类问题，优先把依赖拆成真正需要的原子值；只有在确实需要稳定对象或函数引用时，再使用 `useMemo` 或 `useCallback`。`

#### 模块 2｜深入展开

##### 1）原理链路

```txt
题面：浅比较还是深比较？
  -> 本质：依赖变化怎么判定
  -> 再往下：为什么引用类型容易变
  -> 再往下：为什么函数组件 render 会产生新引用
  -> 结果：effect 为什么会异常重跑
```

- 这题不能只停在“浅比较”这个标签。
- 真正要讲清的是：React 会记录上一次依赖数组，然后在本次渲染后逐项比较。
- 一旦依赖里出现对象、数组、函数，而这些值又在函数体里临时创建，就很容易因为引用变化而触发重跑。

##### 2）业务化解释

```tsx
function ListPage({ status, keyword, page }) {
  const filters = { status, keyword, page }

  useEffect(() => {
    fetchList(filters)
  }, [filters])
}
```

- 这个场景在列表页、搜索页、筛选页里很常见。
- 只要页面重新渲染，`filters` 就是新对象，请求就可能重复触发。
- 如果页面里还有防抖、分页、排序联动，这类问题会更明显。

##### 3）取舍 / 易错点

- 优先方案：直接依赖原子值，比如 `[status, keyword, page]`。
- 次优方案：确实需要复用对象时，再用 `useMemo` 稳定引用。
- 常见误区 1：只会背“浅比较”，讲不出为什么。
- 常见误区 2：看到重复执行就无脑上 `useMemo` / `useCallback`。
- 常见误区 3：少写依赖来“骗过” `effect`，结果引入旧值闭包问题。

##### 4）深挖判断

- 这题应该补内部专题深挖卡。
- 原因：它天然会连到 `Hooks` 原理、`useEffect` 重跑排查、`useLayoutEffect` 时机、闭包旧值等问题。

##### 难题加厚｜额外图

```txt
不稳定依赖
  render 1 -> { id: 1 } -> ref A
  render 2 -> { id: 1 } -> ref B
  A !== B -> effect 重跑

稳定依赖
  useMemo(() => ({ id }), [id])
  render 1 -> ref A
  render 2 -> ref A
  A === A -> effect 跳过
```

##### 难题加厚｜额外例子

```tsx
function Demo({ id }) {
  const query = useMemo(() => ({ id }), [id])

  useEffect(() => {
    fetchData(query)
  }, [query])
}
```

##### 难题加厚｜精炼伪代码

```txt
changed = false
for i in deps:
  if !Object.is(prevDeps[i], nextDeps[i]):
    changed = true
    break

if changed:
  cleanup(prevEffect)
  run(nextEffect)
```

#### 模块 3｜追问与详细回答

##### 追问 1｜为什么 React 不做深比较？

- 深比较成本高。组件 render 频繁时，如果每次都递归比较复杂对象，会带来额外性能开销。
- 深比较语义也不稳定。框架不知道你是依赖整个对象，还是只依赖其中某几个字段。
- React 更希望开发者显式声明依赖边界，而不是由框架替你猜。

##### 追问 2｜依赖里放函数为什么也容易重跑？

- 因为函数本质上也是引用类型。
- 函数组件每次 render，函数体里的函数声明也会重新创建。
- 如果把这个函数直接放进依赖数组，它每次都可能是新引用，`effect` 就会重跑。
- 处理时优先判断这个函数是否只在当前 `effect` 内部使用；如果是，直接挪进 `effect`。只有在需要复用或向下传递时，再考虑 `useCallback`。

##### 追问 3｜是不是所有对象依赖都应该改成 `useMemo`？

- 不是。
- 第一选择永远是：依赖真正需要的原子值。
- `useMemo` 适合的是“这个对象必须作为整体被复用，而且引用稳定确实有价值”的情况。
- 如果只是为了让 `effect` 不重跑就滥用 `useMemo`，代码会变得更绕，维护成本也更高。

##### 追问 4｜如果线上发现 `useEffect` 老是重跑，你怎么排查？

- 先看依赖数组里有没有对象、数组、函数。
- 再确认是不是父组件频繁 render 带下来的。
- 再把每一项依赖单独打印出来，看究竟是谁变了。
- 能拆成原子值就拆，不要优先上 memo。
- 必须保留引用类型时，再考虑 `useMemo` / `useCallback`。
- 最后用 React DevTools 看组件为什么重新渲染。

##### 追问 5｜为什么我感觉依赖没变，开发环境里还是执行了两次？

- 这不一定是依赖比较的问题。
- 在 React 18 开发环境下，如果开启了 `StrictMode`，某些副作用会被额外执行一次，用来帮助发现不安全副作用。
- 所以要先分清：到底是依赖真的变了，还是开发环境的额外检查行为。


## 场景题完整示例

### 完整实例｜`大图加载失败处理`

#### 模块 1｜主回答

##### 1）处理目标

- 目标不是“裂图别太丑”，而是保证页面可用、布局稳定、用户有后续动作、问题可追踪。
- 我会按 `预防 -> 降级 -> 恢复 -> 监控` 四层处理，而不是只在 `onError` 里换一张默认图。

##### 2）分层处理图（ASCII）

```txt
请求原图
  |
  +-- 成功 -> 展示原图
  |
  +-- 失败
        |
        +-- 降级到低清图 / 备用 CDN / 缩略图
        |      |
        |      +-- 成功 -> 展示降级图，并保留查看原图入口
        |
        +-- 仍失败 -> 展示占位图 / 错误态 / 重试按钮
                         |
                         +-- 上报监控
```

```txt
页面加载前
  -> 预留宽高 / aspect-ratio
  -> 避免失败后布局抖动
```

##### 3）兜底流程 / 最小方案

- 先固定宽高或 `aspect-ratio`，避免布局塌陷。
- 原图失败后，优先切缩略图、低清图或备用域名。
- 如果仍失败，展示占位图或错误态；高价值图片再给重试入口。
- 最后上报失败信息，区分资源问题、网络问题还是 CDN 问题。

##### 4）面试口语稿

- 大图加载失败我不会只写一个 `onError` 换默认图，而是分四层处理。第一层是预防，图片在加载前就要固定尺寸，避免失败后页面抖动，同时优先做懒加载、多尺寸图和 CDN 处理。第二层是降级，原图失败后优先切到低清图、缩略图或者备用 CDN，而不是直接空白。第三层是恢复，如果这是用户强关注的图片，比如商品详情主图，我会给重试入口；如果是列表缩略图，就优先保证整体页面可用。第四层是监控，要上报图片 URL、业务 ID、网络环境、失败类型和重试次数，方便判断到底是资源失效、CDN 异常还是前端加载策略有问题。`

#### 模块 2｜深入展开

##### 1）问题拆解

```txt
大图失败不只是“显示不出来”
  -> 用户体验：空白、抖动、点击中断
  -> 性能策略：是否应该直接加载原图
  -> 稳定性：是否有降级和重试
  -> 根因治理：是否能定位资源 / CDN / 网络问题
```

- 场景题核心不是背 API，而是把问题拆成体验、稳定性、性能、监控四层。

##### 2）业务场景

- 商品详情页主图失败，影响的是转化，不能只给一个裂图图标。
- 图库、社区、作品集页面，大图很多，优先要控制首屏成本，通常先给缩略图，再按需切原图。
- 弱网环境下，大图失败可能不是资源不存在，而是超时或链路不稳定，这时降级图比一味重试更重要。

##### 3）取舍 / 易错点

- 高价值单图：可以重试，可以保留“查看原图”入口。
- 列表批量图：优先缩略图和占位图，避免大量失败请求拖垮页面体验。
- 不建议无限重试，否则会放大网络抖动和 CDN 异常。
- 不建议只在前端吞掉错误，不做监控。
- 常见误区：只会说 `img onError`，没有分层处理；忽略布局抖动；不区分资源失效和弱网超时。

##### 4）专题判断

- 这题适合挂到“图片加载链路”“前端稳定性兜底”“监控与告警”三个专题。
- 如果后续追到懒加载、预加载、CDN、多尺寸图策略，应单独补专题卡。

##### 难题加厚｜额外图

```txt
高价值图片
  原图失败 -> 低清图 -> 备用 CDN -> 占位图 -> 重试入口

批量列表图
  缩略图失败 -> 占位图 -> 记录失败 -> 不阻塞页面主体
```

##### 难题加厚｜额外例子

- 商品详情页主图：需要重试和查看原图入口。
- 瀑布流列表缩略图：优先页面流畅，不让单张图失败拖垮整体体验。

##### 难题加厚｜精炼伪代码

```txt
load(primaryUrl)
  -> success: show(primary)
  -> fail: load(fallbackUrl)
       -> success: show(fallback)
       -> fail: show(placeholder)

report({
  primaryUrl,
  fallbackUrl,
  bizId,
  network,
  errorType,
  retryCount
})
```

#### 模块 3｜追问与详细回答

##### 追问 1｜怎么避免图片失败时页面抖动？

- 在图片加载前就要预留稳定空间，常见做法是固定宽高或使用 `aspect-ratio`。
- 这样即使图片失败，页面结构也不会塌陷，用户看到的是占位态或错误态，而不是整块内容跳动。

##### 追问 2｜为什么不能只用默认占位图？

- 因为默认图只能解决“别空着”，解决不了“用户还想继续看内容”。
- 对高价值图片，更合理的是分级降级：原图失败先切低清图，再不行才占位图，同时保留重试或查看原图入口。

##### 追问 3｜怎么区分是资源失效，还是网络太慢？

- 前端先记录错误事件、超时信息、当前网络环境、失败域名和重试次数。
- 再结合 CDN 日志和资源状态看，是 `404 / 403`、防盗链、资源损坏，还是区域网络波动。
- 前端负责暴露现场，根因定位通常要结合服务端和 CDN。

##### 追问 4｜为什么要做多尺寸图，而不是总上原图？

- 很多场景并不需要原始大图，比如列表页、卡片流、预览态。
- 直接上原图会拉高首屏成本，也放大失败概率。
- 更合理的策略是列表页先缩略图，详情页再按需切高分辨率图。

##### 追问 5｜监控要上报什么？

- 至少要有图片 URL、业务 ID、页面位置、网络环境、设备信息、失败类型、重试次数、是否降级成功。
- 这样后面才能分清是单资源问题、某个 CDN 节点问题，还是某个业务页面策略有问题。

## 对比 / 开放题完整示例

### 完整实例｜`Context / Zustand / Redux Toolkit / MobX 怎么选？`

#### 模块 1｜主回答

##### 1）选择结论

- 这题不能答成“谁更好”，而要答成“不同复杂度下怎么选”。
- `Context` 适合低频、简单的共享状态。
- `Zustand` 适合轻量、低样板的中等复杂度状态。
- `Redux Toolkit` 适合复杂业务、多人协作、强约束场景。
- `MobX` 适合响应式驱动明显、希望细粒度自动追踪依赖的场景。

##### 2）选择图 / 决策树（ASCII）

```txt
是否需要跨组件共享状态？
  |
  +-- 否 -> 组件本地状态
  |
  +-- 是
       |
       +-- 状态简单、低频更新 -> Context
       |
       +-- 需要轻量 store -> Zustand
       |
       +-- 需要强规范、强追踪 -> Redux Toolkit
       |
       +-- 偏响应式建模、自动依赖追踪 -> MobX
```

##### 3）最小对比表 / 最小例子

```txt
Context
  关键词：传值、低频共享、轻量

Zustand
  关键词：外部 store、selector、轻量订阅

Redux Toolkit
  关键词：单向数据流、约束、调试、异步流

MobX
  关键词：observable、computed、action、reaction
```

##### 4）面试口语稿

- 我会先看状态复杂度、更新频率、团队协作成本和调试要求。`Context` 更像上下文分发机制，适合主题、语言、用户信息这种低频共享状态。`Zustand` 是比较轻量的外部 store，样板少，上手快，适合大部分中等复杂度前端业务状态。`Redux Toolkit` 更适合复杂业务和多人协作，因为它的数据流、异步流、调试和可追踪性更强。`MobX` 则偏响应式思想，通过可观察对象和依赖追踪自动驱动更新，开发体验很好，但状态变化路径相对更隐式。我的选择标准不是偏好哪个库，而是项目需不需要更强的约束和治理能力。`

#### 模块 2｜深入展开

##### 1）对比维度

- 状态复杂度
- 更新频率
- 团队协作和约束需求
- 调试和追踪能力
- 建模方式是显式数据流还是响应式依赖追踪

##### 2）选项本体拆解

- `Context`：本质是跨组件树传值机制，不是完整状态管理方案。适合主题、语言、当前用户这类低频共享信息。
- `Zustand`：本质是轻量外部 store。常见写法是在模块顶层通过 `create` 创建 store，然后组件通过 hook 读取状态和 action。模块级导出时通常表现为单例 store，但它本身不强制单例，也可以用工厂函数创建多实例 store。它和 `useSyncExternalStore` 的关系是：React 18 之后，外部状态订阅要更好适配并发渲染，`Zustand` 这类库会基于 React 官方的外部 store 订阅能力来保证订阅一致性。
- `Redux Toolkit`：延续 Redux 的单向数据流，即 `dispatch -> reducer -> new state`。优势不只是集中状态，而是边界清晰、变更可追踪、中间件体系成熟、DevTools 调试能力强。
- `MobX`：是响应式状态管理，核心是 `observable`、`computed`、`action`、`reaction`。它会在读取状态时收集依赖，在状态变化时通知依赖它的观察者更新，所以更像“自动依赖追踪 + 响应式派发”。

##### 3）取舍 / 易错点

- `Context` 不是 Redux 的完整替代品。
- `Zustand` 轻量，不代表适合所有复杂场景。
- `Redux Toolkit` 样板更多，但换来的是更强的可维护性和团队协作一致性。
- `MobX` 建模自然，但状态变化路径相对更隐式。
- 常见误区：把 `Context` 当全局状态管理银弹；把 `Zustand` 说成“比 Redux 好”；不结合项目规模和协作方式直接站队。

##### 4）专题判断

- 这题适合继续拆 4 个专题：
  - `Zustand` 的外部 store、selector 和 `useSyncExternalStore`
  - `MobX` 的依赖追踪原理
  - `Redux Toolkit` 的单向数据流和异步流治理
  - `Context` 的传播机制与更新边界

##### 难题加厚｜额外图

```txt

  -> getState()
  -> setState()
  -> subscribe(listener)
  -> selector 取局部快照
  -> 组件只在选中切片变化时更新
```

```txt
MobX
observable state 改变
  -> reaction / observer 收到通知
  -> 只更新真正依赖该状态的视图
```

##### 难题加厚｜额外例子

```txt

  theme / locale / auth user

  中后台筛选条件 / 弹窗中心 / 草稿状态

Redux Toolkit
  交易链路 / 广告投放配置 / 复杂审批流
```

#### 模块 3｜追问与详细回答

##### 追问 1｜`Zustand` 是不是单例模式？

- 不是语言层面强制的单例。
- 如果你把 store 写在模块顶层并导出，全局共享时它通常表现为单例。
- 但如果你用工厂函数在不同实例里创建 store，它也可以是多实例。
- 更准确的说法是：`Zustand` 常见用法是模块级共享 store，但它本身并不强制单例。

##### 追问 2｜`Zustand` 和 `useSyncExternalStore` 是什么关系？

- `useSyncExternalStore` 是 React 官方为外部状态订阅提供的能力。
- `Zustand` 这种外部 store 库，需要把“store 变化”安全地同步到 React 渲染体系里。
- 所以它的核心不是 `useState`，而是“外部 store 订阅 + selector + 与 React 渲染桥接”。

##### 追问 3｜`MobX` 和 `Redux` 的核心差异是什么？

- `Redux` 更显式，状态变化路径固定，适合治理。
- `MobX` 更响应式，依赖自动追踪，适合快速表达业务关系。
- 一个更强调流程可控，一个更强调建模自然。

##### 追问 4｜为什么 `Context` 不能直接替代这些库？

- 因为 `Context` 解决的是传值，不是复杂状态治理。
- 一旦状态更新频繁、异步流复杂、模块很多，单靠 `Context` 很难支撑长期维护。

##### 追问 5｜什么时候该优先选 `Redux Toolkit`，而不是 `Zustand`？

- 当项目进入多人协作、模块联动复杂、异步链路长、需要统一调试和可追踪性时，应优先 `Redux Toolkit`。
- 当项目还是中等复杂度、强调快速开发、希望少样板时，`Zustand` 更合适。
