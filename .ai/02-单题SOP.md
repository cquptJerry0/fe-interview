# 单题 SOP

## 通用前提

- 先确认答案方向正确，再抽象成 SOP；不要一上来只写结构，不校准内容。
- 单题入口卡统一只保留 `2` 个大 Part：`Part 1｜技术讲解`、`Part 2｜面试作答`。
- `Part 1` 的目标是“先把技术讲清楚”；`Part 2` 的目标是“再把答案说出去”。
- `Part 1` 允许按题型选择不同讲法，不再强制所有题都套同一组固定小标题。
- 不引用外部文档；仓里没有的关键知识，优先在本题内补清，系统性内容再沉淀到专题深挖。

## 通用执行顺序

1. 先判断题型与知识状态。
2. 先完成 `Part 1｜技术讲解`，确保读者不靠追问也能看懂主链路。
3. 再完成 `Part 2｜面试作答`，产出可直接背诵、可直接复述的回答。
4. 最后标注关联专题、复习标记和继续深挖入口。

## 知识状态判断

只允许三种状态：

- `已覆盖`：已有高质量入口卡，可直接复用。
- `部分覆盖`：已有入口卡，但解释不够稳，需要补强。
- `需关联专题`：这题背后有系统链路，入口卡要显式挂到专题深挖，而不是临时在单题里硬塞到底。

## 入口卡统一结构

### Part 1｜技术讲解

固定目标：先把“这项技术到底是什么、为什么这样、怎么判断”讲清楚。

固定外壳：

1. `一句话结论`
2. `主链路图（ASCII）`
3. `结论证明材料`
4. `工程视角`

说明：

- `一句话结论` 必须直接回答题面。
- `主链路图` 必须画出“触发条件 / 关键机制 / 最终结果”。
- `结论证明材料` 可以是最小例子、反例、对比、伪代码、判断口诀，不限制形式，但必须能证明结论。
- `工程视角` 必须回答“这题为什么会在真实项目里出问题”。

可变技术块按题型选择：

#### 1）JS 原理题

优先讲法：

- `编译时 / 解析时确定什么`
- `创建执行上下文时放进什么`
- `运行时按什么规则绑定 / 查找`
- `最终为什么得到这个输出 / 行为`

适用题：

- 作用域链
- `this`
- 箭头函数
- 闭包
- `useEffect` 依赖比较
- 事件循环

推荐骨架（`Part 1`）：

1. `一句话结论`
2. `主链路图（ASCII）`
3. `编译时 / 创建环境 / 运行时`
4. `最小例子或反例`
5. `工程视角`

#### 2）CSS / 布局图解题

优先讲法：

- `约束关系图`
- `失败原因图`
- `主方案 vs 打断方案`
- `最小样式例子`

适用题：

- BFC
- `margin collapse`
- 溢出省略
- 定位与层叠
- 可视区与滚动

推荐骨架（`Part 1`）：

1. `一句话结论`
2. `约束关系图（ASCII）`
3. `失败原因图（ASCII）`
4. `主方案 vs 打断方案 / 兼容方案`
5. `最小样式例子`
6. `工程视角`

#### 3）场景题

优先讲法：

- `问题拆解`
- `最小兜底链路`
- `恢复 / 降级 / 监控`
- `排查抓手`

推荐骨架（`Part 1`）：

1. `处理目标 / 一句话判断`
2. `分层处理图（ASCII）`
3. `最小兜底链路`
4. `恢复 / 降级 / 监控 / 排查`
5. `工程视角`

`Part 2` 的追问优先覆盖：

- 为什么不是只做一个前端技巧点
- 怎么区分失败类型
- 什么场景该重试、什么场景该降级
- 怎么上报和定位根因

#### 4）对比 / 开放题

优先讲法：

- `选择结论`
- `决策树`
- `最小对比表`
- `边界与代价`

推荐骨架（`Part 1`）：

1. `选择结论`
2. `决策树（ASCII）`
3. `最小对比表`
4. `选项本体拆解`
5. `边界与代价`
6. `工程视角`

`Part 2` 的追问优先覆盖：

- 为什么不是另一个方案
- 什么时候选型会反过来
- 团队协作、性能、维护成本怎么权衡

### Part 2｜面试作答

固定输出：

1. `20 秒快答`
2. `60-90 秒口语稿`
3. `高频追问`
4. `关联专题 / 复习标记`

要求：

- `20 秒快答` 用来抢答和先占位。
- `60-90 秒口语稿` 是主回答，必须自然、口语化、能直接说出口。
- `高频追问` 至少 `3` 个，复杂题建议 `5` 个，回答必须完整，不能只列标题。
- `关联专题 / 复习标记` 要明确是 `可快答`、`可展开` 还是 `一追就进专题`。

## 不同题型的最低门槛

### 八股 / 原理题

- 必须讲清“规则是什么、为什么、怎么证明”。
- 必须有 `1` 份最小例子或反例。
- 必须有口语稿和追问。

### CSS / 布局题

- 至少 `2` 张 ASCII 图。
- 图里必须直接表现约束关系、失败原因或打断方式。
- 不能只堆属性名，必须让读者一眼看到为什么生效 / 为什么不生效。

### 场景题

- 必须体现分层处理，而不是只给一个技巧点。
- 必须能落到恢复、降级、监控或排查中的至少两项。

### 对比 / 开放题

- 必须是“什么场景怎么选”，不能答成“谁绝对更好”。
- 必须有一个最小对比表或决策树。

## 难题加厚规则

### 默认触发范围

- React 原理
- JS 执行机制
- 状态管理
- 性能优化
- 网络与缓存
- 多层追问明显的开放题

### 触发后最少补充

- `1` 张额外图
- `1` 个额外反例或业务例子
- `1` 段精炼伪代码或判断步骤

### 加厚原则

- 加厚是帮助理解，不是无限加字。
- 口语稿不跟着无限膨胀，额外内容优先加在图、反例、伪代码里。
- 加厚后应做到：即使不继续追问，主链路也已经清楚。

## 质量门禁

入口卡完成后至少满足：

- 有直接回答题面的结论。
- 有图或结构化可视化，不只是文字堆叠。
- 有证明结论的材料。
- 有真实项目视角。
- 有 `20 秒快答` 和 `60-90 秒口语稿`。
- 有 `3` 个以上高频追问详答。
- 有专题挂载或明确说明“当前无独立专题”。
