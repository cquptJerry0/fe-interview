# 领域命令编译器

## 首先体现

将持续扩张的开放接口转化为可编译、可维护领域命令的平台工程能力。

## 系统冲突

GUI 操作通常依赖页面状态、默认参数和多个内部接口串联，无法通过增加 JWT 直接变成稳定的外部能力；OpenAPI 还需要重新定义参数语义、状态流转、数据作用域与错误边界。

OpenAPI 数量持续增长后，全部手写命令会产生重复开发和参数漂移；全部自动生成用户命令，又会把后端接口命名和数据结构直接暴露给使用者。

## 关键设计

1. 将页面操作拆解为稳定的业务动作，统一处理默认值、状态校验、数据作用域和上下游数据结构转换。
2. 基于 BAM / IDL 生成类型化 Client、参数 Schema 和 hidden 基础命令，承担接口覆盖率。
3. 在生成层之上维护稳定业务命令，隔离底层方法名、参数结构和调用细节变化。
4. 对接口字段类型、64 位 ID、参数别名和业务默认值建立明确的生成与适配规则，并通过契约测试校验参数映射。

## 简历钩子

> 领域命令编译器：将 GUI 中依赖页面状态与多接口编排的运营操作重构为稳定 OpenAPI 契约，统一处理参数语义、默认值、状态流转与上下游数据转换；基于 BAM / IDL 生成类型化 Client、参数 Schema 与基础命令，并以领域命令层隔离接口结构和用户语义。

## 面试展开

1. 为什么不能把全部生成命令直接暴露给用户？
2. GUI 操作转换为 OpenAPI 时，哪些页面状态和多接口编排需要被重新建模？
3. 生成层与业务命令层之间如何定义稳定边界？
4. IDL 字段、64 位素材 ID 和参数别名变化时如何保证映射正确？
