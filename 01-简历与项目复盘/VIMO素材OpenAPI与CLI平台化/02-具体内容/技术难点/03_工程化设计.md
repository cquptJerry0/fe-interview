# 工程化设计

## 首先体现

将多人研发、能力使用和客户端升级三条链路统一纳入工程规范的体系化建设能力。

## 自动发布流水线

多人协作后，人工切分支、修改版本、打 Tag 和发布容易遗漏或冲突。基于 MR 合并事件触发自动发布，统一执行质量校验、版本计算、Tag 和 bnpm 发布，将发版收敛为可重复的标准流程。

## Skill 工程化

使用侧由统一入口识别任务意图，并路由到素材、面板、实验或运维中的单个领域 Sub-Skill，统一命令选择、参数约束与操作边界。

研发侧由总入口顺序编排多个阶段 Sub-Skills，将需求澄清、OpenAPI / BAM、Codegen、测试发布与归档串成完整交付链路，降低跨仓协作对个人经验的依赖。

## 客户端版本治理

面向国内外用户版本分散的问题，统一版本检测、包管理器识别、自更新、升级后重执行和 Skill 同步，使 CLI、接口契约和使用知识随同一版本持续演进。

## 简历钩子

> 自动发布：针对多人手工发版易冲突的问题，基于 MR 合并事件自动完成校验、版本计算、Tag 与 bnpm 发布，将发版收敛为标准流程。
>
> Skill 工程化：使用侧由统一入口按任务意图路由单个领域 Sub-Skill，统一命令选择、参数约束与操作边界；研发侧将需求、OpenAPI、Codegen 和测试发布按阶段编排，形成可校验、可追踪的跨仓交付流程。
>
> 版本治理：面向用户版本分散，通过版本检测、自更新、升级后重执行与 Skill 同步，保持 CLI、接口契约与使用知识一致。

## 面试展开

1. MR 合并后如何计算版本，并隔离测试与正式发布通道？
2. 为什么使用侧按领域路由单个 Sub-Skill，而研发侧采用阶段化流程编排？
3. 研发侧总入口如何在 Sub-Skills 之间传递跨仓契约和校验结果？
4. 自更新完成后如何恢复原始命令，并避免更新失败阻断正常使用？
