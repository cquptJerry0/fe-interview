## 1. 当前项目定位

### 1.1 项目名称候选

1. `VIMO 素材全生命周期管理与分发中台`
2. `VIMO 素材生产与分发控制面建设`
3. `VIMO 素材中台业务迭代`

当前推荐使用第一个名称。它能说清平台的业务边界，也为后续展开生产、策略、面板和分发链路留出空间。

### 1.2 一句话简介

VIMO 是面向剪映、醒图等内容创作业务的素材生产与分发控制面，统一承载图片、视频、音频、贴纸、字体及 AIGC 素材的生产管理、策略实验、面板编排和多端分发，治理素材从创建、配置、发布到客户端生效过程中的复杂状态和运营成本。

### 1.3 建议的叙事主线

```text
素材生产
  -> 动态业务字段与策略建模
  -> 发布前变更解释
  -> 面板编排与自动同步
  -> 客户端分发
```

简历上不按“素材、分类、面板、分级、实验”罗列页面功能，而是聚焦三个系统问题：

1. 复杂变更如何被准确解释，降低策略误判和误发布风险。
2. 长链路的素材分发如何自动化，并且具备可追踪、可恢复能力。
3. 动态业务模型如何在前端统一表达，避免多业务线扩展后持续累积分支逻辑。

## 2. 为什么需要建设这些能力

VIMO 管理的是一组会影响客户端展示、下发范围和实验策略的业务对象。一次素材发布可能同时修改基础属性、自定义字段、资源包分级、策略实验和面板分类。这些数据的结构和比对语义不一致，如果只展示原始 JSON，运营无法稳定判断发布影响面。

素材生产完成后，还需要按地区、面板、分类和业务规则完成编排。原始人工链路包含重复查找、新增、移除和发布操作，容易出现漏配、重复配置和半成功状态。随着素材类型和业务线增加，这些成本会继续放大。

前端面临的主要约束是动态性。不同 `ValueType`、不同业务线和不同素材类型需要匹配不同的输入控件、序列化协议、查询方式和回填逻辑。缺少统一模型时，每次新增字段都会带来新的条件分支和状态边界。

## 3. 核心贡献候选

### 3.1 语义化 Diff 引擎将发布风险前置

素材变更分散在基础信息、自定义字段、下发控制、资源包分级、素材信息分级和策略实验等数据模型中。JSON String、嵌套对象和数组乱序会产生伪 Diff，直接对原始对象做深比较无法表达真实业务变更。

改造通过 Recursive Object Normalization 收敛对比输入，统一解析 JSON String 与嵌套对象；对分级、实验组等数组使用业务主键对齐，避免顺序变化被误认为内容变化；再利用 Runtime Field Metadata 将动态自定义字段还原成可读的业务语义。同一 Diff 内核被复用到列表、Hover 和详情等不同展示入口，ByteBench 远程组件采用懒加载和异常降级，避免辅助能力影响素材主流程。

这项能力将不透明的配置变化转换为稳定、可解释的增删改记录，减少运营逐字段核对成本，并降低策略误判与误发布风险。

可用于面试展开的技术点：

- 为什么通用 Deep Diff 无法直接处理业务对象。
- 如何设计 Canonicalization 与 Semantic Key Alignment。
- 如何判断字段新增、删除、修改与无意义顺序变化。
- 如何让同一数据内核承接多种 UI 形态。
- 远程组件加载失败时，如何保护主业务链路。

证据状态：已确认为个人主要贡献，可作为当前业务迭代中最强的前端技术主线。

### 3.2 事件驱动的自动分发链路候选

素材状态、选择分类或分发规则变化后，人工流程需要重复完成面板匹配、分类查找、素材新增和删除。链路跨越 EventBus、FaaS、定时消费与面板 Draft 数据，一次直接同步调用很难同时处理长耗时、重试和部分失败。

当前仓库中的系统链路为：

```text
item_change EventBus
  -> material_lua_check 规则过滤
  -> reconcile 创建 distribute_record
  -> material_event_consume 定时消费
  -> material_web 计算目标分类
  -> 增量新增/删除 ClientSceneContentDraft
  -> 同事务更新 panel_distribute_content
```

链路使用 `task_type` 区分首次自动分发和选择分类变更，并通过任务状态、乐观抢占、失败记录和超时重试承接长链路异常。目标分类计算和 Draft 写入集中在 `material_web`，减少多运行时分散实现造成的规则漂移。

业务收益是将可确定的面板编排规则从人工操作转换为自动任务，减少漏配和重复操作；工程收益是获得可追踪、可重试、可恢复的异步执行边界。

当前 Ownership 边界：

- 完整 `reconcile -> consume -> Draft` 执行器的当前主干实现主要由其他同学完成，暂时不能写成个人独立设计全链路。
- 已确认的个人代码包含面板级“同步后自动发布”配置、`AutoSyncPublishState` 状态模型及前端配置交互。
- 后续需要确认实际承担的需求设计、前端配置、发布协调或联调范围，再决定简历中使用“设计并落地”、“负责某模块”还是“参与建设”。

### 3.3 类型驱动的动态字段查询框架

不同业务线持续增加自定义字段。如果每种字段分别实现输入控件、校验、序列化、URL 回填和查询协议，素材列表会持续累积条件分支。多路由下的字段配置各自维护状态，还会产生配置不同步、跨业务线串数据和旧请求覆盖新结果等问题。

该改造以二十余种 `ValueType` 为中心，建立字段类型到输入控件、输入校验和 Value Codec 的统一映射。查询条件通过 `fieldKey + typedValue` 生成 JSON Stable Token，保证复合值可以在 Searcher、Form 和 URL 之间稳定传递；多条件进行归一化和去重，避免重复查询语义。

状态层按 `bid` 分桶维护 MobX Singleton Store，使管理页和消费页共享同一份字段配置，同时避免不同业务线相互污染。`requestSeq` 只接受最后一次请求结果，保证快速切换业务线或重复刷新时的状态一致性。

收益是将新字段接入收敛为类型模型扩展，减少重复页面逻辑，并为运营提供对动态业务数据的统一查询能力。这一项可以稳定证明前端类型建模、状态治理和平台化设计能力。

证据状态：已确认为个人主要贡献。

## 4. 可替换的强候选：可恢复的批量素材生产流水线

如果自动分发的 Ownership 无法支撑强表述，通用批量创建素材可作为第三项主贡献。该项已确认为个人主要开发内容。

该链路不宜只描述为“基于 JSON 配置生成表单”，可以重新抽象为一条前端批量数据处理与文件上传 Pipeline：

```text
Schema Parser
  -> Excel Validation
  -> File Manifest Resolver
  -> Upload Scheduler
  -> Field Derive
  -> Payload Serializer
  -> Chunk Submit / Retry
  -> Partial Result
```

流水线负责解析 Excel 与素材文件夹，根据 Schema 完成字段校验、枚举映射、派生计算和 Payload 序列化，并将多文件上传、MD5 计算和分批提交拆解为可观测阶段。失败结果保留到行和字段级别，使用户可以针对部分数据修正后重试，无需整批重新执行。

可讲收益包括：将重复单条创建收敛为批量生产工作流；在提交前暴露数据与文件问题；通过并行上传、分批提交和部分结果降低大批量任务的重试成本。
