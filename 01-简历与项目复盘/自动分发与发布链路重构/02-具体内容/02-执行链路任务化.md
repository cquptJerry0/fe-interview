# 执行链路任务化

## 一、思维起点

第一阶段最先解决的不是执行速度，而是缺少一份可靠的执行账本。

回调内直接执行时，系统回答不了：

- 回调超时后，服务端到底执行到哪里？
- 同一事件重复投递，会不会重复写入？
- 任务等待期间配置变化，应该按旧配置还是新配置执行？
- 同一来源的两个版本乱序到达，最终以哪个为准？
- 某一步失败后，应该从哪里恢复？

因此任务化不能只把原函数套进异步消费者，还要定义一次任务稳定的输入、状态、顺序和结果。

## 二、改造前后

```text
改造前

事件到达
  ↓
读取当前配置
  ↓
现场计算
  ↓
直接写库
  ↓
HTTP 超时后结果不明


改造后

事件到达
  │
  ├─ 生成 task_key，拦截重复事件
  ├─ 固化源版本
  └─ 固化本次净变更计划
  ↓
distribute_record
  ↓ 带状态条件抢占
Pending → Processing → Finished / Failed
  ↓
记录 added / removed / skipped / failed
```

## 三、关键设计

### 1. 事件建单

事件侧只识别任务类型、生成业务事件标识并建单，不再在请求内完成整段计算和写库。

任务类型包括：

```text
initial_auto_distribute
choose_category_change
panel_auto_sync
static_review_auto_sync
```

### 2. 固化任务含义

面板同步任务创建时记录源版本和净变更计划。计划保存本次 additions、removals、强插变化和字段更新，不复制整个目标列表。

这里解决的是时间一致性：事件发生时的业务含义，不能被消费者执行时的最新配置重新解释。

### 3. 状态抢占

消费者使用带状态条件的更新：

```sql
UPDATE distribute_record
SET status = 'Processing'
WHERE id = ? AND status = 'Pending';
```

只有受影响行数为 1 的消费者才能继续执行。它不是先查询再更新，而是把状态判断和修改放在一次原子更新中。

### 4. 顺序控制

同一来源到目标流中的新版本等待旧版本完成，避免新版本先执行、旧版本后覆盖。分类同步任务还会作为普通自动分发批次的顺序屏障。

这里不能简单做无序去重，因为分类列表存在顺序，新增动作可能使用前插语义。

### 5. 结果回填

任务最终记录新增、移除、跳过和失败结果。任务表既负责调度，也作为排查、重试和人工补偿的依据。

## 四、满分逐字稿

> 第一阶段我解决的是执行不可控。旧链路收到事件后直接读取当前配置、计算分类变化并写库，请求超时以后，调用方只知道没有响应，却不知道服务端执行到了哪一步。重复事件和配置变化也会让同一次执行的结果不稳定。
>
> 我的做法不是简单套一层异步，而是先定义任务语义。事件到达时生成 distribute_record，用业务事件标识去重，同时把源版本和这次真正需要执行的变更计划固化下来。消费者执行时只认任务中的计划，不再用最新配置重新推导。
>
> 消费端使用带状态条件的更新抢占任务，只有把 Pending 成功改成 Processing 的实例才能执行。同一来源到目标的多个版本还要保持顺序，避免新版本先执行、旧版本后覆盖。
>
> 这样一次自动化操作就从无法观察的回调副作用，变成了有稳定输入、有状态、有结果、可以重试和回溯的任务。后面的增量发布和批量执行都建立在这个基础上。

## 五、方案取舍

### 为什么不只接一个 MQ？

MQ 能把执行从请求中移出去，但不能自动提供源版本、变更计划、业务状态、任务结果和人工补偿入口。这里需要的是消息传输加业务任务记录，不能只换一个触发器。

### 为什么不在执行时读取最新配置？

任务代表某个历史时刻已经发生的业务意图。执行时读取最新配置，会导致同一任务重试时产生不同结果。新配置应该形成新版本或新任务，而不是改写旧任务含义。

### 为什么保存净变更，不保存完整目标列表？

完整列表体积更大，也容易覆盖目标端执行期间产生的新状态。净变更只表达本次意图，消费者在受控事务中把变化合并到当前状态。

## 六、高概率追问

### 问：如何保证重复事件不会重复执行？

> 建单时用业务事件维度的 task_key 拦截重复任务，消费时再用带状态条件的更新抢占。前者解决重复建单，后者解决多个消费者同时执行同一任务。真正写入还在事务中完成，因此重复触发不会无条件重复修改业务数据。

### 问：这是不是 exactly-once？

> 不是严格的物理执行一次。网络超时和进程退出下很难只靠应用层保证 exactly-once。这里接受 at-least-once 触发，再用任务去重、状态抢占和业务写入幂等保证最终结果正确。

### 问：任务执行一半失败怎么办？

> 修改 Draft 时按面板事务提交，单面板内的 Draft、索引、操作记录和发布任务一起成功或一起回滚。任务层再按面板结果回填，失败面板可以重试，不会留下只有一半数据成功的状态。

### 问：任务表会不会无限增长？

> 在线调度只查询 Pending 和可恢复的 Processing，并建立匹配查询条件的索引。Finished 和 Failed 用于审计与排障，可以按时间归档或分区，避免历史记录长期参与热路径查询。

### 问：同一来源的任务为什么不能完全并发？

> 同一分类的动作存在顺序语义，尤其新增使用前插时，任务顺序会影响最终列表。并发边界应该放在不同面板之间，而不是同一来源或同一分类内部。
