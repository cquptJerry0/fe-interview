# 八股三：并发批处理与 MQ

## 一、并发处理方案

### 题目

任务积压时，如何提高并发又保证同一面板结果正确？

### 满分答案

> 我先确定一致性键，再决定并发度。这个项目中，任务是追踪单位，分类是计算单位，面板是事务和发布单位。同一分类动作要保持 taskOrder，同一面板应该进入同一执行分区，不同面板才并行。
>
> 实现上可以按 `hash(bizId, areaKey, sceneKey)` 分区。同一面板天然有序，不同分区由固定数量 worker 并行。并发度受到数据库连接池、锁等待、单批面板数和下游发布能力约束，需要用指标动态调整。

### ASCII 图

```text
任务流
  ↓
按 panelKey 哈希
  ├─ Partition 0：Panel A → Panel A → Panel A
  ├─ Partition 1：Panel B → Panel D
  └─ Partition 2：Panel C → Panel E

分区内串行
分区间并行
```

### 并发度如何确定？

需要同时观察：

- 数据库连接池可用连接。
- 平均事务耗时和 P95 锁等待。
- 单批涉及的面板数与热点分布。
- 下游发布服务 QPS。
- 最老 Pending 年龄。
- 失败和死锁重试率。

从保守值开始压测，逐步提高并发。如果吞吐不再增长而锁等待、连接等待持续上升，说明瓶颈已经转移到数据库或热点键。

### 为什么不能只用 Promise.all 全并发？

> Promise.all 只控制应用层发起速度，不理解业务一致性键，也不会感知连接池和锁竞争。无界并发会把队列积压转移成数据库积压。正确做法是使用有界 worker pool，并按面板分区。

### 刻意思考

并发优化顺序：

```text
先减少总工作量
→ 再确定串行边界
→ 再做有界并发
→ 最后根据指标动态调节
```

### 满分心智

```text
并发不是越大越快，
同键串行、异键并行、全局有界。
```

## 二、批次大小与背压

### 题目

batch size 怎么定？任务继续积压怎么办？

### 满分答案

> batch 越大，公共数据复用越充分，但内存占用、单批失败成本和热点面板数量也会增加。不能只按任务条数决定，需要同时观察动作数、分类数和面板数。
>
> 我会设置任务数、动作数和面板数三重上限，并根据最老 Pending 年龄、批次 P95、锁等待和失败率动态调整。积压继续上升时先提高批次复用率和不同面板并发，再对低优先级生产端限速，形成背压。

### ASCII 图

```text
积压上升
  ↓
扩大 batch，复用公共查询
  ↓
不同面板有界并发
  ↓
仍无法追平
  ↓
降低低优任务生产速率 / 限流
```

### batch 过大的风险

- 内存占用和 GC 压力上升。
- 单批涉及热点面板的概率增加。
- 失败后的重算范围扩大。
- 单批执行超过任务租约。
- 一次拉取占用过多待处理任务，造成其他消费者饥饿。

### 满分心智

```text
batch 解决摊薄固定成本，
背压解决生产长期超过消费。
```

## 三、热点面板治理

### 题目

某个面板特别热，拖慢整个分区怎么办？

### 满分答案

> 先识别热点是任务多、单任务动作多，还是事务锁等待高。如果是单面板高频变化，可以把它提升为独立执行 key 或专属分区，并增加短时间合并窗口，把多次变化压缩成一次最终状态和一次发布。
>
> 但同一面板不能为了吞吐盲目并行，否则会破坏动作顺序和增加行锁竞争。热点治理的方向是隔离和合并，不是同键并发。

### ASCII 图

```text
普通面板 → 通用分区

热点面板 H
  ↓
独立队列 / 分区
  ↓ 短窗口合并
一次状态计算 + 一次发布
```

### 满分心智

```text
热点键要隔离和合并，
不能靠同键并发硬顶。
```

## 四、Outbox 与跨库一致性

### 题目

如果 Draft 和 publish_task 拆到不同数据库，如何保证一致性？

### 满分答案

> 跨库以后不能继续依赖本地事务，也不建议直接在业务事务中远程写第二个库。可以在 Draft 数据库的同一事务中写入 Outbox Event，后台投递器把事件发送到 MQ 或发布库。发送成功后标记 Outbox 已投递。
>
> Outbox 投递通常是 at-least-once，因此下游仍要用 eventId 或业务键幂等。还需要扫描未投递 Outbox 兜底，处理发送成功但状态回写失败造成的重复发送。

### ASCII 图

```text
Draft DB Transaction
  ├─ Update Draft
  └─ Insert Outbox Event
          ↓
      Relay Worker
          ↓
          MQ
          ↓
  Publish Consumer
          ↓ 幂等建单
      publish_task
```

### Outbox 的代价

- 多一张事件表和投递器。
- 需要归档已投递事件。
- 存在重复投递，下游必须幂等。
- 端到端只有最终一致，不是跨库强事务。

### 满分心智

```text
本地事务保存业务事实和待发送事实，
异步投递负责跨系统传播。
```

## 五、MQ 顺序、重复与消息丢失

### 题目

如果引入 MQ，如何保证同一面板顺序和消息不丢？

### 满分答案

> 生产端使用面板 key 做分区键，让同一面板消息进入同一 partition；消费端同一 partition 内串行处理，不同 partition 并行。MQ 通常保证 at-least-once，因此消费者仍然需要业务幂等。
>
> 生产端可靠发送使用事务消息或 Outbox；消费端处理成功后再提交 offset。处理成功但 offset 提交失败会重复消费，所以不能依赖 offset 实现 exactly-once。

### ASCII 图

```text
Panel A ─┐
Panel A ─┼─ hash(panelKey) → Partition 0 → 串行消费
Panel B ─┘                  Partition 1 → 并行消费
```

### 消息积压如何处理？

1. 确认瓶颈在消费计算、数据库还是下游。
2. 在保持分区键顺序的前提下增加 partition 和 consumer。
3. 批量拉取和批量准备公共数据。
4. 对低优生产端限流，避免持续扩大积压。
5. 监控最老消息年龄，而不只看消息条数。

### 满分心智

```text
分区键保证局部顺序，
Outbox 保证可靠发送，
业务幂等处理重复投递。
```

## 六、JSON 列表与关系表

### 题目

为什么 JSON/TEXT 列表会成为瓶颈？关系表如何设计？

### 满分答案

> JSON/TEXT 适合整体读取和低频更新，但分类素材列表一旦高频局部变化，每次都要解析和重写整列，锁冲突和写放大会随列表长度增长。关系表可以把单个素材增删变成行级操作，并使用索引做存在性判断。
>
> 原列表有顺序，关系表不能只有 category_id 和 material_id，还需要 sort_key。迁移要采用双写、历史回填、一致性校验、切读和旧字段兼容投影，不能直接切表。

### ASCII 图

```text
旧结构

category_id → [rid1, rid2, rid3, ...]
每次变化重写整列


新结构

category_material_relation
  category_id
  material_id
  sort_key

单素材增删变成行级操作
```

### 迁移流程

```text
双写新旧结构
→ 历史数据回填
→ 在线一致性校验
→ 新链路切读
→ 旧字段兼容投影
→ 稳定后下线旧写入
```

### 满分心智

```text
JSON 适合整体文档，
关系表适合高频局部变更和关系查询。
```

## 七、最后速记

```text
1. 先确定一致性键，再决定并发度。
2. 同一面板串行，不同面板有界并行。
3. Promise.all 不等于合理并发控制。
4. batch 同时受任务数、动作数和面板数约束。
5. 热点键优先隔离和合并，不做同键并发。
6. Outbox 解决可靠传播，下游仍需幂等。
7. MQ 分区键保证局部顺序，不保证全局顺序。
8. JSON 列表的下一步是带 sort_key 的关系表。
```
