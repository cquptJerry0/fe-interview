# 项目背景与总体架构

## 一、先讲思维

我一开始没有把它理解成一个单纯的消费者性能问题。

当时链路同时出现三类现象：

1. 事件回调容易超时，调用方不知道服务端是否仍在执行。
2. Draft 已更新但正式版本没有发布，链路会停在半成功状态。
3. 自动分发任务长期积压，生产速度持续高于消费速度。

三个现象看似分别属于可靠性、发布和性能，实际来自同一个架构问题：大量业务副作用被藏在回调、定时扫描和逐任务循环里，系统没有明确记录“这次要做什么、执行到哪里、失败后如何恢复”。

所以改造顺序不是先加缓存或并发，而是：

```text
先建立任务边界
→ 再建立发布交接
→ 最后改变批量执行模型
```

## 二、业务背景

素材状态、分类规则或面板配置发生变化后，系统需要完成两段业务过程：

```text
第一段：计算素材应该进入或离开哪些分类，并更新面板 Draft。
第二段：比较 Draft 和线上版本，构建 Diff 并发布正式版本。
```

链路还要处理重复事件、配置变化、版本顺序、失败重试、人工发布插入，以及一批任务同时影响多个分类和面板的情况。

## 三、旧链路问题图

```text
素材事件 / 规则变化 / 面板配置变化
                   │
                   ▼
┌──────────────────────────────────────┐
│ 事件回调：现场读取配置、计算变化、写库 │
└──────────────────────────────────────┘
                   │
                   ├── P1：请求生命周期与业务执行绑在一起
                   │         502 后服务端可能仍在执行，结果不明确
                   ▼
┌──────────────────────────────────────┐
│ 消费者：逐任务 → 逐分类 → 逐次事务     │
└──────────────────────────────────────┘
                   │
                   ├── P2：公共查询和事务被动作数量重复放大
                   │         50 条任务展开 976 个动作，积压 5000+
                   ▼
              面板 Draft
                   │
                   │  没有保存“哪个面板真的发生了变化”
                   ▼
┌──────────────────────────────────────┐
│ 定时器：扫描全部面板，比较 Draft/Online │
└──────────────────────────────────────┘
                   │
                   ├── P3：扫描数百面板重新寻找已知变化
                   │         完整发现过程约 20 分钟
                   ▼
               正式版本
```

旧链路的核心矛盾：

| 问题 | 表面表现 | 架构根因 |
| --- | --- | --- |
| P1 执行不可控 | 回调超时、重复触发、无法恢复 | 没有显式任务和稳定执行计划 |
| P2 消费写放大 | 任务长期积压 | 任务、计算和事务使用同一个粒度 |
| P3 发布发现低效 | 发布延迟、半成功 | Draft 写入与发布发现之间没有可靠交接 |

## 四、改造后总架构图

图中 `M1`、`M2`、`M3` 是三个核心改造点。

```text
素材事件 / 规则变化 / 面板配置变化
                   │
                   │ M1：事件只建单
                   │     固化源版本 + 净变更计划
                   ▼
┌────────────────────────────────────────┐
│ distribute_record                      │
│ 自动分发 / 面板同步任务                 │
│ Pending → Processing → Finished/Failed │
└────────────────────────────────────────┘
                   │
                   │ M3：批量状态归并
                   │     1. 整批加载公共数据
                   │     2. 按分类归并有序动作
                   │     3. 计算最终分类状态
                   ▼
┌────────────────────────────────────────┐
│ 面板事务                                │
│ Draft + 分发索引 + 操作记录             │
│                                        │
│ M2：Draft 真实变化时 upsert publish_task│
└────────────────────────────────────────┘
                   │
                   ▼
┌────────────────────────────────────────┐
│ publish_task                           │
│ 合并同面板连续变化                      │
│ 状态抢占 + 消费租约 + 失败重试          │
└────────────────────────────────────────┘
                   │
                   │ 只构建真实待发布面板的 Diff
                   ▼
               正式版本
```

三个改造点各自解决不同问题：

| 改造 | 模型变化 | 直接结果 |
| --- | --- | --- |
| M1 执行链路任务化 | 回调内直接执行 → 事件建单、消费者执行 | 过程可追踪，失败可恢复，任务含义不随配置漂移 |
| M2 增量发布 | 扫描全部面板 → Draft 变化时登记发布任务 | 变更发现从约 20 分钟降到 10 秒内 |
| M3 批量状态归并 | 逐动作读写 → 整批计算最终状态 | 单批约 20 分钟降到 24 秒，效率约 50 倍 |

## 五、最重要的架构边界

这个项目最值得讲的不是两张任务表，而是三个执行单位被重新分开：

```text
┌─────────────────────────────────────────────┐
│ 任务：追踪单位                               │
│ distribute_record 保留输入、状态和执行结果   │
└─────────────────────────────────────────────┘
                      │ 一条任务可展开多个动作
                      ▼
┌─────────────────────────────────────────────┐
│ 分类：状态计算单位                           │
│ 同分类动作保留顺序，在内存中计算最终列表     │
└─────────────────────────────────────────────┘
                      │ 多个分类属于同一面板
                      ▼
┌─────────────────────────────────────────────┐
│ 面板：事务与发布单位                         │
│ Draft、索引、操作记录、publish_task 一起提交 │
└─────────────────────────────────────────────┘
```

如果三个单位混在一起：

- 以任务作为事务单位，会重复查询和写入相同分类。
- 以分类作为事务单位，同一面板可能部分成功并重复发布。
- 只保留批次结果，又无法回填每条任务的成功与失败。

最终方案让任务负责可追踪，分类负责合并计算，面板负责一致提交。

## 六、总体方案逐字稿

> 我接手后先把一次业务变化从事件入口追到正式版本，发现问题不在单点，而是执行、发布和事务粒度都比较混乱。前半段的副作用藏在回调里，中间没有可靠的发布交接，后半段又把任务、分类计算和事务提交都绑在同一个循环里。
>
> 我最后把链路拆成两级任务。第一级 distribute_record 负责计算并写入 Draft，第二级 publish_task 负责把已经发生的 Draft 变化发布成正式版本。两个任务没有合成一个，是因为它们的失败语义不同：发布失败只应该重试已有 Draft，不应该重新执行自动分发。
>
> 消费者内部又重新划分了三个单位。任务是追踪和结果回填单位，分类是状态计算单位，面板是事务和发布单位。这样既能保留每条任务的执行结果，又能把相同分类的动作合并计算，并保证同一面板的 Draft、索引和发布任务一起提交。
>
> 整个改造不是简单引入任务表，而是把隐式副作用、扫描式发布和逐动作写入，分别变成显式任务、真实变更驱动和批量最终状态计算。

## 七、架构追问

### 问：为什么拆成两级任务，而不是一个大任务？

> 自动分发和正式发布对应两个不同的业务承诺。前者的完成条件是 Draft 和索引已经正确落库，后者的完成条件是 Diff 已进入正式版本。合成一个任务后，发布失败会迫使系统重新判断是否执行 Draft，状态机和重试范围都会变复杂。拆开后，每一级都有明确输入、完成条件和恢复边界。

### 问：为什么性能治理放在最后？

> 没有稳定任务语义时直接批量化，一旦部分失败，很难判断应该重放哪些动作；发布仍靠扫描时，即使 Draft 写得更快，正式版本仍然可能延迟。先把执行和发布交接显式化，再改变消费者内部模型，风险更可控。

### 问：项目最难的地方是什么？

> 最难的是重新确认任务、分类和面板三个业务单位。任务要保留可追踪性，分类要保留动作顺序，面板要保证事务和发布完整。如果边界选错，性能和正确性会互相牺牲。
