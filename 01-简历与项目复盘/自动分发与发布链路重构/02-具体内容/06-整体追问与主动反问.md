# 整体追问与主动反问

## 一、Ownership 追问

### 问：你在项目中的 Ownership 体现在哪里？

> 我负责的不是某一个消费者函数，而是从事件入口、自动分发、Draft 事务到正式发布的整条链路。我先重新定义问题和改造顺序，再推动两级任务边界、发布合并和批量状态归并落地，同时用真实日志和 PPE Case 验证性能。过程中不同模块会有同学协作，但整体方案、关键边界和最终效果由我持续跟进和收口。

### 问：项目最难的地方是什么？

> 最难的不是写任务消费者，而是重新确定每一层的业务边界。任务是追踪单位，分类是状态计算单位，面板是事务和发布单位。如果三个单位混在一起，要么无法追踪单任务结果，要么为了每条任务重复写库，要么同一面板出现部分成功。最终方案是让三个单位各自承担不同职责，再把结果映射回原任务。

### 问：为什么改造顺序是任务化、增量发布、批量执行？

> 可靠性是性能优化的前提。没有稳定任务语义时直接批量化，一旦部分失败，很难判断应该重放哪些动作；发布仍靠扫描时，即使 Draft 写快了，正式版本仍然可能延迟。先把执行和发布交接显式化，再改变消费者内部执行模型，风险最小，也更容易验证。

## 二、正确性与验证

### 问：如何证明批量改造没有改变业务结果？

> 我用了三层验证。第一层是动作级，比较同一批 add/remove 按原顺序逐条执行和归并执行后的分类列表；第二层是落库级，检查 Draft、分发索引、操作记录和 publish_task 是否在同一面板事务中一致；第三层是链路级，用真实 RID 回查 distribute_record、分类 Draft 和发布任务，确认任务结果最终进入正式发布链路。

### 问：如何验证 50 倍性能数据？

> 对比使用近等量动作规模。优化前 50 条任务展开 976 个动作，服务端耗时 1188 秒；优化后 100 条任务展开 965 个动作，耗时 23.5 秒。任务数不同，但动作数接近，所以动作规模是更合理的工作量口径。两组都统计服务端完整处理时间，不使用 HTTP 超时时间代替。

### 问：发布发现 10 秒内是什么意思？

> 它表示定时器从过去完整扫描数百面板约 20 分钟，变成 10 秒内发现显式 Pending publish_task。它不是正式版本完成发布的端到端耗时，Diff 和版本构建需要单独统计。

## 三、失败与恢复

### 问：任务执行到一半宕机怎么办？

> 单个面板的数据写入使用事务，不会留下 Draft 成功但索引失败的中间状态。任务如果停在 Processing，租约到期后可以重新抢占。重新执行仍要经过状态条件和业务幂等，避免重复结果。

### 问：正式发布失败怎么办？

> publish_task 失败后回到 Pending 重试，最多 3 次；超过次数进入 Failed 并告警。自动分发任务已经完成，不会因为发布失败重新修改 Draft。人工发布已经先完成时，Diff 为空按成功 no-op 结束。

### 问：旧消费者租约过期后又恢复怎么办？

> 新消费者重新抢占时会更新 claimAt。完成和失败更新必须匹配本轮 claimAt，旧消费者携带过期令牌，更新影响 0 行，不能覆盖新消费者结果。

## 四、迁移与风险

### 问：如何灰度迁移？

> 先让新旧消费者在相同输入下做影子计算，只比较结果不落库。结果稳定后按业务线或任务类型切小流量，同时保留旧定时扫描作为短期兜底。重点监控 Pending 最老年龄、失败率和 Draft 未发布数量，新链路稳定后再逐步关闭旧扫描。

### 问：方案引入了什么代价？

> 系统从隐式调用变成显式状态机，需要维护任务状态、租约、重试、索引和历史归档，也需要补充新的监控口径。但这部分复杂度原本就存在，只是散落在回调、定时器和人工排查中。任务化是把隐性复杂度集中管理。

### 问：还有哪些问题没有彻底解决？

> 当前主要剩余成本是分类内容保存在 JSON/TEXT 有序列表中，即使每个分类只写一次，仍需解析和重写整列。下一阶段可以引入带 sort_key 的 category_material_relation，但迁移需要双写、历史回填、一致性校验和切读。当前先做批量归并，是因为它不改变存储模型就能解决主要积压，收益更高、风险更低。

### 问：如果重新做一次，会提前补什么？

> 我会更早建立三类指标：最老任务积压年龄、动作到事务的放大率、Draft 到正式版本的端到端延迟。旧链路只看任务是否成功，没有看到 50 条任务被放大成近千次写入，也没有把 Draft 成功和正式发布成功拆开监控。

## 五、十倍规模演进

### 满分逐字稿

> 如果规模扩大十倍，我不会直接把消费者实例扩大十倍。第一步按面板 key 分区，同一面板串行、不同面板并行；第二步根据最老 Pending 年龄、锁等待和下游容量动态调整 batch 与并发，并对低优任务做背压；第三步把 JSON 列表迁移成带 sort_key 的关系表，降低整列解析和重写成本。
>
> 任务触发如果需要更实时，可以增加 MQ 唤醒，但 MySQL 任务表继续作为业务真源。Draft 和 publish_task 如果未来跨库，再用 Outbox 保证可靠投递。演进顺序仍然是先解决当前瓶颈，再改变基础设施，避免一次性引入分区、MQ 和数据迁移三类风险。

### 演进图

```text
当前
MySQL 任务表 + 定时消费 + JSON 列表

第一阶段
按面板分区 + 有界并发 + 背压

第二阶段
MySQL 任务表 + Outbox + MQ 实时唤醒

第三阶段
category_material_relation + sort_key
```

## 六、候选人主动反问

主动反问不要问成知识考试。先结合刚才的项目，再询问对方真实系统中的取舍。

### 1. 任务与发布边界

> 我刚才这个项目里把 Draft 执行和正式发布拆成两级任务，因为两段的失败语义不同。想了解一下，团队类似的异步链路通常按业务阶段拆状态机，还是倾向于使用统一工作流承接？

可以引出任务平台、工作流编排和一致性设计。

### 2. 扫描式架构

> 我们当时经历了从定时全量扫描到真实变更驱动的演进。团队现有系统里还有比较重的扫描任务吗？通常会在什么规模或稳定性信号出现后推动事件化改造？

可以讨论存量架构治理，而不只是新系统设计。

### 3. 事务边界

> 这次我把分类作为计算单位、面板作为事务和发布单位。团队在复杂批处理中通常怎样确定一致性键，会更偏向数据库事务、分区串行，还是补偿式 Saga？

可以观察团队如何从业务语义确定事务边界。

### 4. 性能治理

> 我们这次最大的收益来自先消除写放大，再考虑并发。团队做性能治理时，会固定建设请求放大率、事务放大率或最老积压年龄这类指标吗？

可以讨论容量规划、压测和可观测性。

### 5. 架构演进

> 当前链路剩余的主要瓶颈是 JSON 列表整列重写，下一步才考虑关系表迁移。团队面对“局部重构已经解决大部分问题，但长期模型仍不理想”的场景，通常怎样判断是否值得继续做存储升级？

可以观察团队如何平衡技术债、业务收益和交付周期。

## 七、最后收束

> 这个项目让我形成的一个判断是，复杂自动化链路的问题通常不在某个慢接口，而在执行单位、状态单位和事务单位没有分开。我的改造顺序是先把副作用变成任务，让过程可追踪；再把发布从全量扫描改成变化驱动，让交接可靠；最后把逐动作执行改成批量计算最终状态，让吞吐跟业务规模匹配。性能提升约 50 倍只是结果，真正可复用的是这套从执行语义、事务边界到批处理模型的分析方法。
