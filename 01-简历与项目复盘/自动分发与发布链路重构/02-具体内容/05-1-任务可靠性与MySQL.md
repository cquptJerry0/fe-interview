# 八股一：任务可靠性与 MySQL

## 一、数据库任务表与 MQ

### 题目

为什么使用 MySQL 任务表，不直接把任务放进 MQ？

### 满分答案

> 这个项目需要的不只是传输消息，还需要合并、抢占、重试、审计和人工补偿。publish_task 的 Pending 任务还要按面板 upsert，把连续变化合并成一次发布。数据库任务表既是调度记录，也是业务状态真源，适合承载这些语义。
>
> MQ 的优势是实时推送、削峰和高吞吐，但消息本身不适合作为可查询、可合并的业务状态。规模继续扩大时，我会使用“数据库任务表 + MQ 唤醒”的组合：本地事务先落任务，MQ 只通知消费者尽快处理；即使 MQ 消息丢失，定时扫描任务表仍能兜底。

### ASCII 图

```text
当前方案

业务事务
  ↓
MySQL 任务表
  ↓ 定时拉取
消费者


规模扩大

业务事务
  ├─ MySQL 任务表：业务真源
  └─ Outbox
        ↓
       MQ：实时唤醒
        ↓
      消费者

定时扫描任务表：消息丢失兜底
```

### 刻意思考

数据库任务表的缺点也要主动承认：

- 轮询存在延迟。
- Pending 热索引可能形成写热点。
- 数据库不是为超高吞吐消息传输设计的。
- 历史任务需要归档。

### 满分心智

```text
MQ 解决消息如何到达，
任务表解决业务执行到了哪里。
```

## 二、幂等与 exactly-once

### 题目

如何保证任务不会重复执行？这是 exactly-once 吗？

### 满分答案

> 我不会承诺严格的物理 exactly-once。网络超时、进程退出和消息重投下，执行动作可能被触发多次。项目采用的是 at-least-once 触发加业务幂等。
>
> 第一层用 task_key 防止同一业务事件重复生成有效任务；第二层用带状态条件的更新抢占，只有从 Pending 成功切换到 Processing 的消费者能执行；第三层在业务写入中使用事务、唯一约束或状态条件，保证重试不会重复产生业务结果。

### ASCII 图

```text
重复事件
  ↓
task_key 唯一约束
  ↓
一条有效任务
  ↓
CAS 状态抢占
  ↓
一个有效消费者
  ↓
事务 / 唯一约束 / 状态条件
  ↓
一个最终业务结果
```

### 刻意思考

幂等键必须来自业务语义，而不是随机 requestId。随机 ID 只能区分请求，无法识别同一个业务事件被重新发送。

### 满分心智

```text
不追求动作绝对只发生一次，
追求重复动作不会改变最终结果。
```

## 三、CAS 状态抢占

### 题目

多个消费者同时查到 Pending，如何保证只有一个执行？

### 满分答案

> 不能使用“先 select 判断状态，再 update”的两步方式，因为两个消费者可能同时读到 Pending。正确做法是把状态条件放进 update：
>
> `UPDATE ... SET status='Processing' WHERE id=? AND status='Pending'`
>
> MySQL 原子完成条件判断和更新，只有 affected rows 为 1 的消费者获得执行权。其他消费者更新到 0 行后直接跳过。

### ASCII 图

```text
消费者 A ─┐
          ├─ UPDATE ... WHERE status = Pending
消费者 B ─┘

A affectedRows = 1 → 执行
B affectedRows = 0 → 放弃
```

### 刻意思考

CAS 只解决谁获得当前状态的修改权，不自动解决：

- 执行期间进程宕机。
- 租约过期后旧消费者晚返回。
- 下游副作用是否幂等。

所以还需要租约、消费令牌和业务写入幂等。

### 满分心智

```text
查询状态是观察，
带状态条件的更新才是抢占。
```

## 四、MySQL 事务、隔离级别与行锁

### 题目

面板事务如何保证 Draft、索引和发布任务一致？

### 满分答案

> 同一面板的 Draft、分发索引、操作记录和 publish_task 在一个本地事务中提交。事务成功时四部分一起可见，任一步失败都会整体回滚。
>
> 并发修改相同分类时，需要使用当前读或 update 获取行锁，避免两个事务都基于旧值计算后互相覆盖。项目中还固定表访问顺序，并按 categoryId 排序加锁，减少死锁。

### ASCII 图

```text
BEGIN
  ↓
锁定 / 更新 Draft
  ↓
更新分发索引
  ↓
写操作记录
  ↓
upsert publish_task
  ↓
COMMIT

任一步失败 → ROLLBACK
```

### 继续追问：InnoDB 默认隔离级别是什么？

> MySQL InnoDB 常见默认是 Repeatable Read。普通快照读使用 MVCC，一致性读不会直接加行锁；`SELECT ... FOR UPDATE`、UPDATE 和 DELETE 属于当前读，会读取最新已提交版本并加锁。当前项目关心的是写写冲突，关键是确保最终写回基于被锁定或带版本条件的当前状态。

### 继续追问：Repeatable Read 是否完全没有幻读？

> InnoDB 在当前读下会使用 next-key lock 组合记录锁和间隙锁，避免范围内插入造成幻读；普通快照读通过 Read View 保持一致性视图。但具体是否产生间隙锁取决于索引和查询条件，不能简单说所有查询都会锁范围。

### 刻意思考

如果状态在事务外批量读取并计算，进入事务后必须：

- 重新基于锁定后的当前值计算。
- 或使用版本号做乐观锁，冲突后重新计算。

否则即使最终 UPDATE 加锁，也可能把过期快照覆盖回数据库。

### 满分心智

```text
事务保证一组写入共同成功，
行锁或版本号保证计算依据没有被并发改写。
```

## 五、upsert、唯一索引与并发合并

### 题目

多个事务同时 upsert 同一面板的 publish_task，会不会产生两条 Pending 或丢变化？

### 满分答案

> 数据库先用唯一约束保证同一业务键下只有一条有效 Pending。发生唯一键冲突时进入 update 分支，并对目标记录加锁。合并逻辑读取已有分类和素材范围，与本次变化取并集后写回。
>
> 唯一索引解决“不能有两条”，行锁解决“合并过程不能同时覆盖”，合并函数还必须去重，避免同一 ID 重复增长。

### ASCII 图

```text
事务 A：panel-1 + category-10 ─┐
                              ├─ unique(panel-1, Pending)
事务 B：panel-1 + category-20 ─┘
                                       ↓
                         一条 Pending publish_task
                         categories = {10, 20}
```

### 刻意思考

如果状态字段直接参与普通唯一索引，需要考虑 Published 历史记录是否会互相冲突。常见方案：

- 单独维护 active_key，仅 Pending 时有值。
- 使用生成列构造有效任务唯一键。
- 将历史任务与当前待处理任务拆表。

### 满分心智

```text
唯一约束防止重复记录，
锁内合并防止记录内容丢失。
```

## 六、租约与消费令牌

### 题目

Processing 有超时租约以后，为什么还需要 claimAt？

### 满分答案

> 租约只能说明某个消费者的执行权在时间上过期，不能让已经运行的旧进程自动停止。消费者 A 超时后，B 可以重新抢占；如果 A 随后晚返回，没有额外令牌就可能把 B 的状态覆盖。
>
> claimAt 相当于本轮消费令牌。B 重新抢占时写入新值，所有完成和失败更新都必须同时匹配任务状态与 claimAt。A 携带旧值，更新影响 0 行，因此不能覆盖新一轮结果。

### ASCII 图

```text
A 抢占：claimAt = 100
  ↓ 执行超过租约
B 抢占：claimAt = 200
  ↓
A 晚返回，WHERE claimAt = 100 → 更新 0 行
B 返回，  WHERE claimAt = 200 → 更新成功
```

### 刻意思考

更通用的 fencing token 使用单调递增序号，下游资源只接受比已见 token 更大的请求。时间戳只有在业务条件严格匹配时可以作为消费令牌，不能泛化成所有分布式锁场景下的强 fencing token。

### 满分心智

```text
租约允许别人接管，
令牌阻止旧主人回来写。
```

## 七、MySQL 死锁

### 题目

批量更新多个分类时如何避免死锁？

### 满分答案

> 死锁通常来自两个事务以不同顺序持有并等待资源。项目中固定先操作 Draft，再操作分发索引；同一面板内的多个分类按 categoryId 排序后加锁，尽量让所有事务使用一致顺序。同时缩短事务，只把必要写入放进事务，不在持锁期间做远程调用。
>
> 这些措施只能降低概率，不能承诺绝不死锁。MySQL 检测到死锁后会回滚一个事务，应用层需要识别死锁错误，使用有上限、带随机抖动的重试。

### ASCII 图

```text
错误顺序

事务 A：锁 Category 1 → 等 Category 2
事务 B：锁 Category 2 → 等 Category 1


固定顺序

事务 A：Category 1 → Category 2
事务 B：Category 1 → Category 2
```

### 满分心智

```text
固定锁顺序降低死锁，
有限重试处理剩余死锁。
```

## 八、悲观锁与乐观锁

### 题目

为什么这里使用行锁？能不能使用乐观锁？

### 满分答案

> 悲观锁适合冲突概率高、计算和写入需要基于当前状态完成的场景。锁定分类行后，可以读取最新列表、按顺序应用动作并写回。
>
> 乐观锁可以给 Draft 增加 version，更新时使用 `WHERE version = oldVersion`。冲突后重新读取和计算，锁持有时间更短，但高冲突热点下会产生大量重试。
>
> 当前面板批次内需要一起更新多个对象，本地事务和行锁更直接；如果未来计算耗时变长、冲突较低，可以把计算移到事务外，并用版本号校验后提交。

### 对比

| 维度 | 悲观锁 | 乐观锁 |
| --- | --- | --- |
| 冲突处理 | 先阻塞后执行 | 冲突后失败重试 |
| 适合场景 | 热点高、重算贵 | 冲突低、事务需短 |
| 风险 | 锁等待、死锁 | 重试放大、饥饿 |

### 满分心智

```text
冲突高时锁住再算，
冲突低时先算再验。
```
