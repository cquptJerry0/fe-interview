# 八股二：Redis 与缓存一致性

## 一、Redis 与 MySQL 一致性

### 题目

如果项目中的配置使用 Redis 缓存，如何保证 Redis 和 MySQL 一致？

### 先说项目边界

> 当前任务状态和 Draft 正确性不依赖 Redis，MySQL 是业务真源。即使 Redis 不可用，也不能影响任务最终状态判断。Redis 如果用于配置缓存，只影响读取性能；如果用于跨批次协调，也必须由 MySQL 状态条件做最终正确性兜底。

### 满分答案：Cache Aside

> 常规方案采用 Cache Aside。读取时先查 Redis，未命中再查 MySQL 并回填；写入时先提交 MySQL，再删除缓存，而不是同时更新两份数据。删除失败需要重试、消息补偿或订阅 binlog 再次失效缓存。

### ASCII 图

```text
读路径

Read
  ↓
Redis hit ─────────→ 返回
  ↓ miss
MySQL
  ↓
回填 Redis


写路径

Update MySQL
  ↓ commit success
Delete Redis
  ↓
后续读取回源新值
```

### 为什么一般先更新数据库，再删除缓存？

> 数据库是业务真源，写失败时不能先让缓存表现成新状态。更新数据库后删除缓存，下一次读取会回源得到新值。直接同时更新缓存更容易出现并发写覆盖和双写失败。

### 经典并发窗口

```text
请求 A：Redis miss，读取到旧 DB 值
请求 B：更新 DB，删除 Redis
请求 A：把旧值回填 Redis

结果：旧值在删除动作之后重新进入缓存
```

### 如何治理这个窗口？

按一致性要求选择：

1. 短 TTL：接受短时间最终一致，降低陈旧值存活时间。
2. 延迟双删：数据库更新后立即删一次，等待旧读回填后再删一次。
3. 版本号：缓存值携带数据库版本，只允许更高版本覆盖低版本。
4. Binlog/CDC：数据库提交后异步发送失效事件，补偿删除失败和并发窗口。
5. 强一致读：写后读、审核发布等关键路径绕过缓存或校验版本。

### 延迟双删能保证强一致吗？

> 不能。延迟时间无法准确覆盖所有慢查询和调度抖动，第二次删除也可能失败。它是缩短不一致窗口的工程手段，不是严格一致性证明。真正需要强一致时，应以数据库为准，使用版本校验、串行化或绕过缓存。

### 刻意思考

本项目的任务创建会固化源版本和变更计划，因此即使配置后来更新，已创建任务也不应该被最新缓存值改写。

```text
缓存一致性：读取到的配置是否足够新。
任务时间一致性：任务重试时是否保持创建时含义。
```

这是两个不同问题。

### 满分心智

```text
MySQL 保存事实，Redis 加速读取。
缓存可以短暂不一致，业务真源不能含糊。
```

## 二、Redis 分布式锁

### 题目

如果需要用 Redis 保证同一业务线或面板跨批次串行，怎么实现？

### 满分答案

> 获取锁使用 `SET key token NX PX ttl`，token 必须是当前持有者唯一值。释放锁不能直接 DEL，要用 Lua 脚本先比较 token 再删除，避免误删别人重新获取的锁。长任务还需要续期或 watchdog。
>
> 但只靠 Redis 锁仍然不够。锁可能因 STW、网络分区或续期失败提前过期，旧持有者仍可能继续运行。因此关键写入还要携带 fencing token，或者至少使用 MySQL 状态、版本号和行锁拒绝过期执行者。

### ASCII 图

```text
SET panel:1 token-A NX PX 30000
             ↓
          执行业务
             ↓
Lua:
if GET(key) == token-A then
  DEL(key)
end

最终写库：
WHERE version = oldVersion
或 WHERE claimAt = currentToken
```

### 为什么释放锁要比较 token？

```text
A 获得锁
  ↓ 锁过期
B 获得同一个 key
  ↓
A 执行 DEL
```

如果 A 不比较 token，会误删 B 的锁。Lua 将读取和删除放在一个原子脚本中，只有当前 token 属于 A 时才删除。

### 为什么自动续期仍然不够？

> watchdog 只能降低锁提前过期概率。进程长时间暂停、网络分区或 Redis 故障时，旧持有者仍可能失去锁但继续执行。最终存储必须能够识别并拒绝过期持有者。

### fail-open 还是 fail-close？

- fail-open：Redis 不可用时允许继续，由数据库条件兜底；适合锁只做性能优化。
- fail-close：Redis 不可用时拒绝执行；适合重复执行代价极高，但会降低可用性。

当前项目如果引入 Redis 锁，更适合把它作为减少竞争的优化，MySQL 仍负责最终正确性。

### 满分心智

```text
分布式锁减少并发进入，
数据库条件拒绝过期写入。
```

## 三、缓存击穿、穿透与雪崩

这不是当前项目核心，但 Redis 话题经常顺带追问。

### 缓存穿透

查询不存在的数据，每次都落到数据库。

方案：

- 缓存空值并设置短 TTL。
- Bloom Filter 预判 key 是否可能存在。
- 参数校验和恶意请求限流。

### 缓存击穿

单个热点 key 失效，大量请求同时回源。

方案：

- singleflight 或互斥锁，只允许一个请求回源。
- 逻辑过期，后台异步刷新。
- 热点 key 提前续期。

### 缓存雪崩

大量 key 同时失效或 Redis 整体不可用。

方案：

- TTL 增加随机抖动。
- 多级缓存和高可用部署。
- 限流、熔断和降级。
- 数据库容量保护。

### 项目化回答

> 自动分发任务不能因为缓存雪崩而无限并发回源。公共配置批量加载本身可以减少回源放大；如果 Redis 故障，还需要有界 worker 和数据库限流，防止队列积压直接转成数据库雪崩。

## 四、最后速记

```text
1. Cache Aside：读缓存，miss 回源；写数据库，再删缓存。
2. 延迟双删只能缩短窗口，不能证明强一致。
3. 强一致路径以数据库为准，必要时绕过缓存。
4. Redis 锁必须带唯一 token，Lua 比较后释放。
5. 租约过期后旧进程仍可能运行，最终写入需要 token 或版本条件。
6. Redis 是加速和协调层，不能替代业务真源。
```
