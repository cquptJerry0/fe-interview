# 自动分发与发布链路重构：面试逐字稿

## 使用方式

这份材料不建议逐句背诵。真正需要记住的是一条判断链：

```text
隐式副作用失控
→ 把执行过程变成显式任务
→ 把全量扫描变成真实变更驱动
→ 把逐动作执行变成批量计算最终状态
```

面试时根据时间选择版本：

- 30 秒：只讲项目矛盾、三步架构演进和最终结果。
- 3 分钟：讲清旧链路、总体架构和三个关键改造。
- 深挖：进入某一个故事，重点回答为什么这么判断、普通方案为什么不够、正确性如何保证。

---

## 一、先讲思维：我怎么理解这个项目

### 1. 核心判断

我一开始没有把它理解成一个单纯的消费者性能问题。

当时链路同时出现了三类现象：事件回调容易超时，Draft 已经更新但正式版本没有发布，以及自动分发任务长期积压。表面上看分别属于可靠性、发布和性能问题，但它们有一个共同根因：系统把大量业务副作用藏在回调、定时扫描和逐任务循环里，没有一个明确的执行对象来说明“这次到底要做什么、做到哪一步、失败后从哪里恢复”。

所以我的改造顺序不是先加缓存或并发，而是分三步重新建立链路边界：

1. 先把不可控的副作用变成可追踪、可恢复的任务。
2. 再把正式发布从“扫描所有面板找变化”改成“变化发生时主动登记”。
3. 任务化后继续治理执行模型，把逐任务、逐分类写入改成整批计算最终状态。

这三个改造不是三个零散优化，而是一条从可靠性到发布效率，再到吞吐能力的架构演进。

### 2. 30 秒版本

> 这个项目我主要解决的是自动分发链路不可控的问题。旧链路把计算和写库放在事件回调里，正式发布又依赖定时扫描全部面板，任务一多还会在每个分类上重复查询和提交事务，所以同时出现了回调超时、发布半成功和 5000 多条任务积压。我先把自动分发和面板同步改造成显式任务，再用 publish_task 记录真实发生的 Draft 变更，替代全量扫面板，最后把消费者从逐任务执行重构成批量状态归并。改造后，发布发现从约 20 分钟的完整扫描降到 10 秒内，单批消费从约 20 分钟降到 24 秒，处理效率提升约 50 倍。

### 3. 3 分钟版本

> 这个项目的业务背景是，素材状态变化、分类规则变化或者面板同步配置变化之后，系统要自动完成素材分发、Draft 更新和正式版本发布。旧链路是逐步叠加出来的：有些逻辑直接在事件回调里计算和写库，有些靠定时任务扫描面板状态，还有些在消费者里逐任务、逐分类执行。
>
> 当任务量上来以后，问题不是单点慢，而是整条链路缺少明确边界。回调超时以后无法判断执行到了哪一步；Draft 更新成功、正式发布失败时会出现半成功；消费者虽然是异步的，但每条任务仍然重复加载相同数据，并为每个分类单独提交事务，最终生产速度长期高于消费速度，积压超过 5000 条。
>
> 我的判断是先治理执行语义，再治理性能。第一步，我把自动分发、面板同步和素材状态同步统一成事件建单、消费者执行的任务模型，并在任务创建时固化源版本和净变更计划，避免任务等待期间配置变化导致执行语义漂移。
>
> 第二步，我把正式发布单独拆成 publish_task。只有 Draft 真实变化时才在同一事务里登记发布任务，同一面板的连续变化通过 upsert 合并。这样定时器不再遍历数百个面板做 Diff，只消费真正待发布的面板，完整扫描约 20 分钟的问题被收敛到 10 秒内的任务发现。
>
> 第三步，我根据日志继续重构自动分发消费者。旧链路 50 条任务会展开成 976 个分类动作，耗时 19 分 48 秒。根因不是一条 SQL 慢，而是公共数据、事务和发布登记被动作数量放大。我改成整批加载公共数据，先生成有序动作，再按分类计算最终状态，最后按面板聚合事务提交。100 条近等量任务最终在 24 秒内完成，单批容量从 50 条提升到 100 条，长期积压问题也随之解决。
>
> 这次改造最核心的变化，是把系统从“收到一个动作就执行一个动作”，变成“先明确任务，再计算一批动作共同产生的最终状态，最后按业务一致性边界落库和发布”。

## 二、项目背景：旧链路为什么会失控

### 1. 业务链路

一次素材或配置变化，最终要经过两段业务过程：

```text
素材事件 / 规则变化 / 面板配置变化
                  ↓
       自动分发与面板同步
                  ↓
          更新面板 Draft
                  ↓
            构建版本 Diff
                  ↓
            发布正式版本
```

这里的难点不只是“把素材写进一个分类”。系统还要处理重复事件、配置变化、任务顺序、失败重试、人工发布插入，以及同一批变化对多个分类和面板的影响。

### 2. 旧链路的问题

```text
事件回调
  ├─ 直接读取配置
  ├─ 现场计算变化
  ├─ 逐分类更新 Draft
  └─ 部分链路直接触发发布

定时任务
  └─ 遍历全部面板，比较 Draft 与线上版本

异步消费者
  └─ 逐任务、逐分类重复查询和提交事务
```

这套方式在数据量小时能工作，但规模上来以后暴露出三个结构性问题：

| 表面现象 | 真正问题 |
| --- | --- |
| 回调超时后服务端还在执行 | 请求生命周期和业务执行生命周期绑在一起，无法可靠确认结果 |
| Draft 已更新但正式版本未发布 | Draft 写入和发布发现是两套松散机制，中间缺少可恢复记录 |
| 5000+ 任务持续积压 | 消费者虽然异步化了，内部仍然逐动作执行，固定成本和事务次数被放大 |

### 3. 项目背景逐字稿

> 这条链路不是一次性设计出来的，而是随着自动分发、面板同步和正式发布能力不断增加，逐渐形成了多种执行方式。有的逻辑在事件回调里直接跑，有的依赖定时器扫面板，有的虽然进入了任务消费者，但内部还是逐条执行。
>
> 我接手后先没有急着改某个函数，而是把一次业务变化从事件产生一直追到正式版本。最后发现三个问题其实是连在一起的：前半段没有稳定的任务语义，中间没有可靠的发布交接，后半段又存在严重的写放大。
>
> 所以我把项目目标定义成“重建自动化链路”，而不是“优化一个消费者”。只有先把执行对象、状态和事务边界说清楚，后面的重试、发布和性能优化才不会继续打补丁。

## 三、总体方案：两级任务链路

### 1. 总体架构

```text
素材事件 / 配置变化
          │
          │ 事件建单，固化源版本与净变更计划
          ▼
┌──────────────────────┐
│  distribute_record   │
│  自动分发 / 同步任务   │
└──────────────────────┘
          │
          │ 批量计算最终分类状态
          ▼
┌──────────────────────┐
│  Draft + 分发索引      │
│  按面板事务提交         │
└──────────────────────┘
          │
          │ Draft 真实变化时，在事务内 upsert
          ▼
┌──────────────────────┐
│    publish_task      │
│    正式发布任务        │
└──────────────────────┘
          │
          │ 合并同面板变化，构建一次 Diff
          ▼
      正式版本
```

### 2. 为什么拆成两级任务

`distribute_record` 和 `publish_task` 对应两个不同的业务承诺：

| 任务 | 回答的问题 | 完成条件 |
| --- | --- | --- |
| distribute_record | 这次自动化操作应该怎样修改 Draft | 目标 Draft、索引和操作结果已经落库 |
| publish_task | 已经发生的 Draft 变化怎样进入正式版本 | Diff 已构建并发布，或确认没有待发布变化 |

如果合成一个大任务，Draft 计算失败和版本发布失败会混在同一个状态机里。重试发布时可能重复计算 Draft，重算 Draft 时又可能受最新配置影响。拆开后，前一级只负责产生确定的 Draft 结果，后一级只负责把真实变化发布出去，失败恢复和吞吐治理可以分别设计。

### 3. 总体方案逐字稿

> 我最后把链路拆成两级任务。第一级 distribute_record 承接素材事件和配置变化，负责计算并写入 Draft；第二级 publish_task 只承接已经发生的 Draft 变化，负责构建 Diff 和发布正式版本。
>
> 这两个任务没有合成一个，是因为它们的失败语义不一样。自动分发失败，需要重新计算或回滚对应面板事务；正式发布失败，只应该重试已有 Draft 的发布，不应该再执行一遍自动分发。拆开以后，每一级都有明确输入、完成条件和重试边界。
>
> 在性能上，我又把消费者内部从任务驱动改成批次驱动。任务仍然是追踪和回填结果的单位，但真正计算和提交时，会把一批任务共同影响的分类和面板合并处理。这样既保留每条任务的状态，又不会为每条任务重复支付相同成本。

## 四、故事一：把隐式副作用变成显式任务

### 1. 思维起点

我对第一阶段的判断是：系统最先缺的不是更快的执行器，而是一份可靠的执行账本。

如果逻辑仍然藏在事件回调里，即使把 SQL 优化得很快，也回答不了这些问题：

- 回调超时后，任务到底有没有继续执行？
- 同一个事件重复投递，会不会重复写入？
- 任务等待期间配置发生变化，应该按旧配置还是新配置执行？
- 同一来源的两个版本乱序到达，最终结果以哪个为准？
- 某一步失败后，应该从哪里恢复？

所以第一步必须把“一次自动化操作”建模成稳定任务，而不是只把原函数包进异步消费者。

### 2. 关键设计

#### 事件建单

事件侧只负责识别任务类型、生成业务幂等标识并建单，不再在回调内完成整段计算和写库。

任务类型覆盖：

```text
initial_auto_distribute
choose_category_change
panel_auto_sync
static_review_auto_sync
```

#### 固化执行语义

面板同步任务创建时记录源版本、同步配置和净变更计划。净变更计划只保留这次需要新增、移除和更新的内容，不复制完整目标列表。

这样做解决的是一个很容易被忽略的问题：事件发生时的业务含义，不能被消费者执行时的最新配置偷偷改写。

#### 状态抢占与顺序控制

消费者使用带状态条件的更新把任务从 `Pending` 改为 `Processing`。只有更新成功的消费者才能继续执行，避免多个实例同时消费同一任务。

同一来源到目标的版本流按顺序执行，新版本要等待旧版本完成；分类同步任务还会作为普通自动分发批次的顺序屏障，避免前后两类变化交叉覆盖。

#### 结果可回填

任务最终进入 `Finished` 或 `Failed`，并记录新增、移除、跳过和失败结果。任务表既是调度记录，也是后续排查和补偿的依据。

### 3. 满分逐字稿

> 第一阶段我解决的是执行不可控。旧链路在收到事件后直接读取当前配置、计算分类变化并写库，请求超时以后，调用方只知道没有拿到响应，却不知道服务端执行到了哪一步。重复事件和配置变化也会让结果变得不确定。
>
> 我的做法不是简单套一层异步，而是先定义任务语义。事件到达时生成 distribute_record，用业务事件标识去重，同时把源版本和这次真正需要执行的变更计划固化下来。消费者执行时只认任务中的计划，不重新用最新配置推导一遍。
>
> 任务抢占使用带状态条件的更新，只有把 Pending 成功改成 Processing 的实例才能继续执行。同一来源到目标的多个版本还要保持顺序，避免新版本先执行、旧版本后覆盖。
>
> 这样改完以后，一次自动化操作从一个无法观察的回调副作用，变成了有输入、有状态、有结果、可以重试和回溯的任务。后面的发布任务化和批量执行，都是建立在这个基础上的。

### 4. 为什么不是其他方案

#### 为什么不只接一个 MQ

MQ 能把执行从请求里移出去，但不能自动解决业务语义。没有任务记录时，仍然缺少源版本、变更计划、状态、结果和人工补偿入口。这里需要的是“消息传输 + 业务任务状态”，不是把函数换一个触发方式。

#### 为什么执行时不重新读取最新配置

因为任务代表的是某个历史时刻已经发生的业务变化。执行时重新读取最新配置，可能把一条旧事件解释成新的含义，重试也不再等价。固化计划是为了让同一任务每次执行的目标保持一致。

#### 为什么只保存净变更，不保存完整目标列表

完整列表数据量更大，也容易与目标端当前状态发生覆盖冲突。净变更只表达这次操作的意图，执行时可以在受控事务中合并到当前状态，既保留事件语义，也减少任务体积。

### 5. 面试官追问

#### 问：如何保证重复事件不会重复执行？

> 我分两层处理。建单时使用业务事件维度的 task_key 去重，避免同一事件生成多条有效任务；消费时再使用带状态条件的更新抢占任务，只有从 Pending 成功切到 Processing 的实例才能执行。即使出现超时重试，消费者也会先检查任务状态，不会无条件重复写。

#### 问：这是不是 exactly-once？

> 我不会把它描述成严格的 exactly-once。网络超时和进程退出下，很难只靠应用层保证物理执行一次。这里保证的是任务可以重复触发，但重复触发不会改变最终业务结果，也就是用任务去重、状态抢占和写入事务做到业务幂等。

#### 问：任务创建以后配置改了怎么办？

> 已创建任务继续按创建时固化的源版本和变更计划执行，因为它代表当时已经发生的业务意图。新配置会产生新的版本或新任务，按顺序排在后面。这样不会让历史任务在重试时改变含义。

#### 问：为什么一定要保证同一来源的版本顺序？

> 因为分类列表不是无序集合，新增动作可能有前插语义，旧版本后执行会覆盖新版本结果。我的边界是同一来源到目标流必须串行，不同面板才有并行空间。

#### 问：任务执行一半失败怎么办？

> 真正修改 Draft 时会按面板放在事务里提交，单个面板内部的 Draft、分发索引、操作记录和发布任务要么一起成功，要么一起回滚。任务层再根据各面板结果回填成功或失败，失败面板可以重试，不会留下只有一半索引更新的状态。

#### 问：任务表会不会越来越大？

> 热路径只查询待处理状态，并配合状态和业务维度索引。完成任务用于审计和排查，可以按时间归档或分区。任务表的价值是保留执行事实，但不会让历史数据长期参与在线调度查询。

### 6. 延伸问题

如果面试官继续往任务系统方向追，可以主动展开：

- 状态机如何避免非法跳转。
- 长时间 Processing 任务如何通过租约恢复。
- 失败任务是自动重试、人工重放还是进入死信队列。
- 如何给任务增加 traceId、事件版本和配置版本，支持端到端回放。
- 任务积压时如何按业务线、面板或任务类型做优先级和背压。

## 五、故事二：把全量扫描改成增量发布

### 1. 思维起点

执行任务化以后，Draft 更新过程已经可追踪，但正式发布仍然依赖定时器遍历全部面板，逐个比较 Draft 和线上版本。

这个方案的问题不只是慢，而是发现变化的方式反了。系统明明在 Draft 变化发生的那一刻就知道哪个面板被修改，却把这条信息丢掉，之后再花约 20 分钟扫描数百个面板重新寻找变化。

所以第二阶段的核心判断是：

```text
不要扫描世界寻找变化，
要在变化发生时留下发布事实。
```

### 2. 关键设计

#### Draft 变化时登记发布任务

只有 Draft 真实变化后，才在同一事务中 upsert `publish_task`。如果 Draft 提交成功，发布任务一定存在；如果事务回滚，两者一起回滚，避免 Draft 已变但发布侧完全不知情。

#### 同面板连续变化合并

Pending 任务按 `bizId + areaKey + sceneKey` 唯一标识一个待发布面板。并发变化到达时，upsert 会锁定并更新同一条 Pending 任务，把分类和素材变化范围合并进去。

任务合并的目标不是少写一行表，而是让同一面板的一串变化只构建和发布一次版本。

#### 抢占、租约与消费令牌

消费者扫描 Pending 和租约过期的 Processing 任务，通过带状态条件的更新抢占。`claimAt` 记录本轮消费令牌，旧消费者即使晚返回，也不能覆盖新一轮消费者已经更新的状态。

Processing 租约为 10 分钟，失败最多重试 3 次；超过次数后进入 Failed 并告警。

#### no-op 也可以成功

如果任务等待期间已经有人手工发布，消费者最终计算出的 Diff 可能为空。这不是失败，而是说明目标状态已经达成，任务可以按成功结束，避免无意义重试。

### 3. 满分逐字稿

> 第二阶段我处理的是正式发布。旧方案靠定时器遍历数百个面板，再逐个比较 Draft 和线上版本，一次完整扫描大约需要 20 分钟。它最大的浪费是，Draft 变化发生时系统其实已经知道受影响面板，但没有保留这个事实，后面只能重新扫描。
>
> 我新增了 publish_task。Draft 真正变化后，在同一个事务里 upsert 对应面板的待发布任务。这样 Draft 成功但发布任务丢失的窗口被关掉了。对于同一面板短时间内连续发生的变化，不创建多条独立发布，而是把分类和素材范围合并到同一条 Pending 任务里，最终只构建一次 Diff 和版本。
>
> 消费端使用带状态条件的更新抢占任务，并给 Processing 状态增加 10 分钟租约。为了防止旧消费者恢复后覆盖新消费者的结果，我又加了 claimAt 作为本轮消费令牌。失败任务最多重试 3 次，再进入 Failed 告警。
>
> 改造后，定时器不再扫描所有面板，只读取真实待发布任务，变更发现从约 20 分钟的完整扫描降低到 10 秒内。同时，同一面板的连续变化被合并，减少了无效 Diff 计算和重复版本构建。

### 4. 架构对比

```text
旧方案

定时器
  ↓
扫描全部面板
  ↓
逐个读取 Draft 和线上版本
  ↓
计算是否有 Diff
  ↓
有变化才发布


新方案

Draft 事务
  ↓
真实变化时 upsert publish_task
  ↓
合并同面板连续变化
  ↓
消费者只读取待发布任务
  ↓
一次构建并发布版本
```

### 5. 为什么不是其他方案

#### 为什么用 upsert，而不是每次 insert 一条任务

每次 insert 可以保留完整事件历史，但同一面板短时间内可能产生大量重复发布。正式版本只关心一段时间内累积后的最终 Draft，Pending 阶段使用 upsert 可以天然合并变化范围。操作历史仍由 Draft 和业务操作记录保留，不需要依靠重复发布任务表达。

#### 为什么仍然保留定时器

定时器的职责已经变化了。旧定时器负责全量发现变化，新定时器只负责调度显式任务。这样既保留简单可靠的周期消费方式，也把查询规模从全部面板缩小到待发布集合。

#### 为什么不直接在 Draft 事务里同步发布

版本构建和下游发布耗时更长，也可能依赖外部服务。如果塞进 Draft 事务，会拉长锁持有时间，并把下游故障传导到自动分发。publish_task 相当于两段业务过程之间的可靠交接记录。

### 6. 面试官追问

#### 问：如何保证 Draft 更新成功以后 publish_task 一定存在？

> Draft、分发索引、操作记录和 publish_task 在同一个面板事务中提交。publish_task 不是事务提交以后再异步补写，所以不会出现 Draft 已提交但发布意图完全丢失的窗口。

#### 问：并发 upsert 会不会丢掉某次变化？

> Pending 任务按面板维度唯一。upsert 时会锁定同一条待发布记录，再合并分类和素材 ID，而不是用最后一次请求直接覆盖。并发事务最终串行更新同一行，变化范围取并集。

#### 问：消费者宕机，任务一直停在 Processing 怎么办？

> Processing 是有租约的。超过 10 分钟仍未完成的任务会重新进入可抢占集合。新的消费者抢占后会生成新的 claimAt，后续状态更新必须同时匹配任务状态和本轮 claimAt，避免旧消费者恢复后把新结果覆盖掉。

#### 问：同一面板在发布过程中又有新变化怎么办？

> 正在 Processing 的任务代表本轮已经领取的变化，新的变化会继续登记到 Pending 任务。当前发布完成后，下一轮再处理新增变化。这样不会无限延长当前任务，也不会让发布过程中的变化丢失。

#### 问：人工发布先执行了，自动发布任务怎么办？

> 消费者会基于当前 Draft 和线上版本重新计算 Diff。如果人工发布已经把状态推进到目标版本，Diff 为空就按成功 no-op 结束。系统关注的是目标状态是否达成，不要求每条任务都必须生成一个新版本。

#### 问：为什么不直接用 MQ 或 CDC 触发发布？

> MQ 或 CDC 可以负责通知，但仍然需要一个可合并、可抢占、可重试的业务任务状态。这个场景还要求同面板连续变化合并，所以数据库任务表更适合作为业务真源。后续如果吞吐继续扩大，可以用 MQ 做唤醒，但任务表仍然保留状态和恢复能力。

#### 问：10 秒是发布完成时间吗？

> 不是。这个指标指从全量扫描发现变化，变成定时器在 10 秒内发现显式待发布任务。实际发布耗时还取决于 Diff 和版本构建，这两个口径需要分开讲。

### 7. 延伸问题

这个故事可以继续延伸到：

- Outbox：如果 Draft 和发布任务未来跨库，如何可靠投递事件。
- Debounce：高频面板是否需要增加短时间合并窗口。
- 分片：发布量继续增长后，如何按业务线或面板哈希分配消费者。
- 优先级：紧急人工发布如何越过普通自动发布任务。
- 可观测性：如何监控最老 Pending 年龄、租约过期次数和任务合并率。

## 六、故事三：从逐动作执行到批量状态归并

### 1. 思维起点

任务化解决了执行可追踪的问题，但也把真正的性能瓶颈暴露得更清楚。

当时已经出现 5000 多条积压，而且生产任务的速度长期高于消费速度。最直接的做法是增加消费者并发，但我没有先这么做，因为旧链路的事务和锁粒度都在分类维度，直接加并发只会把重复查询、数据库竞争和死锁一起放大。

我先用一次 50 条任务的真实 Case 做拆解：

```text
50 条任务
→ 976 个分类动作
→ 总耗时 19 分 48 秒
```

前 10 分钟的日志显示，分类写回约占总耗时的 69%。同一批任务在重复读取素材、规则、面板和相似分类；每个分类动作又分别开启 Draft 事务并登记一次发布任务。根因不是某条 SQL 特别慢，而是执行模型让固定成本和事务次数随动作数量放大了近千次。

因此我把优化目标从“更快执行每个动作”改成：

```text
不要逐个执行 976 个动作，
要计算这些动作共同作用后的最终状态。
```

### 2. 优化前

```text
遍历任务
  ↓
每条任务重复加载素材、规则、面板
  ↓
展开多个分类动作
  ↓
每个分类读取一次 Draft
  ↓
每个分类提交一次事务
  ↓
每个分类 upsert 一次 publish_task
```

任务是调度单位，同时也被错误地当成了查询、计算和事务单位。

### 3. 优化后

```text
一批 distribute_record
          ↓
批量加载素材、规则、面板和相似分类
          ↓
生成带 taskOrder 的 add / remove 动作
          ↓
按分类归并，计算每个分类的最终状态
          ↓
按面板组织事务
          ↓
每个分类解析和写回一次
每个面板登记一次 publish_task
          ↓
把动作结果映射回原任务
```

### 4. 关键设计

#### 批量准备公共数据

先建立 Batch Context，把一批任务涉及的素材、规则、面板配置和相似分类一次性加载并复用。只查询本批需要的字段，移除通用查询中与自动分发无关的数据。

#### 动作归并，但不丢顺序

每条任务先转成标准化的 add/remove 动作，并保留 `taskOrder`。相同分类的动作归到一起，按照原任务顺序依次作用于同一份内存状态，最后只产生一个分类结果。

顺序不能丢，因为新增素材存在前插语义。同一批动作如果只做无序集合合并，最终列表顺序会发生变化。

#### 事务边界对齐面板

分类是状态计算单位，面板是业务一致性和正式发布单位。因此先按分类计算最终状态，再按面板提交事务。

一个面板事务中完成：

- Draft 分类列表更新。
- 分发索引更新。
- 操作记录写入。
- publish_task 合并登记。

单个面板失败只回滚该面板，不拖垮整批任务。

#### 结果映射回任务

虽然底层按分类和面板合并执行，但外部仍然以 distribute_record 为追踪单位。每个动作都会保留来源任务，提交后再把新增、移除、跳过和失败结果精确回填到原任务。

这一步很重要，否则批量优化会牺牲任务级可观测性。

### 5. 满分逐字稿

> 第三阶段是性能治理。当时生产任务速度长期高于消费速度，已经积压了 5000 多条。旧消费者处理 50 条任务会展开成 976 个分类动作，总耗时 19 分 48 秒。
>
> 我先做日志拆解，发现写回占了约 69%。问题不在某一条 SQL，而是每条任务都重复加载相同的素材、规则和面板数据，每个分类动作又分别读取 Draft、提交事务和登记发布任务。动作数量一多，固定成本和事务次数就被放大。
>
> 所以我没有直接加并发，而是把消费者从逐任务执行改成批量状态归并。先整批加载公共数据，把任务转换成带顺序的 add/remove 动作；再按分类归并，在内存中计算这一批动作执行后的最终列表；最后按面板建立事务，每个分类只解析和写回一次，每个面板只合并登记一次发布任务。
>
> 这里最难的是不能为了批量化牺牲正确性。同一分类内我保留原任务顺序，因为新增存在前插语义；落库时固定 Draft、分发索引的加锁顺序，并按 categoryId 排序，降低死锁风险；单个面板失败只回滚该面板，执行结果再映射回每条原始任务。
>
> 最终 100 条近等量任务、965 个动作，归并成 183 个分类和 24 个面板事务，服务端耗时约 24 秒。单批容量从 50 条提升到 100 条，处理效率约提升 50 倍，持续积压也得到解决。

### 6. 为什么不是其他方案

#### 为什么不先加消费者并发

旧模型的主要成本来自重复查询和大量小事务。直接加并发不会消除这些成本，反而会增加同分类、同面板上的锁竞争。先减少工作总量，再在不同面板之间增加受控并发，收益和稳定性都更可控。

#### 为什么不只做 SQL 和索引优化

SQL 优化可以降低单次查询耗时，但无法改变 976 个动作重复查询和提交近千次事务的事实。这个 Case 的关键不是把每次操作从 800 毫秒降到 500 毫秒，而是把近千次分类写回收敛为 183 次分类状态计算和 24 个面板事务。

#### 为什么不直接把所有动作合成无序集合

分类内容有顺序，新增动作使用前插策略。两个任务的先后顺序会影响最终列表。如果只做集合 union/difference，素材是否存在可能正确，但排序会错误。批量化只能消除重复计算，不能抹掉业务顺序。

#### 为什么事务边界是面板，不是整批

整批事务会锁住过多面板，一处失败导致全部回滚；按分类事务又会让同一面板出现部分成功，并重复登记发布。面板正好是 Draft 一致性和正式发布的共同边界，既能保证单面板结果完整，也能隔离不同面板的失败。

### 7. 面试官追问

#### 问：50 倍提升是不是因为测试数据不同？

> 对比采用的是近等量动作规模。旧链路 50 条任务展开 976 个动作，耗时 1188 秒；新链路 100 条任务展开 965 个动作，耗时 23.5 秒。任务数不同，但真正决定工作量的动作数接近，所以用动作规模对齐更合理。这个结果来自 PPE 实测，不是只比较理论复杂度。

#### 问：批量归并如何保证与逐条执行结果一致？

> 我保留每个动作的 taskOrder，同一分类内仍然按旧链路顺序依次应用 add/remove，只是把中间状态放在内存，不再每执行一个动作就读写数据库。归并后的最终状态与逐条执行一致，再通过真实 Case 比对 Draft、分发索引、任务结果和 publish_task。

#### 问：同一分类同时被两个批次处理怎么办？

> 数据库写回时会锁定分类对应的 Draft 行，避免并发覆盖；同一批内部严格按 taskOrder 计算。跨批次还依赖任务状态抢占和固定触发周期降低重叠。更高并发下，我会进一步按业务线或面板做分区消费，让同一一致性键进入同一执行分区。

#### 问：如何降低死锁？

> 事务内固定先锁 Draft，再锁分发索引；多个分类按 categoryId 排序后再操作，让不同事务尽量使用相同加锁顺序。并发也只应该放在不同面板之间，避免同面板事务互相交叉。

#### 问：一个面板失败，整批任务怎么回填？

> 面板事务回滚后，该面板相关动作标记为失败，其他已经成功提交的面板不受影响。最后根据动作和来源任务的映射，汇总每条 distribute_record 的 added、removed、skipped 和 failed。这样批量执行不等于只有一个笼统的批次结果。

#### 问：为什么写回仍然占主要耗时？

> 优化后 write 仍然是主要阶段，因为 Draft 当前以 JSON/TEXT 列表保存，更新分类需要解析和重写整份列表。当前方案已经消除了重复写放大；再往下优化需要调整存储模型，例如引入分类素材关系表，而不只是继续调消费者代码。

#### 问：如果任务量再扩大十倍怎么办？

> 第一层先做背压和分区，按业务线或面板哈希，让同一一致性键串行、不同键并行；第二层把 JSON 列表迁移为带 sort_key 的关系表，降低整列解析和重写成本；第三层补齐积压年龄、动作放大率、面板热点和失败率监控，动态调整批次大小，而不是固定提高并发。

#### 问：HTTP 502 但服务端继续执行，任务化后怎么解决？

> 旧链路的问题是调用方把 HTTP 响应当成执行结果。任务化后，HTTP 只确认是否成功建单，真正结果由 distribute_record 状态表达。调用方可以按任务 ID 查询，超时不会再等价于业务失败，也不会因为重试请求而重复执行整段逻辑。

## 七、项目整体追问

### 问：这个项目最难的地方是什么？

> 最难的不是写一个任务消费者，而是重新确认每一层的业务边界。任务是追踪单位，分类是状态计算单位，面板是事务和发布单位。如果这三个单位混在一起，就会出现要么无法追踪单任务结果，要么为了每条任务重复写库，要么同一面板部分成功。最终方案是让三个单位各自承担不同职责，再用映射关系把结果串起来。

### 问：为什么改造顺序是任务化、增量发布、批量执行？

> 因为可靠性是性能优化的前提。没有稳定任务语义时直接批量化，一旦失败很难知道应该重放哪一部分；发布仍靠扫描时，即使 Draft 写快了，正式版本仍然可能延迟。先把执行和发布交接显式化，最后再改变消费者内部执行模型，风险最小，也更容易验证每一步。

### 问：你在项目中的 Ownership 体现在哪里？

> 我负责的不是某一个消费者函数，而是从事件入口、自动分发、Draft 事务到正式发布的整条链路。我先统一问题模型和改造顺序，再推动两级任务边界、发布合并和批量状态归并落地，同时用真实日志和 PPE Case 验证性能。过程中不同模块会有同学协作，但整体方案、关键边界和最终效果是我持续跟进和收口的。

### 问：如何证明改造没有改变业务结果？

> 我用了三层验证。第一层是动作级，比较同一批 add/remove 按旧顺序执行和归并执行后的分类列表；第二层是落库级，检查 Draft、分发索引、操作记录和 publish_task 是否在同一面板事务中一致；第三层是链路级，用真实 RID 回查 distribute_record、分类 Draft 和发布任务，确认任务结果最终进入正式发布链路。

### 问：灰度迁移怎么做？

> 我会先让新旧消费者在相同输入下做影子计算，只比较结果不落库；结果稳定后按业务线或任务类型小流量切换，同时保留旧定时扫描作为短期兜底。发布任务重点监控 Pending 最老年龄、失败率和 Draft 未发布数量。新链路稳定后再逐步关闭旧扫描，而不是一次性切断兜底。

### 问：方案最大的代价是什么？

> 代价是系统从隐式调用变成了显式状态机，需要维护任务状态、租约、重试和历史数据，排障也要建立新的监控口径。但这部分复杂度本来就存在，只是过去散落在回调、定时器和人工处理里。任务化是把隐性复杂度集中管理，而不是凭空增加复杂度。

### 问：还有哪些没有彻底解决？

> 当前主要剩余成本是分类内容仍保存在 JSON/TEXT 列表中，即使每个分类只写一次，仍然需要解析和重写整列。下一阶段可以引入带 sort_key 的 category_material_relation 关系表，但迁移需要双写、历史回填、一致性校验和切读，成本大约是数周。当前先做批量归并，是因为它不改变存储模型就能解决主要积压，收益更高、风险更低。

### 问：如果重新做一次，你会提前补什么？

> 我会更早建立三类指标：任务积压年龄、动作到事务的放大率、Draft 到正式版本的发布延迟。旧链路长期只看任务是否成功，没有看到 50 条任务被放大成近千次写入，也没有把 Draft 成功和正式发布成功拆开监控。如果这些指标更早存在，架构问题会更早暴露。

## 八、延伸设计

### 1. 关系表改造

当前 Draft 分类内容以有序 JSON/TEXT 列表保存，后续可以拆成：

```text
category_material_relation
├─ category_id
├─ material_id
├─ sort_key
├─ source_type
├─ created_at
└─ updated_at
```

迁移顺序：

```text
双写新旧结构
→ 历史数据回填
→ 在线一致性校验
→ 新链路切读
→ 旧字段保留兼容投影
→ 稳定后下线旧写入
```

面试表达：

> 我没有在积压最严重时直接改存储模型，因为那会同时引入数据迁移和执行链路风险。先用批量归并消除主要写放大，把 20 分钟降到 24 秒；如果规模继续增长，再用关系表解决 JSON 整列重写问题。这是收益、风险和交付周期之间的取舍。

### 2. 分区与背压

如果任务量继续扩大，可以用面板作为一致性键：

```text
task
  ↓ hash(bizId, areaKey, sceneKey)
partition
  ↓
同面板串行，不同面板并行
```

同时根据最老 Pending 年龄动态调整批次和并发。当积压超过阈值时，对低优先级自动同步限速，优先保证人工发布和高优业务。

### 3. 可观测性

建议重点监控：

| 指标 | 说明 |
| --- | --- |
| oldest_pending_age | 最老任务等待时间，比单纯队列长度更能反映用户影响 |
| task_to_action_ratio | 一条任务平均展开多少动作 |
| action_to_write_ratio | 动作归并后实际写入次数，衡量写放大 |
| publish_merge_ratio | 同面板发布任务合并比例 |
| draft_to_online_latency | Draft 变化到正式版本生效的端到端延迟 |
| lease_expired_count | 消费者异常退出或任务执行超时信号 |

### 4. 一致性继续演进

如果 Draft 和 publish_task 未来拆到不同数据库，可以引入 Outbox：

```text
Draft 事务 + Outbox Event
          ↓
可靠投递器
          ↓
publish_task / MQ
```

业务真源仍然是数据库中的提交事实，MQ 负责通知和扩展吞吐，不承担唯一状态。

## 九、候选人主动反问

主动反问不要问成知识考试，最好先结合刚才的项目，再询问对方真实系统里的取舍。

### 1. 关于任务与发布边界

> 我刚才这个项目里把 Draft 执行和正式发布拆成了两级任务，因为两段的失败语义不一样。想了解一下，团队现在类似的异步链路是按业务阶段拆状态机，还是更倾向于用一个统一工作流承接？

这个问题可以引出团队的任务平台、工作流编排和一致性设计。

### 2. 关于扫描式架构

> 我们当时经历了从定时全量扫描到真实变更驱动的演进。团队现有系统里还有比较重的扫描式任务吗？一般会在什么规模或稳定性信号出现后推动事件化改造？

这个问题可以把讨论引向存量架构治理，而不是只谈新系统设计。

### 3. 关于事务边界

> 这次我把分类作为计算单位、面板作为事务和发布单位。想了解团队在复杂批处理里通常怎样确定业务一致性键，会更偏向数据库事务、分区串行，还是补偿式 Saga？

这个问题能体现你关注的不是框架名，而是业务一致性边界。

### 4. 关于性能治理

> 我们这次最大的收益来自先消除写放大，再考虑并发。团队在做性能治理时，会不会固定建设请求放大率、事务放大率或最老积压年龄这类指标？

这个问题可以继续讨论容量规划、压测和可观测性。

### 5. 关于架构演进

> 当前链路剩余的主要瓶颈是 JSON 列表整列重写，下一步才会考虑关系表迁移。想了解团队面对“局部重构已经解决大部分问题，但长期模型仍不理想”的场景，通常怎样判断是否值得继续做存储层升级？

这个问题可以观察团队如何平衡技术债、业务收益和交付节奏。

## 十、最后收束

面试最后可以用下面这段话收口：

> 这个项目让我形成的一个判断是，复杂自动化链路的问题通常不在某一个慢接口，而在执行单位、状态单位和事务单位没有分开。我的改造顺序是先把副作用变成任务，让过程可追踪；再把发布从全量扫描改成变化驱动，让交接可靠；最后把逐动作执行改成批量计算最终状态，让吞吐跟业务规模匹配。最终性能提升约 50 倍只是结果，真正可复用的是这套从执行语义、事务边界到批处理模型的分析方法。

记忆时只抓住三句话：

```text
把不可控的副作用变成可管理的任务。
把扫描世界找变化变成变化发生时主动登记。
把执行每个动作变成计算一批动作后的最终状态。
```
