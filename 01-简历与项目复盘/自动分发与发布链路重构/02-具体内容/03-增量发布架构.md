# 增量发布架构

## 一、思维起点

执行任务化以后，Draft 更新已经可追踪，但正式发布仍然依赖定时器遍历全部面板，逐个比较 Draft 和线上版本。

这个方案的问题不只是慢，而是发现变化的方向反了：

```text
系统在 Draft 变化时已经知道哪个面板被修改，
却丢掉这条信息，之后再扫描全部面板重新寻找变化。
```

因此第二阶段的核心判断是：

```text
不要扫描世界寻找变化，
要在变化发生时留下发布事实。
```

## 二、旧发布链路

```text
Draft 被修改
     │
     │ 没有显式记录受影响面板
     ▼
定时器启动
     ↓
扫描数百个面板
     ↓
逐个读取 Draft 与线上版本
     ↓
逐个计算是否存在 Diff
     ↓
有变化才构建和发布版本

完整变化发现约 20 分钟
```

问题集中在两点：

1. Draft 提交和发布发现属于两套松散机制，存在半成功状态。
2. 发现成本取决于全部面板数量，而不是实际发生变化的面板数量。

## 三、新发布链路

```text
面板 Draft 事务
     │
     ├─ Draft 更新
     ├─ 分发索引更新
     ├─ 操作记录
     └─ M2：upsert publish_task
              │
              │ Key = bizId + areaKey + sceneKey + Pending
              │ 合并分类和素材变化范围
              ▼
       同一面板一条待发布任务
              │
              │ 带状态条件抢占
              ▼
Pending → Processing → Published / Failed
              │
              ├─ 10 分钟消费租约
              ├─ claimAt 防止旧消费者覆盖
              └─ 最多重试 3 次
              ▼
       构建一次 Diff 并发布

变化发现降低到 10 秒内
```

## 四、关键设计

### 1. 事务内登记发布事实

只有 Draft 真实变化后，才在同一面板事务中 upsert `publish_task`。

```text
事务成功：Draft 变化和发布任务同时存在。
事务失败：Draft 与发布任务一起回滚。
```

这样关闭了“Draft 已提交，但发布侧完全不知道”的窗口。

### 2. 同面板连续变化合并

Pending 任务使用 `bizId + areaKey + sceneKey` 标识待发布面板。并发变化到达时，upsert 锁定同一条 Pending 记录，把分类和素材变化范围合并进去。

任务合并的核心收益不是少写一行表，而是同一面板的一串变化只构建并发布一次版本。

### 3. 抢占、租约与消费令牌

消费者同时扫描 Pending 和租约过期的 Processing，通过带状态条件的更新抢占任务。

`claimAt` 作为本轮消费令牌：

```text
消费者 A 抢占：claimAt = T1
A 执行超时，租约到期
消费者 B 重新抢占：claimAt = T2
A 晚返回，只携带 T1
状态更新条件不匹配，不能覆盖 B 的结果
```

这和分布式锁中的 fencing token 思路一致：租约只能限制时间，令牌负责拒绝过期执行者。

### 4. no-op 也算成功

如果任务等待期间人工发布已经完成，消费者计算出的 Diff 可能为空。此时目标状态已经达成，应按成功结束，而不是不断重试制造新版本。

## 五、满分逐字稿

> 第二阶段我处理的是正式发布。旧方案靠定时器遍历数百个面板，再逐个比较 Draft 和线上版本，一次完整扫描大约需要 20 分钟。它最大的浪费是，Draft 变化时系统已经知道受影响面板，却没有保留这个事实，后面只能重新扫描。
>
> 我新增了 publish_task。Draft 真正变化后，在同一个事务里 upsert 对应面板的待发布任务，这样 Draft 成功但发布意图丢失的窗口被关掉了。同一面板短时间内连续发生的变化不会创建多条独立发布，而是把分类和素材范围合并到同一条 Pending 任务里，最终只构建一次 Diff 和版本。
>
> 消费端使用带状态条件的更新抢占任务，并给 Processing 增加 10 分钟租约。为了防止旧消费者恢复后覆盖新消费者结果，我加了 claimAt 作为本轮消费令牌。失败任务最多重试 3 次，再进入 Failed 告警。
>
> 改造后，定时器不再扫描所有面板，只读取真实待发布任务，变化发现从约 20 分钟的完整扫描降低到 10 秒内，同时减少同面板的重复 Diff 计算和版本构建。

## 六、方案取舍

### 为什么使用 upsert，而不是每次 insert？

正式版本关心一段时间内累积后的最终 Draft。每次 insert 会保留大量重复发布任务，而 Pending upsert 可以把同一面板变化收敛成一次发布。业务操作历史由 Draft 和操作记录保留，不依赖重复任务表达。

### 为什么仍然保留定时器？

定时器职责已经改变。旧定时器负责全量发现变化，新定时器只负责调度显式任务。查询规模从全部面板缩小到真实待发布集合。

### 为什么不在 Draft 事务中同步发布？

版本构建和下游发布耗时较长，也可能依赖外部服务。放在 Draft 事务中会拉长锁持有时间，并把下游故障传导到自动分发。publish_task 是两个业务阶段之间的可靠交接记录。

## 七、高概率追问

### 问：如何保证 Draft 成功后 publish_task 一定存在？

> Draft、分发索引、操作记录和 publish_task 在同一个面板事务中提交。publish_task 不是事务提交后再异步补写，所以不会出现 Draft 已提交但发布事实丢失的窗口。

### 问：并发 upsert 会不会丢掉某次变化？

> Pending 任务按面板维度唯一。事务锁定同一条待发布记录，再合并分类和素材 ID，而不是最后一次请求覆盖前一次内容。唯一约束保证不会出现两条有效 Pending，行锁保证合并过程串行。

### 问：消费者宕机后 Processing 怎么恢复？

> Processing 有 10 分钟租约。租约过期后任务重新进入可抢占集合，新消费者写入新的 claimAt。后续完成或失败更新必须匹配当前状态和 claimAt，旧消费者晚返回也无法覆盖新一轮状态。

### 问：发布过程中又有新变化怎么办？

> 当前 Processing 代表本轮已经领取的变化，新变化继续进入 Pending 任务。当前发布完成后下一轮再处理新增变化，避免当前任务无限延长，也不会丢失发布过程中的变化。

### 问：10 秒是发布完成时间吗？

> 不是。10 秒指从全量扫描发现变化改成定时器发现显式待发布任务的时间。真正发布耗时还包含 Diff 和版本构建，两个口径必须分开。

### 问：为什么不用 MQ 或 CDC 直接触发发布？

> MQ 或 CDC 可以负责唤醒，但仍然需要可合并、可抢占、可重试的业务任务状态。同面板连续变化还需要合并，因此数据库任务表适合作为业务真源。规模继续扩大后，可以增加 MQ 唤醒，任务表仍保留状态和恢复能力。
