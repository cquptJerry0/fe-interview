# 批量执行与积压治理

## 一、思维起点

任务化解决了可追踪问题，但也把真正的性能瓶颈暴露得更清楚。

当时任务积压超过 5000 条，生产速度长期高于消费速度。最直接的做法是增加消费者并发，但旧链路的事务和锁粒度都在分类维度，直接并发只会同时放大重复查询、数据库竞争和死锁。

我先拆解一次真实 Case：

```text
50 条任务
→ 976 个分类动作
→ 总耗时 19 分 48 秒
```

前 10 分钟日志中，分类写回约占 69%。根因不是某一条 SQL 慢，而是执行模型把公共查询、事务和发布登记放大了近千次。

因此优化目标从：

```text
更快地执行每一个动作
```

改成：

```text
计算一批动作共同作用后的最终状态
```

## 二、优化前：动作数量决定数据库成本

```text
50 条 distribute_record
           │
           ▼
逐任务加载素材、规则、面板、相似分类
           │
           ▼
展开 976 个 add / remove 动作
           │
           ▼
┌──────────────────────────────────────┐
│ 每个动作重复执行                     │
│ 读取分类 Draft                       │
│ 修改列表                             │
│ 提交一次分类事务                     │
│ upsert 一次 publish_task             │
└──────────────────────────────────────┘
           │
           ▼
近千次查询与小事务

结果：19 分 48 秒，生产速度高于消费速度
```

旧模型错误地把任务同时当成：

- 调度和追踪单位。
- 数据准备单位。
- 状态计算单位。
- 事务提交单位。

## 三、优化后：分类计算，面板提交

```text
100 条 distribute_record
           │
           │ 任务仍是追踪和结果回填单位
           ▼
┌──────────────────────────────────────┐
│ Batch Context                        │
│ 一次加载素材、规则、面板和相似分类   │
└──────────────────────────────────────┘
           │
           ▼
965 个带 taskOrder 的 add/remove 动作
           │
           │ M3：按分类归并
           ▼
183 个分类最终状态
           │
           │ 同分类保留任务顺序
           │ 每个分类只解析和写回一次
           ▼
24 个面板事务
           │
           ├─ Draft
           ├─ 分发索引
           ├─ 操作记录
           └─ 每面板 upsert 一次 publish_task
           ▼
结果映射回 100 条原任务

结果：23.547 秒，单批容量 50 → 100
```

## 四、关键设计

### 1. 批量准备公共数据

先建立 Batch Context，把整批任务涉及的素材、规则、面板配置和相似分类一次性加载并复用。查询只保留当前批次需要的字段，移除通用接口带来的无效数据。

### 2. 动作归并但不丢顺序

每条任务先转换成标准 add/remove 动作，并保留 `taskOrder`。相同分类的动作归到一起，仍按原任务顺序作用于同一份内存状态，最后只产生一个分类结果。

不能使用无序集合直接合并，因为新增存在前插语义，动作顺序会影响最终列表顺序。

### 3. 事务边界对齐面板

分类是状态计算单位，面板是业务一致性和正式发布单位。每个面板事务一起提交：

- Draft 分类列表。
- 分发索引。
- 操作记录。
- publish_task。

单个面板失败只回滚该面板，不拖垮整批任务。

### 4. 固定锁顺序

事务内固定先处理 Draft，再处理分发索引；多个分类按 categoryId 排序后加锁。所有事务尽量遵循相同顺序，降低循环等待概率。

### 5. 结果映射回原任务

每个动作保留来源任务。面板提交后，根据动作执行结果汇总每条 distribute_record 的 added、removed、skipped 和 failed。

批量优化改变的是底层执行粒度，不会牺牲任务级可观测性。

## 五、满分逐字稿

> 第三阶段是性能治理。当时生产任务速度长期高于消费速度，已经积压了 5000 多条。旧消费者处理 50 条任务会展开成 976 个分类动作，总耗时 19 分 48 秒。
>
> 我先做日志拆解，发现写回占了约 69%。问题不在某一条 SQL，而是每条任务重复加载相同的素材、规则和面板数据，每个分类动作又分别读取 Draft、提交事务和登记发布任务。动作数量一多，固定成本和事务次数就被放大。
>
> 所以我没有直接加并发，而是把消费者从逐任务执行改成批量状态归并。先整批加载公共数据，把任务转换成带顺序的 add/remove 动作；再按分类归并，在内存中计算这一批动作执行后的最终列表；最后按面板建立事务，每个分类只解析和写回一次，每个面板只登记一次发布任务。
>
> 这里最难的是不能为了批量化牺牲正确性。同一分类内保留原任务顺序，因为新增存在前插语义；落库时固定 Draft、分发索引的加锁顺序，并按 categoryId 排序；单个面板失败只回滚该面板，执行结果再映射回每条原始任务。
>
> 最终 100 条近等量任务、965 个动作，归并成 183 个分类和 24 个面板事务，服务端耗时约 24 秒。单批容量从 50 条提升到 100 条，处理效率约提升 50 倍，持续积压得到解决。

## 六、并发处理方案

### 当前方案

```text
同一分类：按 taskOrder 串行计算
同一面板：一个事务提交
不同面板：具备受控并行空间
```

先减少工作总量，再开放并发。并发度不能只看 CPU，还要观察数据库连接池、锁等待、热点面板和下游发布能力。

### 十倍规模后的方案

```text
distribute_record
       │
       ▼
hash(bizId, areaKey, sceneKey)
       │
       ▼
多个执行分区

同面板进入同一分区并保持顺序
不同面板由不同分区并行处理
```

配合三类控制：

1. 背压：根据最老 Pending 年龄和下游容量限制生产或降低低优先级任务速率。
2. 动态批次：积压高时扩大 batch，锁等待升高时缩小 batch。
3. 热点隔离：高频面板进入独立分区，避免拖慢普通面板。

## 七、方案取舍

### 为什么不先增加消费者并发？

旧模型的主要成本来自重复查询和大量小事务。直接并发不会减少工作量，反而增加同分类和同面板的锁竞争。先消除写放大，再让不同面板受控并行。

### 为什么不只优化 SQL 和索引？

SQL 优化只能降低一次查询耗时，无法改变 976 个动作触发近千次读写的事实。核心收益来自把近千个动作收敛为 183 次分类状态计算和 24 个面板事务。

### 为什么不是整批一个事务？

整批事务锁定过多面板，一处失败导致全部回滚；分类事务又会导致同一面板部分成功。面板是 Draft 一致性和正式发布的共同边界，能够同时保证完整性和失败隔离。

## 八、高概率追问

### 问：50 倍提升是不是测试数据不同？

> 对比使用近等量动作规模。旧链路 50 条任务展开 976 个动作，耗时 1188 秒；新链路 100 条任务展开 965 个动作，耗时 23.5 秒。任务数不同，但动作数接近，因此用动作规模对齐更合理。

### 问：如何证明批量归并和逐条执行结果一致？

> 同一分类内仍按 taskOrder 依次应用 add/remove，只是把中间状态保存在内存，不再每个动作都读写数据库。验证时比较最终 Draft、分发索引、任务结果和 publish_task，并用真实 RID 做落库回查。

### 问：同一分类被两个批次并发处理怎么办？

> 数据库写回时锁定对应 Draft 行，避免并发覆盖。同一批内部按 taskOrder 计算。规模继续扩大后，以面板作为一致性键分区，让同一面板进入同一执行分区，不同面板并行。

### 问：如何降低死锁？

> 缩小事务范围、保持固定表访问顺序、多个分类按 categoryId 排序加锁，并避免同面板并发。发生死锁时 MySQL 会回滚其中一个事务，应用层还需要识别死锁错误并进行有上限、带抖动的重试。

### 问：如何选择 batch size？

> batch 越大，公共数据复用越充分，但内存占用、单事务涉及面板数和失败重算成本也更高。应该根据最老积压时间、每批动作数、锁等待、连接池占用和 P95 耗时动态调整，而不是只按任务条数固定设置。

### 问：写回为什么仍占主要耗时？

> Draft 当前以 JSON/TEXT 有序列表保存，更新分类仍需解析和重写整列。当前方案先消除了重复写放大；继续优化需要迁移到带 sort_key 的关系表，而不只是调整消费者代码。
