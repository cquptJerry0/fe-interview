# VIMO 智能运营 Agent：双轮调研与纠错报告

> 更新日期：2026-08-17
>
> 文档定位：记录本轮研究方法、证据、反证、候选竞争、逐句评审、技术边界和纠错结论。
>
> 当前状态：研究与故事裁决已完成；真实实现范围和指标仍需按证据回填。

## 一、执行摘要

本轮任务不是继续润色旧六条，而是回答三个更基础的问题：

```text
VIMO 运营 Agent 在真实业务中会遇到哪些生产问题
哪些问题值得成为独立简历故事
实习生可以可信地承担哪一段
```

研究过程采用：

```text
A：业务与生产 Agent 难点调研
B：优秀简历、Portfolio 与表达结构调研
C：架构反证、句子级审查和 Ownership 审计

第一轮 A/B
-> C 反证旧结论
-> 第二轮 A/B 重新建立 20 个候选
-> C 终审候选边界与六条聚类
```

平台生产问题最终归为六类，素材管理 SubAgent 的简历视图再收敛为五条：

```text
素材任务理解与执行分流
素材能力接入与动态装配
批量素材确定性执行
素材变更安全与结果闭环
素材任务评测与失败回放
```

这五条围绕素材任务的理解、能力、批量、变更和反馈形成完整链路。Workflow、DAG、Workspace、A2UI、Inbox/Outbox 等内容被放回对应故事的子机制，不再机械拆成简历流水账。

## 二、任务边界与非目标

项目主语：

```text
VIMO 智能运营 Agent
```

平台服务的业务场景：

```text
素材管理
资源位配置
活动配合
```

本项目材料的个人贡献范围：

```text
素材管理 SubAgent
```

素材 SubAgent 的主要运营动作：

```text
查询与解释
批量治理
配置与变更
创建与发布
跨站点或跨业务线处理
审批、回调与回查
失败对象处置
```

本轮非目标：

1. 不用素材全球搬运这一条 Case 代替完整的素材管理 SubAgent。
2. 不把 Text-to-Workflow 写成整个项目。
3. 不依据当前代码仓库的缺口限制理想业务故事。
4. 不将目标架构自动写成个人已上线事实。
5. 不声称实习生独立建设 DeepAgents、OeFlow、IAM、业务服务和 A2UI 框架。
6. 不为了“像生产项目”给每条贡献补一个百分比。

## 四、业务模型与真实运营链路

### 4.1 通用链路

```text
运营目标
  ↓
任务契约：对象、范围、目标、约束、完成条件
  ↓
只读查询：补全真实状态与缺失参数
  ↓
能力装配：身份/站点硬过滤 + 语义候选
  ↓
计划编译：模板绑定、片段组合或长尾生成
  ↓
影响审核：对象快照、范围、风险和确认版本
  ↓
执行：Capability / Agent / Program / Human
  ↓
事实收敛：业务回查、Callback、UNKNOWN、部分失败
  ↓
Trace/Eval：业务结果、轨迹、延迟和成本
```

### 4.2 业务 Case

| Case | 输入特点 | 执行特点 | 完成条件 |
| --- | --- | --- | --- |
| 素材查询与解释 | 对象少、目标明确 | INLINE + Capability | 返回真实素材状态 |
| 素材批量治理 | 对象多、动作同构 | INLINE 或 DURABLE + Program | 目标字段和状态回查一致 |
| 资源位配置 | 素材、分类和版本存在依赖 | Capability/Program | 目标资源位版本已生效 |
| 活动素材配合 | 时间、地区和活动要求不同 | Task Compiler + Review | 素材状态满足活动使用要求 |
| 素材发布 | 参数可能缺失、存在审批 | DURABLE + Capability/Human | 目标版本已发布并可查询 |
| 跨站点处理 | 跨站点、异步、部分失败 | DURABLE + Program/Human | 目标端素材及依赖真实可用 |

跨站点搬运适合贯穿任务编译、批量、变更控制和结果回查，但不能单独代表整个素材管理 SubAgent。

## 五、生产难点全景

20 个候选的完整业务触发、生产失效、核心机制、Ownership 和收益定义统一维护在 `01-生产难点候选池与岗位组合.md`。

候选归并结果：

| 生产问题 | 最终故事 |
| --- | --- |
| 目标、缺参、真实状态、完成条件、执行分流、计划校验 | 开放式运营任务编译 |
| 能力发现、身份裁剪、版本兼容、新素材操作接入 | 素材能力接入与动态装配 |
| Program、并发、背压、对象级结果、精确重跑 | 同构批量确定性执行 |
| 权限、站点隔离、Prompt Injection、影响上限、Review | 高风险写入控制 |
| Workflow 等待、Callback、UNKNOWN、状态对账 | 异步副作用事实收敛 |
| Workspace、Trace、Eval、延迟、模型路由、Token | 质量成本反馈闭环 |

素材管理 SubAgent 的简历视图将“写入控制”和“结果收敛”合并为`素材变更安全与结果闭环`，其余四类分别映射为任务理解、能力装配、批量执行和任务评测。

## 六、三套聚类方案与取舍

### 6.1 方案一：业务闭环型

```text
任务理解与能力选择
计划生成与审核
批量和长任务执行
业务结果回查
质量反馈
```

优点：

1. 面试官容易理解运营任务如何完成。
2. 业务价值最清楚。
3. 不容易陷入框架名堆叠。

缺点：

1. Capability 平台化和批量 Runner 的独立技术深度容易被合并掉。
2. 写前安全与写后可靠性可能被压成一条“执行保障”。

### 6.2 方案二：Agent Runtime 型

```text
Context/Workspace
Tool Retrieval
Task Planner/Compiler
Program Node
Durable Workflow
Trace/Eval
```

优点：

1. Agent 技术画像强。
2. 容易覆盖 DeepAgents、Program 和 Workflow。

缺点：

1. 容易再次按架构模块写流水账。
2. 高风险写入、UNKNOWN 和真实业务完成被藏在 Runtime 名词后。
3. Workspace、DAG 和 OeFlow 容易被错误包装成独立贡献。

### 6.3 方案三：生产工程型

```text
能力供给
任务编译
批量执行
写前控制
写后收敛
质量反馈
```

优点：

1. 每条都有独立的生产问题和控制权。
2. 同时覆盖 Agent、后端可靠性、安全和业务结果。
3. 可以按岗位重排而不改变故事边界。
4. 素材查询、批量治理、跨站点处理和发布回查可以横向贯穿。

缺点：

1. 六条共享较多底层数据，需要明确主归属。
2. 如果每条都塞指标，会显得过度包装。

平台问题分类选择方案三。素材管理 SubAgent 的简历视图再将写前控制与写后收敛合并，形成五条贡献。方案一用于项目口述顺序，方案二只用于技术栈与面试追问。

## 七、为什么素材简历最终是五条

### 7.1 能力供给不能并入任务编译

能力供给解决“当前身份有哪些可调用能力”，任务编译解决“本次目标需要什么计划”。前者的核心问题是目录、硬过滤、检索和版本；后者的核心问题是目标、约束、分流和合法性。

### 7.2 Program 不能并入 Workflow

Program 是节点执行器，解决同构对象循环和聚合；Workflow 是跨节点、跨时间的编排方式。一个 DURABLE Workflow 可以包含 Program Node，一个 INLINE 任务也可以使用 Program。

### 7.3 素材简历中合并写前控制与写后收敛

平台架构中，写前控制与写后收敛仍是两套不同机制；但候选人负责的是素材管理 SubAgent，将二者合并为“素材变更安全与结果闭环”更符合实际模块边界。正文先说明素材范围、站点和影响上限怎样校验，再说明 operationId、UNKNOWN 和业务回查怎样避免重复写入。

### 7.4 Trace/Eval 不能只是每条的附属指标

单条故事可以有自己的指标，但只有统一 Trace、失败样本、回放数据集和灰度门禁才能形成持续优化闭环。其成果不是“记录字段”，而是能定位失败阶段并验证策略变化。

## 八、旧简历逐句评审

评审对象：已删除旧简历中的项目简述、六条贡献和项目收益。

### 8.1 项目简述

原句：

```text
参与 VIMO 运营 Agent 方案建设，重点承担素材搬运预检与任务编译设计，
协同梳理能力接入、批处理和持久流程方案，服务素材全球搬运、批量治理、
面板配置等跨系统运营任务。
```

问题：

1. 只写“素材搬运预检”会把素材管理 SubAgent 缩窄成单一搬运任务。
2. “方案建设、承担设计、协同梳理”连续出现，像工作记录而不是工程成果。
3. 能力接入、批处理和持久流程只是模块枚举，没有核心业务冲突。
4. 没有说明系统最终怎样证明任务完成。

裁决：删除后重写。

替换方向：

```text
VIMO 智能运营 Agent 面向素材管理、资源位配置和活动配合等运营场景，
将自然语言需求转化为可执行、可追踪的跨系统查询、批量操作与运营流程。
```

个人负责范围不塞入项目简介，在重点贡献中统一落到素材管理 SubAgent。

### 8.2 素材全球搬运预检

原句：

```text
重点参与素材全球搬运预检设计，将映射/复制策略、主子素材依赖、
版权与地区约束收敛为统一只读 Preflight……
```

问题：

1. 这是一个具体业务 Case，不能代替素材管理 SubAgent 的完整职责。
2. “重点参与……设计”无法说明个人交付物。
3. 领域规则较重，会让面试官误以为个人只做了一条搬运流程。
4. 其中 completionCriteria、对象级结果和 UNKNOWN 已经与其他条交叉。

裁决：不单独作为顶层贡献，作为任务理解、批量执行和素材变更闭环的面试 Case。

### 8.3 TaskSpec 与二维执行策略

原句：

```text
针对单条查询、同构批量和跨时审批被统一交给 Agent Loop 的问题，
设计 TaskSpec、BootstrapProfile 与 PlanProfile……
```

问题：

1. 概念名过多，业务目标被 Profile 结构淹没。
2. INLINE/DURABLE 与 Capability/Agent/Program/Human 的二维判断是正确边界，但只是任务编译故事的内部机制。
3. 缺参、完成条件、模板优先和 Compiler 校验未形成完整链路。
4. 结果只写“避免”，没有可验证业务结果。

裁决：保留方向，升级为`开放式运营任务编译`，减少内部类型名。

### 8.4 Capability 契约与动态检索

原句：

```text
针对业务能力增多后全量工具注入、跨站点误选和版本漂移问题，
参与制定 Capability 接入规范……
```

问题：

1. 核心工程冲突成立。
2. “参与制定、参与设计”削弱 Ownership。
3. 将权限、副作用、完成回查全部放入一句，容易与写入控制和结果收敛重复。
4. 只强调减少上下文，没有强调新增业务操作的接入与复用。

裁决：保留为独立故事，改为`素材能力接入与动态装配`。正文突出素材 OpenAPI/vimocli 的 Schema、站点、版本和按需装载；权限执行与完成回查只写契约边界。

### 8.5 受控可编程批处理

原句：

```text
针对同构批量任务逐对象 Tool Calling 带来的重复推理和部分失败难追踪问题，
参与设计受限 CommandPlan DSL / AST……
```

问题：

1. 工程冲突和独立性成立。
2. DSL/AST/Compiler/Sandbox 同时出现，像方案名词堆叠。
3. “Agent 描述循环”容易被理解成任意代码执行。
4. 只写“收敛为一次计划”，没有并发、背压、对象级结果和业务规模。

裁决：保留并增强为`批量素材确定性执行`。以 BatchPlan、Runner 和对象级结果为主，DSL/AST 放入面试。

### 8.6 模板优先的 Workflow Compiler

原句：

```text
针对稳定 SOP 重复生成、非标准流程又难以完全模板化的问题，
参与 Workflow Compiler 方案设计……
```

问题：

1. 模板优先和 Compiler 校验是正确机制。
2. 单独成条后与 TaskSpec、执行分流、DAG 和 OeFlow 高度重叠。
3. 把 Workflow 写成项目核心，弱化查询和批量等更高频任务。
4. “编译至 OeFlow”是实现路径，不是独立业务结果。

裁决：并入`开放式运营任务编译`，OeFlow 作为 DURABLE Runtime 基座。

### 8.7 运行观测与分层评测

原句：

```text
围绕 Agent 失败只能从最终回复排查的问题，
参与定义 Run、Node、Attempt 三级 Trace 与评测口径……
```

问题：

1. 方向成立，但“定义字段”不是成果。
2. 延迟、Token 和业务完成结果被并排列出，未说明如何驱动策略调整。
3. 没有明确失败样本怎样回流、评测怎样形成灰度门禁。
4. “后续 POC 和线上验收”把贡献写成了准备工作。

裁决：保留并升级为`素材任务评测与失败回放`，以真实素材状态、失败归因和回放评测为结果。

### 8.8 预期项目收益

原句：

```text
形成从业务预检、任务分级、受控批处理到持久编排的统一设计基线……
```

问题：

1. 这是方案总结，不是项目收益。
2. “统一设计基线、明确边界、统计口径”无法证明运营是否更好用。
3. 没有真实对象、SOP、人工步骤和业务完成率。
4. 把质量、延迟和 Token 都写成未来验收项。

裁决：删除。后续按真实采用、人工步骤、业务完成率和可靠性证据重写。

## 九、整体逻辑评审

旧稿的主要结构问题：

```text
具体业务 Case
-> 任务分流
-> Capability
-> Program
-> Workflow
-> Trace
```

这更像架构组件清单。素材管理 SubAgent 的新结构改为：

```text
素材目标能否理解并分流
-> 当前能力能否正确装载
-> 批量素材能否稳定执行
-> 素材变更能否安全完成并回查
-> 线上失败能否沉淀并回归
```

新的五条覆盖素材任务完整链路，每条只保留一个核心工程冲突和一个主收益。

## 十、完整纠错账本

| 旧判断或写法 | 为什么错误 | 新判断 | 对简历的影响 |
| --- | --- | --- | --- |
| DeepAgents 与 Harness 并列 | DeepAgents 官方定位本身就是 Agent Harness | DeepAgents 负责单 Agent Node 内的规划、工具、文件和上下文 | 不再写“DeepAgents + Harness 层” |
| DIRECT / PROGRAM / WORKFLOW 三选一 | Program 是节点执行器，Workflow 是编排方式 | 先选 INLINE/DURABLE，再选 Capability/Agent/Program/Human | Program 与 Workflow 不拆成互斥路线 |
| Workspace 决定 Workflow 恢复 | 文件现场不等于调度历史 | OeFlow History 决定持久调度位置，Workspace 保存 Artifact | Workspace 不包装成长任务 Runtime |
| OeFlow、VIMO、Workspace 同时维护状态 | 多真相源会产生冲突 | OeFlow 管调度，业务系统管副作用，VIMO 管投影，Workspace 管文件 | 结果收敛强调状态所有权 |
| 每次动态生成稳定 SOP 的完整 DAG | 稳定流程重复生成会引入漂移 | 模板优先，长尾组合或生成候选计划 | Workflow Compiler 并入任务编译 |
| 将素材、面板、实验误写成一级业务 | 它们属于素材管理模块中的对象与流程 | 一级业务按素材管理、资源位配置和活动配合表达 | 项目简介不再罗列领域对象 |
| A2UI 负责审批鉴权和恢复 | A2UI 是声明式呈现协议 | 后端 Review Service 持有身份、Hash 和 Signal | A2UI 不单独吹成安全能力 |
| CommandPlan 等于自由 Shell/JS | 任意代码无法控制能力、范围和副作用 | 受限 BatchPlan/DSL 经 Compiler 后执行 | 简历突出 Runner 和硬约束 |
| Definition Review 与 Impact Review 混淆 | 一个审核可发布流程，一个确认本次对象影响 | 流程定义与任务影响分别审核 | Review 描述不再含糊 |
| INLINE 可随时续接为 DURABLE | 写入后直接续接会丢失副作用边界 | 首次副作用前 Handoff；写后先回查再开新 Run | 放入任务编译和结果收敛边界 |
| 忽略 Signal 双写窗口 | 去重记录与投递可能分别成功 | Inbox/Outbox + 幂等 Signal | 作为结果收敛面试展开 |
| Definition 和 Run 重复绑定版本 | 两处精确绑定会造成漂移和冲突 | Definition 保存约束，BoundRunPlan 冻结精确版本 | 能力供给讲清版本阶段 |
| 目标架构自动写成完成态 | 方案不等于个人线上交付 | 每句话绑定 Ownership 和证据等级 | 最终简历按真实证据选择动词 |
| 预先规定六条 | 容易让新研究迁就旧结构 | 先建 20 个候选，再竞争聚类 | 平台问题归为六类，素材简历按模块边界收敛为五条 |
| 素材搬运占据全部个人主线 | 素材管理 SubAgent 被缩窄为单一流程 | 素材搬运作为查询、批量、变更和回查的综合 Case | 不单列“素材搬运预检”顶层条目 |
| 连续使用“针对、设计、参与设计” | 只描述写作动作，没有工程成果 | 用业务冲突、控制权变化和可验证结果组织 | 降低 AI 模板味 |
| DAG、Workflow 和意图分流拆成三条 | 三者共同回答任务怎样进入可执行计划 | 合并为开放式运营任务编译 | 减少正交和流水账 |
| Capability 等于安全治理 | 能力目录主要服务发现、组合和版本 | 安全由 Principal、Policy、Invoker 和业务鉴权持有 | 能力供给与写入控制分开 |
| Sandbox 等于业务权限 | Sandbox 只隔离文件、进程、网络和凭证 | 资源级权限必须在受控调用出口校验 | 不再写“靠 Sandbox 防越权” |
| 持久执行等于 exactly-once 副作用 | Runtime 重放无法替代外部幂等 | operationId、回查和业务状态收敛真实结果 | UNKNOWN 成为独立可靠性机制 |
| Token 是内部平台首要收益 | 好用、完成率和人工步骤更重要 | Token 仅在质量安全不退化时优化 | 最终只选择性保留成本数字 |

## 十一、关键数据契约

以下代码是设计级 Schema，用于约束讨论和后续最小验证，不代表当前已有完整生产实现。

```ts
type Principal = {

  bizLine: string;
  site: "cn" | "i18n";
  regions: string[];
  permissionSnapshot: string;
};

type TaskContract = {

  principal: Principal;
  objects: {
    domain: "material-management";

    selector: Record<string, unknown>;
  };
  goal: Record<string, unknown>;
  constraints: {
    deadline?: string;
    maxImpact?: number;
    approvalPolicy?: string;
  };
  completionCriteria: Record<string, unknown>;
  contractHash: string;
};

type ExecutionPlan = {
  mode: "INLINE" | "DURABLE";
  capabilities: Array<{
    name: string;
    versionConstraint: string;
  }>;
  nodes: Array<{
    id: string;
    executor: "CAPABILITY" | "AGENT" | "PROGRAM" | "HUMAN";
    needs: string[];
    input: Record<string, unknown>;
  }>;
  planHash: string;
};

type BatchPlan = {
  selectorHash: string;
  operation: {
    capability: string;
    version: string;
    inputTemplate: Record<string, unknown>;
  };
  concurrency: number;
  rateLimit?: number;
  maxImpact: number;
  verify: Record<string, unknown>;
};

type WriteEnvelope = {
  operationId: string;
  principal: Principal;
  capability: string;
  reviewHash: string;
  objectSetHash: string;
  maxImpact: number;
  expiresAt: string;
};

type OperationRecord = {
  operationId: string;
  runId: string;
  nodeId: string;
  objectId: string;
  status: "WAITING" | "UNKNOWN" | "SUCCEEDED" | "FAILED";
  remoteReference?: string;
  lastVerifiedAt?: string;
};

type TraceEvent = {
  runId: string;
  nodeId?: string;
  attempt?: number;
  stage: "UNDERSTAND" | "RETRIEVE" | "COMPILE" | "EXECUTE" | "VERIFY";
  eventType: string;

  objectCount?: number;
  result?: "PASS" | "FAIL" | "UNKNOWN";
};
```

## 十二、关键控制流草图

### 12.1 任务编译

```text
Prompt / Form / File
  -> Parse TaskContract
  -> Resolve missing fields with read-only capabilities
  -> Clarify or reject unresolved critical fields
  -> Retrieve capability candidates after hard filters
  -> Bind stable template or generate candidate plan
  -> Validate schema, type, topology, version and side effects
  -> Build impact preview
  -> Freeze planHash/reviewHash
  -> Execute INLINE or start DURABLE Run
```

### 12.2 批量执行

```text
BatchPlan
  -> Validate selectorHash and maxImpact
  -> Resolve object snapshot
  -> Partition
  -> Run with concurrency/rate limits
  -> Persist object-level OperationRecord
  -> Verify business state
  -> Emit succeeded/failed/unknown artifacts
```

### 12.3 UNKNOWN 收敛

```text
write request sent
  -> response received
       -> verify completionCriteria
  -> timeout or connection lost
       -> mark UNKNOWN
       -> query by operationId / object business state
       -> SUCCEEDED / FAILED / remain UNKNOWN
       -> retry only confirmed failures
```

## 十三、收益与指标门禁

### 13.1 优先指标

```text
第一优先：
  真实素材运营任务、SOP、活跃用户、有效 Run

第二优先：
  人工步骤、SOP 交付周期、业务完成率、人工接管率

第三优先：
  UNKNOWN 闭环、重复写入、对象级完成、批量 P95、定位时长

第四优先：
  Capability Top-K、首次可执行率、Token/成功任务
```

### 13.2 核心定义

```text
业务完成率
= 达成 completionCriteria 的已结束 Run
 / 已结束 Run

对象级完成率
= 业务回查为 succeeded 的对象
 / 进入执行的对象

UNKNOWN 闭环率
= 最终收敛为 succeeded/failed/人工结论的 UNKNOWN
 / 全部 UNKNOWN

Token/成功任务
= 同任务类型总 Token
 / 达成 completionCriteria 的 Run
```

### 13.3 数字进入简历的条件

每个数字必须具备：

```text
统计对象
时间窗口
分母
基线方案
对照方案
数据来源
质量与安全门禁
个人专项的归因边界
```

最终项目收益不需要覆盖全部维度。推荐结构：

```text
覆盖 X 类素材运营任务与 Y 条高频 SOP，
典型任务人工步骤由 A 降至 B，业务完成率达到 C；
同时选择一项最有证据的可靠性或性能结果。
```

## 十八、后续最小验证顺序

