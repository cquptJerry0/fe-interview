# AI 辅助研发提效与知识工程

## 简历初稿

**参与项目：AI 辅助研发提效与知识工程**

**简介：** 针对业务知识随代码演进容易过期、复杂研发流程依赖个人经验且重复操作较多的问题，建设代码驱动的知识保鲜机制，并将高频研发流程沉淀为可复用 Skill。

**核心贡献：**

1. **研发知识保鲜机制建设：** 基于 Codebase CI 构建业务文档巡检流程，以最近一次文档更新为动态基线，提取代码 Diff、变更文件与提交语义，驱动 Agent 识别知识变化并更新 `biz-context`；增加修改范围限制、Patch 校验、人工审批与防循环机制，控制 AI 自动写入风险。该机制已在 6 个合入需求中产生文档同步记录，覆盖素材创建、列表、分级、操作日志和面板分类等领域。
2. **复杂研发流程标准化：** 将跨系统、强依赖上下文的研发流程沉淀为可复用 Skill，统一前置检查、执行步骤、风险确认和结果验证。代表性能力包括：封装 OpenAPI 服务实现、BAM/IDL、网关路由、权限配置与真实请求验证的端到端接入流程；自动识别并同步 US-TTP 依赖；规范 Starling 多语言扫描、发布与回读验证；自动创建开发分支、泳道和 Bits 任务；聚合国内外 TEA 数据并生成用户及 API 调用报表。部分 Skill 已发布至内部 Skill Registry，供团队安装复用。

## 项目场景

VIMO 业务代码持续迭代，素材创建、发布、分级、面板分类等规则会随需求发生变化。业务知识主要沉淀在仓库文档中，依靠开发者主动维护时容易出现代码已经变化、文档仍停留在旧口径的问题，后续开发者和 Agent 都可能基于过期上下文作出错误判断。

OpenAPI 接入、多语言发布、跨机房依赖同步和开发任务创建等流程还涉及多个平台与仓库。每次执行都需要重新确认路径、权限、环境和验证方式，经验难以稳定复用。

## 技术选择

知识保鲜采用“Git 时间线 + CI + Agent + 人工审批”的受控更新链路。Git Diff 和实际代码负责提供事实，Agent 负责判断变化是否进入知识层，CI 负责限制修改范围、传递 Patch 和组织回写流程。

复杂流程采用 Skill 统一描述触发条件、上下文来源、执行步骤、风险护栏和验收标准。对于数据查询、依赖处理等确定性较强的步骤，使用脚本完成计算和结构化输出，减少模型临场拼接命令带来的不确定性。

## 为什么这样做

固定文档只能记录某个时间点的状态。代码持续演进后，文档是否需要更新取决于本次改动是否改变了业务概念、用户流程、字段语义或规则边界，因此需要结合提交时间线和代码 Diff 做语义判断。

复杂研发流程的问题集中在跨系统上下文和执行顺序。将一次操作写成普通说明文档，仍然依赖执行者自行判断；Skill 可以同时约束前置检查、确认节点、执行路径和结果验证，使经验能够被 Agent 和开发者重复使用。

## 为什么不用其他方案

1. **不采用全仓定时重写文档：** 全量扫描会引入大量无关代码，增加上下文成本，也容易把实现调整误判为业务知识变化。
2. **不允许 Agent 直接自动提交：** 文档属于后续开发和 Agent 的事实来源，错误内容会持续影响后续任务，因此保留 Patch Review 和人工审批。
3. **不只沉淀操作文档：** 操作文档能够说明步骤，但难以约束确认、失败处理和回读验证；复杂流程需要固化成可执行工作流。

## 实现细节

### 研发知识保鲜机制

```text
MR 代码变更
  -> 定位最近一次 biz-context 更新提交
  -> 累计提取代码 Diff、变更文件和提交信息
  -> 生成受限的 Agent 上下文
  -> 逐篇判断业务知识是否变化
  -> 仅允许修改 biz-context/biz/*.md
  -> 生成并校验 Patch
  -> 人工审批后回写源分支
  -> 通过 [bot-doc-sync] 避免循环触发
```

关键控制点：

1. 动态基线记录自上次文档更新后的全部代码变化，避免只检查当前 MR 导致历史知识欠债被遗漏。
2. 区分业务知识变化和普通实现变化。字段语义、业务流程和规则边界变化需要更新，重构、日志和样式调整默认跳过。
3. Agent 只能修改指定 Markdown 目录，越界文件会被回滚；Patch 还需要经过大小检查和 `git apply --check`。
4. Agent 执行失败或超时时保留已完成的文档变更，但不会绕过后续校验和人工审批。

### 复杂研发流程标准化

| Skill / 脚本 | 固化的流程 | 主要风险控制 |
|---|---|---|
| `vimo-openapi-onboarding` | 服务实现、BAM/IDL、网关 Rewrite、权限点、发布与真实请求验证 | 区分运行时 PSM 与 BAM PSM，验证 JWT、路由和权限口径 |
| `material-us-ttp-deps-sync` | 比较依赖基线、查询 Luban、打包缺失依赖并更新映射 | 默认只报告，显式确认后才写入依赖映射 |
| `starling-i18n-release` | 扫描并分类翻译问题、更新文案、发布、远端回读 | 区分远端翻译更新与代码集成，回读未确认时不宣称发布成功 |
| `one-click-dev-task` | 准备分支、生成泳道参数、创建 Bits 开发任务 | 必须先 Dry Run，用户确认后才真正创建 |
| `vimo-tea-users` | 查询国内外 TEA 数据、聚合用户和 API 调用、生成 HTML 报表 | 统一时间范围、站点鉴权、异步轮询和截断提示 |

## 效果与收益

1. 知识巡检机制在 6 个已合入需求中产生过文档同步记录，覆盖素材创建、列表、分级、操作日志和面板分类等业务知识，并被其他开发者的需求复用。
2. `vimo-openapi-onboarding`、`starling-i18n-release`、`material-us-ttp-deps-sync` 等 Skill 已发布至内部 Skill Registry。
3. 当前仍需补充 Skill 安装量、使用 PV、流程执行耗时和文档建议采纳率，才能进一步量化整体提效收益。

## 风险与兜底

1. **Agent 误判知识变化：** 以实际代码和 Git Diff 为事实来源，限制修改目录，并保留人工审批。
2. **大规模 Diff 导致上下文失真：** 按后端业务逻辑优先级组织 Patch，在文件边界截断，并明确记录上下文是否被裁剪。
3. **流程 Skill 与平台变化发生漂移：** 关键流程保留真实请求或回读验证，平台参数变化后需要同步更新 Skill。
4. **使用范围表述过度：** 知识巡检自动触发当前已经关闭，简历只描述已落地和已验证的机制，不表述为持续在线运行的全仓平台。
