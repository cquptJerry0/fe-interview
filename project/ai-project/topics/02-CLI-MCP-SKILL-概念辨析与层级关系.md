# CLI / MCP / SKILL：概念辨析与层级关系

## Part 1｜技术讲解

### 1. 一句话结论

CLI、MCP、SKILL 不是并列的三个东西，而是位于不同抽象层级、解决不同问题的三种契约。

面试官问区别，核心考的是你能不能意识到：**它们不是"三选一"，而是"协作关系"——CLI 做执行、MCP 做连接、SKILL 做编排。**

### 2. 各自解决什么问题

| | 解决什么问题 | 一句话定义 | 类比 |
|---|---|---|---|
| **CLI** | Agent 怎么调系统 | 文本命令进、结果出 | 系统调用 |
| **MCP** | Agent 怎么标准化连接工具 | JSON-RPC 协议，定义 Tool 的调用契约 | RPC 接口 / ORM 驱动 |
| **SKILL** | Agent 怎么获取领域知识完成复杂任务 | Prompt + 流程 + Tool 绑定的能力插件 | 业务服务 |

### 3. 不是并列关系，是协作关系

```
用户："帮我安排一个明天的会议"

┌─────────────────────────────────────────┐
│              SKILL 层                    │
│  "+create" Skill:                       │
│    知识：先确认参会人时区，优先推荐上午   │
│    流程：查空闲 → 推荐时段 → 确认 → 创建 │
└──────────────┬──────────────────────────┘
               │ 调用
┌──────────────▼──────────────────────────┐
│              MCP 层                      │
│  calendar_search Tool: 入参出参有 Schema │
│  room_book Tool: 入参出参有 Schema       │
│  calendar_create Tool: 入参出参有 Schema │
└──────────────┬──────────────────────────┘
               │ 底层执行
┌──────────────▼──────────────────────────┐
│              CLI 层                      │
│  lark-cli calendar search --date xxx    │
│  lark-cli calendar create --title xxx   │
└─────────────────────────────────────────┘
```

关键理解：

- **SKILL 不只是编排 MCP Tool**，它还承载 MCP 覆盖不了的东西：领域知识、决策规则、风险控制、Prompt 模板
- **MCP 不只是 CLI 的封装**，它提供的是标准化协议，让任何 Agent 都能调用，不需要知道底层是 CLI 还是 API
- **CLI 不只是底层实现**，它是 Agent 和操作系统交互的最基础方式

### 4. 为什么 SKILL 和 MCP 是两个协议而不是两层

很多人以为 Skill 是 MCP 的上层封装——概念上对，但实现上不完整。

```
MCP 定义的是：Tool 的调用格式
  → 输入什么、输出什么、类型是什么
  → 本质是"能力描述"

SKILL 定义的是：怎么用这些能力完成任务
  → 用哪些 Tool、按什么顺序、中间怎么决策、Prompt 怎么写
  → 本质是"知识 + 流程"
```

**知识这一层，MCP 完全不承载。** 所以 Skill 必须有自己的协议格式。

拿 lark-cli 举例：

```
MCP：暴露原子能力
lark-cli mcp serve
  → Tool: calendar_search, calendar_create, room_book ...

Skill：暴露编排 + 知识
lark-cli skill list
  → "+agenda"  : 查看今日行程（组合了 calendar_search + 格式化 + 提示词）
  → "+create"  : 创建日程（组合了 calendar_search + room_book + calendar_create + 提示词）
```

同一个"创建日程"，走 MCP 和走 Skill 的区别：

| | 走 MCP（Agent 自己编排） | 走 Skill |
|---|---|---|
| 流程 | Agent 自己决定调哪几个 Tool、按什么顺序 | Skill 内部已经定义好 |
| 知识 | Agent 需要自己理解业务逻辑 | Skill 自带："先确认参会人时区，优先推荐上午时段" |
| 出错率 | Agent 可能遗漏步骤或顺序错误 | 流程已验证，不容易出错 |

它们不是"上下层"的封装关系，而是**两种不同的接口契约**：
- MCP 告诉 Agent："你有锤子和钉子"（能力）
- Skill 告诉 Agent："钉钉子要先找好位置，敲三下就够"（知识）

### 5. 关键取舍点

| 决策 | 选什么 | 为什么 |
|------|--------|--------|
| 简单任务走什么？ | 直接调 MCP Tool | 不需要编排，一步到位 |
| 复杂任务走什么？ | 走 Skill | 需要领域知识 + 多步编排 |
| MCP 会不会被 Skill 替代？ | 不会 | Skill 不定义 Tool 的调用格式，只定义怎么用 |
| MCP 会不会被更好的协议替代？ | 可能 | Google A2A 等新协议在探索，但"需要标准化工具协议"这件事是确定的 |
| Skill 协议会统一吗？ | 目前没有 | 各家自定义格式，可能是下一个标准化的方向 |

### 6. 一句话总结

> CLI 是执行层，MCP 是协议层，SKILL 是知识层。三者不互斥，是协作关系——Skill 编排 MCP Tool，MCP Tool 底层可能调 CLI。问区别时要强调：它们在不同层级解决不同问题，不是一个维度的对比。

## Part 2｜面试答题稿

### 题型判断

问"区别"→ 方案对比型，但三个东西不在同一层，不能直接并列比，先对齐维度。

### 思维链

```
背景（各自解决什么）→ 对比维度（抽象层级）→ 逐个展开（机制 + 局限）→ 关联实践
```

### 口语化输出

> "这三个东西不在同一层，直接比区别容易比偏。我先说它们各自解决什么问题，再从层级角度说区别。
>
> CLI 解决的是执行问题——Agent 怎么调用系统。本质是文本命令进、结果出，通用但粗糙，输出是非结构化的，Agent 得自己解析。比如 `git commit`、`curl`，什么都能干，但每个命令的输出格式不一样，Agent 要针对每个命令写解析逻辑。
>
> MCP 解决的是连接问题——Agent 怎么和外部工具标准化通信。它是 Anthropic 提的协议规范，核心价值是解耦：工具提供方按协议暴露能力，消费方按协议调用，不需要硬编码。而且 Tool 的入参出参都有 JSON Schema 描述，LLM 能精确调用，不像 CLI 靠猜输出格式。
>
> SKILL 解决的是知识问题——Agent 怎么获取领域经验来完成复杂任务。一个 Skill 内部可能组合多个 MCP Tool 调用、多条 CLI 命令、甚至多轮推理，但它比 MCP 多了两样东西：流程编排和领域知识。比如'安排会议'这个 Skill，不仅编排了查日历、订会议室、发邀请的流程，还自带了"先确认参会人时区，优先推荐上午时段"这种业务经验。
>
> 所以它们的区别本质上是抽象层级不同：CLI 是执行层，MCP 是协议层，Skill 是知识层。三者不互斥，是协作关系。
>
> 有人说有了 Skill 就不需要 MCP，我不同意。Skill 不定义 Tool 的调用格式，只定义怎么用——就像有了业务代码不代表不需要数据库驱动。真正该讨论的不是 MCP 有没有必要，而是这个协议会不会演进，比如 Google 的 A2A。但'Agent 需要标准化的工具调用协议'这件事是确定的。"

### 追问预判

| 追问 | 应对 |
|------|------|
| "MCP 和 A2A 的区别？" | MCP 是 Tool 级协议（Agent 调工具），A2A 是 Agent 级协议（Agent 调 Agent），层级不同 |
| "Skill 协议为什么没统一？" | 因为 Skill 承载的是领域知识，不同业务差异太大，标准化难度比 MCP 高 |
| "你写过 MCP Server 吗？" | 结合 D2C 实战回答，见 04 篇 |
