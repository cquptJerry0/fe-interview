# 编排与闭环：Skill + MCP + CLI 怎么协作

## Part 1｜技术讲解

### 1. 一句话结论

Skill 做决策、MCP 做连接、CLI 做执行，三者协作的核心是**谁做决策谁做执行**——校验-修复闭环是协作的终极形态。

### 2. 三者的协作模型

```
┌─────────────────────────────────────────────┐
│                 Agent / LLM                  │
│                                             │
│   简单任务 ──→ 直接调 MCP Tool              │
│   复杂任务 ──→ 调 Skill（内含编排 + 知识）   │
└────────┬──────────────────┬─────────────────┘
         │                  │
    MCP 协议            Skill 协议
    (JSON-RPC)          (Markdown/自定义)
         │                  │
         ▼                  ▼
┌──────────────┐   ┌──────────────────────┐
│  MCP Server  │   │    Skill 定义         │
│              │   │                      │
│ Tool A       │   │ Skill X:             │
│ Tool B       │◄──│   prompt + flow       │
│ Tool C       │   │   tools: [A, B]      │
└──────┬───────┘   └──────────┬───────────┘
       │                      │
       │  Skill 可能调 MCP Tool，也可能绕过 MCP
       │                      │
       ▼                      ▼
┌──────────────────────────────────────────┐
│              底层实现                      │
│   CLI / HTTP API / SDK / 文件系统         │
└──────────────────────────────────────────┘
```

关键理解：

1. **Skill 和 MCP 是两条平行接口**，不是串联的上下层
2. Skill 可能复用 MCP Tool，也可能直接调 CLI 或 API
3. MCP 定义能力（能做什么），Skill 定义知识（怎么做更好）
4. 底层 CLI 是最终执行者，但 Agent 不需要直接碰它

### 3. 谁做决策，谁做执行

| 层 | 做什么 | 不做什么 |
|----|--------|---------|
| **Skill** | 决定流程、判断条件、风险控制 | 不直接调系统命令 |
| **MCP** | 连接工具、标准化输入输出 | 不决定流程、不做业务判断 |
| **CLI** | 执行命令、返回结果 | 不做决策、不做编排 |
| **LLM** | 生成代码、理解意图、灵活推理 | 不做稳定重复的逻辑 |

一个容易混淆的点：**Skill 里的流程编排，和 LLM 的推理能力，是什么关系？**

```
Skill 的流程编排：确定性逻辑
  → "必须先 get 再 update"（这是规则，不管什么情况都这样）
  → "不可逆操作必须确认"（这是铁律）

LLM 的推理能力：不确定性逻辑
  → "用户说'帮我安排会议'，但没说时间，我该问什么"（需要理解意图）
  → "这个组件代码应该用 React 还是 Vue"（需要理解上下文）
```

**好的 Skill 是把确定性逻辑沉淀下来，让 LLM 专注处理不确定性逻辑。**

### 4. 四种协作模式

#### 模式一：Agent → MCP → 底层（简单任务）

```
用户："查一下明天的日程"

Agent → MCP Tool: calendar_search({ date: "2024-01-01" })
     → MCP Server → lark-cli calendar search --date 2024-01-01
     → 返回结构化结果
```

特点：一步到位，不需要编排，直接调 Tool。

#### 模式二：Agent → Skill → MCP → 底层（复杂任务，Skill 编排 MCP）

```
用户："帮我安排一个明天的会议"

Agent → Skill "+create"
     → Skill 内部编排：
         1. MCP Tool: calendar_search({ userId, date })  → 查空闲
         2. LLM 推理：推荐时段（结合 Skill 知识：优先上午）
         3. MCP Tool: room_book({ roomId, time })        → 订会议室
         4. MCP Tool: calendar_create({ title, time })   → 建日程
```

特点：Skill 提供流程 + 知识，MCP 提供能力，LLM 做灵活决策。

#### 模式三：Agent → Skill → CLI → 底层（Skill 绕过 MCP）

```
用户："清理一下测试环境的缓存"

Agent → Skill "vimocli-admin"
     → Skill 内部：
         1. CLI: vimocli admin cleanup-preview --scope test  → 预览
         2. 确认
         3. CLI: vimocli admin cleanup --scope test          → 执行
```

特点：不是所有工具都有 MCP Server，有些操作 Skill 直接调 CLI。

#### 模式四：Agent → Skill → Skill → 底层（Skill 级联）

```
用户："创建一个实验，素材用新版本的"

Agent → Skill "vimocli-experiment"
     → 创建实验流程中需要选择素材
     → 调用 Skill "vimocli-material"
         → 查询素材列表
     → 回到实验流程继续
```

特点：Skill 之间可以级联，入口型 Skill 路由到业务型 Skill。

### 5. 校验-修复闭环：协作的终极形态

最复杂的协作不是一去一回，而是**闭环**：

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│   生成 ──→ 校验 ──→ 有问题？──→ 修复 ──→ 再校验      │
│               │                        │             │
│               └──→ 没问题 ──→ 完成     │             │
│                                        │             │
│               ←───── 循环直到通过 ←─────┘             │
│                                                      │
└──────────────────────────────────────────────────────┘
```

以 D2C 场景为例：

```
1. Skill 编排：
   fetch_ui_detail(figmaUrl)          → 拿到 UI 树 + 截图
   LLM 生成代码                        → Agent 自己推理
   generate_styles(uiTree)            → MCP Tool 生成样式
   verify_code(code, screenshot)      → MCP Tool 校验

2. 闭环：
   verify 发现问题：
     - 按钮偏移 3px
     - 颜色差异 #eee vs #ddd
   
3. 修复：
   fix_issue(code, issues)            → LLM 生成修复
   verify_code(again)                 → 再验
   
4. 重复 2-3 直到 verify 通过
```

这个闭环里三种能力都在发挥作用：
- **Skill**：定义了"必须校验→修复→再校验"的流程（确定性逻辑）
- **MCP**：提供 verify_code、fix_issue 两个 Tool（能力）
- **LLM**：理解差异报告、生成修复代码（不确定性逻辑）

### 6. 协作中的常见问题

| 问题 | 原因 | 解法 |
|------|------|------|
| Skill 和 MCP 功能重叠 | Skill 里写死了工具调用逻辑 | Skill 定义流程和规则，具体调用走 MCP |
| 闭环死循环 | 修复后校验还是不过 | 设最大重试次数，超过则人工介入 |
| Skill 间循环依赖 | Skill A 调 Skill B，B 又调 A | 入口型 Skill 做路由，禁止循环依赖 |
| MCP Tool 颗粒度不当 | 太粗 LLM 控制不了，太细编排复杂 | 按"LLM 能控制的粒度"拆 |

### 7. 协作设计的三个原则

**原则一：确定性逻辑沉淀到 Skill，不确定性逻辑留给 LLM**

```
✅ Skill 写："必须先 get 再 update" → 规则，不管什么情况都这样
✅ LLM 做："用户没说时间，我该问什么" → 需要理解上下文

❌ Skill 写："如果用户说 X 则做 A" → 太死板，用户换个说法就匹配不上
❌ LLM 做："每次都先 get 再 update" → 容易忘，不稳定
```

**原则二：校验闭环是必须的，不是可选的**

```
❌ 生成 → 返回（没有校验，质量不可控）
✅ 生成 → 校验 → 修复 → 再校验 → 通过 → 返回
```

**原则三：Skill 可以绕过 MCP，但要标注原因**

```markdown
## 直接调用 CLI 的操作

- `vimocli admin cleanup`：没有对应的 MCP Tool，直接调 CLI
- `rsync`：文件同步不需要结构化输出，CLI 更合适
```

### 8. 一句话总结

> Skill 做决策（流程+知识）、MCP 做连接（标准化能力）、CLI 做执行（系统调用），LLM 做推理（不确定逻辑）。协作的核心原则是：确定性逻辑沉淀到 Skill，不确定性逻辑留给 LLM，校验闭环是必须的。终极形态是生成→校验→修复→再校验的闭环，四种能力各司其职。

## Part 2｜面试答题稿

### 题型判断

问"Skill 和 MCP 怎么协作 / Agent 系统怎么设计"→ 系统设计型

### 思维链

```
定义问题 → 拆解角色 → 四种协作模式 → 闭环设计 → 原则
```

### 口语化输出

> "Skill、MCP、CLI 三者协作，核心是分清谁做决策谁做执行。
>
> Skill 负责决策——流程编排、业务规则、风险控制；MCP 负责连接——标准化工具调用、输入输出有 Schema；CLI 负责执行——最底层的系统调用；LLM 负责推理——理解意图、生成代码等不确定逻辑。
>
> 协作有四种模式。简单任务 Agent 直接调 MCP Tool，一步到位。复杂任务走 Skill 编排 MCP Tool。没有 MCP Server 的工具 Skill 直接调 CLI。跨业务场景 Skill 之间级联。
>
> 但最关键的不是一去一回，而是**校验闭环**——生成之后必须校验，发现问题就修复，修复之后再校验，循环直到通过。这个闭环里 Skill 定义'必须校验'的流程，MCP 提供 verify 和 fix 两个 Tool，LLM 理解差异报告并生成修复代码。三种能力各司其职。
>
> 我总结三个设计原则：确定性逻辑沉淀到 Skill，不确定逻辑留给 LLM；校验闭环是必须的不是可选的；Skill 绕过 MCP 可以，但要标注原因。
>
> 其实整个协作的本质就是一句话：让 Agent 从'临场猜'变成'按协议执行'，但遇到意外情况还能灵活处理。"

### 追问预判

| 追问 | 应对 |
|------|------|
| "闭环会不会死循环？" | 设最大重试次数，超过则标记失败、人工介入。一般在 3 次以内就能收敛 |
| "Skill 级联怎么避免循环依赖？" | 入口型 Skill 做单向路由，禁止 Skill 之间互相调用，只能通过入口路由 |
| "如果一个操作同时有 MCP 和 CLI，走哪个？" | 优先 MCP（结构化、标准化），MCP 没有再走 CLI |
| "这套架构和传统微服务有什么相似？" | Skill≈BFF、MCP≈RPC 框架、CLI≈基础设施。但关键区别是中间有 LLM 做灵活推理，传统架构没有这层 |
